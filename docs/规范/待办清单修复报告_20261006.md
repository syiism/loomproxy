## 3. 三处执行时的判断，写明理由（比提交号更有价值的那一段）

### 3.1 P91 为什么没有用例
拍板的是"改代码、不写空转的用例"。follower 在 `continue` 之后通常会**自己变成 leader**，
新旧两种写法都在一次 `fn()` 后返回；要让它真的多等一轮，必须第三方每轮抢先占槽——那是时序竞争，
用例只会变成偶发红。所以这一条的正确性由读代码决定，风险放在"上游负载时序提前"那一侧，
它写在条目正文里而不是藏在提交信息里。

### 3.2 P94 的存量面靠的是第二半
写入端的新档位管不到**库里已有的旧形状值**。真正兜住存量的是发送端那个原本不存在的失败分支：
解不开就中止发码 + 一条带原始原因的 ERROR（对外仍是固定句「验证码发送失败，请稍后再试」——
`handlers/verify/verify.go` 早就按 P67 那对镜像处理了，本轮只是让它有东西可归因）。
另外确认过一件好事：`ApplySourceGroupLimits` **本来就要求显式 `limit`**（缺就 400），
所以 P69 把通用 CRUD 对齐过去，是消灭仓里唯一的异类，不是新立一条规矩。

### 3.3 P54 为什么连面板一起做
`/admin/stats` 加一格读数而面板不显示，就是 P58 那条「后端一直在发、面板从不显示」的复发。
本轮顺手数了一下同一张响应：`billing_dedupe` 与 `normal_count` 在 `web/src` 里**各 0 处引用**——
那是 P25 的自省读数，从上线起没人读过。这条登记成新项 **P96**（E 类，UI 取向要拍）。

## 5. 上线影响（写给下一次部署，不是写给提交信息）

本轮**含一处生产 DDL** 与两处行为变化：

1. **`users.content_consent_set_at` 新列**（P52）：随 AutoMigrate 出现。
   它是"库里加一列"，按 §11 属生产写操作，**发布前单独取一次授权**，并照换装三查先备份库。
   加列可回滚（旧二进制不读它），这一点与 S57 那次 `in_band_reason` 同形。
2. **`verify_http_headers` 的 `type` 会被纠正成 `json_object`**（P94）：`seedSettings` 对已存在的行只同步 `type`、
   不动 value 与 description，所以启动时那一行的 `type` 列会被改写一次——这是元数据对齐，不是配置值变更。
   **上线前请只读核一眼那一行的现值形状**（`{"k":"v"}` 之外的一律按"发码会被中止"对待，而不是"静默丢头"）。
3. **发码行为变化**（P94 第二半）：`verify_http_headers` 形状不对时，从"带着空请求头照发"变成"拒发 + 500 固定句 + 服务端 ERROR"。
   对外契约的形状没变（信封一字未动），变的是**失败会不会被伪装成成功**。
4. **「限制项」新增行的 API 变化**（P69）：`POST /admin/quotas/limits` 不带 `limit` 时从 200（落 0）变成 400。
   面板与「按分组套用」本来就显式发送这个字段；**直连 API 的旧脚本**要跟着改，这一句写给运维。
5. **趋势图分桶改了算法**（P72）：生产读数不变（那边本来就一致），开发/测试库里这张图每天不再错开 8 小时。
   与 P71② 那条"上线后要复验的读数"不同——那一条动的才是日标轴本身，这一条上线应当看不出任何变化。
6. **启动日志多一类该缺席的行**（P98，本轮后半段）：三族 env 解析器不再静默回落，
   `AUTH_ENABLED=1` / `MONITOR_RETENTION_DAYS=1y` 这类写法会各出一条 `WARNING: 环境变量 …`。
   **语义一个字没动**（布尔仍只认真正的 `true`），所以现网 `.env` 写法正确时**一行都不该多**；
   它一旦出现，那是一条关于现网的新事实（某个键长期以来被默认值顶着），要当场记下并核对那个键，
   不是把它当噪音划掉。这条已写进分支侧 S60 的启动契约。
7. **发码闸门读不动时改为拒绝发码**（P99）：新增 `ErrStorageUnavailable` → HTTP **503**（固定句、不带表名与驱动原文），
   而改前是"三道闸读成 0 → 一路发到通道 → 落库才失败"。方向上这是**收紧**：DB 抖动期间验证码请求会失败，
   代价换来的是"不会在闸门失效时把钱花掉、库里还没行"。同一条里还改了两件相邻的事：
   `default_role` 填了不存在的码时回落 `user` 并出声、连 `user` 也没了就给**空角色**（改前会插出一行空 `code` 的幽灵角色）；
   `NoticeReplacedSetting` 的去重改成按 (键,原因,填的值) 三元组（两步回落链以前会每次注册喊两条）。
   **注册接口对外的成功/失败形状没变**（两条路径都仍然 200 且账号可用），变的是库里的形状与日志。
8. **构建期新增一道门禁**（`todo-status-check`）：只影响 `make build`，不影响运行时——
   但它会在"清单页与归档页两处都留着同一条正文"时把构建拦红，写在这里是为了让下一次撞见红的人知道往哪查。

## 23. 第四十三遍：抽查「这一条的 `已` 是真的吗」——十个档位里八个是实例已、判据未，而**这三个档位以前没有定义**

- **这一遍的判法**：不查代码，查**自己页上的档位**。对 10 条标着 `已` 的行逐个问一句：
  「它声称的机器面，拦住的是**这一类形状**，还是只有**那一个实例**？」
  查法是把每行 固化 格点名的落点（脚本或用例）打开读一遍，看它守的到底是什么。
- **结论一：没有定义。** 页上那句「一条坑被机器拦住以后还留在本页，就是噪声」讲的是**去处**（该删），
  但 已 / 部分 / 未 各收什么形状，**整页一个字都没写**。没有定义的量表必然被各自解读，
  而解读的方向永远是往宽松那头偏——因为宽松那头写着"已做完"，读的人省事。
- **结论二：10 条里有 8 条是"实例已、判据未"**（本轮全部降为 `部分`，每条补一句"为什么不是 `已`"）：
  被钉住的是某处方向、某个触发器、某个具体码；而判据那句是一般问句
  （"永远处理不完的那部分会不会永久挡住队首"、"`Save` 与让它作废的 `Delete` 之间有没有提交点"、
  "抽公共谓词之前有没有列全下游"）。**一般问句不会自己红**。
- **其中两条更糟：档位与自己的正文互相矛盾**——`LIKE 转义符` 那行的固化格里明写着

  `一个配置名承载两种口径` 那行写着「形状上的这一族**还没有更宽的机器检查**，所以先按这一条具体的拆」。
  这就是**「不会自己报错的错」在文档侧的版本**：没有任何一处会红，直到下一个人看见 `已` 就以为不用管了。
- **补上的定义**（一句问句，写在《去处》那一节）：**下一个还没写出来的违例，会不会自己红？**

  且**必须写明为什么写不出机器面**，不留空白。

  页上那句现在与它一致；改数不改句会被门禁拦下——这次更正唯一的机器面就在这里）。

- **这条定义顺带回答了一个悬了很久的问题**：「判据页 > 40 条就触发瘦身」这一条到底怎么兑现？
  答案现在清楚了——**能删的只有 `已`，而按定义重判后只剩 2 条**，
  所以判据页的体量只能靠**合并同族**（同一判据不许占两个位置）降，不能靠"假装走完阶梯"降。
  上一轮那种"把时区七种写法折进三个包各写一份"的做法就是这条路的正例。

  ——固化成**一个实例的用例**不构成删行条件。已改成"判据那一类形状被机器拦住"，并指回那一节的定义。
  这条改动会让 `AGENTS.md` 又大几十字节（它本来就在阈值之上），**但说错的话不能为了守体量而留着**。

## 24. 我自己上一节的脚本丢了八条落点，以及"给判据页上一道扫描"为什么被我删掉

## 31. 维护者问"长任务为什么在带着文档空转"——三条答案，其中一条推翻了我自己给的解释
