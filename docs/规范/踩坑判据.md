# 踩坑判据

> **这一页收的是「还会复发、且还没被机器拦住」的坑。** 与相邻几页的分工（别写串了）：
>
> | 东西 | 去处 |
> |---|---|
> | 产品/代码缺陷本身（要修的那个 bug） | `docs/规范/待办清单.md`，编号条目 |
> | 排错过程、根因分析、方案权衡的详细版本 | Obsidian 知识库（不入库，见 `知识库分工.md`） |
> | 已经固化成做法的规范（响应信封、脱敏、门禁） | `docs/规范/开发约定.md` |
> | 有意的取舍与不做的理由 | `docs/规范/已知取舍.md` |
> | **机制性踩坑 + 一句可自查的判据** | **本页** |

## 准入判据（三条都满足才收）

1. **会复发**：成因是机制，不是「那次环境不对」。一次性环境问题（机器重启、网络抖动）不进这里。
2. **能写成判据**：读者能据此判断「我现在的写法是不是这个坑」。只有结论没有判据的（「当时我运气差」）不收。
3. **别处没有归宿**：缺陷本体进待办清单，过程叙事进知识库。本页只留**判据**，不留故事。

## 退出机制（这条最重要）

> **每条的终点是被固化，不是长存。** 变成一条用例、一个 `make build` 里的检查、一处声明位校验，
> 或升级进 `开发约定` —— 固化之后**把本页那一行删掉**，只在原地留一句「已固化为 `test/xxx_test.go`」。

理由不是美学：`docs/规范/开发约定.md` 早就写了「手写 SQL 的别名/列名必须避开 MySQL 保留字」，
**这几轮仍然有人踩**（把测试别名写成 `keys`，SQLite 全绿、只有生产报 1064）。
文档记了 ≠ 防住了。一页只进不出的踩坑记录，等于把知识押在「下一个人会读它」上——那是最不可靠的存储。

## 条目格式（四段，顺序固定）

```
### <症状>，因为 <真因>            ← 标题即结论：读标题就能自查
- **症状**：看得见的现象（报错文本、读数为什么不对），越具体越好
- **真因**：机制。不写「我不小心」——那对下一个人没有信息量
- **判据**：下次怎么避免，一句可执行的规则
- **固化**：`未`（附建议的固化方式）或 `已 → test/xxx_test.go:NN`
```

## 跨行提取正则把整段正文吞进了表格

- **症状**：生成一张 Markdown 索引表，某几行的单元格里出现整段条目正文（换行、列表符号都在表格里）。
- **真因**：用「到第一个 `）` 为止」这类**否定字符类**在整篇文本上匹配，而正文里到处是半角 `)`，
  贪婪地一路吃到下一个半角括号才停。行内看着正确的规则，跨行就变成任意长。
- **判据**：**先按行切，再在行内匹配**；需要「到行尾为止」就用 `[^\n]*` 或干脆 `.*`（Python 的 `.` 默认不跨行），
  别用 `[^)]*` 这种「看起来像行约束」的写法。生成结构化文本后**打印出来肉眼看一遍**，别只信断言。
- **固化**：`未`（这类只能靠「输出先看一眼」的习惯；若要拦，应在生成脚本末尾加一条断言：单元格内不得含换行）

## 归档索引里的提交号是错的，因为抓了「发现处」的哈希

- **症状**：待办条目搬到归档页后，索引表的「提交号」列填了一个**与该条目无关**的哈希；
  它其实是同条目里「**发现处**：`abc1234`」那一行的提交。
- **真因**：在**条目正文**里抓第一个反引号包裹的 7~8 位十六进制串当作收口提交。
  而一个条目里的哈希至少有三个来源——发现处、讨论中顺带引用的别的提交、真正的收口提交——
  它们在格式上完全同形，`re.search` 只会取第一个。
- **判据**：从条目**自己的标题/状态行**取证据（那是人写来当作结论的地方），**不做正文兜底**；
  取不到就写「见归档页」或「无提交（判定）」。宁可缺一格，不要填错一格——
  缺格会被发现，错格会被引用。
- **固化**：`未`（判据性质；若要拦，可给生成脚本加一条规则：正文哈希与标题哈希不一致时报冲突）

## 覆盖率一格只有 47%，查了半天不是采集在漏

- **症状**：内容维度覆盖率表里某源某动作常年不满，人第一反应是「这个源的采集在漏」，于是去改采集。
- **真因**：源在**参数缺失/上游失败**时返回带内错误（HTTP 200 + 正文里一句 `message`），
  这条明细是「成功 + 五个维度全空」，于是缺口既不在成功率里、也不在 `failed` 里，只在覆盖率里露头。
  详见待办清单 P22/P23、分支侧 S15。
- **判据**：**读数异常先问「失败有没有可能被记成成功」**，再问「采集漏没漏」。
  顺序反了会像这次一样，绕一整圈去查一个不存在的采集缺陷。
- **固化**：`部分` → 骨架 `skeleton-v45` 起有 `in_band_error` 列、覆盖率另出 `in_band_failed`，
  这条判据已可由数据自己读出；剩 P23 的泄露收口未做

## `ORDER BY id ASC` + 单次上限 + 定时循环 = 永远捞同一批

- **症状**：回填循环每轮扫 5000 行、补上 29 处，其余下一轮还是那 5000 行，新数据永远进不来。
- **真因**：**批次推进的经典饥饿**——筛选条件是「还没处理完的」，排序是「最旧的先」，
  而其中最旧的一批是**永远处理不完**的（缓存里没有对应映射）。它们永久霸占队首，上限之下无人晋级。
- **判据**：任何「分批推进 + 周期性重跑」的设计，落笔前先回答一句：
  **永远处理不完的那部分，会不会永久挡住队首？** 会，就换排序方向（推进新数据）、
  或换游标（记 `last_id`）、或先按「能不能处理」过滤再排序。三种选一种，不能空着。
- **固化**：`已` → `test/monitor_backfill_loop_test.go`（扫描方向改回升序则该用例必失败，做过变异验证）

## 想插入一条约定，却把旁边那条顶掉了

- **症状**：文档看起来「加好了一段」，`git diff --stat` 却是 `+3 -1` 而不是 `+3`；
  细看发现**原有的另一条约定整行不见了**。这一类不会报错，只在下次有人引用那条约定时才暴露。
- **真因**：编辑工具按「`old_string` 整段被 `new_string` 替换」执行。为了定位插入点，
  把相邻的整行放进 `old_string`、却没在 `new_string` 里把它抄回去，等于删了它。
  一次会话里连犯两次，说明它不是手滑而是**默认动作就长这样**。
- **判据**：**插入时 `old_string` = 锚点行，`new_string` = 新内容 + 同一句锚点行**（锚点必须原样出现在结果里）。
  每次编辑文档后看 `git diff --stat`：**纯新增的改动删行数必须是 0**，不是 0 就当场解释哪来的删除。
  这条比「肉眼看一遍」强的地方在于它是机器可读的数字，不需要我记得自己刚犯过什么。
- **固化**：`未`（可固化成提交前的钩子：`git diff --cached --numstat` 对 `docs/**` 的删除行做提醒）

## 注释里两个单引号被 gofmt 改成了弯引号

- **症状**：`gofmt -l` 报某个刚写的文件未格式化，`gofmt -d` 显示它把**注释**里的
  `col <> ''` 的两个连续单引号改成了 `”`。代码本身没有任何格式问题。
- **真因**：**未定位**——只确认了症状与绕行方式，没有查清 gofmt 对注释做引号替换的确切触发条件。
  记录在此是为了省下一个人重新排查的时间，不是作为结论可信。
- **判据**：Go 注释里要写含连续单引号的 SQL 字面量时，**改用中文引号或直接改成文字描述**
  （本次改成「拿标识与空串比较」后 `gofmt -l` 立刻干净）。别和格式化器对拗。
- **固化**：`未`（等根因清楚再说；如果每次构建都能秒过，这条大概会自己消失）
