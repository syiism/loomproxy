# 踩坑判据

> **这一页收的是「还会复发、且还没被机器拦住」的坑。** 与相邻几页的分工（别写串了）：
>
> | 东西 | 去处 |
> |---|---|
> | 产品/代码缺陷本身（要修的那个 bug） | `docs/规范/待办清单.md`，编号条目 |
> | 排错过程、根因分析、方案权衡的详细版本 | Obsidian 知识库（不入库，见 `知识库分工.md`） |
> | 已经固化成做法的规范（响应信封、脱敏、门禁） | `docs/规范/开发约定.md` |
> | 有意的取舍与不做的理由 | `docs/规范/已知取舍.md` |
> | **机制性踩坑 + 一句可自查的判据** | **本页** |

## 怎么用（读的顺序）

1. **按症状关键词搜本页的标题**——标题写成「症状，因为真因」就是为了能被症状搜到，不必读完正文。
2. 命中了先核对**成因是否真的一致**：判据是自查规则，不是可以照抄的补丁。同一段报错可能有两条不同成因，
   照抄会把你带到另一条死路上。
3. 都没命中，才重新推导。**解决之后**如果确认是个会复发的机制性坑，按下面的格式补一条再收工——
   口头总结止于这一次，写下来才轮到下一个人。

## 经验的来路与去处（这一页为什么会变厚，又为什么必须变薄）

**这一页是产物，不是前提。** 它的输入只有经验，而它变好的方式有两个方向——长出新条目，和**删掉旧条目**。
只长不删的判据页，等于把知识押在「下一个人会读它」上。

### 来路：四种经验都要主动收

| 来源 | 信号 | 去处 |
|---|---|---|
| **踩坑** | 同类错误第二次发生，或一次调试花掉十几分钟才定位 | 本页（四段格式） |
| **被纠正** | 维护者改回了 agent 的产出（方向、口径、命名、越界） | 越界类 → 长任务提示词的硬约束；口径类 → 本页或 `开发约定` |
| **重复劳动** | 同一件事第二次手工做（取数、核对、发布步骤） | 变成脚本 / 清单 / 门禁检查，**不是"再记一次"** |
| **决策答复** | 待办里登记的阻塞项被人拍板 | 回写进**那一条**，否则下一个人会重新问一遍 |
| **主动巡检** | 清单做完后**没人报问题**的那段时间 | 抽一次源码按下面的判据找（见「巡检怎么算做过」），别等被踩 |

关键在第二类与第三类：**没有被踩出来的低效同样是经验**——「每次都要手工核一遍」本身就是缺陷信号。

**第五类是前四类的对立面**：它不来自任何一次疼痛。等经验自己找上门，收进来的永远是
「已经咬过人的东西」，而**没人报不代表没坏**——本轮就是例子：给移动端做巡检时顺出来的
`btn-secondary`（用了 7 处的类名根本不存在，Tailwind 静默跳过），在桌面端已经糊了好几天，
因为没有一处会失败，所以它永远不会自己变成「经验」。**主动巡检就是补这个盲区的机制。**

### 巡检怎么算做过（写不出这三样就等于没巡检）

1. **查了什么**：范围与方法（哪几页/哪个包、按什么判据扫、只读生产取了哪些数）。
2. **发现了什么**：每条按准入三条落进清单或本页，带 文件:行号 与**自己核过的证据**，
   不写「可能有」。误报要当场撤，别留在册里污染下一轮。
3. **没发现什么**：查过而确认干净的部分也要写一行。否则下一轮无从判断这块是不是已经看过，
   巡检就会退化成「谁手快谁再查一遍」——那是重复劳动，不是自主性。

判据本身：优先找**不会自己报错的错**——静默跳过的类名/配置、两处写同一份值、只读同一份数据两遍、
`== nil` 之类判不出半初始化的检查、以及「文档写过但机器没拦」。这些都是被踩到才会浮出来、
而被踩到时代价已经付过了的东西。

### 去处：升级阶梯（终点是让自己消失）

```
口头经验 → 本页（人读） → 开发约定（做事方式） → 机器拦截（用例 / make vet 扫描 / 声明位校验） → 上面两层删行
```

一条坑被机器拦住以后还留在本页，就是噪声；一条约定每次都得靠人想起来，说明它还没走完阶梯。
所以每条的「**固化**」字段是强制的：**填不出固化去处，等于只记下了、没解决。**

**这三个档位以前没有定义**（第四十三遍发现：那句"被机器拦住以后还留在本页就是噪声"讲的是**噪声的去处**，
没说是删还是留，而 已/部分/未 各收什么形状，页上一个字都没写）。没定义的量表必然被各自解读——
本轮抽查 8 条标着 `已` 的，其中 2 条的**自己的正文**就写着"不算走完阶梯/还没有更宽的机器检查"。
定义补在这里，判据只有一句问句：

- `已`：**下一个还没写出来的违例，会不会自己红？** 会——判据的那一类形状被扫描器或用例接住了，不需要人想起来。
  只有这一档才是"可以删这一行"的状态。
- `部分`：有机器面，但它钉的是**某一个实例**，而判据管的是一整类（"这处方向改回升序用例必红"≠"所有分批推进都不会饥饿"）。
  **实例已、判据未**是最常见的形状，本轮按新定义重判，有 8 条从 `已` 降到 `部分`。
- `未`：只有这一页的文字在守。写不出机器面的要**明说为什么写不出**（语义判断、跨方言没有自动化…），别留成空白。

于是"本页 > 40 条就触发瘦身"这一条的兑现方式也清楚了：**能删的只有 `已`**，
而按上面那句问句重判之后 `已` 只剩 2 条——**这一页的体量只能靠合并同族降，不能靠"假装走完阶梯"降**。

### 收尾义务（每轮各不超过两分钟）

1. **对代码**：本轮引用过的规则与现状不符的，**当场改文档**（以代码为准），不留「下次再说」。
2. **删**：已固化、已过期、已被更好表达取代的行删掉。
3. **合并**：同一事实出现在三处即视为缺陷——留一处正文，其余改成引用。**复述必然漂移。**

> **先删后加**：本页若只增不减，说明前面的条目既没被固化也没被验证。每轮收尾要重数一次分布，
> 而**这里只留最新的那一个数**——历史数字归 `git log -p` 这一段管。
> 「同一份事实记在两处即缺陷」是下面的条目在治的坑，本页不能例外：这段曾经排了七句「再数一遍」，
> 每一句都自称实测而彼此矛盾——其中一对的差就是一行模板被算成了条目。
> 本轮（第四十三遍：给三个档位补定义，并按定义重判）
> **55 条：2 已 / 39 部分 / 14 未**
> （**这是新定义下的第一次数，与上一数不可比**：8 条从 `已` 降到 `部分`，因为它们钉的是实例而不是判据那一类形状，
> 其中两条的正文本来就写着"不算走完阶梯 / 还没有更宽的机器检查"——档位与自己的话互相矛盾。
> 条目总数没变：这一档的更正不产生新行，也不删行；**能删的只有 `已`，而现在只剩 2 条**。
> 上一轮那批（P98 静默回落、P99 读侧吞错、P100 白名单免解析、P101 对哨兵用 `==`）的历史读数归 `git log -p` 这一段管，本页只留最新一个数。）
> 而「断言空转」与「按目录名 git add 漏文件」两条是**并入实例**而不是另起一行——
> **同一条判据不许占两个位置**，上一轮把「写下没有生产调用方」折进「用正则扫配置项漂移」、
> 把「时区/日界七种写法」折进「同一个判据在三个包各写一份」，是同一个规矩。
> （这一句刚被 `judgment-count-check` 抓到过一次：加了条目没改数，页上仍写 31/12——
> **这就是那条检查存在的理由**，也是"数字必须数出来"最省事的证明。）
> 数这个动作的三条判据里，前两条已固化成 `make vet` 的 `judgment-count-check`（红就构建红，不再靠自觉）：
> ① **计数要写明怎么数的**——按「`## ` 条目 ↔ `- **固化**` 字段」配对，排除非条目章节与那行模板；
> ② **数字必须数出来**——写一个估的数字进来，本身就是本页要防的那件事；
> 这一条现在也管到**执行报告与归档索引**：那句「清单页 …N 行」、§8 抬头「共 N 条」、
> 以及 `docs/归档/README.md` 每行的「N 条已收口原文」都由 `doc-numbers-check` 一起数
> （第三处是第十五遍补的：README 那行写「三条」而文件里是四条，**文件名 `P65-P68` 就带着四个号**）
> （触发它的经验是同一轮里两处都写错过——行数凭印象报过 813/860/890 才对上一次 913，
> 条目数从 11 改成 13 之后再加两块仍是错，实测 15。同一个坑在同一个数字类型上第二次靠自觉失败，就该换机器）；
> ③ **走完阶梯的数字要往上走**——它不动，就说明只是在热心地收集痛苦；这一条**机器查不到**
> （没有历史可比，除非把每轮的数也落进仓库，那是拿第二份事实去管第一份），所以它是每轮收尾的人工检查项。
> 再留一句给写条目的人：**没有固化手段的坑先别写进来**，等想到怎么拦再写
> （P55 那条从落笔起就是「已」，它是带着用例一起进来的）；停在「部分」的要写清缺哪一半
> （例：检测器只有 `-race`、或人敲的 SQL 进不了门禁）。

### 可追溯

规则的每次增 / 删 / 改，**提交信息里带上触发它的那次经验**（条目编号、事故一句话、或「谁纠正：…」）。
没有回链的规则，半年后没人敢删——它就从资产变成负担。

## 准入判据（三条都满足才收）

1. **会复发**：成因是机制，不是「那次环境不对」。一次性环境问题（机器重启、网络抖动）不进这里。
2. **能写成判据**：读者能据此判断「我现在的写法是不是这个坑」。只有结论没有判据的（「当时我运气差」）不收。
3. **别处没有归宿**：缺陷本体进待办清单，过程叙事进知识库。本页只留**判据**，不留故事。

## 退出机制（这条最重要）

> **每条的终点是被固化，不是长存。** 变成一条用例、一个 `make build` 里的检查、一处声明位校验，
> 或升级进 `开发约定` —— 固化之后**把本页那一行删掉**，只在原地留一句「已固化为 `test/xxx_test.go`」。

理由不是美学：`docs/规范/开发约定.md` 早就写了「手写 SQL 的别名/列名必须避开 MySQL 保留字」，
**写了多年仍然在同一个仓库里第二次踩**（把测试别名写成 `keys`，SQLite 全绿、只有生产报 1064）。
文档记了 ≠ 防住了。一页只进不出的踩坑记录，等于把知识押在「下一个人会读它」上——那是最不可靠的存储。

> **本页第一条走完阶梯的坑**（2026-10-03）：上面那条保留字约定现在是 `make vet` 里的
> `scripts/check-sql-reserved.sh`——构建时扫 `AS x` / 子查询 `) x` / 反引号标识符，命中即构建失败。
> 它同时是「重复劳动」那一类经验的答案：取一次数（逐词实测 241 个保留字）换成每次自动跑。
> 判据页要涨的条目数趋零，`make vet` 要涨的检查数才是真进步。
>
> **第二条走完阶梯的坑**（同一天，来自「主动巡检」那一源）：`btn-secondary` 这类**写错的自定义类名**。
> 它比保留字更隐蔽——SQL 撞保留字至少在生产报错，而 Tailwind 对不存在的类**连报错都没有**，
> 只是不产出 CSS，所以 7 处 `btn-secondary`、17 处 `label`、5 处 `checkbox` 糊了几天没人报。
> 现在 `make vet` 跑 `scripts/check-css-classes.sh`：用了没定义就红构建，定义可以来自 `styles.css`
> 或本组件自己的 `<style>`。**这两条都不在本页留行**——被机器拦住之后，留在人读的页里就是噪声。

## 条目格式（四段，顺序固定）

```
### <症状>，因为 <真因>            ← 标题即结论：读标题就能自查
- **症状**：看得见的现象（报错文本、读数为什么不对），越具体越好
- **真因**：机制。不写「我不小心」——那对下一个人没有信息量
- **判据**：下次怎么避免，一句可执行的规则
- **固化**：`未`（附建议的固化方式）或 `已 → test/xxx_test.go:NN`
```

## 看到一片空维度先去怀疑采集，因为忘了「这个人可能自己说过别留」

- **症状**：某个用户的全部明细五个内容维度（搜索词/书名/章节/**两个标识**）一格都没有，
  而 handler 的日志明明打印出了 id——看起来像「观测链对某类请求形状整体失明」，于是去查中间件顺序、
  查带内错误、查聚合扇出、查 nginx，甚至准备构造同形状请求本地复现。
- **真因**：`content_consent=0`。P37 的闸口在 `middleware/source/monitor.go` 把维度写进环形缓冲**之前**
  调 `WithholdContent()`，而那七个字段里**含两个标识**（只清名称会被名称回填循环补回来，
  所以当初刻意连标识一起清）。于是「业务路径拿到了 id」与「观测路径什么都没有」**同时成立且都不矛盾**——
  这正是这个开关该有的样子。
- **判据**：排查「维度大面积为空」时，**先查 `users.content_consent` 与 `api_call_logs.content_withheld`，
  再怀疑采集**。这两列就是为「用户选择不留」与「采集在漏」分家而存在的；分不开的话，
  P37 加的那一列等于白加。核对方法：把关掉留存的用户与其明细按归属对齐，
  数三格——「`withheld=1` 却仍带维度」、「该用户关掉之后仍带维度」、「关掉之后完全没写入」，
  前两格为 0 就说明闸口是好的，剩下的只是标记一致性问题。
- **固化**：`未`（这是一条排查顺序，机器很难拦；至少把方法写进本条，别靠下一个人自己想到。
  真正能被机器拦住的是「同意位没有变更时刻」这个结构性缺口——见待办清单 P52 的建议列 `content_consent_set_at`。）

## 跨行提取正则把整段正文吞进了表格

- **症状**：生成一张 Markdown 索引表，某几行的单元格里出现整段条目正文（换行、列表符号都在表格里）。
- **真因**：用「到第一个 `）` 为止」这类**否定字符类**在整篇文本上匹配，而正文里到处是半角 `)`，
  贪婪地一路吃到下一个半角括号才停。行内看着正确的规则，跨行就变成任意长。
- **判据**：**先按行切，再在行内匹配**；需要「到行尾为止」就用 `[^\n]*` 或干脆 `.*`（Python 的 `.` 默认不跨行），
  别用 `[^)]*` 这种「看起来像行约束」的写法。生成结构化文本后**打印出来肉眼看一遍**，别只信断言。
- **固化**：`未`（这类只能靠「输出先看一眼」的习惯；若要拦，应在生成脚本末尾加一条断言：单元格内不得含换行）

## 归档索引里的提交号是错的，因为抓了「发现处」的哈希

- **症状**：待办条目搬到归档页后，索引表的「提交号」列填了一个**与该条目无关**的哈希；
  它其实是同条目里「**发现处**：`abc1234`」那一行的提交。
- **真因**：在**条目正文**里抓第一个反引号包裹的 7~8 位十六进制串当作收口提交。
  而一个条目里的哈希至少有三个来源——发现处、讨论中顺带引用的别的提交、真正的收口提交——
  它们在格式上完全同形，`re.search` 只会取第一个。
- **判据**：从条目**自己的标题/状态行**取证据（那是人写来当作结论的地方），**不做正文兜底**；
  **2026-10-03 又应验一次，形态不同**：回填 P34 提交号时**没跑 `git log`，凭记忆编了四个**
  合法形状的哈希（`9e90d3f` 这类），比抓错位置更糟——抓错至少有出处，编的连出处都没有。
  判据因此加一句硬动作：**填哈希前先 `git log --oneline -N` 把要引的号抄下来**，
  文档里出现的每个哈希都应能在 `git log` 里找到（`git cat-file -t <号>` 一秒辨真伪）；
  找不到就是编的。同一条判据顺带查出 P19 索引行的 `a8e0e0f` 在本库不存在（已按 `4856c61` 更正）——
  错号在被引用之前，得由机器而不是读者的记性来挡。
  取不到就写「见归档页」或「无提交（判定）」。宁可缺一格，不要填错一格——
  缺格会被发现，错格会被引用。
- **固化**：`未`（判据性质；若要拦，可给生成脚本加一条规则：正文哈希与标题哈希不一致时报冲突）

## 覆盖率一格只有 47%，查了半天不是采集在漏

- **症状**：内容维度覆盖率表里某源某动作常年不满，人第一反应是「这个源的采集在漏」，于是去改采集。
- **真因**：源在**参数缺失/上游失败**时返回带内错误（HTTP 200 + 正文里一句 `message`），
  这条明细是「成功 + 五个维度全空」，于是缺口既不在成功率里、也不在 `failed` 里，只在覆盖率里露头。
  详见待办清单 P22/P23、分支侧 S15。
- **判据**：**读数异常先问「失败有没有可能被记成成功」**，再问「采集漏没漏」。
  顺序反了会像这次一样，绕一整圈去查一个不存在的采集缺陷。

## `ORDER BY id ASC` + 单次上限 + 定时循环 = 永远捞同一批

- **症状**：回填循环每轮扫 5000 行、补上 29 处，其余下一轮还是那 5000 行，新数据永远进不来。
- **真因**：**批次推进的经典饥饿**——筛选条件是「还没处理完的」，排序是「最旧的先」，
  而其中最旧的一批是**永远处理不完**的（缓存里没有对应映射）。它们永久霸占队首，上限之下无人晋级。
- **判据**：任何「分批推进 + 周期性重跑」的设计，落笔前先回答一句：
  **永远处理不完的那部分，会不会永久挡住队首？** 会，就换排序方向（推进新数据）、
  或换游标（记 `last_id`）、或先按「能不能处理」过滤再排序。三种选一种，不能空着。
- **固化**：`部分`（第四十三遍更正——原先标 `已`）
  **为什么不是 `已`**：机器只钉住了**这一个实例**（回填循环的扫描方向），而这一条的判据是一般问句「永远处理不完的那部分会不会永久挡住队首」——它管的是所有"分批推进 + 周期性重跑"的代码，没有任何扫描器读得懂这个问题。**实例已、判据未。**

## 「发布后 N 分钟」的读数里混着发布前的数据

## 提交信息里那个提交号被 shell 吃掉了，因为消息用双引号包着反引号

## 不相干的用例报 `race detected`，因为一个长命协程每 tick 读一个"测试里会换"的全局

- **症状**：某条用例自己没有任何断言失败，只报 `testing.go: race detected during execution of test`；
  race 两端一个是测试脚手架换全局配置（写 `conf.Config`），一个是**产品代码里的后台协程**（读它）。
  而且它**一直存在，某天突然开始红**。
- **真因**：后台协程 `sync.Once` 懒启动后跨整个进程存活，每 tick 去读一个"生产只写一次、测试每条用例都换"的全局指针。
  开始红的原因通常不是有人写坏了什么，而是**套件墙钟跨过了那个 tick 周期**（5 分钟、10 分钟、某个超时阈值）——
  加了几条用例就足够跨过它。
- **同日第十四遍的第三种形态（比前两种都隐蔽）**：用例为了造出"平台时区 ≠ 进程时区"的差异，直接改了 `time.Local`。
  `-race` 报的读方是 **`time.Now()`**——它自己就读 `time.Local`，而调用它在 httptest 服务器每个请求的 goroutine 里，
  测试侧完全管不到（前两种形态都是"后台协程读我们自己的全局"，这一次是**标准库读我们改过的全局**）。
  判据：**想验证"某处跟着配置走而不是跟着进程走"，别去动全局**——改断言**返回值携带的 `*Location` 指针身份**
  （`got.Location() != 那个唯一合法的对象` 即红）。它既不动全局，又比"比瞬间"更强：
  宿主机与平台偏移恰好相同时，写死旧值与收口后的实现算出同一个时刻，纯比值断言是空转的。
- **判据**：写后台协程时，它读的每一个全局都要问一句「这个值在进程生命周期内会变吗？」
  会变（含"只在测试里变"）→ **启动时取快照**或显式传参，别在循环里读全局。
  反向那条更省事：**"我加了用例之后，别的毫不相干的用例才开始红"——先怀疑共同前提被时间跨过**
  （ticker 周期、`-timeout`、缓存 TTL、定时清理阈值），而不是怀疑新用例。
- **固化**：`部分` → 检测器就是 `-race` 套件本身（这一族的正确检测器只有它，为"读快照"写单测要导出内部状态，
  那是造绿光不是防错）。根治办法是把 `conf.Config` 换成只读的启动快照 API（编译期就不给后台协程读活指针的机会），
  但那是全仓改动——**等第二次被同一族绊到再动**（同 P56 那条的克制）。
  （待办清单 P57）

## 用被 `tail -N` 截过的查询结果，下了一条"某样东西不存在"的结论

- **症状**：两条同族的近失。① `mysql -e 'SELECT id, code FROM quota_plans' | tail -6` 出来六行，
  没有 `free`，于是差点写下"现网没有 free 套餐、新注册用户一律无套餐"；
  ② 同一族第二次：`... WHERE type IN ('bool','number') | tail -14` 少了两行，
  差点据此说"生产把 `device_watch_enabled` 的 type 存成了别的"。**两次都是 `ORDER BY` 之外的行被切掉了。**
- **真因**：`tail -N` 截的是**尾部**，而带 `ORDER BY id`/默认排序的查询里，**最容易被切掉的恰恰是最小 id /
  字母序最前那一行**——`free` 是 id=1。把"我看到的列表里没有"当成"库里没有"，是把管道行为当成了事实来源。
- **判据**：**否定性结论（"没有 X"）必须用会自己数数的查询来立**——
  `SELECT COUNT(*) WHERE code='free'`、`WHERE key IN (...)` 逐键对照，或者干脆不接 `tail`/`head`。
  要截着看就先问一句「这个结果一共几行，我看了几行」。人敲的 SQL 不进 `sql-check`，
  所以这条只能靠写法自律（与「机器拦不住的那一遍」同族）。
- **固化**：`部分` → 本轮两次都靠"改之前先复算一遍"自纠（`quota_plans` 用 `ORDER BY id` 重跑、
  设置键用一条 `WHERE key IN (...)` 单独问），并把这条写法要求写进修复报告的只读查询清单；
  机器拦法（给临时 SQL 加个 wrapper 禁 `tail`）性价比太低，先不做。
  （触发经验：修复报告 §5c 那一段 = 第一次；本轮 P60 现网核对 = 第二次）

## 临时运维 SQL 的结果集一片 NULL，因为别名撞了保留字、又按列序而不是按身份读值

- **症状**：`ssh hk 'mysql -D loomproxy -e "…"'` 出来的表格看着像模像样，但某一整列是 `NULL`；
  读数被写进文档，下一次复核才发现归属整个是错的——本轮就把「两个自建套餐（`fql`/`add`）的 14 行授权」
  误记成「`LegacyGroups` 展开的存量组行」。
- **真因**：两层。① `make vet` 的 `scripts/check-sql-reserved.sh` **只扫仓库里的 `.go` 文件**，
  人临时敲的 `-e "..."` 不在门禁范围内——同一批保留字在构建里防得住、在人手上防不住
  （那条查询正是把 `l.limit` 当列别名用）；② 更要紧的是读结果时**只按列的顺序认列、没按身份认列**：
  JOIN 少一层、别名撞词、`-N -B` 的转义，都会让某列静默变 NULL 而表格照样整齐。
- **判据**：临时 SQL 先看**列名与行数对不对得上问题**，再读值；凡「本该有值却是 NULL」的列，

- **固化**：`部分`——仓库内 SQL 已由 `sql-check` 拦（`make vet` 第二条）；人敲的那一遍进不了门禁，

## `Limit(n).Delete()` 在 SQLite 上不生效，一次「限量清理」把该留的也删了

- **症状**：给号池写「死号保留 N 条」的用例时，断言 `库里剩 2 条` 实得 `0 条`；
  而被改的那行代码在**生产（MySQL）上行为是对的**，在**开发/测试（SQLite）上静默删光**。
  这条藏了很久：`purgeDead` 自 P4 起就是这么写的，而它过去的测试只断言「死号变少了」。
- **真因**：GORM 的 `.Limit(n).Delete()` 生成 `DELETE ... LIMIT n`，SQLite 默认编译不带
  `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`，该子句被忽略（不是报错）——`Limit` 在**读**路径人人都记得，
  在**写**路径没人怀疑。加上默认「断言变化量而不是保留集」的写法，绿色一路到生产。
- **判据**：**限量删除一律「先 `Order(...).Pluck("id", &ids)`、再按 ids 删」**，别把 `Limit` 交给 DELETE；
  写这类用例时断言必须写成**保留集**（「剩几条、留的是哪几条」），不是「少了多少」。
  只写「变少」的用例等于没写——`Delete()` 删光永远满足它。
- **固化**：`部分`——`test/pool_test.go` 三条断言（生效上限数值 + 保留集条数 + 不限总号数时的原语义）
  已经把这条钉住，变异验证：换回 `Limit().Delete()` 立刻红两处；
  剩下的「别在写路径用 Limit」属人读代码时的判据，机器层要拦得先有跨方言的 SQL 审计（超出 `sql-check` 的范围）。

## 换装装上了没传完的文件，因为把「异步任务的输出」当成了「任务的结果」

## 代码里写的 0 落到库里变成 1，因为 GORM 对带 `default` 标签的零值字段直接省略该列

- **症状**：把接口消耗改成「不计费」（`Cost: 0`），代码、评审、用例看数据都对了，库里那行却是 1，
  用户照样被扣。生产上同一批播种出来的 `recommend` 行 cost 有 0 有 1 的混合形状就是这么来的——
  看起来像「有人手工改过」，其实是同一句 `Create` 的两种命运（面板走 map 更新能写 0，`Create` 写不进去）。
- **真因**：字段带 `gorm:"default:1"` 时，GORM 在 `Create` 里**跳过零值字段**，让数据库默认值生效。
  「显式写 0」与「压根没写」在结构体里是同一个值，分不出来；于是默认值反过来覆盖了意图。
  标签只在**建表**时是默认值，在写入时却成了「空着不写」的开关——两个身份没写在同一处，谁都不知道。
- **判据**：凡是 **0 本身有业务含义** 的列（不计费、不限额、不缓存、不限速…），
  `default` 标签必须与「0 的含义」一致（`default:0`）或干脆不写标签、由代码显式赋值；
  并且要有一条用例 **Create 之后读回来**断言是 0——只断言「我传了 0」不算，
  丢就丢在 SQL 之前的那一步。已有行不会被这个坑影响（`Updates(map)` 能写 0），
  所以症状总是「新东西不对、老东西好好的」，很容易误判成配置漂移。
- **固化**：`部分`——用例 `TestSeededCostsOnlyContentIsBillable` 逐行读回播种结果；
  通用形状机器扫不出来（要先理解「这一列的 0 有没有意义」），所以留在本页与 `models/quota.go` 的字段注释里。

## LIKE 的转义符写成反斜杠：一种方言默默无效，另一种直接 1064

- **症状**（两段，同一处代码先后两次咬人）：
  ① 管理端用户列表按 `keyword=al_1` 搜索返回 0 行（人就在库里）；
  ② 加上 `ESCAPE '\'` 修完之后，同一句在**生产 MySQL 上直接 1064**、面板该页 500。
  第 ② 段是本次修复自己造出来的，而且 **sqlite 全绿**——用例跑的是默认方言，压根没执行到 MySQL 那条路径。
- **真因**（三家实测，不是抄文档）：
  - SQLite：LIKE **默认没有转义字符**，不写 `ESCAPE` 时 `\_` 是两个普通字符，谁也匹配不上；
  - MySQL/MariaDB：字符串字面量里 `'\'` 的**反斜杠会转义收尾引号**，SQL 变成不闭合 → 1064；要表示一个反斜杠得写 `'\\'`；
  - PostgreSQL 标准模式不处理反斜杠，`'\\'` 又是两个字符，而 ESCAPE 只接受单个字符；
  - 而 SQLite 对 `'\\'` 明说 `ESCAPE expression must be a single character`。
  **结论：不存在任何一种反斜杠写法能三家同时成立**，所以「换个转义符」不是风格选择，是唯一解。
  更深一层：`escapeLike` 的注释原本写着「SQLite/MySQL/PostgreSQL 的 `ESCAPE '\\'` 语义一致」——
  **这句话是错的，而它正是故障源头**：一个错误的跨方言断言被三处代码引用，谁都没怀疑过。
- **判据**：
  ① 写 LIKE 一律走 `likeESCAPE(列名)` + `escapeLike(输入)`，**别手抄 `ESCAPE` 子句**；转义符用 `!`，
  且 `!` 自身也要转义（否则用户搜 `!%` 会反过来吃掉转义符）；
  ② 任何跨方言断言（"几家都一致"）必须**在每一家上各跑一次**再说成立——本仓用例只跑 sqlite，
  所以 sqlite 绿**不构成**跨方言证据；
  ③ 只要一句 SQL 在两种驱动下形状可能不同，就把它当成两种都要过：能静态扫的先做成扫描（见固化）。
- **固化**：`部分`（第四十三遍更正——原先标 `已`）
  第 4 条：源码里 `ESCAPE` 后面出现反斜杠即构建失败；
  第 5 条：**同族的另一处**（P44 的 `RevokeExcessSessions` 用了裸 `.Offset()`），
  MySQL 要求 `OFFSET` 与 `LIMIT` 同现（sqlite / PostgreSQL 都接受裸 OFFSET），
  链式调用里 `.Offset(` 没有配套 `.Limit(` 就构建失败——这条也是现网报出来才发现的，
  而且因为处置内部 `return 0` 吞错，**表现为「开关开了却没踢人」，比崩溃更难发现**。
  另有 `test/admin_user_search_test.go`（sqlite 侧断 `_` 按字面匹配、`%` 不匹配全表）。
  **残留风险明说**：本仓没有 MySQL 侧自动化用例，跨方言这两条目前全靠静态扫描 + 人，
  加进 MySQL 方言用例之前不算走完阶梯。扫描器自身做过变异验证（坏 fixture 红、好 fixture 绿）。
  **为什么不是 `已`**：本行自己就写着「残留风险明说：本仓没有 MySQL 侧自动化用例，跨方言这两条目前全靠静态扫描 + 人，加进 MySQL 方言用例之前不算走完阶梯」——**档位在 cell 里被自己的话推翻过一次，今天按那句话降下来。**

## 想「留着旧值」而复制了一个 `*time.Time` 字段，旧值随后被同一次 Update 顺着指针改掉

- **症状**：登录响应里那句「自上次登录以来有 N 台设备被移出」永远不出现。
  代码看着完全正确：`prev := user.LastLoginAt` → 更新 `last_login_at` → 用 `prev` 算窗口。
  单测第一版还是绿的——因为它把「移出」安排在**本次登录的自动收口**里，
  那次移出发生在 `now` 之后几微秒，无论顺序对不对都能算到（**假绿**）。
- **真因**：`user.LastLoginAt` 是指针。`prev := user.LastLoginAt` 复制的是地址，不是时刻；
  而 `db.Model(&user).Update("last_login_at", now)` 会写进 GORM 已经解析过的那个字段——
  同一个 `time.Time` 对象被就地更新，`*prev` 跟着变成新值。
  于是「上次登录以来」退化成「本次登录这一瞬以来」，而那一瞬之后的移出确实很少，读数是空的。
- **判据**：要留旧值就**拷值**（`t0 := *p; prev = &t0`），别拷指针；
  而且这类「顺序敏感」的用例必须把被测事件安排在**本次动作之外**（本次之前发生），
  否则变异验证会把一个恒真的断言当成防住了。
- **固化**：`部分`（第四十三遍更正——原先标 `已`）
  第三次登录才读 notice；上限故意调宽，让本次登录不产生移出）。
  变异验证：把 notice 的入参改成覆盖之后的 `user.LastLoginAt` → 「登录响应没有 notice」红。
  第一次做这个变异时它是以**编译失败**（`prevLoginAt` 未使用）的形式红的，那不算验过——重做才确认。
  **为什么不是 `已`**：用例钉的是 notice 那一条通路；「要留旧值就拷值，别拷指针」与「顺序敏感的用例要把被测事件安排在本次动作之外」两句都没有机器面（前者要类型流向分析，后者是**写用例的人的判断**）。第一次变异以编译失败的形式红，那不算防线。

## 变异验证不红 / 探针读数不对，因为断言没有样本、写得太宽、通路不受控，或根本没经过被测状态（断言空转与断言过宽）

- **症状**：两种都是「把被测改动反转跑变异，用例照样绿」。

  ② **过宽**——断言要写到**能分辨成因的具体值**（状态码、字段名、集合内容），

     同一族还有「只断条数变少」而不写**保留集**（`Limit(n).Delete()` 那条就是这么糊过去的）。

## 用 `git checkout --` 还原自己的临时变异，把同一文件里未提交的真改动一起抹掉

- **症状**：变异验证跑完，五条全红（本该如此），还原后重跑却仍然红——
  因为"还原"把**改动前**的状态当成目标，本轮刚写进那个文件的收口代码一起没了。
  这一轮是在第五步之后撞到的，症状是扫描器报 `handlers/verify/verify.go:57:func settingInt` 复现。
- **真因**：`git checkout -- <文件>` / `git restore` 的语义是"回到 HEAD"，
  而变异实验的工作树里那个文件本来就带着未提交的真实改动。两种还原机制混用（前四步用 `cp`、
  最后一步图省事用 git）时，失效的那一步不会报错，只会**安静地少掉一段代码**。
- **判据**：**变异用 `cp` 自备份、用 `cp` 还原**，全程同一套机制；
  需要 git 的还原命令时，先确认该文件相对 HEAD 没有自己要留的改动（`git diff --stat -- <文件>` 为空才行）。
  还原后**立刻复跑一次那条用例或那个扫描**——本轮是先看到扫描器报出一条已删的函数，才回头发现还原过头了。
- **固化**：`部分` → `scripts/mutate-restore.sh`（变异前 `cp` **工作树基线**而不是 HEAD、跑验证、
  `cp` 还原、还原后**逐字节比对基线**，不一致就非零退出）。
  **第二次真的被绊到了**：第二十九遍做变异时用 `git checkout --` 还原，把同一文件里本轮未提交的修复一起抹掉，
  `git diff --stat` 当场变空——那条判据自己写着「第二次被绊到再上脚本」，所以本轮照它落了脚本。
  剩下的口子：脚本只保证"还原到基线"，不保证基线本身是想要的那个状态，所以 `git diff --stat` 仍要人看一眼。
  **第三次撞的是脚本自己（第三十五遍）**：参数里的 target 给的是 `auth.go`，变异脚本 `open()` 的却是 `setting.go`——
  旧版备份/还原的都只是那个**没被碰过的** target，而最后那句"已还原并逐字节核对"核对的也是它（`cp` 刚复制过，
  永远不会不一致，**那句话是装饰**），于是真变异留在工作树里、要等下一次复跑测试才发现。两处已修：
  ① 还原范围改成"target ∪ `git diff --name-only` 的全部脏文件"，核对对象是**这批文件的哈希清单**
  （那才是一句会失败的话）；② target 没被 patch 改动就直接 `exit 3` 并把脏文件还原回去——
  一次什么都没改到的变异，它的红与绿都不属于被测代码。
  另记一句实现细节：还原循环里 `[ -f x ] && cp …` 在 `set -e` 下会在还原到一半时退出（测试失败让整条列表返回非零，
  而它是循环体最后一条语句），所以那两处一律写成 `if` 形式。

## 窄屏页面横向溢出，因为共享件的插槽没给宽度约束、插槽内容又不可断行

- **症状**：某一页在手机上整页可以横向拖 20 多像素，而页面里没有任何"本该横滚"的表格——
  溢出的是顶部标题栏那排下拉。构建绿、用例绿、`css-check` 也绿（类名全都存在）。
  实测：`/panel/ranking` 在 390 视口 `scrollWidth=414`。
- **真因**：flex 子项默认 `min-width:auto`，**不会缩到内容宽度以下**。共享件 `PageHeader.vue` 的
  actions 容器虽然写了 `flex-wrap`，但它那个**单个**子项（三个并排 `w-auto` 下拉）自身就超宽，

- **判据**：凡是**共享件开的插槽**放得下控件的，容器侧要写 `min-w-0 max-w-full`（把"你别想顶开我"写成约束），

- **固化**：`未`（可固化形态：把这条探针落进仓库当 `make` 的一个可选目标——但它是分钟级、需要浏览器与

## 按天聚合的图里，日界由**库侧**判：一种方言归一到 UTC，另一种按连接时区

- **症状**：`GET /admin/monitor/trend` 的日标轴是平台时区（P71 刚收口的），柱子的高度却由
  `date(created_at)` 决定。临时探针实测（sqlite）：写入北京 `2026-10-05 04:40`，串存成
  `2026-10-05T04:40:00+08:00`，而 `date(created_at)` 返回 **`2026-10-04`** —— SQLite 的日期函数
  把带偏移的串**先归一到 UTC** 再取日。生产是 MySQL（DSN `loc=Local`、宿主机 Asia/Shanghai），
  `DATETIME` 存的就是北京墙上时间，`DATE()` 给 `2026-10-05`，与平台日界一致。
  **于是这张图在开发/测试库里每天错开 8 小时，在生产里对**——正是「sqlite 绿不算跨方言证据」那个老判据的反方向：
  这次是 **sqlite 红也不算什么，而 sqlite 绿同样不说明生产对**。
- **真因**：日界这件事被交给了两个执行者。Go 侧负责窗口下界与日标序列，SQL 侧负责分桶；
  而 `date(...)` 的语义在各方言里不同（是否按偏移归一、是否用连接时区），
  所以"同一个时刻的两种写法"（带不带 `T`、带不带 `+08:00`）会走到不同的日界上。
  探针还量到一条附带的不对称：**同一个瞬间**用 `+08` 写法做 `>=` 下界与用 `UTC` 写法做下界，
  sqlite 命中结果不同——本轮把它写明但不当缺陷处理，因为收口后 app 侧所有下界都由 `utils.DayStart` 生成，
  这一条不对称**没有 app 通路**（`test/quota_refresh_test.go` 在 sqlite 上实测通过，先例证伪了"P41 会算多"的猜测）。
- **判据**：**凡是"按天/按小时聚合"的读数，日界只能在 Go 侧算一次**（`utils.DayStart`），
  不要在 SQL 里用日期函数分桶——`date()`/`DATE()`/`::date` 三家语义不一样，
  而方言分支写进 SQL 的那一刻起，`TZ_OFFSET_HOURS` 就再也管不住它了。
  写完这种聚合先问一句：**这个日界是库算的还是代码算的？**答"库算的"就必须在两种方言上各量一次。
- **固化**：`部分`——分桶已搬回 Go 侧（P72 于 2026-10-06 拍板选 A，`handlers/admin/monitor.go` 的一处 `bkey` 生成日键，
  库侧不再判日界），并由 `test/p72_trend_day_bucket_test.go` 钉住（变异=把归日改回 UTC → 那条断言当场红）。
  **候选的 SQL 扫描仍不上**，理由与登记时相同：`date(created_at)` 这类写法在**别的方言上是对的**，
  误报率取决于豁免名单怎么写；判据页这一行留着，是因为「按天聚合先问一句日界是谁算的」这条**问法**本身没被机器覆盖。


## 按某一列排序下发而没有二级键，同一份数据每次排出不同顺序

- **症状**：两种，都不报错。① 管理端「设备与密钥」按聚合列排序时**翻页重行/漏行**
  （大量账号的活跃会话数都是 1，那一列全是并列；第二页把第一页的人又排一遍）。
  ② `base.Registry.AllSorted()` 文档写「按优先级降序」，而注册表里同优先级的项每次调用排出**不同顺序**
  ——底层是 `sync.Map`，`Range` 的遍历顺序按桶散列，`sort.Slice` 又是非稳定排序，
  并列项的最终顺序就取决于这次 Range 先撞到哪个桶。
- **真因**：**"排了序"不等于"全序"**。比较器只在有区分度的那一列上说话，并列时返回 false 两边都不换，
  于是并列区间的顺序 = 输入顺序 = 上一个环节的随机性（map 桶序、并发完成顺序、DB 无 `ORDER BY` 的返回序）。
  随机性不会自己冒出来，它只在被下发的时候变成缺陷。
- **判据**：**凡是被下发给面板/调用方的列表，排序比较器要么按唯一键排，要么补到唯一键为止**
  （第二、第三级键选"这一行在这张表里唯一"的那一列——`user_id`、注册名、`(source, action)` 都行）。
  写完排序先问两句：**并列时谁来定序？** **输入顺序是谁给的？**
  答"输入顺序"而输入是 map / 并发 / 无 `ORDER BY` 的查询，就等于没排序。
  验它的方法不是读代码：**把同一份数据取两次比对序列**（一次取回不够，随机性只在重复里现形）。
- **固化**：`部分` → `test/registry_order_test.go`（12 个同优先级 + 3 个高优先级、注册顺序打乱，
  期望序列由用例自己按「优先级降序 + 名字升序」算，**重复调用 20 次**每次都要等于它；
  变异：去掉二级键 → 连续三次跑都红，不是靠运气撞上的一次不一致），
  外加 `handlers/admin/devices.go` 那句写在函数头上的判据注释（P45 的学费）。
  **未固化的那一半**：新写一个 `sort.Slice` 忘记二级键没有任何机器拦截
  （扫"比较器只有一句 return"误报率极高——按唯一键排的合法写法就是这样），
  所以这一条要靠每次改排序时按上面的两句自查。

## 免鉴权的路径拼接只验了一段，`..` 就从另一段走出去

- **症状**：`GET /data/../probe_secret.json` 在本地实例上**直接返回了 DATA_DIR 父目录里那个文件的内容**，
  免鉴权；`GET /data/..` 则把父目录的 `.json` 文件名列表念出来。接口 200、日志干净、原有用例全绿——
  因为"能读到声明好的字典"这件事它本来就该做到，谁也没测过读**不该**读到的东西。
- **真因**：`filepath.Join(base, source, name+".json")` 里两个段都来自 URL，而 gin 会把路径参数**原样**交出
  （`..` 就是一个合法段，路由匹配并不排除它）。`filepath.Join` 又会顺手清理 `..`，
  于是"看起来在拼路径"实际在做的是**目录跳转**。编码形态（`%2e%2e%2f`）这次被路由形状挡在外面
  （多出一段就匹配不上），但那是运气不是校验——所以判据不能只对着能跑通的那一种写法。
- **判据**：**任何由请求拼出来的文件路径，守卫要站在两处**：
  ① 入口——每一段单独验（不许空、不许是 `.`/`..`、不许含 `/` 或 `\`、不许以前导点开头）；
  ② 落盘点——`filepath.Abs` + `filepath.Rel` 之后判定结果仍在根目录之内。
  只留 ① 等于信任未来没人放宽它；只留 ② 会得到一个含糊的成功响应（读到"没找到"但状态是 200）。
  **两道要各自单独测**：把 ① 摘掉看 ② 是否顶住、把 ② 摘掉看 ① 是否顶住、都摘掉必须红。
  只测"全都装上时空手过"的用例，等于没测。
- **固化**：`部分` → `test/datafiles_traversal_test.go`（五种请求形态 + 反向自检"合法路径仍要读得到"，
  三种摘除组合各自实测过：都摘 → 内容与名单都泄露（红）；只留地板 → 不泄露但响应含糊（红在"必须明说非法"那条）；
  只留入口 → 不泄露且明确拒绝（绿）。**没有固化的那一半**：新写一条免鉴权的文件读取路由时，
  没有任何机器检查要求它做这两道——`make vet` 扫不出"这里 Join 了一个请求来的段"。

## 每 tick 都会重试的路径，失败日志必须「同一种只说一次、恢复时带上累计数」

- **症状**：一个持续性但不是故障的状态（上游当天收益到顶、正在维护、网络一时不通）在日志里变成
  **每 60 秒一条**。第一次留下这个形状的是生产 v62 上线后的 `qm_device`：`ErrCapacityReached`
  每轮巡检喊一条 error，几天下来「这个池有问题」的读数被彻底泡坏（待办清单 P36 为此单独加了 `capNoted`）。
  第十八遍巡检发现**同一个形状还在维护循环的另外三处**（台账刷新失败、续领失败、转正替补失败），
  而那里的"失败"里包含业务上的正常状态——`sources/uxx/provider.go` 的 `Claim` 在金币当天到顶时
  返回的就是「金币不足（x/y），今日收益已到顶」，那不该每分钟喊一次。
- **真因**：日志语句被写在**重试路径**里，而重试是周期性的。单次看它是"出错就说"，
  放进每 tick 一次的循环里就变成"每 60 秒说一次同一句话"——**同一句话的频率不是信息，是噪音**。
  反过来，只 suppress 不补恢复也会骗人：读日志的人看到一条失败后再没下文，
  分不清"早就恢复了"与"还在坏"。
- **判据**：**凡是周期性重试出口上的失败日志，都要问两句**——
  ① 同一种失败连续出现时会不会只说一次？② 恢复时会不会补一条、并带上此前累计了几次？
  两问有一个答不上来就在框架里加一道守卫（号池这一族已经加在 `base/pool` 的 `noteBad` / `noteGood`，
  键含身份与路径、值取错误文案——**文案变了就算状态变化，必须再说一次**）。
  接口缓存（P68）、设置被兜底替换（P48）、号池名额（P36）是同一条判据的四次应用。
- **固化**：`部分` → `base/pool` 的 `noteBad`/`noteGood` + `test/pool_failure_notice_test.go`
  （连跑 4 轮同样的失败只许出 1 条、恢复条必须带「此前连续失败 4 次」；换一种错误文案必须再喊一次。
  三次变异各拦一处：去掉只说一次、摘掉恢复那一句、只认键不认文案）。
  **未固化的那一半**：新加一条周期性重试路径时，没有任何机器检查要求它接这道守卫；
  而 `topUpColdLocked` 的**建号失败仍每轮喊**——那是 P36 明确保留的决定（建号不是对同一目标的无损重试，
  持续失败通常就是真故障），这遍刻意不去改它，只把边界写在这里。

## 后台 goroutine 调用的正是「别人写的代码」时，panic 会带走整个进程；而 recover 之前还得先把锁放开

- **症状**：平台跑得好好的，某个数据源解析了一条畸形上游响应，进程没了。`Restart=always` 会把
  崩溃循环伪装成「运行中」（v63 换装三查第 3 条就是这个形状），所以运维看到的经常不是崩溃而是
  「读数突然不动了」。第十九遍巡检发现号池有两条这样的路径：启动装填（`go pool.StartAll()`）
  与维护 tick——**它们都在调源实现的 `Provider.Create/Refresh/Claim`，又都不在任何 Recovery 中间件里**。
- **真因**：请求路径上的 panic 有人兜（gin 的 Recovery 中间件），于是"panic 会被拦住"变成了一条
  **只在一条通路上成立的隐含前提**；后台协程复用同一批回调时，这个前提没跟着过去。
  更麻烦的是第二层：如果临界区是显式 `Lock()` / `Unlock()`，panic 会**穿着锁跑出去**——
  recover 之后锁永久 held，于是从"崩"变成"这个池再也不维护了，但进程活着、面板数字还在"，**比崩更难发现**。
- **判据**：**凡是「非请求通路」上调用外部实现的代码**（后台协程、启动钩子、任务队列、聚合扇出），
  落点必须自带 recover；同一条判据的另一半是——**被这种路径调用的函数里的临界区一律用 `defer` 解锁**
  （把显式 Lock/Unlock 的段落收成一个带 defer 的小函数）。写 recover 时先问：panic 穿出去时，
  我持有的锁、我打开的文件、我已改到一半的内存状态，各由谁收尾？
- **固化**：`部分` → `base/pool` 的 `guardPanic` / `locked` + `test/pool_panic_guard_test.go`
  （三条用例：维护 tick panic 拦下 + 锁必须放开 + 下一轮照常；启动路径 panic 拦下 + 锁必须放开；
  装填期与并发 Acquire 的竞争交给 `-race`。四次变异各拦一处：临界区退回显式 Lock/Unlock → 报"锁仍被持有"；
  摘掉维护 recover、摘掉启动 recover → 用例直接 panic 中止（**注意：这两支是"测试二进制炸掉"的红，
  不是断言失败的红**，仍然是有效拦截，因为不兜住的形状本来就会炸进程）；装填不持锁 → `DATA RACE`）。
  **未固化的那一半**：没有机器检查保证「新的后台协程调用外部实现时接了 recover」——扫「哪些函数会被
  非请求通路调用」需要调用图，误报会高于收益；同族的先例已在本仓两处（`base.RunSourceBoots`、
  `app.callSourceHandler`），第三条也应由下一个人手动接。

## 覆盖「正在被执行的那条路径」必须用 rename，不能逐字节写；而文档里的换装纪律必须由脚本自己执行

- **症状**：部署后服务连炸几十次，`journalctl` 里两种味道——`code=exited, status=203/EXEC`（ELF 都读不全）
  与 `code=killed, status=11/SEGV` **且没有任何一行应用日志**。14 天 journal 里数出三次：
  09-28 23:42（118 次 203/EXEC + 118 次 SEGV）、10-01 10:58、10-04 01:10（后两次各约 50 秒到 2 分钟）。
  共同形状：重启发生在文件还没写完的那一刻，systemd 把半截二进制拿来 exec，
  而 `Restart=always` 把崩溃循环伪装成「运行中」——**运维看到的不是"崩了"，是"一直在启"**。
- **真因**：`install -m 0755 源 目标` 与 `cp 源 目标` 都是**打开目标路径逐字节写**（inode 不变），
  写完之前那条路径上是一个既非旧版也非新版的文件。同目录 `mv`（rename）是原子的：活路径要么旧、要么新，
  不存在中间那一格。现网实测过对照：`cp` 覆盖前后 inode 相同，`place`（临时名 + `mv`）覆盖前后 inode 变了。
- **判据**：**凡是可能被正在运行的进程执行的产物（二进制、`.so`、systemd unit 指向的脚本），落地一律
  「同目录临时名 → rename → 复算校验 → 再重启」**；跨目录/跨文件系统不算原子，先落到目标同目录。
  另一半是元判据：**文档里要求人记住的步骤，脚本没做到就等于没做**——本页第 2 条早就写了
  「核 md5 与 install 在同一条远端命令里、装完复算」，而 `scripts/deploy.sh` 自己用的是非原子的 `install`，
  手工换装才有的三查并没有防住"用脚本换装"这条路。
- **固化**：`已` → `scripts/deploy.sh` 的 `place()`（临时名 + `mv -f` + 目标 md5 复算，不一致就 die 不重启），
  安装与回滚两路都走它；`make vet` 第 9 条 `scripts/check-deploy-atomic-install.sh`
  （活路径当目的地出现 `install`/`cp`/`tee`/重定向即红；`place` 里少了 `mv -f` 或少了
  **对目标**的 md5 复算与比较也红）。五次变异各拦一处：安装退回 `install` 直写、`mv` 换成 `cp`、
  删掉目标复算那一行、比较改成永真、回滚退回 `cp`。
  **反面教训也记一笔**：规则② 最初只 `grep md5sum`，删掉「对目标复算」那行照样绿——
  因为源文件那一半的 `md5sum` 还在。**规则要指向被删的那个东西本身**。

## 持着锁去调别人的实现，而传出去的 ctx 没有截止：一个卡住的上游就把整块状态机冻住

- **症状**：某个源的探活/领取接口挂住（TCP 连着但不回数据）。现象不是"这个源报错"，而是
  **该池的所有请求一起挂住、维护协程一去不回**，面板上号池数字停在原地、进程还活着。
- **真因**：`base/pool` 调 `Provider.Refresh/Claim/Create` 时传的是裸 `context.Background()`——
  框架侧**没有任何截止**；而上游那一次调用是否限时，取决于源自己有没有给 http.Client 设超时。
  更要命的是调用点：维护与装填都是**持着 `p.mu` 调钩子**的（`Acquire` 也走同一把锁），
  所以一次不返回的调用等于把整个池的请求路径一起扣住。第十八、十九遍把 panic 与竞争治了，
  这一条是同一族里"通路"判法的第三面：**panic 有人兜、锁用 defer 放，还得有截止**。
- **判据**：**跨层传出去的 ctx 必须自带截止**（`WithTimeout`），尤其当接收方是"别人写的实现"、
  而调用方持有共享锁时。配套两句自查：
  ① 框架能保证的只有"传一个带截止的 ctx"——**不读 ctx 的实现照样能卡住你**，
     所以这条契约要写在 Provider 的声明处而不是写在心里；
  ② 持锁调外部实现的每一处，都要问"最坏多久返回"，答不出就是没有上限。
- **固化**：`部分` → `Config.HookTimeout`（默认 30 秒，`POOL_HOOK_TIMEOUT_SEC`）+ `hookCtx()`
  接在 `refresh` / `claim` / `callCreate` 三个出口 + `test/pool_hook_timeout_test.go`
  （假源在"上游卡住"模式下只等 ctx：断言维护一轮在 5 秒内返回、ctx 的截止落在配置值内、

## 一个配置名承载两种口径：读的一侧必须只有一种含义

- **症状**：把 `CACHE_TTL` 从 300 调大（"缓存留久一点"），结果 Redis 卡死时**请求要挂 5 分钟**才失败——
  因为 `utils/cache.go` 把这个值同时当成 socket 的 `ReadTimeout` 用了（库里默认是 3 秒）。
  没有任何报错，只是"改了一个参数，动了一个没打算动的东西"。
- **真因**：一个环境变量、两处读取、两种语义（键存活时间 vs 网络超时）。这类不是写错，是**当初复用**：
  两处都想要"一个秒数"，于是要了一份。同一族的另一条是限额的 `period`（待办清单 P70：
  写进去、存下来、面板当单位显示，而没有任何判定读它）——那是"有写无读"，这是"一读两用"。
- **判据**：**读一个配置名前问一句"这个名在这里是什么意思，和另一处一样吗"**；
  只要两处含义不同，就必须拆开名字（而不是在某处 `// 这里其实是超时`）。
  参数值的量级也是线索：**网络超时与缓存存活期不可能同量级**，看到 `Timeout: <某个 TTL>` 就该停一下。
- **固化**：`部分`（第四十三遍更正——原先标 `已`）
  `.env.example` 把这件事写在参数旁边；`test/pool_hook_timeout_test.go` 的
  `TestCacheTTLNotUsedAsNetworkTimeout` 扫源码：任何 `Timeout` 行引用 `CacheTTL` 即红
  （变异：把那行改回 `time.Duration(conf.Config.CacheTTL) * time.Second` → 用例点名到 `utils/cache.go:95`）。
  **形状上的这一族还没有更宽的机器检查**（要判"两个含义"得读语义），所以先按这一条具体的拆。
  **为什么不是 `已`**：本行自己写着「形状上的这一族还没有更宽的机器检查（要判两个含义得读语义），所以先按这一条具体的拆」——用例 `CacheTTLNotUsedAsNetworkTimeout` 拦的是 `CacheTTL` 这一个名字，不是"一名两义"这个形状。

## 截断文本要按 rune，不是按字节：`s[:n]` 落在多字节字符中间，错误文案就带半个字符出来

- **症状**：日志与面板的错误文案尾部出现乱码（U+FFFD）——不是上游给了乱码，是我们自己把它切断了。
  第二十三遍巡检在骨架里数出两处、分支里三处：`base.errBodySnippet`（上游非 2xx 的响应体前 256 字节摘要）、
  `handlers/verify` 的 `truncateStr`（发码平台响应体前 200），以及分支的 uxx/qimao/fq 三个协议层错误摘要。
  **中文响应体是常态**，而 256 与 200 都不是 3 的倍数（汉字 3 字节），所以只要正文够长，截点几乎必然落在 rune 中间。
- **真因**：Go 的 `string` 切片按字节走，`len()` 是字节数；写这段代码时"256"想表达的是"一小段"，
  没有第二个人去问"这一段是不是完整字符"。同仓里已经有做对的那一份（`base/subject.go` 的
  `truncateRunes` 明确注释"按 rune 截断（中文安全）"），**所以这不是不知道，是同一个动作写了两份、只有一份对**。
- **判据**：**凡是截"可能给人看的文本"（错误文案、日志摘要、面板字段）一律按 rune 截**；
  只有 hex/base64/ASCII 定长标识、日期串（`Day[:10]`）这类形状确定的才允许按字节切。
  按字节读进来的东西（如 `io.LimitReader`）转成文案前，要把不完整的尾巴削掉（`utf8.Valid` 从尾部退，最多退 3 次）。
  后果不是崩溃而是**读数骗人**：看到乱码的人要先花一轮猜"这是上游真给了乱码还是我们切的"。
- **固化**：`部分` → `test/utf8_truncation_test.go` 两条（100 个「测」= 300 字节走摘要通路、
  300 个「渠」走发码失败通路，各断言结果 `utf8.ValidString` **且自己数样本**：截断确实发生、
  中文确实还在结果里——否则 ValidString 是空转）。两处变异各拦一处（退回按字节截 → 红）。
  **未固化的那一半**：没有机器检查拦"新的按字节截断"——`s[:n]` 是不是在截"给人看的文本"要看语义，
  扫不准（`hex.EncodeToString(b)[:n]`、`Day[:10]`、`maskIdent` 那些按字节切本来是对的）；
  分支树同族三处在同一遍里已改完（S53，分支提交 `3869c51`）。

## 缓存键必须带全"这条值属于谁"的维度：少一段不是命中率低，是把别人的值发给你

- **症状**：监控面板的章节榜里，某本书的章节标题是**另一本书**的标题。
  现网实测（只读计数）：`(source, chapter_ident)` 有 **123 组跨书重复**，
  极端例子是 uxx 的标识 `0`——出现在 **96 本不同的书**下、对应 **35 个不同标题**。
  更糟的不只在显示：`MONITOR_BACKFILL_SEC` 的名称回填循环会按同一个键反查，
  把借来的标题**写进明细行**，于是错读数被固化（存量落在这些组里的有 912 行）。
- **真因**：章节标识的唯一性范围是**上游自己定的**——有人发章节 URL（全局唯一），有人发章号（只书内唯一）。
  缓存写成 `source|ident` 时，等于假定"标识在全站范围内唯一"，而这个假定没有任何声明与校验；
  同文件里书维度的键是 `source|bookId`（书标识本来就全局唯一），**两处形状相同、含义不同**，
  所以照着旁边那一行写不会有人拦。
- **判据**：**给一个标识建键之前先问"它在哪个范围内唯一"**，键就必须至少包含那个范围：
  书标识在源内唯一 → 键带 `source`；章节标识只在书内唯一 → 键带 `source + 书标识`。
  推论两条：① **范围不够就整条不做**（没有书标识时既不登记也不反查——
  「名称留空是合法状态，猜一个才是错」，这句话本来就在同一文件的 store 契约里）；
  ② 同形状的代码不等于同语义，**抄旁边那行之前先抄它的前提**。
- **固化**：`部分` → 键改成 `source|bookIdent|ident`（内存缓存 + Redis 持久化两侧同形），
  三个调用点（目录登记、请求期反查、监控回填）一起带上书标识；
  `test/chapter_name_scope_test.go` 两条：同一 `ident` 在两本书下各查得自己的标题、
  回填不会把另一本书的标题写进这一本的明细行；**两条都带反向自检**
  （先证明 book-two 自己的行填得上，"留空"才不是整条通路坏了）。
  变异：把 `chapterIdentKey` 的书维度摘掉 → 四条断言各红一处（含"缺书标识时竟然查出了值"）。
  **未固化的那一半**：没有机器检查能问"这个键带全维度了吗"——那要看上游的取值域；
  存量那 912 行要不要清已登记成决策项（报告 §8）。

## 丢掉转换函数的 err，不是丢掉失败，是收下它钳到的那个值：`page, _ := strconv.Atoi(x)` 会让越界页码活下来

- **症状**：管理面六个列表端点上，`?page=999999999999999999999`（或任何超出 int64 的页码）
  返回的是**第一页的数据**，而响应体里回显 `"page": 9223372036854775807`。
  不报错、不崩溃、面板也不显示异常——只有"这一页到底是第几页"这件事在骗人。
- **真因**（三层叠起来才成立，每一层单看都合理）：
  ① `strconv.Atoi` 对超范围输入返回 `ErrRange`，**但返回值仍然是钳到 `MaxInt64` 的结果**——
     所以 `page, _ := strconv.Atoi(s)` 丢掉的不是"一个失败"，而是"一句说明这个值不可信的话"；
  ② 旧写法的守卫只有 `if page < 1 { page = 1 }`，MaxInt64 顺利穿过；
  ③ `(page-1)*pageSize` 在 `int` 上**溢出成负数**（实测 20 一页时是 -40），
     而 GORM 对负 offset 的处理是**整段不写 OFFSET**（DryRun 只剩 `… ORDER BY id DESC LIMIT 20`）——
     于是数据库老老实实给了第一页，代码却把那个越界页码原样回显。
- **判据**：**丢掉转换错误之前，先看这个函数在失败时返回什么值**——
  返回零值时 `, _` 是"用 0 兜底"（勉强可读），返回**钳位值**时 `, _` 是"收下 MaxInt64"（这就是本次的形状）。
  推论两条：① 数字参数必须**同时**判 err 与上下限，只判 `< 1` 挡不住"正好等于 `MaxInt64`"
  这种**连错误都没有**的输入（它走的是合法路径！）；
  ② 凡进入 `Offset()`/`Limit()`/循环次数/切片的算术，要先证明它**不会在 int 上溢出**，
  而不是指望下游某层替我夹（GORM 丢掉负 OFFSET 就是这种"替我夹"，它给的是错答案而不是坏消息）。
- **固化**：`部分` → 分页收成 `utils.Paginate`（单一处定义，页长上限 `PageSizeMax=100`、
  页码上限 `PageMax=1e6`，后者存在的唯一理由就是让 `(page-1)*pageSize` 不可能溢出）；
  `make vet` 第 10 条 `scripts/check-pagination-single-source.sh`
  （控制面再出现就地 `Atoi(c.Query("page"…))` 即红；内联夹复活即红；`Paginate` 少了任一夹即红）；
  两层用例：`utils/paging_test.go`（新旧两式逐点同值 + 把"旧式确实会拿到 MaxInt64"也断言下来当凭据）、
  `test/pagination_out_of_range_test.go`（三种越界页码都回显 page=1 且与第一页逐行同）。
  变异：让 `Paginate` 退回旧语义 → 单元两条 + e2e 三条同时红（回显 `9.223372036854776e+18`）。
  **未固化的那一半**：`strconv` 之外的同类（`ParseFloat`、`ParseBool`、`Unmarshal` 部分失败）
  没有扫描器覆盖，"丢掉 err 前先看失败时它返回什么"这件事机器判不了。

## 列表端点的关联名称要整页一次取回；测它的断言必须是「条数随不随行数变」，不是某个绝对条数

- **症状**：卡密列表 `GET /admin/redeem-codes` 一次请求发 **31 条查询**（25 行的一页），
  而 3 行的一页发 9 条——**行数一多查询就线性增长**（待办清单 P87，实测数字，不是估算）。
  现网这张表今天只有 39 行，所以没人觉得慢；它是 `redemption_codes` 这种**只增不减**的表（待办清单 P54
  点名的四张之一）形状上的问题：行涨了才显现，而那时已经没人记得这里为什么慢。
- **真因**：循环里逐行 `db.DB.First(&u, *rc.UsedBy)` 取兑换者用户名。
  代码作者其实**做了缓存**（`userNames` map），但缓存只能压掉"同一值重复查"，压不住"每个值各查一次"；
  套餐名那一侧的缓存还有个更小的 bug：用 `planName == ""` 当"没查过"，
  于是**套餐名为空或套餐已被删**的行每行都要重查一次。
- **判据**：**给列表附名称/关联字段时，先问"这次请求发了几条 SQL"，再问它随不随行数变**——
  正确形状是把整页的 id 去重后**一条 `IN` 取回**（本仓到处已是这个形状：`Where("id IN ?", ids)`、
  `user_id IN ?` 聚合、`name IN ?` 批量套用到组，见 `handlers/admin/devices.go`、`source_groups.go`）。
  **测它的断言要测增长率而不是绝对数**：一次请求的固定开销（鉴权、设置读取、Count、列表、两次 IN）本来就有几条，
  写死"≤6"会让第一条正常的中间件读就把用例弄红（我自己第一次就是这么红的：实测 7 条），
  而"两批行数不同的样本发出**相同条数**"这个性质既不需要猜常数，又正好是缺陷的定义。
- **固化**：`部分` → `handlers/admin/redeem.go` 的 `namesByPlanID` / `namesByUser`（整页去重 + 一条 IN）
  + `test/redeem_list_queries_test.go`（GORM 查询计数回调，25 行 vs 3 行两批样本比对条数，
  并断言名称仍然对——包括"套餐不存在的行留空"这一支；只测条数的话把两次取名整个删掉也能"变快"）。
  变异：把兑换者用户名退回逐行 `First` → 用例报「25 行 31 条 / 3 行 9 条」而红。
  **覆盖面边界要写明**：把**套餐名**退回逐行（每页去重后只有 2~3 个不同套餐）不会被这条用例抓到——
  它不增长，只多几条常数。那条路径我按"常数级多查"接受，没有为它加断言。

## 写库的返回值没人读：症状不在写的那一步，而在"额度怎么扣不完""我明明改过了"

- **症状**：`quota_usage_logs` 的两处 `db.DB.Create(...)` 没读 `.Error`（待办清单 P88）。
  写失败的对外表现是**什么都没有**：请求 200、监控明细成功、面板当日已用量偏小。
  同一次巡检还扫出三类同形状：三个配置写入口（用户自配地址 / 平台默认地址 / 用户级额度覆盖）
  写失败仍回「已更新」；`verification_codes.attempts` 那个**防爆破计数器**写不进去，
  本次请求靠内存值挡住，库里那一列却从此不前进；`user_roles` 去重失败时真症状要等下一行
  AutoMigrate 报"索引冲突"才浮出来，而那句话不会提"清理没跑成"。
- **真因**：GORM 把错误挂在返回值上而不是 panic，**不读就等于吞**；
  而这类写入又分布在"已经成功的路径"上（上游已返回、内容已下发、面板已准备说"已更新"），
  所以没有任何调用方会因为它的失败而报错——它只让**判定**与**计数器**读到偏宽松的答案。
  **静默的来源不是"没人写错误处理"，是"失败方向朝里"**：错误朝内吞掉，外面看不出。
- **判据**：**凡是"某处判定的读对象"或"审计事实"的写入，必须读 `.Error`；写不进就出声，
  别把失败留给三个月后的读数去解释**。落笔前先答三个问题：
  ① 这张表是谁的读对象？（`quota_usage_logs` → `UsedToday`；`user_source_configs` → baseurl 解析；
  `verification_codes.attempts` → `maxAttempts`；`auth_sessions` → 鉴权）
  ② 读对象在缺这一行时会得出**偏宽松**还是**偏严格**的答案？偏宽松就是静默放行，不是静默失败。
  ③ **同族写入口先比对再动手**：本仓三个写入口回 500 而这三处回 200，
  "别人都检查而这一处不检查"比"这里没检查"显眼得多，比对是唯一能自动想到另外两处的办法。
  另：**改法只出声不改语义**（回不回 500、要不要 fail-closed 是两件事，各自拍），
  把"出声"和"改对外行为"捆在一起做，会让前者被后者拖住不做。
- **固化**：`已` → `make vet` 的 `ledger-write-check`（`scripts/check-ledger-write-checked.sh`：
  8 张判定/审计表的字面量写入口 + 任何 `Updates/UpdateColumn(s)`，收尾行没有 `.Error` 即构建红；
  受检表名在 `models/` 下找不到定义也红——**扫描器不许对着不存在的名字空转**）
  + `gate/billing.go` 的 `recordUsage`（两处扣减合成一处）
  + `test/silent_write_notice_test.go` 四条用例（sqlite 触发器钉死插入/更新，
  断言"出声 + 不泄密 + 撤掉触发器后正常路径必须真的落库"）。
  变异四次：把 `recordUsage` 的日志条件改永假 → 红「额度流水没写上而日志一个字都没有」；
  把用户侧 500 摘掉只留日志 → 红「status = 200（msg="ok"）」；平台侧同理；
  计数器日志改永假 → 红。**两次红报的是缺陷自己的两种症状**，不是编译错误。
  **盲区写明**：只认 `Create(&models.X{` 字面量形式，`Create(row)`/`.Save(&var)` 不在网内
  （本轮数过：非用例代码里落在这两个形态的真 DB 写入 0 处）。
- **来路**：第二十九遍巡检（§13 第五源那一族：「静默跳过的配置 / 两处写同一份值」）。

## 嵌套块里 `x := ...` 让 `x` 换了类型：入参被遮掉那一瞬间，编译与用例都不会响

- **症状**：`app/aggregate_search.go` 的扇出判定写成 `allowed, c, reason := gate.AggregateTargetVerdict(...)`，
  而外层函数的入参就叫 `c`（`*gin.Context`）。`AggregateTargetVerdict` 的第二个返回值是 **cost int64**，
  于是同一个函数里 `c` 有两种类型：`if !isRouteSource {` 这个**内层块**里是 int64，块外是 gin.Context。
  今天没有故障——下面那句 `gate.DeductAggregateTarget(c, caller, ...)` 写在块外，所以拿到的是 context。
  **这条不是 bug 而是雷**：那句代码的正确性靠"它写在块外"这个作用域细节，而不是靠名字（待办清单 P89）。
- **真因**：Go 的 `:=` 只在**同一作用域**里才是赋值，进了嵌套块就新建变量并遮蔽外层同名变量；
  而那个函数的返回值顺序是 `(allowed, cost, reason)`，第二个位置正好是最容易顺手叫 `c` 的那个字母。
  `go vet` 不查这个（它管 printf、锁、printf 参数这类），用例更测不出来——**这块代码今天的行为完全正确**。
- **判据**：**见到 `:=` 左边出现与函数入参同名的变量，就把左边逐个与入参表对一遍**，
  问一句"这个字母在这个块里还是不是外面那个东西"。写的时候用两条规则避开：
  ① 多返回值接住的名字不要用单字母；② 与入参同名的一律换名（本轮改成 `targetCost`）。

## 进程日志是**第二条留存面**：脱敏只管响应，而 Go 的 http 错误原文必带完整 URL——查询串里就是用户在读什么

- **症状**：`ERROR: 聚合搜索目标源失败: source=uxx action=search err=Get "https://…/?c=search&wd=<用户搜索词>&page=1": context deadline exceeded`。
  现网 14 天实测（journald 总量 255,720 行）：**URL 里带查询串的行 260 行，其中 121 行带搜索词参数、9 行带书或章节标识**（待办清单 P92）。
  同一件事在库里有 `content_consent`（P37）与 `MONITOR_RETENTION_DAYS` 两道管，**在进程日志里一道都不管**：
  同意位关掉的是"写进环形缓冲之前"的抹除，保留期轮转的是库表，journald 按自己的策略走。
  于是 §11 那句「阅读行为数据只经 `/admin/*` 出明细」过去有第二条出路。
- **真因**：Go 的 `http.Client` 错误文本长这样 `Get "<完整 URL>": <底层原因>`，
  任何把 `err` 原样打进日志的地方都会带出 URL；而 Legado 一族的**接口参数全在查询串里**
  （搜索词、书目标识、章节标识），URL 拓扑本身就是内容。
  骨架的 `sanitizeUpstreamMsg` 只挂在**响应出口**，注释甚至写着"完整错误已由 handleError 记入服务端日志"——
  **那句话在当时是对的，也正是这条缺口的入口**：没人回头问"记进去的那份该不该洗"。
- **判据**：**凡"数据能不能留"的开关，要按面清点**（响应 / 库 / 进程日志 / 指标），

  修法口径：**日志洗"内容"不洗"拓扑"**——隐去查询串、保留协议+域名+路径，
  因为排障要看"打到哪个站的哪个接口"，而查询串对排障几乎没用。
  这与对外文案的判据**不同**（对外是"出现 URL 就整句换掉"），**所以两份不许合并成一份**，
  否则总有一侧被另一侧削坏。
- **固化**：`部分` → `app.scrubQueryForLog`（接在 `handleError` 与聚合搜索两处日志点）
  + `app/log_scrub_test.go`（四种形状各断两件事：该隐的一个不留 `wd=`/`item_id=`/`sig=`…，
  该留的一字不动 域名/接口路径/`context deadline exceeded`；再加一条"没有 URL 的原文不许被动过"）。

  **没上门禁的原因**：要判"这条 `%v` 打的 err 会不会带 URL"得靠类型流向，误报率高；

  清它属服务器写操作，等授权（报告 §8）。

## 被拦下的请求每一个都 panic 一次，因为新加的字段读落在既有的 nil 保护之外

- **症状**：响应正文里出现**两份 JSON 拼在一起**：
  `{"code":-1,"msg":"系统维护中，请稍后再试"}{"code":-1,"msg":"内部服务异常"}`。
  状态码是对的（503），日志级别正常，面板一切正常——只有读 body 的人知道出事，
  而 Legado 那一类下游会直接解析失败。
- **真因**：两层叠在一起。① `RecordCall` 早就把所有 subject 字段的读法收在
  `if subject != nil { … }` 里（函数注释明写「subject 可为 nil——那时各维度留空」，
  因为被 access/billing 拦下的请求从没进过 handler，nil 是**常态**不是异常）；
  这次新增的那一维写进了**结构体字面量**里，字面量在那个 `if` **之前**。
  ② 第二层见上一条（尾解锁）。**"这里已经有 nil 保护"不等于"我新加的读法在保护之内"**——
  加字段的人看的是"这一段有没有 nil 检查"，而不是"我这一行离检查隔了几行"。
- **判据**：**在已有 nil 保护的段落里新增读取，要新写一次断言证明保护覆盖到它**，而不是目视；
  可执行的查法是数一遍"保护块之外有没有对该指针的 `.`"（本轮就是这么找到的）。
  另一句同样适用的判据来自本条的症状本身：**可恢复错误的处理器必须先看响应是否已发出**
  （`c.Writer.Written()`）——已经发出去时再写一份信封不会替换它，只会**接在后面**，
  于是"一个处理器"变成"两份契约"。
- **固化**：`部分` → `middleware/transport/recovery.go` 加 `Written()` 一支并打 `debug.Stack()`
  （原来 `PANIC: %v` 只有一行结论，"哪一层炸的"仍要靠复现，而这里炸的偏偏是最难复现的那种）
  + `base/metrics.go` 把新维度收回保护内 + 上面那条环形缓冲断言。
  **没上门禁的原因**：「新增的字段读是否在保护之内」是数据流问题，正则判不了；
  能拦的是"保护块外出现指针解引用"这种窄形状，误报率取决于函数写法，等有更多例子再上。

## 把尾解锁改成闭包时顺手拆成两次加锁，"查-占"的原子性就这么没了

- **症状**：一个与改动无关味道的红——`TestSingleflightCoalescesConcurrentRequests` 报
  「期望上游只被调用 1 次，实际 2 次」。代码看着对，编译过，`-race` 也没喊。
- **真因**：原写法是 `Lock(); if c, ok := calls[key]; ok { … } c := 新建; calls[key] = c; Unlock()`——
  **查与占在同一段临界区里**，这是请求合并成立的全部依据。把它改成"每段临界区包一个闭包"时，
  很自然地拆成了"读一次的闭包" + "写一次的闭包"：两个 goroutine 可以同时读到空、各自新建，
  后登记的覆盖掉先登记的，于是同一 key 的并发不再合并，上游被打两发。
  尾解锁的修法要求的是**换解锁姿势**，不是**换临界区的边界**——这两件事在"包闭包"这个动作里挨得极近。
- **判据**：**改锁的释放姿势时，临界区的边界必须一字不动**；原来在同一次持锁里完成的
  "检查 + 写入"（check-and-set、双检锁、占槽、去重登记）**必须留在同一次持锁里**。
  要拆段就得有新的正确性论证，而它不属于"顺手"的范围。
  写完先跑那条**并发合并类**用例（本仓是 `resilience_test.go` 那条 + 本轮补的 `test/singleflight_test.go`），
  而不是只看 `-race`——**这条不是数据竞争，race 检测器看不出覆盖**。
- **固化**：`部分` → `test/resilience_test.go` 的 `TestSingleflightCoalescesConcurrentRequests`
  当场把这次改坏抓住（断的是**上游被调用次数 = 1**，正是能分辨"合并没了"的具体值，不是"返回成功"）；
  `test/singleflight_test.go` 在 `Flight` 这一层直接数 `fn` 执行次数，同样会红。
  **没上门禁的原因**：扫描器判不了"这两段本该是一段"——那是语义。但这条判据值得每次做同类重构时先读一遍。
- **来路**：本轮 P93② 的执行过程，主角是我自己的第一版改法。

## 对哨兵错误用 `==`（`switch err { case 哨兵: }` 也算）：包一层就永不命中，而 default 往往才是被走到的那支

- **症状**：不报错、不红、不 panic——只是某条分支**再也不被走到**。本轮的实例形如
  `switch err := db.…First(&x).Error; err { case nil: … case gorm.ErrRecordNotFound: 直走 default: 拒绝 }`：
  今天 GORM 返回原句所以命中，一旦上游多包一层（驱动、插件、一次"顺手加个 context"的重构），
  "查不到"就掉进 `default`，而 `default` 是**拒绝发码**。症状因此从"发不出去"变成"偶尔发不出去"，
  比一直错更难查——它跟着数据走（第一次发过的目标不再触发）。
- **真因**：Go 的 `switch` 与 `case` 用的是 `==` 语义，`errors.Is/As` 才是为包装链设计的。
  这一族的隐蔽处在于**写法看起来完全正确**：`switch err` 是标准库自己的惯用法示范，
  只是标准库的示范里 case 的都是它自己保证不被包装的错误。
- **判据**：**凡比较"是不是这个错误"，一律 `errors.Is` / `errors.As`**；
  `err == 哨兵` 与 `switch err { case 哨兵: }` 两种写法一起禁（后者更容易躲过评审，因为它"看着像类型分派"）。
  反过来，`err != nil` 是安全的，不在这条范围内。评审问句：*这个 err 从出口到这里，中间可能被谁包过一层？*
  还有一句配套：**分支的"意外那一支"要有名字**——`default` 里如果做的是"失败关闭"，
  那么永不命中的 case 会被 default 悄悄接住，而它的行为可能正好相反（本例是拒绝而不是放行）。
- **固化**：`部分` → 实例当场改掉（待办清单 P101，`1673115`），而**那一支确实被用例覆盖**这件事是验证过的：
  把 case 判死成 `false && errors.Is(…)`，`test/p99_verify_gate_test.go` 的基线断言当场红
  （首次发码走的正是"没发过码"这一支）。**没上门禁**：`err == 哨兵` 的静态识别要区分"比错误"与"比别的同名变量"，
  误报面不小，且本轮全仓扫下来 `err ==` 形式 0 处、`switch err` 形式 1 处（已修）——
  为一条只咬到一次的规则加构建红，按本页"等第二次再上扫描器"的规矩先登不拦。
- **来路**：第三十八遍巡检；而扫出来的第一处是**本轮自己刚提交的代码**（`a5386d0`）。
