  进程内存的 map 里，**库里没有任何表承载它，管理面也没有端点读它**。
  所以在它之前，「这个 IP 被锁了吗、锁到几点」只有一个答案办法——重启进程，而重启会连带清掉所有人的锁、
  中断所有在途请求。附带一条同源缺陷：条目只按 IP 建、**没有任何回收路径**，见过的每个 IP 都留一行，
  被爆破时内存直接跟着对方的 IP 池长。
- **影响**：误锁一个 NAT 出口（同一出口 IP 下多个正常用户同时重登录）时管理员没有定向手段；
  「防爆破有没有在工作」在面板上不可见，出事只能靠 journal 里的 401/429 行反推。
- **本轮做的（轻方案：只加「可读」与「可清」，不加留存）**：
  - `handlers/auth/auth.go`：加 `pruneLocked`（越过 `attemptPurgeThreshold=4096` 时顺手扫一次，平时热路径零额外成本；
    快照也扫，所以「面板开着」不再等于内存增长）、`SecurityAttemptSnapshot()`、`ResetAttemptLock(ip)`
    （锁与失败连击一起归零，返回清掉的条数——0 不是错误，那个 IP 本来就没记录）。
  - 两条管理端点：`GET /admin/security/attempts`、`POST /admin/security/attempts/reset`（同一个 `AdminRequired()` 组，只认会话）。
    reset 用 POST 是有副作用的写；**刻意不与 `DELETE /admin/blocked-ips/:id` 同形**——那是删库里的一行，这是清进程内状态。
  - 面板「IP 拉黑」页加一节「登录限频锁定」：锁定项排前面，列通道 / IP / 窗口内尝试与上限 / 失败连击 / 锁到几点 + 解锁按钮；
    空态一句话写明「读数只反映当前进程，不代表最近没人试过」。
- **没做的那一半，以及为什么**：另一条路是新建 `login_attempts` 表把每次尝试落库（可事后统计、可告警）。
  本轮刻意不做——那会把「谁在何时用什么用户名试登录」变成一份新的长期敏感留存（IP + 用户名），
  按 §11 要定保留期、只能经 `/admin/*` 出明细；而**当下的痛点只是「读不到、解不了」**。
  真需要审计链时按那份口径单独立项，不要顺带塞进一个运维按钮。
- **仍在册的两条**（同一片代码，别以为 P40 把它们一起解决了）：
  ① 锁定**只按 IP、不按账号**，所以分布式爆破或「挑一个账号慢速试」都摸不到阈值，账号侧没有独立闸门；
  ② 自动拉黑（`middleware/ipblock/autoblock.go`）只数**数据面路由**的 403/429（`monitor` 的 `Applies` 是 `s.Source != ""`），
  **登录失败根本不喂给它**，两条机制互不知情；`verify_code_scenes` 现网是 `register,forgot_password`（登录没有验证码这道闸）。

  只取方法与计数，IP 与账号一律不进仓库）——
  `/auth/login` 共 **1179 次**：200 × 610、401 × 536、429 × 19、400 × 14；
  那 **536 次失败来自 222 个不同 IP**，直方图是 106 个 IP 各失败 1 次、49 个 2 次、29 个 3 次……
  **单 IP 14 天内最多 14 次**。读法有两层：

### 第十二遍（判法：找「返回值被丢掉」的位置，而不是数日志语句）

## P75 请求参数的值一律是 string，而对它做数字断言是静默死代码【①已上门禁 + 运行时守卫；②扫描盲区写明】

- **背景/证据**（第十七遍巡检，判据「从 `interface{}` 里取出来的数字还是不是原来那个数字」）：
  `app.buildParams` 只把 `c.Query(p)` 的结果放进 `params`——**值一律是 `string`**，而容器类型是
  `map[string]interface{}`，编译器不帮忙。于是 `params["page"].(float64)` 这类写法**恒不成立**：
  不报错、不日志，只是悄悄走默认值。携带形态里真中过一次——
  `sources/fq/form/handlers.go` 的 `toPage` 早先就是这个形状，症状是「分类第三页没有内容」
  （上游每次收到的都是同一个 offset），今天的代码里还留着那段注释当遗言。
- **这一族有三种口径，取数字前先问手里是哪一种**：
  ① 请求参数 `params["key"]` / `getParam("key")` → **只有 string**，要数字用 `strconv.*`；
  ② 上游响应（各源自己 `json.Unmarshal` 出来的）→ 默认 `float64`，除非那段自己开了 `UseNumber`；
  ③ 平台出口 `base/legado.normalizeEnvelope` → 刻意 `UseNumber()`，所以是 `json.Number`
    （走 float64 会把 1675148 这样的字数在回写时变成 `1.675148e+06`——那条注释也是这么写的）。
- **两棵树都数过（这就是"没发现什么"的部分）**：骨架非测试代码里对 params 的数字断言 **0 处**
  （唯一一处 `params["__uid"].(uint)` 是**平台自己注入**的键，值真的是 uint）；
  分支 `sources/**` 里 **0 处**；`.(float64)` 的其余命中全在测试里读平台自己的响应 JSON（那里就是 float64 ✓）。
- **修法（① 已做，提交 `ce94015`）**：
  - `make vet` 新增 `param-assert-check`（`scripts/check-param-number-assert.sh`）两条规则：
    ① 不许对用户可控的参数值做数字断言（键必须是双引号字面量且不以 `_` 开头）；
    ② 不许**声明**以 `_` 开头的参数名——那是平台注入键的保留前缀（`__uid` 是 uint、`_datafile_parts` 是 []string）。
    第二种不是风格问题：`buildParams` 之后平台只在"解析出了 uid 时"覆盖 `__uid`、**没解析出来时不会删除**，
    所以源一旦声明同名参数，客户端 `?__uid=7` 就能占住那个键，将来任何按 string 读它的代码读到的都是伪造值。
  - `app.buildParams` 加运行时守卫：声明里出现 `_` 前缀的键一律忽略，并**每种键名只说一次** ERROR
    （一次性是同 P36/P48 那族的"只在状态变化时出声"——这是每请求路径）。
- **② 扫描盲区（写明，不留成"看起来已被拦住"）**：规则②只在**同一行**里能看见 `QueryParams` 与 `"_x"` 时成立，
  多行写成的声明列表扫不到；规则①也扫不到"先拷进变量再断言"（`page := params["page"]; page.(float64)`）
  与"用变量作键"。这些正是**运行时守卫存在的理由**——两道站的位置不同，不是重复劳动。
- **验证**：规则①/②各注入一次违例（`params["uid"].(uint)`、假源声明里加 `"_uid"`）→ 都红，还原后绿；
  运行时守卫用一次临时探针验（假源声明里加 `__uid` + 带 `?__uid=999` 请求）→ **告警恰好 1 条**、探针文件跑完即删。
  **这条守卫没有常驻用例**：要触发它必须在夹具里声明一个 `_` 前缀参数，而那正是规则②禁止的形态——
  把违例写进夹具会让门禁与用例互相打架，所以它是"验证过但不住在测试里"的一道地板，理由写在这。
  另外，**这条扫描器自己空转过两次**（`\.?(${NUMERIC})` 少了转义的括号 → 模式永远匹配不上），
  是"注入违例必须看到具体命中行"这条判据把它抓回来的；详见踩坑判据「断言空转」那条新增的第 ⑤ 种形态。
- **发现处**：第十七遍巡检。

## P97 额度转移：把某个数据源的当日额度转给另一个源（复用「额度覆盖」，不限额的两端都不参与）【新增·维护者 2026-10-06 提出；A 类·待设计确认后落地】

- **需求原文（维护者）**：新增"额度转移"能力，用于把**其他数据源的额度转移到指定数据源**；
  **可以复用额度覆盖**（`user_quota_overrides`）；**不限额度的数据源既不参与转移、也不接受转移**。
- **落在现有哪一层**（先把归属钉住，免得长出一个平行系统）：
  限额的优先级是 **用户数据源级覆盖（追加语义）> 套餐限额 > 不限**（AGENTS §9），
  所以"转移"的**唯一合法落点就是 `user_quota_overrides`**——它本来就是"这个人在这个源上多给/少给多少"的那一行，
  转移只是把两行的数字重排，**不新造第三份限额事实**。
  另一条现成纪律一起生效：**限额/计费/授权的键一律是数据源码**，分组只是视图（§9），
  所以转移的入参必须是 `(用户, 源A, 源B, 数量)`，不接受 `group_id`。
- **两条硬边界（来自需求，也是判据）**：
  1. **`-1`（不限额）的两端都拒**：转出方是 `-1` 没有"可转的量"，转入方是 `-1` 接受转移毫无意义
     （它本来就用不完）。**判定口在写入之前，不在 UI 上遮一下就算**——两端任一为 `-1` 直接 400，
     文案是给人看的那句「不限额的源不参与转移」，不带 SQL 与内部形状（§10）。
  2. **转入的目标源必须已经授权**：`quota_limits(scope=source, target=源B)` 不存在 = 该套餐根本不能用源B（P34），
     把额度转给一个用不了的源等于造一行永远花不掉的数据。**授权与额度是同一行的两件事**这一条不能在这里破。
- **一条必须先说清的语义（写这段时我一开始把它说错了，改在这里）**：
  `gate.EffectiveSourceLimit` 的口径是 **有效额度 = 套餐限额 + 用户覆盖**（覆盖行是**增量**：正值追加、负值扣减，结果下限 0），
  而 `gate.userOverrideLimit` 里 **`Limit == 0` 不是"覆盖成 0"，是"没有覆盖、回退套餐"**——它是个哨兵。
  于是"转移 N"的正确算术是 `A.覆盖 -= N`、`B.覆盖 += N`，而且**两端都不许把行留在 0 上**：
  转出方一旦正好落到 0，它不是"额度为零"，而是**一夜回到套餐全额**，等于这次转移凭空造出了额度。
  这是 P48（`settingInt` 把 0 当"没配"）与 P85（`pool.Config` 三种 0 并存）那一族「0 是没写还是要 0」的**第三个实例**，

  + `make test`（`go test ./... -race -count=1 -timeout 20m`）+ 两个产物。
- **差别不是一点点**：
  1. **没有 `-race`** —— P78/P80 那两条号池竞争全靠 `-race` 才红（报告里写着「单跑那条用例撞不出来」）；
  2. **只跑 `./test/`** —— 包内单测不在部署前跑。这正是分支侧 S30 记的盲区，
     而 `make test` 跑 `./...` 就是为它改的（AGENTS §3 写了这条历史），**部署脚本没跟着改**；
     对分支尤其要紧：`sources/*` 的用例只在包内（S59 的 wd 用例也按这条放包内）。
  3. **16 道门禁一道都不跑** —— sql 保留字、css 类名、导航完整性、设置读取口、`tz-check`、
     `ledger-write-check`、`lock-defer-check`、`todo-status-check`……全都不在部署路径上。
- **影响**：**部署脚本绿不等于门禁绿**。现网每次发布如果只敲 `deploy.sh`，
  那从上一次 `make build` 之后引入的所有回退都不会被发现——而 `deploy.sh` 的自动回滚只在**冒烟失败**时触发，
  冒烟只测 `GET /` 是否 200（15 秒窗口），**代码能跑起来不等于检查都过了**。
- **建议（拍一个才动，属工具链不是产品行为，但仍是要一句决定的事）**：
  | 选项 | 做法 | 代价 |
  |---|---|---|
  | **A（我的建议）** | 把 `deploy.sh` 的那一段换成 `make vet` + `make test`（或干脆 `make build` 后取现成产物） | 部署慢一些（`make test` 是 `-race ./...`，本仓实测 `./test` 一包就 ~440 秒）；换来"部署路径上的门禁与开发路径同一份" |
  | B | 保持脚本不变，在发布预案里硬性要求"先 `make build` 绿再 `deploy.sh`" | 零代码改动，但**靠人记**——正是 P79 那次把「换装三查」从纪律搬进脚本时所否定的形态 |
  | C | 给 `deploy.sh` 加 `--full-gate` 开关，默认仍窄 | 又是"两条路径"，默认那条还是漏的 |
  **B 是我现在给 S60 写的做法**（预案里硬性要求先 `make build`），A 才是把纪律变成机器的那一步。
