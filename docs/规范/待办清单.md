## P40 登录防爆破的状态只能靠「重启进程」来查看和清除：现在可读、可定向解锁；账号侧形状已可观察【轻方案已处理；①已拍 A：只观察、不做账号闸门；②自动拉黑不覆盖登录失败——继续在册，不拍】

- **现象/证据**：限频器 `ipAttemptLimiter`（`handlers/auth/auth.go`）把窗口计数、失败连击、锁定到期全放在
  进程内存的 map 里，**库里没有任何表承载它，管理面也没有端点读它**。
  所以在它之前，「这个 IP 被锁了吗、锁到几点」只有一个答案办法——重启进程，而重启会连带清掉所有人的锁、
  中断所有在途请求。附带一条同源缺陷：条目只按 IP 建、**没有任何回收路径**，见过的每个 IP 都留一行，
  被爆破时内存直接跟着对方的 IP 池长。
- **影响**：误锁一个 NAT 出口（同一出口 IP 下多个正常用户同时重登录）时管理员没有定向手段；
  「防爆破有没有在工作」在面板上不可见，出事只能靠 journal 里的 401/429 行反推。
- **本轮做的（轻方案：只加「可读」与「可清」，不加留存）**：
  - `handlers/auth/auth.go`：加 `pruneLocked`（越过 `attemptPurgeThreshold=4096` 时顺手扫一次，平时热路径零额外成本；
    快照也扫，所以「面板开着」不再等于内存增长）、`SecurityAttemptSnapshot()`、`ResetAttemptLock(ip)`
    （锁与失败连击一起归零，返回清掉的条数——0 不是错误，那个 IP 本来就没记录）。
  - 两条管理端点：`GET /admin/security/attempts`、`POST /admin/security/attempts/reset`（同一个 `AdminRequired()` 组，只认会话）。
    reset 用 POST 是有副作用的写；**刻意不与 `DELETE /admin/blocked-ips/:id` 同形**——那是删库里的一行，这是清进程内状态。
  - 面板「IP 拉黑」页加一节「登录限频锁定」：锁定项排前面，列通道 / IP / 窗口内尝试与上限 / 失败连击 / 锁到几点 + 解锁按钮；
    空态一句话写明「读数只反映当前进程，不代表最近没人试过」。
- **没做的那一半，以及为什么**：另一条路是新建 `login_attempts` 表把每次尝试落库（可事后统计、可告警）。
  本轮刻意不做——那会把「谁在何时用什么用户名试登录」变成一份新的长期敏感留存（IP + 用户名），
  按 §11 要定保留期、只能经 `/admin/*` 出明细；而**当下的痛点只是「读不到、解不了」**。
  真需要审计链时按那份口径单独立项，不要顺带塞进一个运维按钮。
- **仍在册的两条**（同一片代码，别以为 P40 把它们一起解决了）：
  ① 锁定**只按 IP、不按账号**，所以分布式爆破或「挑一个账号慢速试」都摸不到阈值，账号侧没有独立闸门；
  ② 自动拉黑（`middleware/ipblock/autoblock.go`）只数**数据面路由**的 403/429（`monitor` 的 `Applies` 是 `s.Source != ""`），
  **登录失败根本不喂给它**，两条机制互不知情；`verify_code_scenes` 现网是 `register,forgot_password`（登录没有验证码这道闸）。
- **① 的准备已做完，停在执行门前（同日续跑批次，提交 `212b229`）**：先量了现网的形状（只读 journal，14 天，
  只取方法与计数，IP 与账号一律不进仓库）——
  `/auth/login` 共 **1179 次**：200 × 610、401 × 536、429 × 19、400 × 14；

## P97 额度转移：把某个数据源的当日额度转给另一个源（复用「额度覆盖」，不限额的两端都不参与）【新增·维护者 2026-10-06 提出；A 类·待设计确认后落地】

- **需求原文（维护者）**：新增"额度转移"能力，用于把**其他数据源的额度转移到指定数据源**；

- **落在现有哪一层**（先把归属钉住，免得长出一个平行系统）：
  限额的优先级是 **用户数据源级覆盖（追加语义）> 套餐限额 > 不限**（AGENTS §9），
  所以"转移"的**唯一合法落点就是 `user_quota_overrides`**——它本来就是"这个人在这个源上多给/少给多少"的那一行，
  转移只是把两行的数字重排，**不新造第三份限额事实**。
  另一条现成纪律一起生效：**限额/计费/授权的键一律是数据源码**，分组只是视图（§9），
  所以转移的入参必须是 `(用户, 源A, 源B, 数量)`，不接受 `group_id`。
- **两条硬边界（来自需求，也是判据）**：
  1. **`-1`（不限额）的两端都拒**：转出方是 `-1` 没有"可转的量"，转入方是 `-1` 接受转移毫无意义
     （它本来就用不完）。**判定口在写入之前，不在 UI 上遮一下就算**——两端任一为 `-1` 直接 400，
     文案是给人看的那句「不限额的源不参与转移」，不带 SQL 与内部形状（§10）。

     把额度转给一个用不了的源等于造一行永远花不掉的数据。**授权与额度是同一行的两件事**这一条不能在这里破。
- **一条必须先说清的语义（写这段时我一开始把它说错了，改在这里）**：
  `gate.EffectiveSourceLimit` 的口径是 **有效额度 = 套餐限额 + 用户覆盖**（覆盖行是**增量**：正值追加、负值扣减，结果下限 0），
