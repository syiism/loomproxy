- **③的落地记录**（2026-10-10）：缓存放在 **`handlers/rank` 的出口层**，不放在 `subjectrank.Query` 里，两个理由都是硬的：
  **(a) 类型形状**——`utils.Cache` 的 Redis 段 `Get` 回来的值是 `json.Unmarshal` 进 `interface{}` 的**通用形状**
  （`[]interface{}` 的 map），内存段回来的还是写入时那份 `[]Item`。在 `Query` 里做 `cached.([]Item)` 这种断言，
  **测试（纯内存）永远命中、生产（Redis）永远落空**——"加了缓存"在最贵的那一层静默等于没加，而且没有任何一处会报错。
  出口层缓存的是**要发出去的那份响应体**，两段同形，断言不需要存在。
  **(b) 陈旧语义按档位不同**——管理端那份带 `last_called_at`，陈旧的语义是"排障时看到一个假时刻"，
  要说清这件事得先决定在响应里怎么标；公开榜根本不下发那一栏。所以本轮只给公开榜加缓存，管理端不缓存。
  **键的原料**：`admin` 布尔 + `allowSources` 的**排序后散列** + `days` + **`WindowStart(days)` 的 Unix** + `source` +
  `media` + `limit` + `dims`（由 `boards` 现算，不手抄）。前缀分两段 `rank:boards:all:` / `rank:boards:pub:`——
  **窗口起点必须单独进键**：`days` 只是长度，`WindowStart` 取平台时区当日零点，跨了日界同一个 `days` 问的是另一个总体。
  **只缓存两张榜的行**：`sources` 与 `medias` 每次现取（改名或下架一个源不该跟着榜再活一个 TTL），
  陈旧只发生在榜的计数上，并由响应里的 `cache_ttl_sec` 说出来（面板不自己抄——P46 那条口径）。
  **新增环境变量 `RANK_CACHE_SEC`（默认 60，<=0 每次真算）**，写进 `.env.example` 与 `conf/conf.go`。

  本仓库也有先例（`filters_meta` 由响应下发）。它是**加字段**、不改状态码不改既有字段形态。
  **用例四条**（`test/groupb/rank_boards_cache_test.go`）：命中不重算 / 键带身份段 / `<=0` 回到真算 /
