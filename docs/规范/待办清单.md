## P23 带内 error 正文的文案没有统一脱敏收口：`sanitizeUpstreamMsg` 只挂在 `handleError` 上【①已处理（`73a7736`）；②源侧文案待整】
- **现象/证据**：`app/app.go:335` 的 `sanitizeUpstreamMsg` 是平台唯一的对下游脱敏点，而它只在
  `handleError`（handler 返回非 nil error）里被调用（`app/app.go:328`）。数据面另一条出口——
  响应体里自带错误文案（如正文的 `ContentType=="error"` + `message` 字段，属 Legado 书源传统写法）
  ——**不经过 `handleError`**，文案原样下发。传输层失败时这类文案往往是 `*url.Error`，
  **内嵌完整请求 URL**（含签名参数与上游域名）。底座不携带源，具体命中点由部署侧清点。
- **影响**：`sanitizeUpstreamMsg` 的注释写明了它存在的理由——「签名站会带上 app_key/device_sn/sig 一类参数，
  也暴露自家上游域名」。走带内正文的那条路把这条防护整个绕过，泄露面在**响应里**（客户端可读、
  可能被日志/缓存留存），不在服务端日志里。这不只是文案不友好，是凭证外流。
- **建议修法**（两步，第一步不必等任何决策）：
  ① **骨架侧加一道统一收口**：数据面响应写回前，凡「错误形态」的正文（`ContentType=="error"`
  的 `ContentResponse`，或等价的形状）其 `message` 一律过 `sanitizeUpstreamMsg`。
  判据沿用现成的「串里含 `://` 就整条换成通用提示」。这是对 §10 那条既有约定的**强制执行**，
  不是新增政策；文案会变（下游可见），但变的正是那条本就不该出去的 URL。
  位置建议放在 `app/app.go` 的响应写回处或 `base/legado` 的信封层，别散到各源。
  ② **源侧自有错误文案**：返回真 error 交给 `handleError`，或像某些源那样自己包一层安全文案
  （只说「播放服务暂时不可用」这类，不拼 `err.Error()`）。① 落地后 ② 就不是泄露面，属整洁性问题。
- **发现处**：2026-10-03 盘 P22②-b 的后续计划时，用生产日志给带内失败分类，看到错误正文的形状直接撞在这一点上。
- **①已处理（`73a7736`）**：骨架侧统一收口落在响应写回处（`app.scrubInBandMsg`），
  认规范 DTO 与松散 map 两种形状——**与 `ObserveCall` 认同一组形状**是硬要求，
  否则「标成带内失败」与「文案脱敏」会分叉。四条用例（两种形状收口、不含 URL 的本地文案照旧可见、
  **正文不许被扫**），变异验证两次红。
  偏离原建议之处：位置从「`handleError` 附近」改成「`c.JSON` 之前」——`handleError` 根本不在带内那条路上。
- **②仍在册**：分支侧九处 `err.Error()` 拼进正文的写法（部署侧清点），① 落地后不再是泄露面，属整洁性；
  归分支 S15/S19 的 ②-b 一起看，不为它单独发一轮。

## P35 `MaxDevices` 与 `MaxDead` 互不知情：死号既清不掉又占满建号名额【①已处理；②软删行已可见，是否自动清理待拍】

- **现象/证据**：`base/pool/state.go` 里 `MaxDevices`（总号数闸门，计数含 `dead`）与 `MaxDead`
  （死号超量才物理清理）是两个各算各的旋钮。**当 `MaxDevices < MaxDead` 时，清理条件永远不成立、
  而死号永远占名额**——生产 uxx 正是这个形状（`UXX_MAX_ACCOUNTS` 未配 → 默认 5，`POOL_MAX_DEAD=10`），
  于是 2026-10-03 出现过「池内 5 行 = hot1+cold2+dead2、0 个建号位」，框架自己一点不动，
  只在日志里留一条 `create cold device failed: 号池已达总号数上限`。

## P40 登录防爆破的状态只能靠「重启进程」来查看和清除：现在可读、可定向解锁；账号侧形状已可观察【轻方案已处理；① 的观察与面板已就绪，闸门本身待拍】

- **现象/证据**：限频器 `ipAttemptLimiter`（`handlers/auth/auth.go`）把窗口计数、失败连击、锁定到期全放在
  进程内存的 map 里，**库里没有任何表承载它，管理面也没有端点读它**。
  所以在它之前，「这个 IP 被锁了吗、锁到几点」只有一个答案办法——重启进程，而重启会连带清掉所有人的锁、
  中断所有在途请求。附带一条同源缺陷：条目只按 IP 建、**没有任何回收路径**，见过的每个 IP 都留一行，
  被爆破时内存直接跟着对方的 IP 池长。
- **影响**：误锁一个 NAT 出口（同一出口 IP 下多个正常用户同时重登录）时管理员没有定向手段；
  「防爆破有没有在工作」在面板上不可见，出事只能靠 journal 里的 401/429 行反推。
- **本轮做的（轻方案：只加「可读」与「可清」，不加留存）**：
  - `handlers/auth/auth.go`：加 `pruneLocked`（越过 `attemptPurgeThreshold=4096` 时顺手扫一次，平时热路径零额外成本；
    快照也扫，所以「面板开着」不再等于内存增长）、`SecurityAttemptSnapshot()`、`ResetAttemptLock(ip)`
    （锁与失败连击一起归零，返回清掉的条数——0 不是错误，那个 IP 本来就没记录）。
  - 两条管理端点：`GET /admin/security/attempts`、`POST /admin/security/attempts/reset`（同一个 `AdminRequired()` 组，只认会话）。
    reset 用 POST 是有副作用的写；**刻意不与 `DELETE /admin/blocked-ips/:id` 同形**——那是删库里的一行，这是清进程内状态。
  - 面板「IP 拉黑」页加一节「登录限频锁定」：锁定项排前面，列通道 / IP / 窗口内尝试与上限 / 失败连击 / 锁到几点 + 解锁按钮；

  ① 锁定**只按 IP、不按账号**，所以分布式爆破或「挑一个账号慢速试」都摸不到阈值，账号侧没有独立闸门；

## P48 `settingInt` 把 0 和负数当成「没配」：上限类设置填 0 会静默回默认【①替换已出声；②0 的语义待拍】

> **拍板的地方搬家了**：这条写下来时那份实现在 `handlers/auth/device_watch.go`，
> P61（提交 `3bc078d`）把三份整数读取收成一处 **`db.SettingInt`**，所以下面提到的 `settingInt`
> 现在只有一个落点。② 真要拍，改的是 `db/setting.go` 那一条函数；
> 而 P63 新加的 `db.SettingIntNonNeg` 已经给出一个反向实例——**0 在有的键上是哨兵，不是笔误**，
> 所以这一问的合理落法可能不是"给全部键定一个 0 的口径"，而是"每个键自己声明走哪条读取口"。

- **现象/证据**：`handlers/auth/device_watch.go:38-43` 的 `settingInt(key, def)` 判据是
  `if err != nil || n <= 0 { return def }`，`max_active_sessions`/`device_watch_window_days`/`suspect_distinct_ips`
  三条都走它。于是管理员把 `max_active_sessions` 设成 **0**（想表达「一台都不许多出来」）
  得到的是**默认 5**；`suspect_distinct_ips=0`（想表达「凡多 IP 一律标红」）得到的是**默认 8**。
  面板上显示的是他填的 0，读数是 5/8——两份事实在这里合成了一条静默的替换。
- **影响**：不是崩溃也不是报错，是**配置自己说话不算**。这类「填了个边界值被吞掉」的坑
  与 P36/P35 那批「水位参数被静默夹住」是同一族，区别是那次系统会把夹取结果显示出来（`dead_retention`），
  这里什么都不说。
- **建议修法**：把「非法」与「合法的 0」分开——`strconv` 失败或越界（如 >365）才回默认并**在响应里带上生效值**；
  `0` 对各键的语义要先定：会话上限 0 应该等于「关掉多设备容忍（每次登录都收口到 1）」还是「不适用」，
  这是产品口径，不是解析器该替他决定的。**所以这条先请维护者拍：0 该是什么意思。**
- **发现处**：本轮 §4b 巡检读 `settingInt` 时发现的同形状问题（判据 `n <= 0` 混用了「未配」与「配成 0」）。
- **进展（①已处理，提交 `b46d518`；②仍待拍）**：`settingInt` 把三种情形分开——**没填** / **不是整数** / **填了非正数**，
  任何一种被替换成默认值时经新增的 `db.NoticeReplacedSetting` 出一条 ERROR，
  **同一种替换只喊一次**（判据取自 P36 号池 `ErrCapacityReached` 的「状态变化才出声」：
  读设置在登录与管理端读数的热路径上，每请求一条会把真正该看的读数泡坏）。
  顺手修掉同一条判据里的另一种静默：值带首尾空白（面板里粘贴进去常见）过去被 `Atoi` 拒掉而回默认，
  现在按填的数字生效。**0 的语义一点没动**——`max_active_sessions=0` 照旧按默认 5 走，
  因为「关掉多设备容忍（收口到 1）」与「不适用」之间选哪个是产品口径；日志只做**记账**，不代替拍板。
  另外两处同形状的判据**刻意没接**：`handlers/admin/admin.go` 的 `expireWithinDays` 读的是**查询参数**不是设置项，
  任何调用方都能喷出一串不同的值，去重表在那里会变成无界增长的内存（设置键的个数是固定的，所以那边安全），
  而它也不留第二份事实——填的值不落库，请求结束就没了。面板显示仍是管理员填的原始值，
  生效值这条线只在「设备与密钥」读数页有（`max_active_sessions` 随读数下发）。
- **同形状的第二处（本轮巡检补，尚未接）**：`handlers/verify/verify.go:57` 有自己的一个
  `settingInt`——手写十进制逐位解析（不是 `strconv`），判据同样是 `n <= 0 → def`，
  管着 `verify_code_ttl_sec`/`verify_send_interval_sec`/`verify_daily_send_limit`/`verify_code_max_attempts` 四条。
  **① 的出声只落在 device_watch 那一份上**，因为两份拷贝合并成一个入口会顺带改变验证码那四条的取值行为
  （手写解析器连 `+5`、`-0`、超 int 溢出都各有自己的偏法），那是又一次语义盘点、不该塞进这一轮。
  下次动验证码时把两份收成一份（走 `db` 那一个入口），P48 这条判据才在这两个地方同时成立。

### 第十九遍（判法：「这段代码跑在哪条通路上，谁兜它的 panic」）

- **查了什么**：不找"写错的表达式"，找**执行通路**——把包级可变状态与后台 goroutine 逐个问三句：
  ① 它跑在请求链上（有 gin Recovery 兜）还是后台协程上（没人兜）？② 它调的是平台自己的代码还是**源写的钩子**？

  `loginAccountWatch`、`redeemLimiter`、`dataFileMisses`、`privateNetworks`、`userAgents`、`Dims` 等），

- **撞出了什么**（两条，同一段路上连着）：

  `app.callSourceHandler` 逐目标 recover）。请求链上的 `Acquire`/`Reauthorize` 有 gin 兜，

  更硬的一层：`Maintain` 的三段临界区是显式 Lock/Unlock，**panic 会穿着锁跑出去**——

  四次变异各拦一处：临界区退回显式 Lock/Unlock → 报「panic 之后 p.mu 仍被持有」；
  摘掉维护 recover / 摘掉启动 recover → 测试中止（**这是"二进制炸掉"的红，不是断言失败的红**，
  但本来不兜住的形状就是炸进程，所以仍算拦住）；装填不持锁 → `DATA RACE`。
- **没发现什么**（写给下一轮，别重查）：包级状态三族（map/slice/scalar）全部有主、有锁或只读；
  `sync.Map`/`atomic` 那几处用法正确；`userAgents`/`Dims`/`boards` 这类表只读；

## P52 `content_withheld` 有少量行没被标上：核对到时间轴一级【已定案·非缺陷；残留一处结构缺口】

- **现象/证据**（2026-10-04 生产只读核对，为查分支 S47 那条「五维全空」撞上）：
  关掉留存的 22 个用户里，样本用户 id 1027 有 70 行，其中 **6 行没被标 `content_withheld`**（全在 `recommend`），
  另有 4 行在别的用户身上同样未标——第一眼像「闸口漏了几行」。
- **定案（时间轴逐条对齐，不是推测）**：该用户 `content_consent` 最后更新于 **12:01:47**，
  而那 6 行未标的时刻是 **12:00:36 / 12:00:42 / 12:00:51 / 12:01:04 / 12:01:17 / 12:01:19**，
  全部**早于**这次更新；已标的那 64 行则从 **12:02:35** 起。
  → 未标的 6 行是他**还没关**的时候发生的请求，标记为 0 是**正确**的；已标的最早一行距开关 48 秒，
  说明开关一落地闸口就开始工作。**「access 之前返回所以没置标记」那个假设被这份读数否掉了**（至少在这个用户身上）。
  同一条查询换个角度也自洽：`created_at >= users.updated_at` 之后仍带任何一个内容维度的行 = **0**；
  `content_withheld=1` 却仍带维度的行 = **0**。
- **所以 P52 不是缺陷**，但核对过程中撞出一个真的结构缺口：**同意位没有「变更时刻」**。
  `users.content_consent` 只有当前值，`updated_at` 会被任何一次改昵称/邮箱顶掉——
  这次能定案纯粹是因为那个用户当天只动过这一次、时间轴刚好干净。
  换一个「先关、隔天改昵称、再关回来」的用户，同样的问题就答不了。
  要答得了就加一列 `content_consent_set_at`（只在同意位**真变**时写），
  顺带让「关掉之后还有没有新行被捕获」变成一条随时可查的读数，而不是靠时间轴巧合。
  **加列是生产库写操作（AutoMigrate），单独等授权**；本轮不动。
- **建议下一步**（如果这条被拍要做）：一列 + 写入口在 `POST /auth/privacy` 的**值真变**时盖时刻，
  用例断言「改成同样的值不刷新时刻」「反过来会刷新」——后者正是这次定案所依赖的那条信息。
- **发现处**：本轮为分支 S47 定案做的只读对齐（读数记在 S47 的定案补记与本条）；
  判据页同批补了一条「看到一片空维度先查同意位与 `content_withheld`，再怀疑采集」。

  而 `utils.VerifyAuth` 的第一句是 `if !conf.Config.AuthEnabled { return nil }`——**网关关闭时它整个直通，
  于是不会有人往 context 里写 `user_id`**；紧接着处理函数自己 `c.Get("user_id")` 拿不到就回 401。
  中间件说"这次不用鉴权"，处理函数说"我必须有归属"，两条各自合理，接线处没人负责。
- **另一种更糟的读法要先排除**：两种 401 的**文案不同**——中间件回「缺少鉴权凭证（Authorization Bearer /
  Cookie / X-API-Key / api_key）」，处理函数回裸的 `"unauthorized"`。
  生产上实测拿到的是前者（一次匿名只读 `GET /endpoints`，见报告 §5g），
  说明**生产 `AUTH_ENABLED=true`、这条缺陷在现网是休眠的**；亮着的是照 `.env.example` 填的新部署与开发环境。
  顺带：那块错误文案是英文裸词，中文界面里读不出"要登录还是网关没开"（P23① 那条脱敏/可读性的同族）。
- **选项（各含代价）**：
  A 这条路由改用 `utils.AuthenticateAny`（控制面口径：JWT 或**账号级** API Key 必须有归属）——
    代价：静态 env 密钥的调用者从 401 变成 403 + 一句明确文案，是**对外可见的错误码变化**；
    `AUTH_ENABLED=false` 的部署里这条端点从"必然失败"变成"必须带凭证"，更一致但仍拒匿名。
  B 拿不到 `user_id` 时退回"公开清单"（列出全部启用源的端点）——
    代价：把按套餐过滤的信息变成公开面，同一端点两套口径（治理信息不该随配置变形）。
  C 让 apiauth 在网关关闭时也解析并注入身份（"不强制，但带了就认"）——
    代价：**改的是全局中间件语义**，所有挂在 apiauth 后的处理函数都可能从"拿不到归属→401"
    变成"拿到归属→按某个账号走"，风险面远大于这一条端点。
  D 不做，只在 `.env.example` 与文档里写明"关掉网关时 `/endpoints` 不可用"——
    代价：明知有一个默认配置就会坏的整块 UI，用一句注释放行。
- **我的建议**：**A**，并把处理函数那句裸 `unauthorized` 换成与中间件同一族的中文文案
  （"这个端点需要登录会话或账号 API Key：网关鉴权关闭时也要带凭证，因为它按调用者的套餐过滤端点"）。
  **不选 C**——为了一个端点去动全局凭证语义，正是本仓反复讲的"改一处漂三处"。
- **影响范围**：`app/app.go` 一条路由 + `handlers/*` 里那两处 401 文案；**零 DDL、不改数据面**。
  面板「数据源」页在默认配置下恢复可用。
- **被它阻塞的条目**：无。它阻塞的是"新部署者第一次打开数据源页会不会以为产品坏了"。
- **答复后回写位置**：本条状态行；`docs/架构/鉴权模型与会话.md` 补一句"网关开关与逐端点归属要求的分工"；
  AGENTS §7 的"三形态统一可用"那段要写明 `/endpoints` 属于哪一类。

## P72 趋势图按天分桶由**库侧**判日界：sqlite 把 +08 的串按 UTC 归一，生产 MySQL 按本地【只登记未修·跨方言结构缺口】

- **现象/证据**（临时探针实测，跑完即删；命令与形状记在 P49 第十四遍那段）：
  写一行 `created_at = 北京 2026-10-05 04:40` 进 sqlite，读回来看两个数——
  存储串是 `2026-10-05T04:40:00+08:00`（带 'T' 与偏移），而 `date(created_at)` 给的是 **`2026-10-04`**：
  SQLite 的日期函数把带偏移的串**先归一到 UTC** 再取日界。
  生产是 MySQL：DSN 带 `loc=Local`、宿主机 `Asia/Shanghai`，`DATETIME` 存的就是北京墙上时间，`DATE()` 得 `2026-10-05`，
  **与平台日界一致**。所以这条不一致**只在 sqlite（开发/测试）上出现**。
- **影响**：`GET /admin/monitor/trend` 的日标轴（`days`）现在按平台时区算（P71 刚收口的），
  而每根柱子的高度由 `date(created_at)` 分桶——开发/测试库里北京 00:00–08:00 这段调用会挂到**前一天**的柱子上，

## P74 免鉴权的 `/data/../<文件>.json` 能穿出 DATA_DIR 读父目录的 .json【①已修 + 三道实测；②两处残留】

## P75 请求参数的值一律是 string，而对它做数字断言是静默死代码【①已上门禁 + 运行时守卫；②扫描盲区写明】

- **背景/证据**（第十七遍巡检，判据「从 `interface{}` 里取出来的数字还是不是原来那个数字」）：
  `app.buildParams` 只把 `c.Query(p)` 的结果放进 `params`——**值一律是 `string`**，而容器类型是
  `map[string]interface{}`，编译器不帮忙。于是 `params["page"].(float64)` 这类写法**恒不成立**：
  不报错、不日志，只是悄悄走默认值。携带形态里真中过一次——
  `sources/fq/form/handlers.go` 的 `toPage` 早先就是这个形状，症状是「分类第三页没有内容」
  （上游每次收到的都是同一个 offset），今天的代码里还留着那段注释当遗言。
- **这一族有三种口径，取数字前先问手里是哪一种**：
  ① 请求参数 `params["key"]` / `getParam("key")` → **只有 string**，要数字用 `strconv.*`；
  ② 上游响应（各源自己 `json.Unmarshal` 出来的）→ 默认 `float64`，除非那段自己开了 `UseNumber`；
  ③ 平台出口 `base/legado.normalizeEnvelope` → 刻意 `UseNumber()`，所以是 `json.Number`
    （走 float64 会把 1675148 这样的字数在回写时变成 `1.675148e+06`——那条注释也是这么写的）。
- **两棵树都数过（这就是"没发现什么"的部分）**：骨架非测试代码里对 params 的数字断言 **0 处**
  （唯一一处 `params["__uid"].(uint)` 是**平台自己注入**的键，值真的是 uint）；
  分支 `sources/**` 里 **0 处**；`.(float64)` 的其余命中全在测试里读平台自己的响应 JSON（那里就是 float64 ✓）。
- **修法（① 已做，提交 `ce94015`）**：
  - `make vet` 新增 `param-assert-check`（`scripts/check-param-number-assert.sh`）两条规则：
    ① 不许对用户可控的参数值做数字断言（键必须是双引号字面量且不以 `_` 开头）；
    ② 不许**声明**以 `_` 开头的参数名——那是平台注入键的保留前缀（`__uid` 是 uint、`_datafile_parts` 是 []string）。
    第二种不是风格问题：`buildParams` 之后平台只在"解析出了 uid 时"覆盖 `__uid`、**没解析出来时不会删除**，
    所以源一旦声明同名参数，客户端 `?__uid=7` 就能占住那个键，将来任何按 string 读它的代码读到的都是伪造值。
  - `app.buildParams` 加运行时守卫：声明里出现 `_` 前缀的键一律忽略，并**每种键名只说一次** ERROR
    （一次性是同 P36/P48 那族的"只在状态变化时出声"——这是每请求路径）。
- **② 扫描盲区（写明，不留成"看起来已被拦住"）**：规则②只在**同一行**里能看见 `QueryParams` 与 `"_x"` 时成立，
  多行写成的声明列表扫不到；规则①也扫不到"先拷进变量再断言"（`page := params["page"]; page.(float64)`）
  与"用变量作键"。这些正是**运行时守卫存在的理由**——两道站的位置不同，不是重复劳动。
- **验证**：规则①/②各注入一次违例（`params["uid"].(uint)`、假源声明里加 `"_uid"`）→ 都红，还原后绿；
  运行时守卫用一次临时探针验（假源声明里加 `__uid` + 带 `?__uid=999` 请求）→ **告警恰好 1 条**、探针文件跑完即删。
  **这条守卫没有常驻用例**：要触发它必须在夹具里声明一个 `_` 前缀参数，而那正是规则②禁止的形态——
  把违例写进夹具会让门禁与用例互相打架，所以它是"验证过但不住在测试里"的一道地板，理由写在这。
  另外，**这条扫描器自己空转过两次**（`\.?(${NUMERIC})` 少了转义的括号 → 模式永远匹配不上），
  是"注入违例必须看到具体命中行"这条判据把它抓回来的；详见踩坑判据「断言空转」那条新增的第 ⑤ 种形态。
- **发现处**：第十七遍巡检。
- **被它阻塞的条目**：无。
- **答复后回写位置**：本条状态行（回填提交号）；`docs/规范/开发约定.md` 已加「三种 map 的数字口径」那条；
  分支侧若在合并后撞到规则①/②，处理方式同 S50（分支自己的落点自己改，不改骨架门禁）。
