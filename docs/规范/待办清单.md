## P1 `db.GetSetting` 的列引号只兼容 MySQL/SQLite【已处理】（提交号：cf932f9）

- **现象/证据**：`db/setting.go` 读设置用 `Where("`key` = ?", key)`（反引号硬编码，注释写的就是「MySQL 保留字」）。
  PostgreSQL 的标识引用是双引号，反引号是语法错误 → `First` 报错被吞掉，函数返回空串。
- **影响**：`DB_TYPE=postgres` 的部署上**所有系统设置都读成空**（榜单放行名单、代理开启名单、验证码开关、自动拉黑阈值…），
  且不会报错，只会表现成「设置没生效」。和 `api_keys.key` 那次是同一类坑（那次的教训是「条件用 map 形式让 GORM 按方言加引号」）。
- **建议修法**：条件改 `Where(map[string]interface{}{"key": key})`；顺带全库扫一遍同类硬引号。
- **发现处**：2026-10-01 修 `api_keys.key`（`92d608e`）时同源比对出来的。
- **已处理**（提交号：`cf932f9`）：全库扫到的写死反引号一次收干净——`db/setting.go`、`db/seed.go` 两处
  （废弃键清理与 type 对账）、`handlers/auth` 两个 `getSetting*`、`handlers/admin/{settings,admin}.go` 三处，
  外加三支用例里的手写 SQL；条件一律换成 map 形式让 GORM 按 dialector 加引号。`ListSettings` 的
  `ORDER BY key` 两种引号都做不到跨方言（不加引号 MySQL 1064、加反引号 PG 报错），改成取回后内存排序。
  新增守卫 `test/dialect_quoting_test.go`：一份全库反引号扫描（行尾 `dialect-allow` 显式豁免）+ 一份
  postgres 方言 DryRun 的直接证据（`DisableAutomaticPing` + 不连库，本机没装 PostgreSQL 也跑得起来）。
  **仍未在真实 PG 部署上验证过**——这条能给出的最强证据就是方言 DryRun 生成的 SQL 形态。

  0=关掉只留手动；一轮里按单批上限连捞到「捞空」或「补不动」，重入用一个 `atomic.Bool` 挡住

  **两处偏离原建议**：① 原建议没提扫描顺序，实际必须改——`ORDER BY id ASC` 配上循环等于让一批
  永远反查不到的陈旧行长期霸占 5000 行的窗口、新行一条也进不来，改成 **DESC**（补不到的必须是没人再看的旧行，
  因为榜、覆盖率、明细页读的都是近窗口），用例专门钉这条（改回 ASC 必失败）；
  ② 原建议「启动后先跑一次」改成**先等一整轮**再动手——源的 OnBoot 导入与第一批请求还没把缓存 warm 起来，
  立刻跑只会捞空并白占一次连接。「补不动」那条日志只在状态变化时打一次（这类行会长期在结果里，
  每轮各打一行就是纯噪声；重新补到东西后恢复，才看得见「又开始缺名」）。


## P21 xmly 正文调用的书名/书目标识覆盖率明显低于其他源【未处理】

- **建议修法**：先按上面那句把参数名核实清楚，再决定改哪一侧，且**改在 `sources/xmly` 里、不在骨架加特例**——

## P22 数据源用「带内错误」返回正文失败，HTTP 仍是 200：成功率与覆盖率一起说谎【未处理】

- **现象/证据**：十个源（本分支携带）的 `content` handler 在**参数缺失**与**上游失败**时都返回
  `legado.ContentResponse{ContentType: "error", Data: map{"message": ...}}` 且第二个返回值为 `nil`
  （`sources/*/content.go`，命中 30 处、分布在 6 个文件，如 `sources/xmly/content.go`、`sources/qq_luomu/content.go`、
  `sources/uxx/content.go`）。handler 没返回 error，装配层就按成功收口：**状态码 200、明细记成功、
  内容维度全空**（`ContentType:"error"` 也不是任何合法媒介，媒介那一格同样留空）。
- **影响**：三处读数失真——① 监控的 `Success`/`SuccessRate` 把失败的正文请求算成成功，
  ② P19 的覆盖率表里 `failed` 数不出来（它按 `status >= 400` 判），一格 47% 的覆盖看起来像「采集在漏」，
  实际是「请求在失败」，③ 额度与计费按请求计，失败的正文照样扣一次额度。面板与榜都会往错误的方向被读。
- **建议修法**：**先定产品口径再动手**，这不是纯观测问题——带内 error 是 Legado 书源的传统写法，
  改成返回错误会让下游从「拿到一段错误文本当正文」变成「收到非 0 code 的失败」，是**可见行为变更**，
  要维护者拍板。两条路：① 骨架侧只加观测、不动响应（`ObserveCall` 认出 `ContentType=="error"`，
  在明细上标一个「带内失败」维度，榜/覆盖率/成功率各按自己的口径决定是否把它计入失败）——低风险、
  不动下游；② 各源改成返回真实错误、由 `handleError` 收口成 4xx/5xx——读数是治了，但下游可见。
  先 ① 再 ② 也成立：观测维度先立起来，改状态码时不会瞎。
- **发现处**：2026-10-02 追 xmly 书名/标识覆盖率缺口（P21）时读到 handler 的失败分支，顺手 grep 发现全体同源同形。
