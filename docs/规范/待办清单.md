## P22 数据源用「带内错误」返回正文失败，HTTP 仍是 200：成功率与覆盖率一起说谎【①观测已落地；②-a 必填参数已前移；②-b 上游失败待数据】

- **现象/证据**：各数据源接口包的 `content` handler（底座不携带源，这是实现侧的写法；实测十个源同形）在**参数缺失**与**上游失败**时都返回
  `legado.ContentResponse{ContentType: "error", Data: map{"message": ...}}` 且第二个返回值为 `nil`
  （`sources/*/content.go`，命中 30 处、分布在 6 个文件，如 `sources/xmly/content.go`、`sources/qq_luomu/content.go`、
  `sources/uxx/content.go`）。handler 没返回 error，装配层就按成功收口：**状态码 200、明细记成功、
  内容维度全空**（`ContentType:"error"` 也不是任何合法媒介，媒介那一格同样留空）。
- **影响**：三处读数失真——① 监控的 `Success`/`SuccessRate` 把失败的正文请求算成成功，
  ② P19 的覆盖率表里 `failed` 数不出来（它按 `status >= 400` 判），一格 47% 的覆盖看起来像「采集在漏」，
  实际是「请求在失败」，③ 额度与计费按请求计，失败的正文照样扣一次额度。面板与榜都会往错误的方向被读。
- **建议修法**：**先定产品口径再动手**，这不是纯观测问题——带内 error 是 Legado 书源的传统写法，
  改成返回错误会让下游从「拿到一段错误文本当正文」变成「收到非 0 code 的失败」，是**可见行为变更**，
  要维护者拍板。两条路：① 骨架侧只加观测、不动响应（`ObserveCall` 认出 `ContentType=="error"`，
  在明细上标一个「带内失败」维度，榜/覆盖率/成功率各按自己的口径决定是否把它计入失败）——低风险、
  不动下游；② 各源改成返回真实错误、由 `handleError` 收口成 4xx/5xx——读数是治了，但下游可见。
  先 ① 再 ② 也成立：观测维度先立起来，改状态码时不会瞎。
- **发现处**：2026-10-02 追 xmly 书名/标识覆盖率缺口（P21）时读到 handler 的失败分支，顺手 grep 发现全体同源同形。
- **已处理·①观测落地**（提交号：`7cd6677`，2026-10-02）：按路线①先立观测、不动响应——
  `base/legado.ObserveCall` 认出 `ContentType=="error"` 在明细标 `in_band_error`
  （`api_call_logs` 新列，NOT NULL 默认 false，AutoMigrate 补列；SQL 判据用 `IS TRUE`/`IS NOT TRUE`，
  对 NULL 安全——旧行没有列值仍按纯 HTTP 口径参与统计，PG/MySQL/SQLite 通用）。
  **成功率类读数一律把它计入失败**：会话聚合（`base.RecordCall`）、维度榜（`subjectrank.Query`，SQL 与
  环形缓冲两条路径）、趋势图、保留期归档；覆盖率表的 `failed` 同口径，另出 `in_band_failed` 单列带内的
  那部分——「一格不满」从此能区分是请求在失败还是采集在漏。面板明细行标「带内失败」、覆盖率表加一列。
  用例四条（`test/inband_error_test.go`）：ObserveCall 双路径识别、RecordCall 口径、HTTP 全链路
  （假上游 `contentType:error` → 200 → 明细带标记且会话计失败）、覆盖率两列。
  **仍开放的是②**：各源改返回真错误由 `handleError` 收口——下游可见行为变更，代码在分支侧六个 source 文件，
  等维护者拍板；**计费按请求计的口径本轮未动**（影响③仍在，改它是另一个产品决策）。
- **② 的落地建议（把原来的两条路再切一刀，别按「全部改真错误」做）**：按**失败种类**分开处理，收益与风险差一个量级。
  ②-a **参数缺失那一类前移到路由层判 400，根本不进 handler**。这类是「形态不符」的确定性失败，
  留在 handler 里返回带内 error 只有坏处：下游 Legado 会把那句「缺少参数」**当正文渲染进阅读器**——
  读者看到的是一行错误文本而不是提示。落法建议是一个**新声明位**（如 `SourceMeta.RequiredParams map[action][]string`），
  由底座在 `access/billing` 之后、进 handler 之前统一校验：一处改动覆盖所有源，不动任何源文件的业务分支，
  且因为 `succeeded()` 的判据是 `status == 200`（`gate/billing.go:76`），**这一类的额度问题自己就没了**——
  不需要另开「失败是否扣额度」的产品决策。②-b **上游失败那一类（取直链失败、解析不出、凭证失效）先保留带内 error**：
  改成 5xx 会触发下游换源与重试，把一个已经脆弱的上游再放大一轮，而这类抖动本该由 `base.Fetch` 的
  熔断与过期缓存降级吸收；`in_band_error` 从本版起已能单独数出来，**先拿一周真实数据看占比再定**。
  顺序：②-a 先做（可回退、只碰底座、顺带修额度），②-b 用数据说话；两刀都不要和计费口径改动混进同一次发布。
- **②-a 已落地**（骨架 `skeleton-v47`：声明位 `SourceMeta.RequiredParams` + `middleware/source/reqparams.go`，链上 350）：
  源声明 `map[动作][]必填参数`，底座在**进 handler 之前**校验，缺任何一个回
  `400 {"code":ErrorCode,"msg":"缺少必填参数: xxx"}`。三条位置约束都写在代码注释里且是用例钉住的：
  晚于 `monitor(200)`（挡下的请求必须进明细，且是一条 **400 而不是「200 + 带内失败」**——用例断言
  `RecentCall.Status==400 && !InBandError`，并断言会话聚合的 `Failed` 计入这一次）、
  晚于 `baseurl(300)`（`baseUrl` 是解析出来放 context 的，早于它就永远判缺参）、
  早于 `access(400)/billing(500)`（`gate/billing.go:76` 的 `succeeded()` 判 `status == 200`，
  所以形态错误**天然不再扣额度**，原影响③的这一半随之消失，不需要另开「失败扣不扣」的决策）。
  `Applies` 只看「该 源×动作 有没有声明」，未声明一律直通——**空搜（`search` 不带 key）是合法形态**，
  所以这条校验是逐个源显式采纳的，不是一次全局收紧。声明了未声明的动作在 `RegisterSource` 期 `log.Fatalf`
  （写错动作名等于校验永远不跑，症状是「缺参请求又在返回假正文」，比炸难查得多）。
  **源侧那 9 处 `missing itemId/bookId parameter` 的带内分支现在成了不可达代码，删除动作在携带分支侧做**
  （底座不携带源，见 AGENTS §1）；②-b（上游失败那 21 处）按上面的建议保留，等 `in_band_error` 的一周数据。


## P23 带内 error 正文的文案没有统一脱敏收口：`sanitizeUpstreamMsg` 只挂在 `handleError` 上【①已处理（`73a7736`）；②源侧文案待整】
- **现象/证据**：`app/app.go:335` 的 `sanitizeUpstreamMsg` 是平台唯一的对下游脱敏点，而它只在
  `handleError`（handler 返回非 nil error）里被调用（`app/app.go:328`）。数据面另一条出口——
  响应体里自带错误文案（如正文的 `ContentType=="error"` + `message` 字段，属 Legado 书源传统写法）
  ——**不经过 `handleError`**，文案原样下发。传输层失败时这类文案往往是 `*url.Error`，
  **内嵌完整请求 URL**（含签名参数与上游域名）。底座不携带源，具体命中点由部署侧清点。
- **影响**：`sanitizeUpstreamMsg` 的注释写明了它存在的理由——「签名站会带上 app_key/device_sn/sig 一类参数，
  也暴露自家上游域名」。走带内正文的那条路把这条防护整个绕过，泄露面在**响应里**（客户端可读、
  可能被日志/缓存留存），不在服务端日志里。这不只是文案不友好，是凭证外流。
- **建议修法**（两步，第一步不必等任何决策）：
  ① **骨架侧加一道统一收口**：数据面响应写回前，凡「错误形态」的正文（`ContentType=="error"`
  的 `ContentResponse`，或等价的形状）其 `message` 一律过 `sanitizeUpstreamMsg`。
  判据沿用现成的「串里含 `://` 就整条换成通用提示」。这是对 §10 那条既有约定的**强制执行**，
  不是新增政策；文案会变（下游可见），但变的正是那条本就不该出去的 URL。
  位置建议放在 `app/app.go` 的响应写回处或 `base/legado` 的信封层，别散到各源。
  ② **源侧自有错误文案**：返回真 error 交给 `handleError`，或像某些源那样自己包一层安全文案
  （只说「播放服务暂时不可用」这类，不拼 `err.Error()`）。① 落地后 ② 就不是泄露面，属整洁性问题。
- **发现处**：2026-10-03 盘 P22②-b 的后续计划时，用生产日志给带内失败分类，看到错误正文的形状直接撞在这一点上。
- **①已处理（`73a7736`）**：骨架侧统一收口落在响应写回处（`app.scrubInBandMsg`），
  认规范 DTO 与松散 map 两种形状——**与 `ObserveCall` 认同一组形状**是硬要求，
  否则「标成带内失败」与「文案脱敏」会分叉。四条用例（两种形状收口、不含 URL 的本地文案照旧可见、
  **正文不许被扫**），变异验证两次红。
  偏离原建议之处：位置从「`handleError` 附近」改成「`c.JSON` 之前」——`handleError` 根本不在带内那条路上。
- **②仍在册**：分支侧九处 `err.Error()` 拼进正文的写法（部署侧清点），① 落地后不再是泄露面，属整洁性；
  归分支 S15/S19 的 ②-b 一起看，不为它单独发一轮。

## P35 `MaxDevices` 与 `MaxDead` 互不知情：死号既清不掉又占满建号名额【①已处理；②软删行永不进清理，在册】

- **现象/证据**：`base/pool/state.go` 里 `MaxDevices`（总号数闸门，计数含 `dead`）与 `MaxDead`
  （死号超量才物理清理）是两个各算各的旋钮。**当 `MaxDevices < MaxDead` 时，清理条件永远不成立、
  而死号永远占名额**——生产 uxx 正是这个形状（`UXX_MAX_ACCOUNTS` 未配 → 默认 5，`POOL_MAX_DEAD=10`），
  于是 2026-10-03 出现过「池内 5 行 = hot1+cold2+dead2、0 个建号位」，框架自己一点不动，
  只在日志里留一条 `create cold device failed: 号池已达总号数上限`。
  当时是靠人工**软删**那两行才腾出名额（分支 S27）。
- **影响**：静默失能。池看起来在跑（`hot=1 cold=2` 是能用的），实际一旦再有号判死就补不回来，
  而且没有任何一个读数说「是因为死号占位」——管理员只能靠背 SQL 查。
- **建议修法**（分支 S27 登记的原文）：`MaxDevices>0` 时有效 `MaxDead = min(MaxDead, MaxDevices - 目标可用号数)`，
  或干脆让 dead 不计入 `MaxDevices`。
- **①已处理（`1d882a4`，文档同步在 `3108146`）**：取**第一条**方案（保留上限给可用性让路），并把「不计入」那条否掉——
  `MaxDevices` 的本职是「上游不可逆增长」的闸门，死号在上游确实还存在，不计入等于放开闸门刷号。
  落地形态：
  - 新增 `usableTarget()`（燃烧型 = 1 活跃 + `ColdSpares`；摊薄型 = `TargetDevices`）与 `deadRetention()`
    （`MaxDevices=0` 时原样返回 `MaxDead`，不改老语义）；`purgeDead` 用生效上限；
  - **建号入口在判住之前先清一次腾名额、再重数**——不等到下一轮巡检，因为间隔里源侧一直在拿不到号的错里空转；
  - 快照加 `dead_retention`、面板在两者不等时显示「死号只留 N（配置 M，被总号上限压到）」：
    谁压的、为什么压，得系统自己说（P19 同一条判据）；
  - `ErrCapacityReached` 的文案带上「死号占位几条 / 保留上限多少」，排查方向一眼分得开。
  偏离原建议之处：原建议只改清理阈值，落地时多加了「建号前先腾位」这一步——
  只改阈值的话，`MaxDevices=1、ColdSpares=1` 这类小池要等一轮巡检才回血。
- **顺带掀出一条藏得更久的错**：写「保留 2 条」的用例时断言实得 0 条，真因是
  `purgeDead` 原来用 `.Limit(n).Delete()`——**SQLite 忽略 DELETE 上的 LIMIT**（不报错），
  也就是说这条「限量清理」在开发/测试库上一直是「全删」。改成先 `Pluck id` 再按 id 删。
  判据与为什么过去没被发现（用例只断言「变少了」）写在 `踩坑判据` 对应那条。
- **②仍在册**：`purgeDead` 与名额计数都走 GORM 默认作用域，**软删的行两边都不看**——
  它们既不占名额（这是 S27 用软删能腾位的原因），也永远不会被清理，表会长一堆隐形垃圾。
  要不要给框架加一条「软删行超期物理清理」（像监控明细那样的保留窗口），是个独立决策；
  现状是运维手工清一次少一次，不 urgent。

  看日志的人只会得出「这个池一直在坏」。**不报错的错最贵，重复的错会淹掉 next 一条真错。**
- **已处理**：两半——一半治形状，一半治噪音（只做前一半止不住生产日志，只做后一半留着自相矛盾的配置）。

    （这条也是第一版写的，用例的「Maintain 没建号」把它拦回来）。
  - ② `topUpColdLocked` 对 `ErrCapacityReached` **只在状态变化时出声**（新增 `capNoted`，建号成功即复位），

  - 用例 `TestPoolWatermarkYieldsToCapacity`：夹位五行表（含「名额宽裕不动水位」「不限总号数不参与」）

## P37 用户隐私协议：阅读数据留存的同意位【已处理】

- **需求原文**：搜索词与阅读记录是否同意网关留存，承诺只用于排行榜展示、且只展示书名与搜索词、
  不泄露其他用户信息；个人中心可设，**默认同意**；不同意时接口调用监控不捕获该用户的这两类数据。
- **落地形态**：
  - 存储 `users.content_consent *bool`：NULL = 从未表态 = 同意。默认档写在读的一侧
    （`User.KeepsContentData()`），**不是一次回填数据才能成立**——升级前所有存量用户立刻获得
    「默认同意」的语义，而这条不碰生产库。三处要问「NULL 算什么」（采集闸口、面板下发、用例），
    所以判据收成一个方法而不是三处字面量。
  - 闸口在 `middleware/source/monitor.go`：`RecordCall` 之前调 `CallSubject.WithholdContent()`，
    维度在写进环形缓冲**之前**就被抹掉——此后进程外没有任何一份副本，不是「先落库再遮」。
  - 清的是七个字段：搜索词、书名、章节名、**书目标识、章节标识**、媒介、结果数。
    `InBandError`（成功率观测）**保留**：它说的是请求成没成，不是用户读了什么。
  - 新增 `api_call_logs.content_withheld`：把「用户选择不留」与「采集在漏」分开。
    不分开的话退出用户必然掉进覆盖率「缺失」那一侧，下一个读数字的人会把合规行为当成系统故障来查
    （P19 那条判据的反方向：读数要自己说得清）。
  - 端点 `POST /auth/privacy`，**只认会话**（与 `/auth/me·password·sessions` 同一组）：
    这一位记的是「本人授权网关留不留我的数据」，让长期密钥也能改就变成
    「密钥泄露 → 攻击者替受害者打开留存 → 会话列表里看不见」。
    没有挂进 `/auth/me`：那会让同一份事实有两个写入口（P34/P17 的老形状），
    而 `/auth/me` 又必须带邮箱，改个开关还要顺带重写邮箱。
  - 面板 `Profile.vue` 新增「阅读数据留存」一节：承诺正文 + 开关 + 关闭后的效果说明。
- **偏离原建议之处**（需求只说「不捕获搜索词与阅读记录」，落地时多做了三件事，都是看见后果之后加的）：
  1. **标识一起清**：名称回填循环（`MONITOR_BACKFILL_SEC`，默认 900 秒）按 `(source, 标识)` 反查缓存
     补写 `book_name/chapter_title`，判据正是「名称为空」。只清名称等于**当场说不捕获、下一轮又被自己补回来**。
     这条是写完用例做变异验证才暴露的：用例第一版手工插行（行里本来就没标识），
     把「忘清标识」这个变异测成了绿——真管道断言补上后立刻红。
  2. **加 `content_withheld` 标记**：需求里没有，但没有它就分不开合规与故障。
  3. **默认档读成同意但不写库**：需求说「默认同意」，第一反应是播种时写 `true`；
     那是一次生产库写操作、且新增列在 MySQL 上本来就会给旧行填默认值——两条都不必要。
- **公开榜的承诺核对**：维度白名单只有 `keyword` 与 `book`（`handlers/rank/rank.go:34-42`），
  章节/媒介/身份都不出公开端点；「不泄露其他用户信息」在改动前就成立，
  用例 `TestPrivacyConsentOffWithholdsDimensions` 顺手钉住「退出用户的词不入榜」这条**新**依赖。
- **覆盖率的分母摘掉了退出行**（`subjectrank.Coverage`：`rows_`/`failed` 只数 `content_withheld IS NOT TRUE`
  的行，另出一列 `withheld`，面板覆盖率表加「未捕获」一列）。理由与 P19 同源而方向相反：
  覆盖率回答的是「采集在不在漏」，把用户主动不留的行算进分母，等于用合规选择去扣采集的分——
  下一个人会去修一个不存在的问题。判据用 `IS NOT TRUE`（沿用同一条查询里 `in_band_error IS TRUE` 的写法，
  这一列可能为 NULL，两套判据必然漏算那条坑就写在判据页）。
- **承诺的后半句单独钉了一条用例**（`TestPrivacyPromisePublicRankCarriesNoIdentity`）：公开榜响应里
  不得出现用户名、邮箱、`username`/`ip`/`last_called_at`/`latency` 任何一样，榜条目字段只允许
  `name/total/book_id`，维度只允许 `keyword/book`。白名单在代码里是写死的，
  但**写死不等于守得住**——以后有人往 `boards` 里加一列（哪怕"只是多个字段"），这条会立刻红。
- **告知放在注册那一步**（`Register.vue`）：默认同意意味着「什么都不做就会开始留存」，
  那告知就不能等用户进了个人中心才看到。个人中心仍是唯一的设置入口（一份事实一个写入口）。
- **不在本轮做的**：关闭时**不追溯删除**已落库的历史明细。用户按这个开关的语义是「以后别留」，
  删历史是另一个决策（要不要给「删除我的全部记录」做入口，涉及审计口径与备份，见 `docs/规范/安全与合规.md`）。

## P38 聚合搜索：一条请求打多个源，结果自带来源【已处理】

- **需求原文**：`base/legado/search_base.go` 增加聚合搜索；搜索响应体加 `source` 字段硬性填当前数据源码；
  聚合接口在原有搜索基础上加 `sources` 参数（逗号分隔数据源码）。
  补充：`kind` 字段的**第一项**必须是数据源码。
- **落地形态**：
  - `BookItem.Source`（`json:"source,omitempty"`，与 `BookDetail.Source` 同键）；
    单源与聚合**都在出口统一打标**（`app/app.go`），源自报的值被覆盖——
    这个字段的作用是「回到哪个源取正文」，源写错一个字整条链断在第二步。
  - `PrependSourceToKind`：源码进 `kind` 第一位，保持原形状（字符串还是字符串、数组还是数组），
    已有的同名项挪到最前不重复。两处都给的理由写在函数注释里（有些 Legado 版本只认标准字段）。
  - `GET /{source}/search?sources=a,b` → `app/aggregate_search.go` 扇出：入口源永远排第一、
    去重、上限 8 个源、同时在飞 4 个、每源 20 秒墙钟、单源 panic 只废掉它自己。
  - 下发 `sources_status`：每源一个成因枚举（`ok/ungranted/disabled/need_login/no_plan/limit_exceeded/`
    `missing_params/not_found/handler_missing/unsafe_base_url/upstream_failed/internal_failure`），
    **不带任何上游文案**（出口脱敏的口径同样适用于这里）。
- **治理这条不能省**：handler 内部调别的源**不经过中间件链**，access/billing/ratelimit 对它是盲的。
  所以扇出侧逐个补：
  - **访问判定**走 `gate.SourceAccessVerdict` ——它是从访问控制中间件里**抽出来的同一个函数**，
    不是复制的逻辑。两处各写一遍「谁能用哪个源」迟早漂移，而这里的漂移方向是安全漂移（写松就是绕过套餐）。
  - **额度**走 `gate.AggregateTargetVerdict` + `DeductAggregateTarget`：每个真正打出去的目标各扣一次
    （不扣就是「免费档 200 次/日换 N 个源 = 200×N 次上游」的空头支票）；
    **入口源不重判也不重扣**——链上已经为它做过，再来一次就是同一件事扣两遍（变异验证：去掉守卫 → 入口源被扣 2 次，红）。
  - **baseUrl** 各源各解析一遍（`middleware/source.ResolveBaseURL` 也是从中间件里抽出来的），
    用户给某个源单独配过站点地址时，扇出不能装看不见；用户配置仍过 SSRF 校验。
- **两条已知偏差，写清楚别长成没人知道的第二套口径**：
  1. P25 的「同内容冷却扣减」对扇出目标不生效（内容维度在扣减之后才由 `ObserveCall` 回填，
     扣的那一刻 subject 是空的）。后果是**偏多扣不偏少扣**，与「聚合不得比直连便宜」一致。
     抹平它要改 subject 的生命周期，动到计费主路径，风险大于收益。
  2. 监控明细只记**路由源**那一条（与今天所有请求一样），扇出的其他源不进明细，
     只有 `sources_status` 与服务端日志看得见。要不要给每个目标记一行「谁聚合调了我」，
     是个独立的观测决策（它会改变每请求的写放大）。
  3. **速率限制与自动封禁仍按入口源判定**：`ratelimit(600)` 与 `ipblock.RecordFailure` 都只看见这条路由，
     所以「每源每秒 N 次」的窗口在聚合下变成「每入口源 N 次」——聚合一次可以打 N 个源各一下，
     而每个源的窗口只被入口那一下记到。封禁同理：坏源的连续失败不会累积成该源相关的封禁。
     补齐它要把限流的键与计数从中间件里抽出来给扇出侧复用，而聚合下「一个请求占 N 个窗口」
     本身是不是产品想要的口径，是个需要拍板的问题（不是技术活）——**在册，没做**。
  4. **单目标超时 20s、同时在飞 4 个**：8 个源的最坏墙钟约 40s，比直连的 20s 长。
     下游阅读器自己的超时更短时，它会先放弃——那时用户看到的是「搜索超时」而不是「某个源慢」。
     先记在这里，真实源接进来跑一轮再决定要不要收紧或改成「先到先出」。
- **本轮巡检（§4b 第五经验源）的三样**：
  查了——打标与 `ObserveCall` 的先后（打标必须在观测之后，否则带内错误的判定被形状变化带偏）、
  `sources` 参数是否会漏进源自己的 params（不会：它不在任何源的 `QueryParams` 白名单里）、
  扇出是否绕过了上游缓存与 singleflight（没有，各源仍走自己的 `BaseHandler`）、
  匿名/env 密钥调用方在扇出里是什么身份（匿名 → 免费档逐源判）、`baseUrl` 在扇出里的来路。
  发现了——覆盖率分母会被退出行拖低（已修，见 P37）、承诺后半句没有用例（已补）、
  入口源会被重复扣（已修）、匿名与未知源两条路径没有用例（已补，
  `TestAggregateSearchAnonymousOnlyFreePlan` / `TestAggregateSearchUnknownSourceName`）。
  **没发现什么**——没发现第二个「绕过闸门」的口子（限流与封禁那条是**已登记的在册偏差**，不是漏检）；
  没发现扇出对上游缓存/熔断的重复打击（各源独立走自己的获取栈，按 host 的熔断仍生效）；
  没发现 `sources_status` 会透出去任何上游文案（枚举封闭在常量里，`grep` 过一遍赋值点）。
- **一条设计上的反悔**：第一版让「全部目标都失败」返回 200 + 空列表，理由是下游好读。
  错了——空列表在下游与监控里的读数是「这次没搜到」，而真相是「上游都坏了」，
  成功率/覆盖率/榜三处一起说谎，而且单源聚合（本该等价于直连）与直连的状态码还不一致。
  现在：入口源失败就把它的错误原样抛出去（聚合 ≡ 直连），全失败则报「全部目标源均未返回结果」。

## P40 登录防爆破的状态只能靠「重启进程」来查看和清除：现在可读、可定向解锁【轻方案已处理】

- **现象/证据**：限频器 `ipAttemptLimiter`（`handlers/auth/auth.go`）把窗口计数、失败连击、锁定到期全放在
  进程内存的 map 里，**库里没有任何表承载它，管理面也没有端点读它**。
  所以在它之前，「这个 IP 被锁了吗、锁到几点」只有一个答案办法——重启进程，而重启会连带清掉所有人的锁、
  中断所有在途请求。附带一条同源缺陷：条目只按 IP 建、**没有任何回收路径**，见过的每个 IP 都留一行，
  被爆破时内存直接跟着对方的 IP 池长。
- **影响**：误锁一个 NAT 出口（同一出口 IP 下多个正常用户同时重登录）时管理员没有定向手段；
  「防爆破有没有在工作」在面板上不可见，出事只能靠 journal 里的 401/429 行反推。
- **本轮做的（轻方案：只加「可读」与「可清」，不加留存）**：
  - `handlers/auth/auth.go`：加 `pruneLocked`（越过 `attemptPurgeThreshold=4096` 时顺手扫一次，平时热路径零额外成本；
    快照也扫，所以「面板开着」不再等于内存增长）、`SecurityAttemptSnapshot()`、`ResetAttemptLock(ip)`
    （锁与失败连击一起归零，返回清掉的条数——0 不是错误，那个 IP 本来就没记录）。
  - 两条管理端点：`GET /admin/security/attempts`、`POST /admin/security/attempts/reset`（同一个 `AdminRequired()` 组，只认会话）。
    reset 用 POST 是有副作用的写；**刻意不与 `DELETE /admin/blocked-ips/:id` 同形**——那是删库里的一行，这是清进程内状态。
  - 面板「IP 拉黑」页加一节「登录限频锁定」：锁定项排前面，列通道 / IP / 窗口内尝试与上限 / 失败连击 / 锁到几点 + 解锁按钮；
    空态一句话写明「读数只反映当前进程，不代表最近没人试过」。
- **没做的那一半，以及为什么**：另一条路是新建 `login_attempts` 表把每次尝试落库（可事后统计、可告警）。
  本轮刻意不做——那会把「谁在何时用什么用户名试登录」变成一份新的长期敏感留存（IP + 用户名），
  按 §11 要定保留期、只能经 `/admin/*` 出明细；而**当下的痛点只是「读不到、解不了」**。
  真需要审计链时按那份口径单独立项，不要顺带塞进一个运维按钮。
- **仍在册的两条**（同一片代码，别以为 P40 把它们一起解决了）：
  ① 锁定**只按 IP、不按账号**，所以分布式爆破或「挑一个账号慢速试」都摸不到阈值，账号侧没有独立闸门；
  ② 自动拉黑（`middleware/ipblock/autoblock.go`）只数**数据面路由**的 403/429（`monitor` 的 `Applies` 是 `s.Source != ""`），
  **登录失败根本不喂给它**，两条机制互不知情；`verify_code_scenes` 现网是 `register,forgot_password`（登录没有验证码这道闸）。
- **验收**：`test/login_lockout_test.go` 两条新用例（读快照 + 解锁后同一 IP 立刻能登录；会话独占与 IP 合法性）。

## P41 单日额度手动刷新（管理员「刷新额度」）：动起算点，不动账本也不动限额【已处理】

- **需求**：管理员要能在用户管理里给某个用户把当日额度刷回来。原话是「就放在用户管理的操作中『刷新额度』」，
  落点选了**「额度」弹窗内**（该行操作列的第 6 个按钮会让窄屏放不下，而刷新的效果必须和「已用」显示在同一屏，
  管理员才看得见自己刚做了什么）。
- **实现选择（为什么不是删流水）**：当日额度是 `quota_usage_logs` 上按「零点起」求和的流水聚合。
  三种做法里：删今天那几行=毁掉「今天到底用了多少」的证据（这张表按约定只追加）；
  写一条负数冲正=在总和里掺假账，下一个人读到的合计就不是任何人真实消耗的量；
  **推起算点**=只改「从几点开始算」这一份事实，账本一行不动。所以新列是
  `users.quota_reset_at *time.Time`（NULL=从未刷新；AutoMigrate 加列、不回填、可回滚）。
  过了零点它自己失效，不需要定时任务去抹——这也是选水印而不是选「剩余天数计数器」的原因。
- **一处定义，两处共用**：`gate.UsageSince(user)` = max(零点, 刷新时刻)；`gate.UsedToday` 的参数从
  `userID` 改成 `*models.User`，**少传一个用户就编译不过**——否则早晚有人在新调用里悄悄回到「只认零点」的旧口径。
  判定（`gate/billing.go` 的 429、聚合侧的 `AggregateTargetVerdict`）与读数（`/quota/dashboard`、
  `/admin/users/:id/quota`）走同一个函数，额度详情还额外下发 `quota_reset_at` 与 `usage_since`，面板把「已用自 X 起算」写出来。
- **端点**：`POST /admin/users/:id/refresh-quota`（`AdminRequired()`，只认会话）。用 POST 不用 GET：它有副作用。
  响应带 `used_before`（这次抹掉了多少已用量）——只回「已刷新」等于让管理员不知道自己放开了什么。
  每次刷写在服务端一行 `ADMIN: 刷新单日额度 user=… operator=… 刷前当日已用=…`。
- **刻意留下的口子（要说清）**：可以反复点，一次点击=再给一天的量，所以单日额度对这名用户暂时不构成约束。
  这是「管理员手工放行」本来的语义；如果以后要限「每人每日只能刷一次」，加一句「水印已在今日零点之后就不再改」即可，
  不必现在就上一个没人要的计数器。
- **验收**：`test/quota_refresh_test.go` 三条——刷完能再用一次而**紧接着那次照样 429**（证明没把限额改大）、
  流水行数与合计只增不减、面板「已用」跟着水印走（合计 2 点而起算点后 1 点，两个数同时断言）；
  另两条覆盖「昨天的水印今天失效」与权限（普通用户 403、管理员密钥进不去、未知 id 404）。
  变异验证两次都红：`UsageSince` 忽略水印 → 「刷新后应放行，实得 429」+「已用应归 0，实得 1」；
  `RefreshUserQuota` 不写库 → 「刷新后应放行，实得 429」。
- **用户侧看见了什么**：`/quota/dashboard` 的「已用」与判定共用同一个 `UsageSince`，所以刷新后用户那边也归零；
  但用户侧**没有显示起算点本身**——「已用 0 / 下次重置 明日 0 点」在那一刻并不假（零点后水印确实失效），
  只是藏起了「管理员刚替我刷过一次」这件事。要不要在用户侧写明，是产品决定，本轮没顺手加
  （加了就要动首页卡片与文案，不是这个按钮该带的事）。
- **上线要做的**：AutoMigrate 加 `users.quota_reset_at` 一列（加列、不回填、可回滚）。

## P42 首页平台卡片左上角三个圆点改成三段额度指示灯（红/黄/绿 × 亮 1/2/3 个）【已处理】

- **需求原文**（维护者 2026-10-04）：「首页平台卡片左上角的三个圆点使用红、黄、绿作为背景色，
  分 0~33%、34%~66%、67%~100%，第一档时第一个圆点亮红其余亮默认底色，其他档位也是如此。」
  读法：一档亮 1 个红、二档亮 2 个黄、三档亮 3 个绿，其余仍是默认底色。
- **现状**：三个圆点在 `web/src/pages/Dashboard.vue:60-62`，**三个都是 `bg-border` 的纯装饰**（仿窗口按钮），
  不携带任何读数。同一张卡片已经有两个额度读数：右上角 `%` 标签（`Dashboard.vue:69`）与底部进度条
  （`Dashboard.vue:100`），驱动量都是 `s.usage_pct`。
- **要先定的一件事：圆点亮的到底是哪个百分比**。按给定的颜色方向（低档红、高档绿），驱动量应该是
  **剩余额度百分比**（`remaining / effective_total`）而不是现有的 `usage_pct`——
  同一个数字用同一套颜色，两种读法方向相反：按 `usage_pct` 就成了「用得越少越红」，
  而卡片右上角那个 `%` 标签现在说的是「用到 90% 才红」（`usageTone`，`Dashboard.vue:303-306`）。
  **这不是细节**：一张卡片上两个指示灯方向相反，读的人只会挑一个信。
  所以开工前先拍一句：圆点说的是「还剩多少」。
- **另一处必须一起改的**：现有 `usageTone` 的档界是 **60 / 90**，需求给的是 **33 / 66**。
  两条线并存 = 同一份额度在一张卡片上被切成两套档（tag 说黄、圆点说绿）。
  建议把档界收成**一个函数**（如 `utils.js` 的 `quotaBand(pct)` 返回 `red|yellow|green`），
  圆点与右上角 tag 都吃它的返回值——否则这条需求做完就是 P17/P34 那个老形状（两份事实）。
- **未定/边界**（现有代码里都有对应行为，改的时候要说清显示什么）：
  ① **不限额**（`effective_total = -1`）与 **额度为 0** 时 `usage_pct` 后端算成 0（`handlers/quota/quota.go:200-212`），
  按需求会点亮「一档红」，而红说的是「快没了」——这两类应该走「不亮灯 / 灰灯」而不是红档，
  建议给 band 函数一个 `null` 档，让「没有额度概念」在视觉上是**缺格**而不是最差档；
  ② 管理员视角这张卡片显示的是全站消耗（没有个人 remaining），圆点按什么口径要一并定；
  ③ `remaining` 在后端已做下限 0，超扣不会出负数，所以不会算出 >100% 或 <0 的百分比。
- **验收判据**（写用例时的口径）：给定 `pct`，卡片上点亮的圆点数与颜色必须**由同一个函数决定**——
  断言「tag 的颜色 == 圆点的颜色」比断言两个各自的阈值更防漂移；
  前端没有单测框架，这条靠 `make vet` 的未定义类扫描 + 真机读数（本环境无浏览器，需截图或真机验收，同 P33 的处境）。
- **发现处**：维护者提需求；`usage_pct` 方向冲突与 60/90 档界冲突是读 `Dashboard.vue` 时当场发现的，不是实现时才发现。

- **拍板的两件事**（维护者答复）：① 圆点说的是**剩余额度**（不是现有的 `usage_pct`）；
  ② 档界按需求给的 33/66 收成**一处判据**，`usageTone`（旧的 60/90）删除——所以右上角百分比标签的
  颜色也跟着改了：那里显示的仍是「已用 X%」的文字，但颜色与灯同源。一张卡片上从此只有一条线。
- **实现落点**：`web/src/utils.js` 新增 `quotaBand(remaining)` / `remainingPct(item)` / `quotaLitCount(band)` /
  `QUOTA_DOT_CLASS`；`Dashboard.vue` 三颗装饰点改成 `v-for` 的指示灯，标签改成 `quotaTag(s)`。
  剩余百分比直接从 `remaining / effective_total` 算，不用 `100 - usage_pct`（两头各取一次整会读出
  「已用 0%、剩余 0%」这种自相矛盾的数）。灯色写成**静态类名表**而不是拼字符串——
  Tailwind 只认源码里出现过的字面量，拼出来的类名不报错也不产 CSS（P31 那一族）。
- **没有额度概念 = 满格绿**（维护者拍的：「不限额和管理员视角显示三颗绿灯」）：
  `effective_total < 0`（不限额）与管理员视角（后端给 -1，全站消耗本来就没有个人剩余额度）都落到绿档、三颗全亮。
  我原本选的是「缺格」（一颗都不亮），那条不成立——三颗不亮的灯读起来像「这里没有数据」，
  而真相是「这个源不受额度约束」，那是最充裕的一档。「不限」这件事交给标签的文字说（显示「不限」而不是「0%」：
  0% 说的是「一点都没用」），**不用灯去表达一个灯表达不了的状态**。
  `effective_total = 0` 仍是红档：那是有额度概念、且一点都没有。
- **验收**：纯函数用 node 跑了 10 组边界（100/67/66/34/33/0/额度0/-1/null/无 item）+ 上下越界钳位，
  全对（改成满格绿后重跑：`-1`/`null`/无 item 三例从「不亮」变「三颗绿」，其余不变）；
  `make build`（含未定义类扫描与 race 套件）为门禁。**真机读数仍缺**——本环境没有浏览器，
  灯的观感（`bg-pale-*-fg` 三个饱和度在 `bg-surface-alt` 上够不够显眼）要看一眼才知道，
  同 P33 的处境。用例侧「tag 颜色 == 圆点颜色」这条判据靠两者共用 `quotaBandOf(s)` 保证，
  不是靠各自断言阈值。

## P43 套餐名/角色名的**用户维度显示别名**：默认名不动，读侧覆盖【已处理】

- **管理员视图的判据**：**读数不能被被观察者修饰**——列表/详情同时下发 `plan_name`（默认）与

- **验收**：`test/display_alias_test.go` 四条——本人 `display_name` 是别名而 `name` 仍是默认名、

  （空串在本端点语义是「清除」，所以「太长」必须与「清空」分开——第一版就是栽在这里）；

  固化 = `test/admin_user_search_test.go`（sqlite 侧）+ `make vet` 的 SQL 扫描第 4 条（源码里出现
  `ESCAPE` + 反斜杠即构建失败）。**残留风险写在这**：本仓没有 MySQL 侧自动化用例，
  跨方言这条目前只能靠扫描器兜，不算走完阶梯。

## P44 多设备登录监控与自动处置（防 VIP 借号 / 滥发密钥）【已处理：默认关，读数先上线】

- **需求原文**：「添加用户多设备登录监控，防止 vip 用户借号或者生成大量 apikey 给其他人使用。」
- **拍板四条**：① 做到 **监控 + 自动处置 + 通知**；② 处置范围 = **自动吊销多余会话，密钥只监控不冻结**；
  ③ 通知走 **登录时提示**（复用现有响应，不建站内信表）；④ 阈值做成**系统设置项**，默认
  `max_active_sessions=5`、`device_watch_window_days=7`、`suspect_distinct_ips=8`、
  `device_watch_enabled=false`（和 `auto_block_enabled` 一样默认关——一上线就踢人会误伤）。
- **零 DDL 的取舍**（本轮定的是「不动明细表」）：`auth_sessions` 本来就有
  `device`(UA 解析)/`ip`/`last_active_at`/`expires_at`/`revoked_at`，账号维度算得出；
  `api_call_logs` 有 `username`+`ip`，而**用户密钥调用是归属到用户名下的**
  （`utils/auth.go:134-138` 的 `Set("username", …)`；本轮修掉了 `models/api_call_log.go` 与
  `base/metrics.go:82` 两处「API Key 为空」的过期注释——按旧注释读会以为密钥调用是匿名的，
  那就会误判「多 IP 算不出来」）。
  **代价要说清**：`api_keys` 只有 `last_used_at`（5 分钟节流），没有来源 IP/设备，
  所以「具体哪把 key 被别人在用」答不了，只能答「这个账号近期从几个不同 IP 调用、有几把 key」。
  这也是为什么密钥侧不自动处置——定位不到就冻，只能整账号冻。
- **判据（最重要的一条）**：**只按会话数处置，绝不按 IP 数处置**。IP 数超阈值只标红，不吊销——
  校园网/公司 NAT/家庭共享下一个出口 IP 后面是多个真实用户，按 IP 踢人必然大面积误伤。
  自动吊销的动作是「会话数 > `max_active_sessions` → 按 `last_active_at` 升序吊销多余的」，保留最近的。
- **要认清它的边界**：吊销会话只是**提高借号成本**，不是阻断——借号者会重新登录（重新登录不受影响，
  因为本轮没选「拦新登录」）。真正挡住需要限制登录本身，那是一条产品决策（误伤面大），
  等这轮的读数攒出来再谈。
- **通知的实现**：不建新表。登录时查「`revoked_at` 落在该用户上次登录时间之后的会话数」，
  在 `/auth/login` 的响应里带一句「近期有 N 台设备被移出登录」（同时更新 `last_login_at` 前取值，顺序别写反）。
- **留痕**：服务端 journal 一行（`SECURITY: 自动移出会话 user=… 保留=… 移出=…`）+ 会话行本身的 `revoked_at`
  （同一秒批量出现就是「自动处置」的形状，与用户自己点「登出其他设备」的 `revoked_at` 同形，
  所以**日志里必须写清是哪一种**，否则事后分不清谁干的）。
- **管理面落点**：一个跨用户的「设备与密钥」列表（活跃会话数 / distinct device / 窗口内 distinct IP /
  密钥数量 / 疑似标记 / 近期被移出数）。**若新开一页必须同时进导航**，否则 `make vet` 的 `nav-check` 直接红
  （v58 那条固化）；也可以并进 `/admin/users` 加列，但列已经很多，P30 的窄屏裁剪要一并考虑。
- **隐私边界**（§11）：设备/IP/UA 明细只经 `/admin/*` 出，不进公开端点、不进访问日志之外的地方。
- **实现落点**：设置项四条在 `db/seed.go`（`device_watch_enabled=false`、`max_active_sessions=5`、
  `device_watch_window_days=7`、`suspect_distinct_ips=8`）；处置函数 `db.RevokeExcessSessions` +
  `handlers/auth/device_watch.go`（挂在 `issueToken` 里——注册/登录/找回密码三条路都过这个函数，
  写两处就会长出两套口径）；读数 `GET /admin/devices` + 面板「设备与密钥」页（新页同时进
  `main.js`、`App.vue` 的 iconMap 与侧栏、`Admin.vue` 的卡片，否则 `nav-check` 红）。
  口径随读数一起下发（`config` 字段）：「8 个 IP 算不算异常」取决于当时的阈值与开关。
- **验收**：`test/device_watch_test.go` 五条——默认档实测（开关关着时 6 个会话一个都不许被移出，
  这不是形式：「配置默认关」如果没人读它到底做了什么，它就只是个字符串）、
  登录后收敛到上限且被踢的是**最久未活跃**那个、被移出的 token 调 `/auth/me` 必须 401、
  **反向断言**「IP 再多也不许动会话」（上限调宽到 10、造 12 个来源 IP，一个都不许掉）、
  移出提示走登录响应（`notice`，不建站内信表）。
  变异验证三次：`deviceWatchEnabled` 恒真 → 默认档红；处置不看上限清空其它会话 → IP 用例红；
  notice 取覆盖之后的时间 → 提示用例红。
- **过程中修掉的两个自身错误**（都记进本页了）：
  ① 第一版 notice 用例把「移出」安排在**本次登录的自动收口**里，于是无论取值顺序对不对都能算到——假绿；
     改成「先登录、再点登出其他设备、第三次登录才读」才真正钉住顺序，随后暴露出
     `prev := user.LastLoginAt` **拷的是指针**、同一对象被随后的 Update 就地改掉（判据见本页）。
  ② 第一次做那个变异时是以**编译失败**（变量未使用）的形式红的，那不算验过，重做了一遍。
- **仍然在册的剩余项**：① 密钥侧「哪把 key 在被别人用」答不了（`api_keys` 无来源 IP），
  要答就得给明细加列或给 key 补使用留痕——本轮明确不做；② 「拦新登录」是更强的阻断，本轮不选；
  ③ 库里 `revoked_at` 分不出「系统踢的」与「用户自己登出其他设备」，只有 journal 那行能分清，
  真要审计得单独记（本轮接受这个限制并在文案里不假装能区分）。

## P45 「设备与密钥」页加按次数排序（字段由实现方定）【未处理】

- **需求原文**（维护者 2026-10-04）：「设备与密钥管理添加按次数排序，至于用哪些字段你看着来。」
- **现状**：`ListDeviceActivity`（`handlers/admin/devices.go`）固定 `Order("id DESC")` 取一页用户，
  然后把这一页的 id/username 交给三个聚合函数。**排序必须先有全量聚合**——
  现在每页只聚合当页那 20 人，按次数排就变成「在这一页内部排序」，跨页不可比。
  所以这条的真实工作量不在 SQL 的 `ORDER BY`，而在把「按页聚合」改成「全量聚合 + 内存排序 + 再分页」。
- **排序字段（我定）**：`sessions`（活跃会话数）/ `devices` / `login_ips` / `call_ips` / `keys` /
  `revoked`（窗口内被移出数）/ `last_login`。**默认 `sessions` 降序**——这页存在的目的就是"谁最不像一个人在用"。
- **为什么可以全量聚合**（2026-10-04 生产实测）：`auth_sessions` 3226 行、`api_keys` 268、
  `api_call_logs` 28413、`users` 1052。三份 group-by 都是毫秒级；**但窗口外的 `api_call_logs` 会一直长**，
  所以 `call_ips` 的聚合必须带窗口过滤（已有 `WatchWindowStart()`），
  实现后要用 `EXPLAIN` 或直接计时确认它没变成秒级——**如果它慢了，就把 `call_ips` 从排序键里摘掉**，
  并在页面脚注写明"哪几列能排"，而不是让读者以为任何列都能排（这是读数页自己的口径，别留给猜）。
- **注入面（这条最要紧）**：排序键与方向来自 query，**绝不能拼进 `ORDER BY`**。
  必须是白名单映射（`sort → 内存比较函数` 或 `sort → 固定 SQL 片段常量`），
  非白名单值回落到默认而不是回 400：面板因为参数拼错打不开，比静默用默认更糟。
  现在 keyword 那条路径刚因 ESCAPE 炸过一次（P43 附带），同一个函数里再加一个字符串拼接位就是再加一次。
- **分页稳定性**：并列值（大量账号都是 1 个会话）必须带二级 tie-break（`user_id DESC`），
  否则翻页会出现同一条在两页都出现、另一条永不出现——**排序不做稳定性检查，比不排序更容易骗人**。
- **面板**：表头点击三态（默认 → 降序 → 升序），复用 `table-base`；
  窄屏次要列被裁（P30 的形状）意味着**被裁掉的列没法点**——要么给窄屏一个排序下拉，
  要么明写"窄屏只能按已显示列排"。这条得选一个，别留成"窄屏无法排序"的意外。
- **可选伴侣（不做也成立）**：`suspect_only` 只看标红的账号——排序解决了"先看谁"，
  筛选解决"根本不想看其余"。默认不做，等有人抱怨翻页烦再加。
- **验收**：① 非白名单 `sort`/`dir` 值不进 SQL（用例断参数被忽略且回 200 + 默认序）；
  ② 两个并列计数的账号在翻页第 1/2 页不重复不丢失；
  ③ 排序正确性用注入的已知分布断（造 A=5 会话、B=2、C=9 → 顺序 C,A,B），不靠肉眼；
  ④ `call_ips` 聚合耗时实测一次并记进本条目，慢了就摘掉排序键。
- **发现处**：维护者提需求；"按页聚合不能跨页排序"与注入面是实现时先撞出来的，所以写在登记里而不是事后。

## P46 用户管理加筛选（现在只有一个关键词框）【未处理】

- **需求原文**（维护者 2026-10-04）：「用户管理界面添加筛选功能，当前的搜索太单一。」
- **现状**：`ListUsers`（`handlers/admin/admin.go:143`）只有两个入口——关键词（用户名/邮箱/昵称 LIKE）
  与 `with_deleted` 复选框；排序固定 `id DESC`。1054 个账号只能靠翻页和搜索，运营想问
  「谁的套餐快到期」「谁从没登录过」「谁被手工放过额度」都问不出来。
- **筛选项（我定，都有对应列且现网有数据）**：
  1. **套餐**（`plan_id`）。另留一个"绑定的套餐已不可见"的态：`quota_plans` 带 `deleted_at`，套餐软删后   用户的 `plan_id` 仍指着它——**现网实测 0 例**，所以这不是"今天有的数据"，而是"下拉里不能只有活的套餐",   否则将来软删一个套餐时这批用户会在筛选里凭空消失（`JOIN` 掉而不是显示成"无套餐"）；
  2. **角色**（`user_roles` join，单角色模型所以等值即可）；
  3. **账号状态**三态：正常 / 已禁用 / **已删除**——把现在的 `with_deleted` 复选框收进来。
     复选框的问题是它把"正常 + 已删除"混成一锅，而想单独看已删除的偏偏办不到；
  4. **到期**：永久 / 有效中 / **N 天内到期**（默认 7）/ 已过期——`plan_expire_at` 的 NULL 与未来/过去三态，
     这是运营最常问的一条（"下周该找谁续费"）；
  5. **活跃度**：从未登录 / 最近 7·30·90 天登录过 / 90 天以上未登录（现网**从未登录 32 个**，
     注册不用是真实存在的形态，不是脏数据）；
  6. **留存同意位**：未表态(NULL) / 已同意 / 已关闭（现网**关闭 16 个**）——
     P37 之后监控读数的覆盖率会因此变化，得能一眼看到是谁、多少人；
  7. **被手工刷过额度**（`quota_reset_at` 非空，含"最近 N 天内刷过"）——P41 留的口子，
     不做这个筛选，"单日额度形同虚设"这件事就只有 journal 里查得到；
  8. **持有密钥数**：无 / ≥1 / ≥5（每人上限 10 个，`/admin/devices` 已能看单人，缺的是"谁一堆 key"）；
  9. **活跃会话数 > 上限**（疑似共享，与 P44 同一口径）——把 P44 的标红变成一个能点开的集合。
- **实现约束（三条，都是这轮刚付过学费的）**：
  ① 参数一律**白名单 + 占位符**，绝不拼 SQL 片段——同一个函数里那句 LIKE 今天刚因 `ESCAPE` 在生产炸过；
  ② 非法值回默认而不是 400：列表页因为一个拼错的 query 打不开，比静默用默认更糟；
  ③ 时间类判断的边界（`NULL` 算什么、`<=` 还是 `<`）必须写进用例而不只写进代码——
     "即将到期"与 P19 那类「NULL 一片」的读数坑同族。
- **聚合类筛选项（8、9）怎么做**：用 `EXISTS` 子查询，别拉全量进内存。
  规模依据是 2026-10-04 生产实测（`auth_sessions` 3226、`api_keys` 268、`users` 1052），
  这个量级 `EXISTS` 毫秒级；**与 P45 的关系要摆正**：P45 是"全量聚合后排序"，这里是"按聚合结果筛行"，
  两处的聚合口径必须共用一个定义，否则会出现"页面上按会话数排序的结果和筛出来的不是同一批人"。
- **交互与窄屏**：筛选控件复用监控页的形状（`select.input.input-sm`；候选可能因硬删而缺时用 `datalist`，
  理由见 `Monitor.vue:135` 那段注释）。筛选状态**写进 URL query**，这样"发给同事一条链接"能复现同一个视图；
  窄屏按 P30 的裁剪纪律：筛选条默认折叠成一行摘要（"3 个条件：套餐=vip、到期≤7天、状态=正常"），
  否则 9 个下拉会把手机屏全占掉——**筛选做完整却看不见，等于没做**。
- **不要做的**（先记下来免得顺手加）：保存筛选方案、导出 CSV、跨页选择批量操作。
  现网 1052 个账号，没有"同一组条件每天看"的证据之前，方案管理器就是白送一套要维护的 UI 与一份新留存。
- **默认行为不变**：不带任何参数时的视图与今天完全一致（`id DESC`、不含已删除），
  上线这一条不该改变任何人现在看到的页面。
- **验收**：每个筛选项至少一条用例（含 NULL 边界与非法值回默认）；
  ③④⑥⑦ 这几项用现网真实存在的形态造数据（从未登录、关闭留存、刷过额度），
  不要用理想数据测——`status` 现网**全是 1**，"已禁用"筛不出东西是**正确结果**，
  用例不能因为它返回空就断言失败。
- **发现处**：维护者提需求；`with_deleted` 那个复选框的语义问题、以及"筛出来和排出来不是同一批人"的
  聚合口径风险，是读 `ListUsers` 与 P44/P45 现状时发现的。
