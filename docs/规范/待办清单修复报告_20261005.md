### 6.2 这批未提交改动暴露的五处静默（都是"上一轮没收口"的形状）

1. **HEAD 连续两个提交编译不过**。`3672d22` 的 numstat 里带着 `handlers/admin/admin.go +18/-2`
   ——那是 P62 的**读侧半边**（引用 `db.SensitiveSettingKeys`），而定义它的 `db/setting.go` 留在工作区。
   `git grep -c SensitiveSettingKeys HEAD -- '*.go'` 只剩引用侧四命中，定义零命中。
   这是判据页「按目录名 `git add` 会漏掉目录外的文件」那条的**第二次**，而且比第一次严重：
   上次是"文档没提交全"，这次是**基线本身不可编译**——任何人在那个提交上 `make build` 都会红。
   根因不是漏 add，是**那两次提交根本没跑门禁**：同一批里 `db/seed.go` 那段 `for` 顶格没缩进，
   `gofmt -l` 一直指着它，而 fmt-check 是 `make vet` 的第二条。
   **判据**：分片提交时"引用新符号的那一半"必须与定义同一次提交；每次提交前 `make build`，
   不是"改完再说"的收尾动作。
2. **废弃键与播种名单交叠**：`site_name` 进了 `gone` 硬删名单却还躺在 `settings` 里，
   而清理跑在播种**之前** → 每次启动先删再种回来，键永远摘不掉。这是 P34②
   「DROP 完下次启动空表原样复活」的同一形状，**所以它上门禁**（6.1 第一条的③）。
3. **`nil` 保护之外多读了一个字段**：`RecordCall` 原来把所有 subject 字段读在
   `if subject != nil { … }` 里，这次新加的 `InBandReason` 写进了结构体字面量——
   于是每个被 access/billing/维护门拦下的请求 panic 一次。**"加了一行保护"不等于"新读法在保护之内"**。
4. **panic 把尾解锁一起跳过 = 锁被永久持有**（P93）。gin 的 recovery 在最外层兜住，
   所以没有崩溃日志、进程照旧 `is-active`、`Restart=always` 也帮不上——症状是下一个请求卡死。
   这一条与 P77/P78 是同族，但**P78 那句「临界区一律 defer 解锁」目前只是约定**：
   当场数出全仓还有 **19 个函数（21 处 `Lock()`）分布在 15 个文件**是尾解锁——其中两个文件
   （`base/pool/state.go`、`base/pool/status.go`）正是 P78 那一轮"已收口"的对象。
5. **P90② 的清单点名点漏一处**：原文写「`GET/PUT /auth/me`」（一条路由记成两条）而整个漏了
   `POST /auth/password`。改到第五处时没人发现少改了一处，**是按路由表逐个发非法体的用例发现的**。
   判据：**对外面清单是给人读的，用例是当场发的**——要证明"六处都改了"，得有一条把六条路由走一遍的用例。

## 9. P93② 的执行：门禁上仓（全仓、无豁免），首跑 33 处一次改完
**提交：`174742a`**（P64 那半句文案的收也在同一颗里）。文档同步在它之后。


上一节把这条列为"下一轮的候选扫描"。用户拍的是"按推荐方案执行"，所以本轮就上，且范围从我原来建议的
`base/`+`gate/` **放大到全仓**——`middleware/ipblock` 与 `db/blocked_ip` 也在每一个请求的路上，
留一半"已知会毒化"没道理；而**范围一刀切下去，就不需要判断"这段会不会 panic"**（那正是需要人来判、
也因此最容易做成噪音的那一步）。

**门禁**：`scripts/check-lock-defer-unlock.sh` → `make vet` 第 15 道。一条规则：
函数里每把锁（`Lock`/`RLock`）**不许有裸解锁行**，且加锁次数 == `defer` 解锁次数。
两次变异各拦一种形状：还原成尾解锁 → 红；删掉一个 `defer` → 红并报「加锁 1/0 次与 defer 解锁 0/0 次配不齐」。

**首跑 33 处，我手工只数到 19 个函数**——差的是扫描器口径更宽抓到的三样：任意缩进深度（循环体与
goroutine 字面量里的也算）、连 `RLock` 一起算、按"函数 × 锁"配对。手工漏的那些恰好都是这三类
（`resolveIPs` 读写两段夹 `return`、`dnsCacheCleanup` 的循环体、两个 limiter 工厂的 double-check 读段、
`IsIPBlocked` 夹 `return` 那一支、`proxyAllowedForPath`、`validateProxies` 的 goroutine 局部锁）。
**这就是"上门禁而不是靠人列清单"的当场证据**，也是判据页那条被整行删除的理由（固化成门禁 = 退出机制兑现）。

**改法按形状分两种**，一律原地加 defer 是错的：
- 临界区在函数尾部且后面没事 → 直接 `defer`；
- **多段临界区 / 循环体里** → 每段包一个闭包 `func(){ mu.Lock(); defer mu.Unlock(); … }()`。
  反例写进脚本头部：循环体里就地 defer 要等协程退出才解锁，**第二次 tick 就抢不到锁**；
  `replenishProxies` 那种"读一段 → 网络复验 → 写一段"的，就地 defer 等于持锁跑网络请求
  （正是 P81 反着干）。

**顺手挖出一处真实竞争**：`base/pool/status.go` 的 `Status()` 在 `p.mu.Unlock()` **之后**读
`len(p.cooldown)`——无同步读，与维护协程并发撞上就是 race。收进 `p.locked(…)` 一起解决。
P78 那一轮说"临界区一律 defer 解锁"时没把同一个文件看完，尾解锁留下的洞就是这么把一次字段读丢在锁外面的。

**补的用例与两次变异验证的教训**：`test/singleflight_test.go`（我改了它的锁结构，而原有覆盖是从 handler
层打进来、经过别的锁，挡不住这里改坏）。
- 第一条变异（删掉 `defer f.finish`）**用例照绿**——单飞自带 2 秒兜底超时把这次救回去了。
  换成真正的病类变异（**锁不释放**）才红。**教训：变异要模拟的是那类病，不是那行代码**。
- 而它第一次红的方式是整测试二进制 `panic: test timed out`（180 秒），堆栈指向用例自己。
  于是每一次 `f.Do` 都套上截止时间（`doWithin`），现在 10.02 秒红在这一行：
  `Do("k-panic") 在 10s 内没返回——单飞锁被上一次 panic 带走了`。
  **判据：断言死锁的用例必须自带截止时间，否则它不是断言，是超时计数器。**

### 9.1 执行中我自己撞回去的两次（都由既有用例抓住）

1. **把"查-占"拆成两次加锁 → 请求合并没了**。`Flight.Do` 原来是同一段持锁里 `if c, ok := calls[key]; ok` 再
   `calls[key] = 新建`；我"每段包一个闭包"时把它拆成读一次、写一次，两个 goroutine 于是可以同时读到空、
