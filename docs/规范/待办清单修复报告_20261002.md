## 2. 每项的关键取舍（只记不显然的部分）

- **P1**：`ORDER BY key` 无论加不加引号都做不到跨方言（不加 MySQL 1064，加反引号 PG 语法错），
  所以 `ListSettings` 改成取回后在内存里排，而不是寻找「第三种引号」。守卫有两份：全库扫描（行尾
  `dialect-allow` 是显式豁免通道，已给断言 GORM 生成 SQL 的用例标注）+ postgres 方言 DryRun 直接证据。
- **P2**：丢弃分成两个计数——队列满丢的 `dropped` 与投进队列但 Redis 没写进去的 `failed`，
  混在一起就分不清是「产能不够」还是「Redis 有病」。单批 `Exec` 加 3s 超时是这轮真正的止血：
  原先沿用长生命周期 ctx，Redis 一卡就把写协程钉死，队列才会一路涨到丢。
  纯内存时 `name_cache.persist` **缺席**而不是报 0——「没接」和「接了没丢」是两件事。
- **P3**：媒介白名单用 `base.MediaValues/IsMediaValue`，**不用 `base.IsValidMedia`**——后者认空串
  （源未声明媒介是合法状态），拿它校验入参会把「空媒介」放行成合法筛选。非法值返回 400 而不是空榜，
  因为空榜会被读成「真没人读这个形态」。管理端 `/admin/monitor/subjects` 收同一个参数，两处共用引擎不分叉。
- **P4**：`MaxDevices` 不参与 `withDefaults` 的零值回填（0=不限，填默认值等于把不限制的池锁死）。
  闸门判在 `createColdLocked` 入口，一次覆盖 Acquire / Reauthorize / 冷备补齐三条建号路径。
  计数含 spent/dead，与源侧原来自实现的口径一致，`purgeDead` 腾出的名额重新可用。
  顺带修了 `Acquire` 的错误形态：原先只报「无可用号」，把「补号被上限拦了」吞掉了，现在双 `%w` 一起带出。
- **P6**：`Kind` 是**声明位不是策略开关**——框架不据它分叉任何行为，只透传进快照。只声明现有形态一个常量
  （`KindBurnWallClock`），spread 之类等 P5 真落地时由实现方自带，不预置没有实现的枚举。
- **P8**：两个可选方案里选了「改文档」而不是「把 `/datasources` 加进默认白名单」——后者是产品决策
  （决定书源客户端能否匿名拉清单），本轮没有替维护者改默认行为的授权。
- **P9**：建议里给了两支（串行构建 / 随机端口），选随机端口——串行只是把问题藏起来，而两个仓库各自
  `make build` 是日常动作。附带更正了原现象描述：**不是**「监听固定端口 8081」，harness 早就在抢随机端口，
  真问题是 bind-then-close 的 TOCTOU 窗口。
- **P16**：`/data` 承载书源 JSON 的托管下发，这条通道的正确性质是「改完文件立刻可见」，
  补一个带 TTL 的 Get 反而会制造事故面，所以按「承认不缓存」这一支收，并把启动时的 `prefillDataFiles` 一并删掉。

## 3. P7 复核结论（本轮未取得读数 → 维护者已核实，本条通过）

**能确认的部分**：三个键由 `sources/uxx/adcooltune.go:27-29` 定义，落在 `system_settings`，
语义是 `cooldown`=当前冷却估计 / `lo`=已知等到这里还领不到的最大值 / `hi`=已知等到这里领得到的最小值；
标定规则是「成功减 7 分钟 / 失败加 1 分钟 / 上下界收到 1 分钟内钉住」（`docs/数据源/号池方案-uxx会员cookie池.md` §）。
本地 MySQL 的演练库 `loomproxy_upg` 里 `pool_devices` 有 uxx 池的真实换号痕迹
（dead 3 个：2026-10-01 22:58→23:16；hot 1 个：00:29；cold 1 个：00:39，约 20 分钟内换了一次号），
但那张表里没有 `uxx_ad_*` 三行——**本地演练没跑到广告兑换环节**，所以这三个键一次都没被写过。

**不能确认的部分**：生产库里的实际值。本轮硬约束是禁止触碰服务器，我没有取这个读数，
因此**「是否已收敛到贴合真实间隔」这一问题仍未回答**——它是运维读数问题，不是代码缺陷。

**给维护者的复核指令**（在生产库里执行，一条 SQL + 一处面板）：

```sql
SELECT `key`, `value`, updated_at FROM system_settings
 WHERE `key` IN ('uxx_ad_cooldown_sec','uxx_ad_cool_lo_sec','uxx_ad_cool_hi_sec');
-- 判据：hi-lo 收到 ≤60s 即认为已钉住收敛；cooldown 落在 (lo, hi] 内且不再频繁跳动即为贴合
SELECT status, COUNT(*) n, MIN(created_at), MAX(created_at)
  FROM pool_devices WHERE pool='uxx' GROUP BY status;  -- 换号频率看 hot/spent/dead 的时间跨度
```
面板侧对照「号池」页 uxx 池的号数与状态时间线；若 `cooldown` 长期贴着 `hi`，说明真实间隔比标定值长，
把兑换节奏调慢（不是改代码，是等它自己收敛——自适应只在领不到时加宽）。

## 8. 风险提示

1. **P1 未在任何真实 PostgreSQL 部署上验证过**。这条改的是「所有系统设置都读成空」这类**静默失效**，
   最强证据只是 GORM postgres 方言的 DryRun SQL 形态。上 PG 部署时请先验一条：面板改一个设置 → 立刻读得到。
2. **P9 改的是启动路径**（`app.Run` 从 `ListenAndServe` 改为显式 `net.Listen` + `Serve`）。优雅停机路径没动
   （`Shutdown` 后 `Serve` 仍返回 `ErrServerClosed`），但这是**产品监听行为**的改动，
   上线首轮要看一眼启动日志里那行 `LoomProxy starting on <host:port>` 是否正常。
3. **P2 的队列扩到 32768**：极端情况下（Redis 长时间不可达）写侧内存上界随之变大，
   量级是「条目数 × (键 + 名称) ≈ 数 MB」，不是无界；`failed`/`dropped` 现在能在面板看到，
   真出问题时先看这两个数再决定是加批还是查 Redis。
4. **P4 的 `MaxDevices` 含 spent/dead 计数**：死号会占位，池可能因死号攒满而不再建号（与收编前口径一致，
   不是新风险，但换成了框架实现后更容易被忽略）。清理靠 `MaxDead`/`purgeDead` 腾名额；
   若要改成「只数非 dead」属于框架口径变更，本轮没做。
5. **P3 改了共享引擎的函数签名**（`subjectrank.Query` 多一个参数），两个调用点都已改；
   将来新增调用点若漏传 `mediaFilter` 会编译失败而不是静默放行，这是有意的。
6. **pytest 一条链路未跑**（本机无该模块）：P9 的正确性目前由「三个并发实例各得不同端口 +
   日志解析正则对真实输出验过」支撑，不等于跨进程用例全绿。
