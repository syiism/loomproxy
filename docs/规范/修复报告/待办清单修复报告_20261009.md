## 3. 归因那一跳：三处"看着像同族"，其实是两种成因

**这是本轮最值钱的一格，而且是维护者一句「现在重新看这个问题，还能修得动吗」逼出来的。**

初稿（`c15b0fa` 前后）把 `:167`、`:508`、`:209` 并写成"同一形状各复现一次"。复测把三条 `EXPLAIN` 摆在一起才看见：

- `:167`（带 `source = 'fq_novel'` 这个**等值列**）→ 优化器放弃几乎没有选择性的 `created_at` 范围扫描，
  拿单列 `idx_source`，**时间窗退化成回表过滤**，扫描量绑的是"该源的历史长度"。这一格 ② 的复合索引能救。
- `:508` 与 `:209` 的 `WHERE` 里**根本没有等值列**，走 `idx_created_at` 扫 79k 行——**扫描量等于窗口本身**，
  实测 560~606ms 与 552~787ms，**比 `:167` 的 250ms 更贵**。复合索引救不到它们，
  它们贵在"窗口≈全表（89%）"，要动的是保留期或预聚合。

**所以答案分两半**：榜单本身修得动（①②③，最慢那格 1.97s → ~0.25s 是实的），
但**告警的大头（82 次里那 54 次）不在这一族**。判据页那条因此补了一段"同族的另两处不是同一个成因，别并成一条"，
并把《来路》写成"归因在本条上改过一次"——**没有回链的改判，下一轮就会照初稿再走一遍**。

顺带一次同族纠正：`datasource:*` 为 0 我先写成"那层缓存坏了"，复采到 1 格且同刻 `quota:cost` 有 31 格在写，
才定回"请求稀疏 + TTL 自然到期"。**采样时刻不是一个机制的证明，两次才行。**

## 4. ① 落地：改法、两处代价、三次变异

改法：聚合带 `MAX(id) AS last_id`（书名维度再加 `MAX(CASE WHEN book_ident <> '' THEN id ELSE 0 END) AS ident_id`），
跨源合并取极值；两栏的值由**一次** `SELECT id, created_at, book_ident WHERE id IN ?` 主键点查取回。
`MAX(id)` 与原 `ORDER BY id DESC LIMIT 1` 命中同一条（id 自增），并且顺手对上了"同一毫秒可能有多条"那一格——
原写法用 id 而不是时间做序，正是在处理这件事。

实现里自己造出来的一个 bug，被自己的用例抓住：**id 与条目下标的映射必须在排序与截断之后建**，
第一版用排序前的 `len(items)` 做键，翻页长就错位。改成 `boardRow{Item, lastID, identID}` 让 id 跟着行走。

两处代价写明（都进 P118 的落地记录，不只留在本报告）：

- **不能取 `MAX(created_at)`**（见 §5）。
- **一处口径收窄**：聚合带 `allowSources`、原榜尾单查不带，于是公开榜这两栏的总体从此与它的计数一致。
  管理员传 nil 无变化；公开榜只下发 `book_id`（`last_called_at` 本来就不出）。
  这不是顺手改的，是把两栏拴在同一个总体上的必然结果——**写下来是因为它会让"改动前后读数不同"有解释可查**。

用例 `test/groupb/subjectrank_board_queries_test.go` 两条腿（沿用 `redeem_list_queries_test.go` 的形状，
判据正本在踩坑判据「列表端点的关联名称要整页一次取回」）：
**条数不随页长增长**（1 条页长 vs 3 条页长比条数，不写死常数——同一张表上还有后台名称回填的读，常数会被污染成假红）、
**值还要对**（`book_ident` 三个向量各钉一次：最新一行缺标识→取次新带标识的、两行都有→取较新、同名跨源→取带标识里较新的）。

三次变异，各红在预期的那一半上：

| 变异 | 结果 |
|---|---|
| `MAX(CASE …) AS ident_id` → `MAX(id) AS ident_id` | 值断言红：`P118缺标识最新行` 期望 `"bk-old"`、实为 `""` |
| 整段主键点查取回删掉 | 两栏皆空红（三条向量的 `book_id` 与四个 `last_called_at` 一起报）——这正是"只测条数"挡不住的那一半 |
| 退回逐条目单查 | 条数红：报「1 条页长发 2 次、3 条页长发 6 次」，且 `ORDER BY id DESC` 那条形检查一起响 |

## 5. 跨方言那一格：CI 会红、线上不会红

`Select("… MAX(created_at) AS last_called")` 扫进 `time.Time`，测试段当场报
`sql: Scan error on column index 8, name "last_called": unsupported Scan, storing driver.Value type string into type *time.Time`，
而**同一条 SQL 在现网 MySQL 上是好的**。真因是聚合表达式丢掉列的类型亲和：列有 DATETIME affinity，
驱动按 affinity 转；`MAX(col)` 的结果没有 affinity 可依，SQLite 就交回 string。

**这与「手写 SQL 别名撞 MySQL 保留字」是同族、方向相反**：那条是 SQLite 全绿、只有生产红（所以靠线上暴露 + 门禁补扫）；
这条是生产全绿、只有 SQLite 红——**测试段是唯一会出声的地方**。于是 AGENTS §3 那句
「**`test/` 段跑的是 `./...` 而不是只跑 `./test/`**（包内单测不被门禁跑到就等于没写）」在这里第二次兑现：
这一格能被看见，只因为门禁真的把 sqlite 上的用例跑了。已升成判据页一条（`部分`：实例由用例钉住，
没被覆盖的路径不会红，扫描器那一档写不出理由见条目）。

## 6. 与 deploy 那棵树的耦合：为什么先开 worktree

数据源主力已转到装配仓 `loomproxy-deploy`（`replace loomproxy => ../loomproxy-base` **恒在**，见 P116）。
这决定了冲突的形状不是 git 冲突而是**构建耦合**：骨架的工作树是 deploy 本地构建的直接输入，
源侧那棵树一次 `make build` + 换装，就会把骨架里没收尾的改动一起带上生产——而 CI 不受影响
（`build.yml` 把 replace 改指 checkout 出来的骨架并按 tag clone）。

所以本轮全程在 worktree（`.qoder/worktrees/p118-board-n1`）做，`../loomproxy-base` 那个被指着的工作树保持干净，
收尾才 rebase 到 main 之上、ff 合入。顺带钉住一条**别当证据用**的东西：
线上日志里的文件路径**永远显示 `/home/muyang/work/loomproxy-base/`**（handlers 本来就是骨架的文件，
编译时源在那儿），**不能靠它判断某次上线带没带骨架改动**，只能看 deploy commit + 骨架 tag 两个数。
