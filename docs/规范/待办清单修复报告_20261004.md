### P48② 上限类设置里的 `0` 到底是什么意思

- **背景**：`max_active_sessions` / `device_watch_window_days` / `suspect_distinct_ips` 三条走同一个整数读取口
  （`db.SettingInt`，P61 起三条并一）。
  ① 已落地：填了不生效的值会**出一条日志**（同一种替换只喊一次），但**语义照旧**——0 仍被当"没配"、按默认 5/7/8 走。
- **选项**：
  A **0 = 不适用（维持现状）**：代价是"管理员填 0、系统按 5"这件事仍然要靠日志才知道，面板不回显生效值。
  B **0 = 关掉该项容忍（会话上限 0 → 每次登录收口到 1）**：代价是**踢人开关的上限填错就能一次登出所有人**，
  把一次配置失误变成一次现网事故；而且它与已有的 `device_watch_enabled` 开关**语义重复**（要关就该有个开关，而不是把数值压成 0）。
  C 不做：维持 A 的行为 + ① 的日志。
  **P63 给这一问补了一个实例，方向与 A 相反**：携带形态里 uxx 的标定边界用 **0 当哨兵**
  （`hi == 0` 意思是"还没有上界证据"），而冷却值也可以被管理员设成 0 表示"不设冷却"——
  也就是说"0 算什么"不是全局可拍的，它**按键不同**。所以这一问的落法应当是"读的那条函数名"而不是"一个全局口径"

  不是把全局默认改掉。B 与那个 `device_watch_enabled` 布尔开关做同一件事，两件工具做一件事必然漂移。
- **影响范围**：只影响这三条设置的解释；不改任何对外行为、不动库。
- **被它阻塞**：无（只阻塞"面板显示生效值还是显示填写值"这一格 UX）。

### P77 源实现 panic 的失败语义：从「崩进程 + 秒级重启」改成「一条 ERROR + 本轮跳过」，要不要保留

- **背景**：号池的启动与维护 tick 直接调数据源写的 `Create/Refresh/Claim`，而这两条路径上没有 Recovery。
  修前一次 panic = 整进程退出（`Restart=always` 秒级拉起，代价是**全部在途请求中断、全部号池重新装填**）；
  修后 = `guardPanic` 记一条带堆栈的 ERROR、本轮跳过、下一 tick 照常。同一原则在
  `base.RunSourceBoots`（源启动钩子）与 `app.callSourceHandler`（聚合逐目标）早已是「拦下继续」，
  所以本仓的既有取向支持修后这个方向——**但这是我替你改的一处运行时失败语义，不是纯内部重构**，
  而且它有一个反方向的理由：带 panic 的源会**每 tick 刷一条 ERROR**（同文案只喊一次，见 P76 的守卫），
  而崩一次重启反而把坏状态清了。现网 14 天里 `panic:` 计数为 **0**，所以今天两种选择都没有活症状。
- **选项**：
  - **A. 保留现状（拦下 + 一条 ERROR + 本轮跳过）**——代价：一个真在 panic 的源会变成"该池静默失灵 + 日志一条"，
    需要人看 ERROR（面板 `GET /admin/pools` 不会因此变色）；好处：一个源坏不牵连另外十二个源与全部在途请求。
  - **B. 改回 fail-fast（只留 `p.locked` 的 defer 解锁，摘掉两处 `defer guardPanic`）**——代价：
    「一个源解析畸形响应」重新等于全站重启，且 `Restart=always` 会把连续 panic 伪装成"运行中"（v63 记过的形状）；
    好处：坏状态一定被重启清掉。
  - **C. 折中：拦下，但连续 N 轮（比如 3 轮）同一处 panic 就主动 `log.Fatalf` 交给 systemd**——代价：
    多一个不自助的判据（N 取几没数据支撑），且实现要小心"临界区 panic 后锁已放开"这一条已经满足了；
    好处：既不让一个源带走全站，也不让"静默失灵的池"长期只有日志。
  - **D. 什么都不拍**：现状已经是 A，不拍就不动。
- **我的建议**：**A（保留），并把它当成全仓规则**——非请求通路调用外部实现一律拦下（判据页已这样写）；
  如果你更担心"静默失灵的池没人发现"，那我建议 C 而不是 B，因为 B 的代价由**所有源**分摊。
  另有独立的一格读数可以补（不属于本条）：号池快照里加一格「本轮 panic 次数」，让面板也能看出这个池在挨打。
- **影响范围**：`base/pool/state.go` 的两处 `defer p.guardPanic(...)`（`cc2aa72`）；
  改回 B 只删两行、不动 `locked`/`initLedger`/`ticker` 那三处（**它们各自管的是竞争与死锁，与失败语义无关**）。
- **被它阻塞的条目**：不卡任何条目；卡的是「下一次带 panic 的上线，运维该看日志还是看进程」。
- **答复后回写位置**：`docs/归档/2026-10-续跑轮/待办清单-P77已收口.md` 的「对外可见的语义变化」那一段，

### P88 的一半：三个配置写入口从「200 已更新」改成「500 保存失败」，要不要维持

### P88 的另一半：验证码失败次数写不进库时，要不要 fail-closed

- **背景**：`verify.Check` 里错码校验走 `db.DB.Model(&row).UpdateColumn("attempts", row.Attempts+1)`，
  过去没读结果。这条列是**防爆破计数器**：本次请求的判定用的是内存值 `row.Attempts+1`（所以单次请求没问题），
  但库里那列写不进去就不前进，**下一次读到的还是旧值**——对着验证码慢猜的人永远撞不到 `maxAttempts`。
  本轮只加了"出声"（ERROR 一行），没改判定语义。
  现网读数（只读）：`verify_code_scenes = register,forgot_password` 两个场景**都开着**，
  而 `verification_codes` 全表 4 行、`MAX(attempts) = 0`——活路径、极冷流量。
- **选项**：
  - **A. 保持现状（只出声）**：代价是写失败期间防爆破对这条路实质失效，
    但日志有一条说得出来的 ERROR；好处是不引入新的用户侧失败。
  - **B. fail-closed（写不进就当作已到顶，直接拒）**：代价是**数据库抖一下就把正在输验证码的人全挡在门外**，
    而"输错三次"与"库连不上"对用户是同一句话；收益是安全默认更紧。
  - **C. 计数器改内存 + 库双写**（进程内 map 兜住库写失败）：代价是多一份状态、多一条"两份什么时候一致"的判据，
    而重启就回到 0——对本仓已有的登录防爆破（`ipAttemptLimiter` 纯内存、刻意不落库）来说，
    这等于给同一件事造第二套口径。
- **我的建议**：**A**。判据是「**先让失败可见，再决定它算不算事故**」——B 与 C 都是在没有一条读数的情况下
  先改语义或加状态。真出现"计数器写失败频繁"时，那条 ERROR 的量级就是拍 B 的依据（本轮已把日志写全，
  包括停在旧值上那一层意思）。C 明确不推荐：与本仓 P40「登录防爆破不落库」的既有取舍相冲。
- **影响范围**：无（本轮只加了一条日志）。选 B 会改 `verify.Check` 的返回路径与用户可见提示。
- **被它阻塞的条目**：无。卡"防爆破对验证码是否真的有效"这一句话能不能说出口。
- **答复后回写位置**：`docs/规范/待办清单.md` 的 P88 条目「还有一处语义没动」段；
  选 B 时同步 `docs/架构/鉴权模型与会话.md` 的验证码段（那里现在写的是"连击 10 次锁定"的 IP 口径，
  要补一句单码口径的失败关闭语义）。
