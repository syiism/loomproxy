## 3. P39 与 P47 的验证台账

> **先记一件新门禁自己的事**：`check-test-order.sh` 上线后第一次红，红在**它自己的假警报**上——
> 新写的用例里那句「装配优先：`conf.Config` 与数据源注册表都是装配时才建好的全局态」是**注释**，
> 而扫描器按整行文本匹配，把注释里的名字当成了引用。
> 修法是把注释行剔除再判定，并且**两个方向都复验**：坏 fixture（真的在 `newTestServer` 之前读全局）仍红、
> 只含注释的写法不再红。规则：**机器拦截上线当天就要拿一个假警报样本去试**，
> 因为假警报的代价不是多跑一次，是大家开始无视它——那条与 `btn-secondary` 的「静默跳过」是同一族失效。


**P39（成本缓存失效）**：`gate.CostCacheKey` 一处定义、读写两侧共用；`UpdateQuotaCost` 按行自身的
`group_code`/`interface` 失效。用例三段（键被填 / 改价后键消失且不扣 / 同行禁用立刻 403），
变异三次，其中一次**故意记录了没红的部分**：把冷却参数那句改回 300 之后，「不再扣」那条断言失去牙齿
（P25 的同内容冷却本来就会让第二次不扣）——所以那句调 0 是承重位，不是装饰。

**P47（禁用后的密钥窗口）**：`utils.InvalidateUserApiKeys(userID)` 挂在禁用、删除、**改名**三处。
状态码这一处值得记：403「无效的 API Key」= 归属查库查不到（失效做成了），401「用户不存在」= 身份来自缓存、
往下才发现库里没人（失效没做成）。**第一版断言写的是「非 200」，两种都能过——是变异把它揪出来的**，
改成断具体码之后四处变异各拦住一处。

**固化增量**：`make vet` 新增第 6 条 `scripts/check-test-order.sh`（集成用例在 `newTestServer(t)` 之前
引用 `conf.Config`/`db.DB`/`utils.DefaultCache()` 即构建失败）。这条从「口头」直接走到「机器拦住」，
按判据页的退出机制**没在判据页留行**；存量扫描 0 处违规，坏 fixture 红过一次。
判据页的条目分布因此从 24 条 5/8/11 变成 **24 条：5 已 / 8 部分 / 11 未**（本轮只合并了「断言空转」那条，
把它扩成「空转 + 过宽」两种失灵，条数不变）。

## 4. P22②-b 的复核结论（判据 + 样本窗口）

样本窗口：生产 `api_call_logs` 全表 2026-09-24 03:15:05 ~ 2026-10-04 20:00:37，共 30535 行；
取**近 7 天** 29187 行算占比。读数：

- 带内失败（`in_band_error`）**139 行 = 0.5%**，且**全部落在 `content` 一个动作**；
  分源：`uxx` 55/638、`xmly` 51/2224、`fq_novel` 20/9743、`hg_drama` 6/83、`fq_audio` 5/31、`qq_luomu` 2/678。

  真故障是 403 265 / 400 48 / 502 44 / 504 39 / 522 11。

**结论：维持带内、不改 5xx**（理由与重开条件写在待办清单 P22 的 ②-b 段）。
**重开阈值也写死了**：带内占比爬到几个百分点以上、或某源长期 >20%。

**采到的三条结论在待办清单 P51 的收口记录里（一张路径表 + 三句话）**，本处只记方法与两条自己踩的小坑：

1. `ssh hk '…$p…'` 里多写一个反斜杠，远端拿到的就是字面 `$p`，`curl` 于是回 `HTTP=000 bytes=0`——
   **这看起来完全像"服务没在监听"**。判据：拿到 `000` 先看自己的引号层级，再怀疑对端（同类：只看 `is-active` 不读启动契约）。
2. `mysql -N loomproxy -e 'SELECT id, code FROM quota_plans' | tail -6` 把 **`free` 那一行切掉了**，
   于是我差点写下"现网没有 free 套餐、所以新注册用户一律无套餐"这条"发现"。
   回去用 `ORDER BY id` 复算才发现 `free` 是 id=1、只是排在最前而被 `tail` 吃掉。
   判据：**否定性的读数（"没有 X"）必须用会自己数数的查询来立**（`COUNT(*) WHERE code='free'`、
   或干脆不接 `tail`），不能靠"我看到的列表里没有"——`tail -N` 截的是**尾部**，
   而 id 最小那一行往往正是默认档。这条与「断言空转」同族：**眼睛扫过的集合不等于被测的集合**。

## 5b. P52 与 S47 定案：一次「先查经验再想方案」的正面样本（读数都是生产只读）

分支 S47 立案时写的三个假设（重复参数 / 观测前 panic / 路由没挂 wrapper）全都指向「采集链有洞」。
本轮按 §13 的默认动作先回查 P37 那一页——**同意位关掉时清的是七个字段，含两个标识**
（只清名称会被名称回填循环补回来）——于是方向从「找洞」变成「先数有没有人说过别留」。
把关掉留存的 22 个用户与其明细按归属对齐，三格读数：

| 读数 | 值 | 说明 |
|---|---|---|
| `content_withheld=1` 且仍带任一维度 | **0** | 闸口抹得干净，没有「标了却没清」 |
| 该用户关掉（`created_at >= users.updated_at`）之后仍带维度 | **0** | **没有任何一行阅读内容是在他关掉之后留下的** |
| 关掉之后有行、但没被标 withheld | **4**（另一用户 70 行里 6 行，全在 `recommend`） | 时间轴对齐后**也不是缺陷**：那 6 行是 12:00:36~12:01:19，而该用户关开关的时刻是 12:01:47，已标的 64 行从 12:02:35 起——未标的都在关掉之前 |

**这条定案顺手否掉了一个假设**：我原先怀疑「没走到 access 的请求既不清字段也不置标记」（P52 的候选解释 ①），
时间轴读数把它否了——闸口在开关落地后 48 秒就开始工作。
**真正的残留是结构性的**：同意位没有「变更时刻」这一列，这次能定案纯靠那个用户当天只动过一次；
换一个先关、隔天改昵称、再关回来的人，同样的问题就答不了（`updated_at` 会被任何一次更新顶掉）。
加 `content_consent_set_at` 是生产库写操作，等授权，本轮不动。

**为什么后两格分不开**：同意位没有变更时刻，只能拿 `users.updated_at` 近似，而它会被任何一次改昵称顶掉。
所以 P52 两条候选解释都留着、各写了怎么验；要真正分开得加一列 `content_consent_set_at`（生产库写操作，单独等授权）。
判据页新增一条（分布 25 条：5 已 / 8 部分 / 12 未）：**看到一片空维度，先查 `content_consent` 与 `content_withheld`，再怀疑采集**。

### P48② 上限类设置里的 `0` 到底是什么意思

- **背景**：`max_active_sessions` / `device_watch_window_days` / `suspect_distinct_ips` 三条走同一个 `settingInt`。

### P40① 账号侧要不要独立闸门（现在只按 IP）
