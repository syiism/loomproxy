# Goal 提示词 · 一次性落地两个方案（零停机 + 骨架为库）

> 用法：把本文件全文作为 goal 模式的开场提示词发给 agent。它自包含、不依赖会话历史。
> 轮询：随时问"当前进度"，agent 按 §6 的状态表回报。
> 参考：`docs/规范/长任务提示词-待办清单循环.md`（通用流程约束）、`docs/规范/踩坑判据.md`。

---

## 0. 目标（一句话）

在**不碰线上、不改 API 契约**的前提下，一次性完成两件事：
1. **P115 零停机升级**：把 systemd socket activation 的代码与单元文件落地到仓库。
2. **骨架为库、数据源为应用**：把方案页推进到"可执行清单"，让维护者能照着建出第一个数据源仓库。

两件事**依次做**：先零停机（小、独立、可验收），再骨架为库（大、纯文档）。做完第一件先报状态，再做第二件。

## 1. 硬约束（必须停下来等人）

- **对服务器做任何写操作**：部署、`systemctl`、改线上 `.env`——本任务只交付代码与模板，**不碰线上**。
- `git push`——只在维护者明确要求时推；默认只提交到本地。
- **改 API 契约**：响应状态码、响应文案形态——零停机只改启动方式，不改 API。
- **新建私有数据源仓库**——本轮只写清单，不真的去建仓库。

## 2. 自治域（不询问，直接做）

- `main.go` 的改动（约 30 行）。
- 新增 `deploy/` 目录下的 systemd 单元文件模板。
- 修改 `docs/方案/骨架当库-数据源当应用.md`。
- 新增 `docs/方案/数据源仓库-落地清单.md`（step-by-step）。
- 本地跑 `make build`。

## 3. 开工三查（未查完不准动代码）

1. **查经验**：扫 `docs/规范/踩坑判据.md`，搜关键词：`socket activation`、`systemd`、`fd`、`优雅停机`、`replace`、`go.mod`、`embed`、`web/dist`。命中就照判据自查。
2. **查基线**：`git status --short` 必须干净；`git log --oneline` 看骨架有无未合入；读 `main.go`、`web/embed.go`、`go.mod` 确认方案页的假设。
3. **查清单**：通读 `docs/规范/待办清单.md`，确认 P115 是本轮唯一实施任务，其余 P 编号不动。

三查之后、动手之前，把那张"五条硬表"（开工三查结果）原样输出一次——这是每轮的开场动作，不是收工时补的。

## 4. 第一个里程碑：P115 零停机

### 4.1 做什么

1. `main.go` 里 `net.Listen` 之前先试 `activation.Listeners()`：
   - 被 systemd socket activation 拉起 → 用传进来的 fd（`listeners[0]`）。
   - 否则 → 回退 `net.Listen("tcp", addr)`（本地开发不受影响）。
2. 新增两个 systemd 单元文件模板：
   - `deploy/loomproxy.socket`：`[Socket] ListenStream=8081`，`[Install] WantedBy=sockets.target`。
   - `deploy/loomproxy.service`：改 `ExecStart` 与 socket 绑定，`TimeoutStopSec=30s`（在途请求上限）。
3. 新增 `docs/架构/部署-零停机.md`：写清原理、单元文件内容、升级步骤、回退方法。

### 4.2 验收（做完这些才算完成）

- `make build` 全绿（含 `-race`）。
- `go run .` 不带 systemd 时能正常起（回退路径不破坏开发体验）。
- 待办清单 P115 状态更新为"代码已落地，待线上验证"。

### 4.3 完成后：**停下来报状态，再做第二件事**

输出：
```
[里程碑 1 完成]
- 改了哪些文件：...
- make build 结果：绿/红（红则附日志）
- 回退路径验证：go run . 是否正常起
- P115 状态：...
- 下一步：开始里程碑 2（骨架为库落地）
```

## 5. 第二个里程碑：骨架为库、数据源为应用

### 5.1 做什么

把 `docs/方案/骨架当库-数据源当应用.md` 从"方向定稿"推进到"可执行清单"：

1. **逐条对照当前代码**，确认方案页的假设：
   - `main.go` 是否真的"薄到不需要同步"？如果不是，写清楚"骨架侧还要做什么"。
   - `web/embed.go` 的 `//go:embed dist` 是否真的依赖骨架目录的 `web/dist`？
2. **补全可执行内容**：
   - `go.mod`、`main.go`、`sources/deploy_all.go` 三个文件的**完整内容**（能直接 cp 的全文，不是示例片段）。
   - Makefile 的完整内容（含 `SKELETON` 变量、`web` 目标、`build` 目标）。
   - CI 5 步流程写成一个可复制的 YAML 片段（Gitee Go / GitHub Actions 任选，标注选了哪个）。
3. **新增 `docs/方案/数据源仓库-落地清单.md`**：step-by-step，维护者照着做能建出第一个数据源仓库。
4. **风险清单**：列"第一次建数据源仓库时最容易卡住的 5 个地方"，每个配一句"怎么验证没卡住"。
5. **回退方法**：如果建不起来，怎么退回"单体仓库 + sources/* 分支"的老形态。

### 5.2 验收（做完这些才算完成）

- 方案页每条都可执行（不写"TODO"、不写"待补充"）。
- 落地清单是 step-by-step（不是概念描述）。
- 不改动现有 Go 代码（本轮只动 `docs/`）。

### 5.3 完成后：输出最终状态

```
[里程碑 2 完成]
- 改了哪些文档：...
- 方案页假设验证结果：main.go 薄/不薄；embed 依赖确认
- 落地清单是否 step-by-step：是/否
- 风险清单条数：5
- 回退方法：已写/未写
```

## 6. 轮询：随时问"当前进度"

Agent 每次被问进度，按这个表回报：

| 里程碑 | 状态 | 说明 |
|---|---|---|
| 开工三查 | ✅/⏳/❌ | 三查结果一句话 |
| 里程碑 1：P115 零停机 | ⏳/✅/❌ | 做到哪一步（改 main / 写单元文件 / 跑 make build / 更新待办） |
| 里程碑 2：骨架为库落地 | ⏳/✅/❌ | 做到哪一步（读代码 / 补方案页 / 写落地清单 / 风险清单） |

- ✅ = 完成
- ⏳ = 进行中
- ❌ = 卡住（附原因）

## 7. 停止条件（碰到就停下来报）

- `go-systemd/activation` 库与 CGO（sqlite3）有冲突——报，不强行绕。
- 回退路径导致本地开发体验变差（必须设环境变量才能起）——报，这是设计错误。
- 方案页假设不成立（`main.go` 不薄、embed 有坑）——报，写清"骨架侧要先做什么"。
- `make build` 红了——修到绿为止，不许跳过；修不好就报。
