# Goal 提示词 · 审批（两个方案落地完成后）

> 用法：在 agent 完成"一次性落地两个方案"的两个里程碑后，把本文件全文作为 goal 模式的开场提示词发给 agent。
> 作用：让 agent 自审完成质量、输出审批材料、等待维护者拍板。
> 前置状态：`docs/方案/Goal提示词-一次性落地两个方案.md` 的两个里程碑都已 ✅。

---

## 0. 目标

把两个里程碑的产出整理成**可审批的材料包**：自审完成质量、列出变更清单、标注风险与回退方法、输出一份"维护者拍板用"的摘要。**不做任何新改动**——本轮只审、只整理、只等指令。

## 1. 硬约束（本轮绝对不做）

- **不 push**——等维护者明确说"推"才推。
- **不改代码、不改文档**——本轮只审、只写审批材料。
- **不碰线上**——部署是维护者的动作，不是 agent 的。

## 2. 审批材料（必须输出的四项）

### 2.1 变更清单

按里程碑分两组，每组列出：
- 改了哪些文件（路径 + 一句话说明）。
- 新增了哪些文件（路径 + 用途）。
- 删了哪些文件（如果有）。

### 2.2 验收结果

- **里程碑 1（P115 零停机）**：
  - `make build` 是否全绿（含 `-race`）？红则附日志。
  - `go run .` 回退路径是否正常起？
  - 单元文件模板是否完整（socket + service 两个）？
  - P115 状态是否已更新？
- **里程碑 2（骨架为库落地）**：
  - 方案页每条是否可执行（不写 TODO）？
  - 落地清单是否 step-by-step？
  - 风险清单是否 5 条？
  - 回退方法是否写清？

### 2.3 风险与回退

- **本轮改动能回退吗**？每个变更对应一句"怎么回退"。
- **有没有未解决的问题**？列出来（比如"go-systemd/activation 与 CGO 有未验证的兼容性"）。
- **线上部署时最容易踩的坑**？列 3 条。

### 2.4 维护者拍板摘要（一段话）

不超过 200 字，说清：
- 这轮干了什么。
- 干得怎么样（验收过没过）。
- 维护者下一步要做什么（推不推、上不上、什么时候上）。

## 3. 轮询：随时问"审批材料齐了吗"

Agent 按这个表回报：

| 材料 | 状态 | 说明 |
|---|---|---|
| 变更清单 | ✅/⏳/❌ | 按里程碑分了几组 |
| 验收结果 | ✅/⏳/❌ | make build 绿/红；回退路径正常/异常 |
| 风险与回退 | ✅/⏳/❌ | 每条变更有没有配回退 |
| 拍板摘要 | ✅/⏳/❌ | 200 字以内 |

## 4. 等待指令

材料包输出后，agent 进入**等待状态**。维护者可能说：

- **"推"** → agent 执行 `git push`，输出推送结果。
- **"改 X"** → agent 按指令改，改完重新跑审批材料流程。
- **"先不推"** → agent 停在本地，不做任何动作。
- **"上线"** → agent 提醒：部署是维护者的动作，agent 不碰线上；agent 只输出"部署步骤清单"（如果还没写）。

## 5. 最终交付物

- 一份审批材料包（变更清单 + 验收结果 + 风险回退 + 拍板摘要）。
- 等待维护者指令，不擅自推进。
