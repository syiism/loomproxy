# 骨架当库、数据源当应用——仓库边界与构建方案

> 状态：**可执行清单**。骨架侧假设已逐条对码核对（结论在 §8），装配文件全文在 §3.2、§4 与 §7，
> 照着建的 step-by-step 见 [`数据源仓库-落地清单.md`](数据源仓库-落地清单.md)。本页不改代码。
> 动机：骨架（本仓库）已经不携带任何数据源，`sources/all.go` 是空 package、`sources/*` 分支只进私有远端
> （AGENTS §12）。这意味着"代码边界"在仓库层已经分开，但"构建产物边界"还没成文——
> 本页把它写成正式约定：**骨架是 Go module 库，数据源仓库是应用，各编各的二进制**。

## 1. 形态选择：为什么是"编译期拼装"而不是运行时插件

"可插拔"在 Go 生态有三种实现，逐一审过：

| 形态 | 结论 | 理由 |
|---|---|---|
| Go plugin（`-buildmode=plugin`） | **不采用** | 官方长期不推荐；CGO（本项目 sqlite3）兼容差；主程序与插件必须同版本 Go、同依赖图；调试与分发都是噩梦 |
| Sidecar 独立进程 + RPC | **不采用** | 源直接调 `base.Fetch` / `pool.Register` / 内存缓存，要把这些能力全部 RPC 化，性能与复杂度都不划算 |
| **库 + 应用（本方案）** | **采用** | 骨架已是库形态：`main.go` 只有信号处理 + `app.Run(ctx)`；源靠 `init()` 自注册；零架构改动 |

**边界**：这不是"运行时热插拔"（不重启加源），而是"编译期拼装"——加一个源 = 数据源仓库加一行空白导入 + 重编。
Go 没有顺手的运行时加载，这个边界是语言现实，不是取舍失误。

## 3. 仓库契约

### 3.1 骨架侧（本仓库）要守的事

- `main.go` 保持"信号处理 + `app.Run(ctx)`"的极简形态，它是给数据源仓库复制用的模板——**不要在 main 里塞业务逻辑**。main 薄到升级时几乎不需要同步：所有业务装配都在 `app.Run` 里，数据源仓库复制过去后，骨架改 main 一般只动 import 列表（加/减源）。
  **P115 核对补记（2026-10-09）**：socket activation 的监听选择落在 `app/app.go` 的 `Run` 里（`net.Listen` 本来就在那里），`main.go` 一个字没动——这条契约经受了第一次"骨架升级"的检验。
- 发版打 tag（`skeleton-vNNN` 继续）。**核对更正**：`skeleton-vNNN` 这个名字不是合法的 Go module 语义版本（module 版本必须裸 `vX.Y.Z`），
  而本方案里数据源仓库**永远**靠 `replace` 指向 checkout 出来的骨架目录（原因见 §4 的 dist 耦合），`require` 的版本号从不参与解析、只是占位——
  所以**钉骨架版本的真凭据是"checkout 哪个 tag"，不是 go.mod 里的 require 版本**。tag 的另一半职责仍是分支纪律的三点 diff 基准（AGENTS §12）。
  若将来想让纯 `require` 路线成立，骨架侧要先做的两件事：module path 改成带域名的导入路径、`web/dist` 进版本库或改为发布资产——都不在本轮。
- **破坏性变更约定**：骨架在 `v1.0` 前，接口（`base.Handler`、`SourceMeta`、`pool.Provider` 等）变更一律视为 breaking，release note 必须列出；`v1.0` 后走 semver（major bump = breaking）。
- 公开仓库保持 `sources/all.go` 空、不夹带任何源实现。**这个空 package 是"骨架不携带源"的边界标记**（让 `sources/` 目录能 import、让"加源 = 加文件"的故事成立），不是功能，也不是给骨架自测用的。
- `web/dist` 不进 git（维持 `.gitignore` 现状）；构建时由 `make web` 产出。

### 3.2 数据源侧（私有仓库）要做的事

1. `go.mod`（**完整内容**，cp 之后照落地清单第 4 步跑 `go mod tidy` 补齐 indirect 与 go.sum）：
   ```go
   module loomproxy-deploy

   go 1.26.5

   require loomproxy v0.0.0

   // 本地开发期指相对路径；CI 里用 `go mod edit -replace` 改成绝对路径（§6 CI 步骤第 4 步）
   replace loomproxy => ../loomproxy
   ```
   - **require 的版本是占位**（§3.1 更正：`skeleton-vNNN` 不是合法 module 版本；replace 存在时版本不参与解析）。
     临时联调用 pseudo-version（`v0.0.0-<commit>`）也可以，但它同样被 replace 覆盖，不产生额外约束。
   - **replace 在 CI 里必须用绝对路径**（如 `/workspace/loomproxy`），不能依赖相对路径 `../loomproxy`——CI 的 workspace 布局不一定和本地一致。
   - **不能用纯 `require` + `go mod download` 拉模块缓存**：因为 `web/dist` 不在 git 里，模块缓存里没有 dist，`go:embed` 会失败。CI 必须 checkout 骨架源码目录。
2. `main.go`（**完整内容** = 骨架 `main.go` 原样 + 唯一一行空白导入）：
   ```go
   package main

   import (
   	"context"
   	"log"
   	"os"
   	"os/signal"
   	"syscall"

   	"loomproxy/app"

   	_ "loomproxy-deploy/sources" // 数据源仓库唯一的增量：携带源的空白导入清单
   )

   func main() {
   	ctx, cancel := context.WithCancel(context.Background())
   	defer cancel()

   	sigCh := make(chan os.Signal, 1)
   	signal.Notify(sigCh, syscall.SIGINT, syscall.SIGTERM)

   	go func() {
   		sig := <-sigCh
   		log.Printf("Received signal: %v, shutting down...", sig)
   		cancel()
   	}()

   	if err := app.Run(ctx); err != nil {
   		log.Fatalf("Server error: %v", err)
   	}
   }
   ```
3. `sources/deploy_all.go`（**完整内容**，`mynovel` 换成真实源码）：
   ```go
   // Package sources 数据源仓库的携带清单：本文件的空白导入即「本部署携带哪些源」。
   // 加/下线一个源 = 这里加/删一行（+ 对应源包目录 sources/<源>），重新 go build。
   package sources

   import (
   	_ "loomproxy-deploy/sources/mynovel"
   )
   ```
4. 源包实现：照 AGENTS §5 的约定，在 `init()` 里 `base.RegisterSource` + `base.Register`，内嵌 `base/legado` 基类；
   启动动作放声明位 `OnBoot`，**不要放包 `init()` 里读 env**（AGENTS §5：`.env` 在 `app.Run` 里才读）。

## 4. 构建链（关键：web/dist 从哪来，以及它为什么锁死了 replace 策略）

`web/embed.go` 用 `//go:embed dist`，dist 在 `.gitignore` 里。数据源仓库 `go build` 时 embed 的是
**骨架模块自己的 `web/dist`**（go.mod replace 后，骨架源码在 `../loomproxy/web`）。

**这里有一个容易被忽略的耦合**：因为 `web/dist` 不在 git 里，数据源仓库构建**必须**用 replace 指向已 checkout 的骨架源码目录，不能用纯 `require` + `go mod download`——模块缓存里只有 git 跟踪的文件，没有 `dist`，`go:embed` 会直接失败。

- 构建前必须先在骨架目录跑过 `pnpm install && pnpm build`，产出 `../loomproxy/web/dist`。
- 数据源仓库不需要重写前端、不需要 cp dist——只要骨架目录的 dist 存在，`go build` 时自动 embed 进去。
- Makefile 的 `build` 目标依赖 `web` 目标：`web` 目标就是在骨架目录跑 pnpm build。

**数据源仓库 Makefile（完整内容，可直接 cp）**：

```makefile
# 数据源仓库的 Makefile：只负责装配产物。骨架门禁（vet + -race 全量测试）在骨架目录跑，
# 不在这里重复一遍——`make skeleton-check` 就是替你把那条线拉过来。
SKELETON ?= ../loomproxy
BIN            := loomproxy-go
RELEASE_BINARY := loomproxy-go-release

.PHONY: web skeleton-check vet build go-build run

web:
	cd $(SKELETON)/web && pnpm install && pnpm build

# 骨架全量门禁：等价于在骨架目录 make vet && make test
skeleton-check:
	$(MAKE) -C $(SKELETON) vet
	$(MAKE) -C $(SKELETON) test

vet:
	CGO_ENABLED=1 go vet ./...
	@test -z "$$(gofmt -l . | grep -v '^web$$')" || { gofmt -l .; echo "gofmt 未过"; exit 1; }

build: web vet go-build

# 与骨架 go-build 逐字一致：调试版留符号排障、strip 版部署用；产物名是部署契约（deploy.sh/Dockerfile 认这两个名字）
go-build:
	CGO_ENABLED=1 go build -o $(BIN) .
	CGO_ENABLED=1 go build -ldflags="-s -w" -o $(RELEASE_BINARY) .

run: build
	./$(BIN)
```

## 5. 日常流程

| 场景 | 操作 |
|---|---|
| 加/下线一个源 | 数据源仓库 `sources/deploy_all.go` 加/删一行 + 源包；`go build` |
| 升级骨架 | 改 `go.mod` 的 require 版本 → `go mod tidy` → 跑全量测试 |
| 骨架改 bug | 骨架仓库提交 + 打新 tag；数据源仓库 bump 版本 |
| 本地联调 | `replace loomproxy => ../loomproxy` 指本地路径，两边同时改 |

## 6. 已知坑（落地时别再踩）

- **CGO 必须**：sqlite3 依赖 gcc。构建机要装 C 工具链。
- **版本严格对齐是特性**：骨架改了 `base.Handler` 接口签名，数据源仓库不 bump 版本就编不过——这是逼着同步，不是阻碍。
- **`.env` 不进 git**：数据源仓库放自己的 `.env.example`；生产 `.env` 与 `data/` 目录照旧在部署目录。
- **CI 构建步骤**（写死，第一次跑别猜）：
  1. checkout 骨架到指定 tag，放在 `/workspace/loomproxy`（绝对路径，不依赖相对布局）。
  2. 在 `/workspace/loomproxy/web` 跑 `pnpm install && pnpm build`，产出 `web/dist`。
  3. checkout 数据源仓库到 `/workspace/deploy`。
  4. 数据源仓库 `go.mod` 的 replace 写成 `=> /workspace/loomproxy`（绝对路径）。
  5. 在 `/workspace/deploy` 跑 `CGO_ENABLED=1 go build -o loomproxy-go .`。
- **Dockerfile 构建上下文**：因为 embed 依赖骨架目录的 `web/dist`，构建上下文**必须同时包含数据源仓库和骨架目录**。两种做法二选一：
  - **多阶段**：第一阶段 node 镜像里 checkout 骨架 + 构前端；第二阶段 golang 镜像里把骨架源码和数据源源码一起挂进去，replace 指容器内绝对路径，`go build`。
  - **本地先 build 再打包**：在 CI 里先跑上面的 CI 步骤产出 `loomproxy-go`，Dockerfile 只 COPY 这个二进制 + 运行时依赖，不重复构建。**推荐这种**——Docker 里跑 Go 构建 + CGO + pnpm 三件套容易踩工具链版本问题。
- **不要把 sources/all.go 搬进数据源仓库再 import 骨架的 sources 包**：骨架的 sources 包是空的，import 它没意义；源包直接放数据源仓库自己的 `sources/` 下。

## 7. CI 装配脚本（**选 GitHub Actions 语法**；§6 五步的逐字翻译，可直接 cp）

> 为什么选 GitHub Actions：语法是事实标准，私有 Gitee/Gitea 自建 runner（act、gitea-actions-runner）也吃这份 YAML；
> Gitee Go 的 `.workflow` DSL 细节以官方当前文档为准，这里不凭印象写第二份事实来源。
> 骨架 tag 只有一个钉点：`env.SKELETON_TAG`，升级骨架 = 只改这一行。

```yaml
name: build-deploy-binary
on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      SKELETON_TAG: skeleton-v107          # ← 骨架版本的唯一钉点（就是 §6 第 1 步 checkout 的 tag）
    steps:
      # 1. checkout 骨架到指定 tag，绝对路径 / 固定目录（不依赖相对布局）
      - name: Checkout skeleton
        run: |
          git clone --depth 1 --branch "$SKELETON_TAG" \
            https://gitee.com/syiism/loomproxy.git "$GITHUB_WORKSPACE/loomproxy"

      # 2. 前端产物：web/dist 不在 git 里，go:embed 依赖它（§4 的耦合）
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - name: Build frontend
        run: |
          corepack enable
          cd "$GITHUB_WORKSPACE/loomproxy/web" && pnpm install && pnpm build

      # 3. checkout 数据源仓库
      - uses: actions/checkout@v4
        with:
          path: deploy

      # 4. replace 指绝对路径（go mod edit 比 sed 稳：幂等、不依赖原文形态）
      #    国内 runner 还要一句 `go env -w GOPROXY=https://goproxy.cn,direct`（2026-10-09 实测：默认 proxy 超时）
      - name: Point replace at checked-out skeleton
        run: |
          cd "$GITHUB_WORKSPACE/deploy"
          go mod edit -replace "loomproxy=$GITHUB_WORKSPACE/loomproxy"

      # 5. 编译产物（CGO 必需：sqlite3；ubuntu runner 自带 C 工具链）
      - uses: actions/setup-go@v5
        with:
          go-version: "1.26.5"
      - name: Build binary
        run: |
          cd "$GITHUB_WORKSPACE/deploy"
          go mod tidy
          CGO_ENABLED=1 go build -ldflags="-s -w" -o loomproxy-go-release .
      - uses: actions/upload-artifact@v4
        with:
          name: loomproxy-go-release
          path: deploy/loomproxy-go-release
```

Docker 打包照 §6 末条的定稿：**CI 先产二进制，Dockerfile 只 COPY**——不在容器里重复 pnpm+CGO 三件套。

## 8. 骨架侧假设核对（对码 2026-10-09，基线 `6260566` + P115 改动）

| 假设 | 核对结果 | 证据 |
|---|---|---|
| `main.go` 薄到不需要同步 | **成立**。全文件 29 行：信号处理 + `app.Run(ctx)`，无业务逻辑。P115 的监听选择也刻意放进了 `app.Run` 而不是 main，main 至今零改动 | `main.go` |

| `//go:embed dist` 依赖骨架目录的 `web/dist` | **成立，且比方案页写的更具体**：嵌入指令是 `//go:embed dist/* dist/assets/*`（两条 pattern，不是裸 `dist`）；路径相对 **embed.go 所在包**，即 replace 后骨架模块源码里的 `web/`——所以 §4 的"replace 到已 checkout 源码目录"是唯一可行路径。dist 缺失时编译直接报 `pattern dist/*: no matching files found` | `web/embed.go` |

| 骨架 `sources/all.go` 是空 package 边界标记 | **成立**：只有 doc comment + `package sources`，无导入 | `sources/all.go` |

**骨架侧还要做什么**：无阻塞项。一条待办——首个数据源仓库建立后，骨架发 tag 时顺手在 release note 里列 breaking（§3.1 第三条的约定从那次起生效）。

## 9. 不做的事

- 不引入 Go plugin / cgo 动态加载。
- 不把 base.Fetch / pool 等能力 RPC 化（不做 sidecar）。
- 不做"运行时热加载新源"——加源就重编，30 秒的事。
- 骨架仓库不发"预编译库"（.a 文件）——Go 的库分发就是源码 + 版本号。
