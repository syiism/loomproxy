# 数据源仓库 · 落地清单（step-by-step）

> 目标：照着本页，从零建出第一个数据源仓库并编出可部署的 `loomproxy-go`。
> 方案与理由在 [`骨架当库-数据源当应用.md`](骨架当库-数据源当应用.md)（下称《方案页》），本页只有动作。
> 全文基于 2026-10-09 对码核对（基线 `6260566` + P115），文件内容以骨架仓库正本为准。
> **本轮只写清单，不真的建仓库**——每条步骤是给执行者的一次动作，做完打勾。

## 前置（开工前各查一次，命令直接跑）

| # | 检查 | 命令 | 通过形态 |
|---|---|---|---|
| a | Go ≥ 骨架 go.mod 声明 | `go version` | `go1.26.5` 或更高 |
| b | CGO 可用 | `go env CGO_ENABLED` && `gcc --version` | `1` 且 gcc 在位 |
| c | node + pnpm | `node --version && pnpm --version` | 与骨架 `web/package.json` engines 相容 |
| d | 模块代理可达（国内机默认 proxy 会超时，2026-10-09 实测） | `go env -w GOPROXY=https://goproxy.cn,direct` | 之后 `go mod download` 静默完成 |

## 1. 把骨架以库的形态放到旁边

```bash
git clone https://gitee.com/syiism/loomproxy.git loomproxy
cd loomproxy && git checkout skeleton-v107   # ← 钉住的骨架 tag，与后面 CI 的 SKELETON_TAG 同一个值
```

**验收**：`ls ../loomproxy/app/app.go`（相对数据源仓库将来所处的位置）能列出文件。

## 2. 产出 `web/dist`（go:embed 的前置，缺了必卡）

```bash
cd loomproxy && make web    # = cd web && pnpm install && pnpm build
```

**验收**：`ls loomproxy/web/dist/index.html` 存在。这一步不产 dist，第 6 步编译会报
`pattern dist/*: no matching files found`（《方案页》§4 的耦合，风险清单第 1 条）。

## 3. 建私有数据源仓库

在私有远端（git.syiism.cc.cd）新建空仓库 `loomproxy-deploy`（**只进私有远端，不进公开远端**——AGENTS §12）。
本地 clone 到与骨架平级的目录：

```
work/
├── loomproxy/          ← 第 1 步的骨架
└── loomproxy-deploy/   ← 本仓库
```

**验收**：`cd loomproxy-deploy && git status` 是干净仓库。

## 4. 落四个装配文件（全文 cp，不要手抄）

正本都在《方案页》，逐字取用：

| 文件 | 取自 | 首轮内容调整 |
|---|---|---|
| `go.mod` | 《方案页》§3.2 第 1 项 | 原样 |
| `main.go` | 《方案页》§3.2 第 2 项 | 原样 |
| `sources/deploy_all.go` | 《方案页》§3.2 第 3 项 | **首轮把 import 块留空**（还没有源包，先证明"库+装配"这条路是通的），第 7 步再填 |
| `Makefile` | 《方案页》§4 | 原样（`SKELETON ?= ../loomproxy` 与目录布局相符） |

另外建 `.gitignore`：`loomproxy-go`、`.env`、`data/`。

**验收**：`grep -c loomproxy go.mod main.go` 都有命中；`main.go` 里除 `loomproxy-deploy/sources` 那行外与骨架 `main.go` 逐字一致。

## 5. 模块联调

```bash
cd loomproxy-deploy
go mod tidy        # 补齐 gin/gorm 等 transitive require 与 go.sum
go mod edit -json | grep -A3 '"Old"'   # 核对 replace 生效
```

**验收**：`go list -m loomproxy` 输出一行且带 `=> ../loomproxy`；`go mod tidy` 无 404/超时。

## 6. 第一次全绿构建（零源形态）

```bash
make build        # web（骨架目录 pnpm build）→ vet → go build，产物 ./loomproxy-go
```

**验收**：`file loomproxy-go` 是 ELF；体积与骨架产物同量级（面板 dist 已嵌入）。

## 7. 实现第一个源包并登记

1. 建 `sources/mynovel/`（包名 = 源目录名），照 AGENTS §5：`init()` 里 `base.RegisterSource(SourceMeta{...})` + `base.Register(...)`，
   内嵌 `base/legado` 基类；启动动作放声明位 `OnBoot`（**不要在包 `init()` 里读 env**——`.env` 在 `app.Run` 才加载）。
2. `sources/deploy_all.go` 的 import 块加一行 `_ "loomproxy-deploy/sources/mynovel"`。

**验收**：`go build ./...` 绿；启动后日志的路由对账里有 `/{你的源码}/{动作}`（缺了就是空白导入没生效，风险清单第 5 条）。

## 8. 本机冒烟（最小运行单元：二进制 + 同目录 .env + data/）

```bash
cd loomproxy-deploy
cp loomproxy/.env.example .env      # 按需改 DB_TYPE=sqlite、JWT_SECRET（默认值+启用鉴权=拒启动，AGENTS §11）
mkdir -p data
./loomproxy-go
```

**验收**：`curl -s localhost:8081/datasources` 返回列表且含你的源；`curl -s -o /dev/null -w '%{http_code}' localhost:8081/panel/` 出 `200`。

## 9. 骨架门禁复算（发版前跑，不是每次提交都跑）

```bash
make skeleton-check    # = 骨架目录 make vet && make test（-race 全量）
```

**验收**：全绿。携带形态的包内单测在骨架 `./...` 里跑不到（源包在数据源仓库），
数据源仓库自己的用例放 `tests/` 并 `go test ./... -race` 一并跑（AGENTS §3 那句"包内单测不被门禁跑到就等于没写"同样成立）。

## 10. CI 接线

取《方案页》§7 的 GitHub Actions YAML（5 步逐字对应 §6 的 CI 流程）放入数据源仓库，
把 `SKELETON_TAG` 改成第 1 步钉的值。**骨架升级 = 只改这一行。**

**验收**：CI 产物 `loomproxy-go` 下载后 `sha256sum` 与本地 `make build` 在**同 tag、同 Go 版本**下可对齐（对齐不了先查 runner 的 Go/Node 版本漂移）。

## 11. 部署

沿用骨架的部署链：`scripts/deploy.sh`（在骨架 clone 里，`DEPLOY_DIR` 指向生产目录）
或按 AGENTS §3 手工换装三查；零停机切换见 [`docs/架构/部署-零停机.md`](../架构/部署-零停机.md)。
`.env` 与 `data/` 留在部署目录、不进仓库。

**验收**：`systemctl is-active loomproxy` 为 active **且** 日志有 `LoomProxy starting on` 关键行（按启动契约核对，不看 is-active 单条——AGENTS §3）。

## 12. 版本纪律（日常循环）

| 事件 | 动作 |
|---|---|
| 加/下线源 | `deploy_all.go` 加/删一行 + 源包 → `make build` → 部署 |
| 骨架出 bug 修复/新版本 | 骨架打新 tag → 改 CI 的 `SKELETON_TAG` + 本地 `git -C ../loomproxy checkout <新tag>` → `go mod tidy` → 第 6/9 步 → 部署 |
| breaking 变更 | 看骨架 release note 的 breaking 清单（《方案页》§3.1 约定）；接口不匹配会在 `go build` 直接编译失败，不会静默 |

## 风险清单：第一次建数据源仓库最容易卡住的 5 个地方

| # | 会卡在哪 | 症状 | 怎么验证没卡住 |
|---|---|---|---|
| 1 | **`web/dist` 不在位**（go:embed 读的是骨架源码目录的 dist，而 dist 不进 git） | `go build` 报 `pattern dist/*: no matching files found` | `ls ../loomproxy/web/dist/index.html` 存在；不存在就回第 2 步 |
| 2 | **replace 形态不对**（相对路径在别的布局失效，或有人删了 replace 想用纯 require） | `go list -m loomproxy` 报错 / proxy 404（module path 无域名，永远拉不到） | `go mod edit -json` 里 Replace 指向**实际存在的骨架目录** |
| 3 | **模块代理不可达**（骨架新增 `go-systemd` 等依赖，国内机默认 `proxy.golang.org` 超时——2026-10-09 实测） | `go mod tidy` 长时间无输出后 `dial tcp ... i/o timeout` | `go env GOPROXY` 含 `goproxy.cn`；`go mod download` 静默完成 |
| 4 | **CGO 关 / 无 gcc**（sqlite3 驱动是 CGO 的） | 编译报 `build constraints exclude all Go files`（go-sqlite3），或运行时 `unknown driver "sqlite3"` | `go env CGO_ENABLED` 出 `1`；`make build` 用着 `CGO_ENABLED=1` 前缀 |
| 5 | **空白导入缺位**（源包写了但 `deploy_all.go` 没登记，或 import 路径打错） | 二进制正常启动，但 `/datasources` 没有你的源、`/{source}/{action}` 全 404——**构建不报错，最阴的一条** | 第 8 步的 `curl /datasources` 含你的源码；启动日志路由对账行点名到它 |

## 回退方法（建不起来就退回老形态，零损失）

老形态 = 单体仓库 + 携带数据源的 `sources/*` 分支（AGENTS §12、骨架的 `make precheck-branch` 就是给它配的）。回退动作：

1. 把数据源仓库 `sources/<源>` 整目录复制回**骨架仓库**的 `sources/<源>`（包导入路径从 `loomproxy-deploy/sources/…` 改回 `loomproxy/sources/…`，只改 import 行）；
2. 骨架 `sources/all.go` 的空白导入加对应行；
3. 骨架目录 `make build` 出产物——之后一切照旧（分支门禁、deploy.sh、tag 纪律都没动过）；
4. 数据源仓库目录归档留底即可——它不持有生产状态：`.env` 与 `data/` 本来就在部署目录，不在它里面。

回退不丢任何东西的前提是**第 3/4 步的文件从未直接在生产上改过形态**：二进制名、部署目录、systemd 单元、`.env` 契约全程未变（变的只有"源码住哪个仓库"）。
