### ① 跑完：身份认出来了，而且把发布的前提改了（维护者批准的"第 0 步"）

- **方法（比"重打比对"便宜且决定性）**：Go 二进制自带 VCS 指纹——装配仓的 `go build` **没有**关 `-buildvcs`，
  所以 `go version -m <二进制>` 直接给出主模块的伪版本。取文件与核对：
  ```
  scp hk:/www/go_project/loomproxy/loomproxy /tmp/prod-loomproxy
  md5sum /tmp/prod-loomproxy          → c2c3253621deee884e275ebbf39d3933（与远端那一遍逐字一致）
  go version -m /tmp/prod-loomproxy   → mod loomproxy-deploy v0.0.0-20261009123835-4b7e96271ae7+dirty
  ```
  **`+dirty` 意味着这一行不能单独当结论**（它只说"基线是 `4b7e962`、工作树当时有未提交改动"，不说改动是什么）。
- **认出改动的是"增删两侧各取一个字面量互证"**（`SOURCE=ee29dab` 那一颗的 `sources/zj_novel/altcha.go`）：
  | 字面量 | pre 树 | post 树 | **线上那颗** |
  |---|---|---|---|
  | `ALTCHA PBKDF2`（S103 新增） | 0 | 1 | **1** |
  | `codeChallenge,omitempty`（S103 删除） | 1 | 0 | **0** |
  | `;base64,`（S103 删除的图码取法） | 2 | 0 | **0** |
  三格互相咬合，**方向唯一**：线上那颗**含 S103 的代码**。
- **所以结论要写成两句，不是一句**：
  ① `ee29dab`（S103）**早在 10-09 22:06 就在线上了**——那次换装是把"还没提交的 S103 工作树"打进去的，
  所以 mod 行才停在 `4b7e962+dirty`。**"S103 没上线"这个本轮写过多次的前提是错的**（本条 ① 之前也是这么写的）。
  ② 而它上线之后现网并没有变好：今日 06:00 起 339 条里 `upstream_status` 带内失败仍 86 条、504 81、429 38。
  **下一件要做的事不是再发一版，是查那 86 条信封里到底是什么业务码**（站方信封 `code:0/4001/401/403/429` 一族，
  S103 明确保留未动）——这条已在装配仓登记为 **S104**（带三种形状怎么分离的取证步骤，全是读）。
