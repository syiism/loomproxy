## P112 GET 那条通路没有"进门判据"，而上游故障时的降级会把这份坏值直接端出去【已收口（判定收口）：② 已落地并上线（`807e1dc`，在 `skeleton-v110` 内）；① 取数 + 代码路径两头都做完，**判为不办**——不是证据不够，是证据说这条路在现网最热的那一段堵着；重开触发条件原文留着】

- **代码事实**（都点得到行）：`FetchJSON` 的写入条件是 `err == nil && cacheKey != ""`（`base/base.go:448`），
  `FetchText` 同形（`base/base.go:533`）——**只看有没有报错与状态码，不看 body 内容**。
  `FetchShared` 后来补的那道 `ResponseFilter`（`base/fetch_shared.go:108-112`）**没有回灌到这两条 GET 通路**。
  第二层更要紧：故障降级读 `getUpstreamCacheStale`（`base/upstream_cache.go:40-48`）**既不判过期也不判内容**，
  调用点在 `base/base.go:456` 与 `base/base.go:540`。
- **形状的来源**：与分支侧 S89 同源（信封站 HTTP 200 + body 里 `code != 0` 的业务失败被当成功）。
  那次是分支在现网实测出来的——一枚坏信封进缓存后，同章后续 15 个请求各 2ms 命中它、每个再报一次"读不了"。
  **教训当时只落在 `FetchShared` 这一条路上，GET 那两条没人回灌。**
- **还没有的那半证据（别把"形状可疑"写成"缺陷已成立"）**：我只在代码上确认"门槛不在"，
  **没量过现网哪个源真的因此端出过坏值**。处置第 0 步是取一次数：
  `api_call_logs` 里按 源×动作 分组数带内失败（`in_band_error`）与"同一 URL 短窗口内重复且耗时 ≈ 0"的组合，
  量完再决定动不动结构。
- **三个出路**：① 把 `ResponseFilter` 同一条口子接到 `FetchJSON`/`FetchText`（改动面大：每个源的"成功"要由源自己声明）；
  ② **给降级那一步加时限**——`getUpstreamCacheStale` 现在**无限期**地端出旧值（它连"过期多久"都不看），
     改成只降"TTL 的某个倍数之内"的值。改动小、不要求骨架认识任何源的成功形状；
     **注意它挡不住"刚写进去的坏值"**（那条只能靠 ①），别把它写成比实际更强——
     我登记时先写的是"只降曾经成功的值"，回代码才看清**写入侧本来就只有 `err == nil` 才写**，
     那句说法站不住，已按代码改掉（判据：出路也要过"回代码验证"这一道，不只缺陷描述要过）；
  ③ 维持现状，但在 `docs/架构/弹性获取栈与环境变量.md` 写明"GET 通路的缓存不做内容判定"（**单独做等于用文档追认可疑行为，不选**）。
- **建议**：先 ②（顺手把"多久以内"做成配置项，默认给一个保守值），① 等它上线后再判要不要办。
  **（②已落地）**：`getUpstreamCacheStale(key, maxStale)` 加了过期时限闸——只端出"过期未超过
  `h.UpstreamCacheTTL × UPSTREAM_CACHE_STALE_MULT`"的旧值；倍数做成环境变量，默认 3、<=0 不限（旧行为）。
  ①（ResponseFilter 回灌 FetchJSON/FetchText）仍待做，那条挡的是"刚写进去的坏值"。
- **2026-10-10 本轮的准备与阻塞（停在执行门前）**：① 的第一动作是条目自己写的「处置第 0 步：取一次数」，
  **本轮没取成——现网只读取数的通路（主机别名与登录方式）在两棵树的仓库里都没有记载**（运维事实按 §1.4 落在
  分支侧操作记录，而那些记录只写"做过四次 ssh"、没写怎么连）。查询本身已经备好，拿到通路就是一条命令的事：
  ```sql
  -- (1) 带内失败与"看着像命中坏缓存"的分布：按 源×动作
  SELECT source, action, COUNT(*) AS calls,
         SUM(in_band_error) AS in_band_failed,
         SUM(status BETWEEN 200 AND 299 AND latency_ms <= 2) AS fast_2xx,
         SUM(in_band_error AND status BETWEEN 200 AND 299 AND latency_ms <= 2) AS fast_in_band_failed
  FROM api_call_logs
  WHERE created_at >= '2026-10-03 00:00:00'          -- 日界给字面量，不让库侧按连接时区归日（判据页那条）
  GROUP BY source, action
  ORDER BY fast_in_band_failed DESC, in_band_failed DESC;

  -- (2) "同一个内容标识被反复快速返回"的取样：坏值若进了缓存，形状就是它
  SELECT source, action, book_ident, chapter_ident, COUNT(*) AS times,
         MIN(created_at) AS first_seen, MAX(created_at) AS last_seen
  FROM api_call_logs
  WHERE created_at >= '2026-10-03 00:00:00'
    AND status BETWEEN 200 AND 299 AND latency_ms <= 2
  GROUP BY source, action, book_ident, chapter_ident
  HAVING COUNT(*) >= 5
  ORDER BY times DESC LIMIT 20;
  ```
  **判读口径先写好**（免得数取回来再找说法）：`(1)` 里 `fast_in_band_failed` 有非零行 = GET 通路确实在
  反复端出同一个坏载荷（带内失败 + 快得像是命中缓存），① 成立、值得动结构；全是 0 而
  `in_band_failed` 集中在慢的那一侧 = 坏值来自上游而不是缓存，① 的性价比就要重排——
  注意**明细表里没有 url 列**，第二查用 `book_ident`/`chapter_ident` 当"同一个内容"的代理，
  这是近似而不是同一件事，写结论时要如实标出来。**被它阻塞的条目**：无（① 是这条自己的后半，不挡别人）。
- **取数已完成（2026-10-10，`ssh hk` + `mysql -uroot loomproxy` 只读，窗口 `created_at >= 2026-10-03 00:00:00`，
  窗口内 86,827 行）**——两条 SQL 都发了，还加发了一条延迟分布与一条"同一标识重复"的取样。读数与结论：
  1. **条目里预设的那格实锤没有量级**：`status 2xx 且 latency_ms<=2 且 in_band_error` 那一列**全表为 0**
     （整个窗口里 `latency_ms<=2` 的行只有 114 条：content 35 / search 64 / chapter 13 / detail 2）。
     也就是说**现网没有在"GET 通路把坏值反复端出"这个形状上受害者**。
  2. **带内失败确实很多，但它们住在另一条通路上**：`zj_novel/content` 19,990 次里 15,263 次带内失败（76%）、
     `wd_novel/content` 1,110 里 991（89%）。查装配仓源码确认 **`zj_novel` 正文走 `FetchShared`**
     （装配仓 `protocol.go` 头部明写"不用 FetchJSON：本包要 POST 带自定义头与体"——**路径不写反引号，它在装配仓那棵树里**），
     而 `FetchShared` 正是 S89 那次补了 `ResponseFilter` 的那条路——**它不是 P112 说的 GET 通路**。
  3. 那批失败里的"快"（同一 `chapter_ident` 重复 20~36 次、`min_ms` 低到 5~8ms 而同批 `max_ms` 到 17s）
     **不是命中缓存端出坏值**，是本地闸门快速返回错误载荷的形状（凭证/ALTCHA 那一族，归装配侧 S102/S103 的在办范围）：
     同一条标识既有 5ms 又有 17s，命中缓存的那一批不会有上游等待，慢的那些才是真打上游。
     **这一格已从"按形状推断"补成按代码路径证明**（同日下半程读装配仓源码，路径都在 `sources/zj_novel/`）：
     (a) 那些快的带内失败全部来自**发上游之前就返回的本地闸门**——`content.go:166` 的
     `contentThrottle.cooling()`、`:179` 的槽位池 `errWindowWait`、`:215` 的 `fallbackLimiter.allow()`、
     `:223`/`:230` 的三件套没成套（注释自己写着"不打上游（白刷只会把 401 读数做实）"）；
     (b) 正文缓存的**进门判据比 `ResponseFilter` 更强**：v2 的写入点在 `storeContentCache`，门槛是
     "解得开才写得进去"（连"信封对但键不对"一起排除），读面 `peekAnyContent` 还要 `json.Valid` 才认
     （`altcha.go:329`），所以一句错误文案**写不进这一层缓存**；
     (c) `protocol.go:532-538` 明写该包的 `ResponseFilter` 声明位**已无使用方**并记了来路
     （S89 那次实测的那枚 `{"code":4001}` 就是这么变成"解得开才落地"的）。
     结论落地：**GET 那两条通路缺的那道内容判定，在现网最热的正文路径上并不缺**——它缺在别处（`FetchJSON`/
     `FetchText` 的调用方），而本轮量到的形状里没有人正在从那里端出坏值。
  **于是 ① 的判定改了**：GET 两条通路**结构上仍然缺那道内容判定**（代码事实未变），
  但本轮取数没找到现网受害者，而补 ① 的代价是"每个源要自己声明成功形状"——
  **建议：① 维持在册但不办，等两件事之一发生再动**：(a) 出现一条带 `in_band_error` 且 `latency_ms` 个位数
  又确实来自 `FetchJSON`/`FetchText` 的现网读数；(b) 下一次动获取栈的重构顺路把它接上（那时边际成本最低）。
  **登记时留的那句"这一格还没按代码路径证明"已经补上了**（(a)(b)(c) 三条见第 3 点），所以现在不是"证据不够先别动"，
  而是**证据说这条路在现网最热的那一段是堵着的**——① 的成本（每个源自己声明成功形状）没有对应的收益面。
  **②（时限闸）已上线就是这条的防线**：它挡不住"刚写进去的坏值"，但本轮量到的量级是 0 次，
  所以那句"挡不住"目前不欠现网账。
