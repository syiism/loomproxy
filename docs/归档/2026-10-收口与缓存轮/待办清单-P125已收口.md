## P125 `check-tag-sync` 现在长期报红：私有侧 `origin_` 缺 `skeleton-v110` 与 `skeleton-v111`【已收口：维护者拍 A（补推）而非我建议的 B，11:5x 推完并复算三目标全齐】

- **现象（2026-10-10 11:3x 现测）**：`skeleton-v111` 推完公开两侧之后跑 `./scripts/check-tag-sync.sh 108`：
  ```
  tag            本地      origin#github.com     origin#gitee.com      origin_(git.syiism.cc.cd)  判定

  ```
  **`v110` 那一行不是我这次造成的**——它是上一场发版就留下的缺口，这次只是被同一条检查第二次念出来。
- **为什么这条不能就这么放着**：这条脚本的设计是"按 **push URL** 展开、逐目标复算"，
  它存在的理由正是"「我推过」不是证据，对端列出来才是"（判据页《下发位置是部署事实》那一族与 AGENTS §3 换装三查第 4 条）。
  **一条长期红的检查与一条没有的检查等价，而且更糟**——它教人的仍然是"无视输出"（门禁台账那句，本轮已经用掉两次）。
- **选项（含"不做"）**：
  A **补推**：`git push origin_ skeleton-v110 skeleton-v111`（一条命令两处，红即消）。
    代价：私有 Gitea 上多两颗粒骨架 tag——如果它本来只该托管装配仓，这就是往错的树上钉东西。
  B **把它从发布目标里摘掉**：`check-tag-sync.sh` 里给 `origin_` 加一条带理由的排除（骨架 tag 的发布目标是公开两侧；
    私有远端承载的是装配仓 `loomproxy-deploy`，与骨架 tag 无关）。代价：以后真需要私有侧也带 tag 时，得记得把排除撤掉。
  C 什么都不选（**不选**：那这条检查从"复算器"退化成"每次都念一遍的噪音"，而它的第一次价值恰恰是当场抓到 v93/v88 那两次失真）。
- **我的建议**：**B**。依据是仓库分离之后版本的正本只剩一处（装配仓 `基线追溯.md` 那句：现役骨架版本由 `build.yml` 的
  `env.SKELETON_TAG` 一处钉），CI 拉的也是公开侧（`https://gitee.com/syiism/loomproxy.git`，本次实测 v111 已在公开两侧）——
  **私有侧带不带骨架 tag，没有任何一条链路读它**；而一条检查里"读它的人不存在"就等于把噪音写成规则。
- **影响范围**：只动 `scripts/check-tag-sync.sh` 的目标清单（或补推两个 ref），不碰生产、不碰装配仓代码。
  **被它阻塞的条目**：无；但它挡着"下一次发版后跑这条检查能否当真"这一件事。
- **发现处**：2026-10-10 推 `skeleton-v111` 之后按 AGENTS §3 换装三查第 4 条复算那次（v110 的缺口是上一场留下的）。

- **为什么维护者选 A 而我建议 B，两种选法差在哪，留一句给下一轮**：
