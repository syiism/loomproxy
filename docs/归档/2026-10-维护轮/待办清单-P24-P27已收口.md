## P24 空态页面照样整段露出「口径说明」长文字，观感差【已处理】（提交号：`63b1cbf`）

- **现象/证据**（维护者报，2026-10-03）：排行榜页各榜无数据时，页面一片空白，底部那段约 11 行、三百余字的
  「口径：两张榜的数字不同义……」照样整段显示。判据本身没错（`web/src/pages/Ranking.vue:48` 确实包了 `v-if`），
  错在**判据选错了**：它判的是 `boards.length`（后端有没有返回「榜的定义」），不是「有没有数据行」。
  各榜的 `rows` 全空时卡片里已经是 `UiEmpty`（`web/src/pages/Ranking.vue:34`），页脚那段却还在。
- **同类落点**（同一手法，全仓清点过一遍）：`web/src/pages/admin/Monitor.vue:87-91`（内容维度表上方「两列口径不同」约 4 行，
  位于 `UiEmpty` 之上、无数据仍显示）、`web/src/pages/admin/Monitor.vue:208`（历史明细上方说明，恒显示）。
  再往上是页顶 `subtitle` 长句（`Interfaces.vue:3`、`Pools.vue:3`、`Datasources.vue:3`）——**页顶不是「空态露长文」，本轮不动**。
  `Datasources.vue`（接入指南页）正文就是页面目的，排除。
- **影响**：纯观感，但它是用户第一眼看到的页面；空态本应只说「这里现在没有数据」。
- **建议修法**：把「有无数据行」作为显示判据（`boards.some(b => b.rows.length)` 之类，一处 computed），
  Monitor 两处同样 gate 到各自列表长度。**先查过耦合**：页脚那段不含 `reveal` 类，列表 key 是 `b.dim`/`it.name`，
  收掉它对观察时机与 key 都无副作用（§10 那条 `reveal` 坑不适用）。
  全仓没有 `<details>`/tooltip 类折叠件（`UiField` 的 `hint` 是恒显小字），本轮**不新建交互件**——
  要「默认收起」是另一件事，别和「空态不显示」混做；两者都做会把文案复制成两份，那需要先并入常量。
- **发现处**：2026-10-03 维护者提的三条之一。
- **已处理（`63b1cbf`）·偏离原建议之处**：原建议只做排行榜那一处，实际按同一手法收了**四处**
  （`Ranking`/`Monitor` 两处/`Profile`/`admin/Datasources`）——维护者说的是「不要出现长文字」这个类，
  不是一个页面；`Profile` 那条尤其该收：用法说明正好挂在「还没有 API 密钥」的空态上面。
  没做折叠件（全仓没有 `details`/tooltip，新建属另一件事）。
  **验证程度要如实写**：本地临时实例复现了「boards=2 而 rows 全 0」这个成因形状，
  但本环境没有浏览器（无 chromium/playwright），所以没做点击验证——接口形状 + 模板条件两级核对，不是 UI 实测。

## P25 同一篇内容在几秒内被重复扣额度：扣减只看状态码，不看内容身份【已处理】（提交号：`013df54`）

- **现象/证据**（维护者报，已用生产库只读取数复核）：2026-10-03 01:46:33 / :35 / :37（间隔 2 秒，共 4 秒窗口），
  某用户 `uxx/content` 三条明细**状态全 200、`book_ident` 与 `chapter_ident` 完全相同、章节标题同为「第01集」**，
  而 `quota_usage_logs` 里对应三条 `cost=1` 的流水——**同一次阅读被扣了三次**。
  耗时是 `10012ms / 1868ms / 1874ms`：**第一条慢到下游放弃，客户端重试同一篇**，这才是它的成因。
  当日全库同类（同用户+同源+同接口+同内容、30 秒内 ≥2 次）共 **13 组 / 27 行**；`fq_novel` 上多是 1~2 秒的两次，
  `uxx` 有 14 秒的两次。规模不大，但每一例都是用户可感知的「额度白扣」。
- **真因（机制）**：`gate/billing.go:76` 的 `succeeded()` 只判 `status==200`，扣减（`gate/billing.go:188` 写流水）
  是**按请求**计费的，代码里没有任何「同内容」的概念。AGENTS §12 已把「按请求计费（含上游缓存命中）」列为有意取舍，
  所以这不是 bug 而是该取舍的**边界外溢**：请求重试与「重读同一章」在用户眼里是同一件事。
- **影响**：免费额度（例：五源 200/日）被重复消耗；用户侧表现为「没读几章就没额度了」。
  下游重试越多，越伤的是刚付费读同一篇的人。
- **建议修法**：给扣减加一道**冷却期**——`uid + 源 + 接口 + 内容标识` 在窗口内只扣一次。三条路与其取舍：
  - **A 进程内冷却 map（推荐）**：`succeeded()` 之后读 context 里的 `CallSubject`
    （`middleware/middleware.go:67` 的 `CtxCallSubject`，`base/legado/observe.go:35-36` 已把 `BookKey`/`ChapterKey`
    从请求参数抽好，uxx 正文即 `bookId`+`itemId`，足够唯一），命中最近扣减即跳过写流水。
    零 DDL、形态可直接照 `gate/ratelimit.go:108-155` 的 map + janitor 抄。代价：单进程内有效（本部署就一个二进制）、重启丢。
  - **B 流水表加内容标识列**：跨进程有效且可审计，但要 DDL + 每请求多一次查询，且并发窗口仍在。
  - **C Redis SETNX+TTL**：跨进程最准、TTL 天然，但要引第二处 Redis 依赖，且 Redis 故障时必须退化为「照常扣」。
  **为什么不能用「查最近 N 秒明细」**：明细行是内存环形缓冲淘汰时才批量落库（`base/metrics.go:131-154`），
  且 monitor 的 `RecordCall` 发生在 billing 返回之后——扣减那一刻**明细行还不存在、id 也拿不到**。
  这条是我自己先想过一遍的弯路，写下来免得下一个人再想。
- **配套**：`conf` 加 `BILLING_DEDUPE_SEC`（0=关，沿用 `envInt` 惯例与「0 表示关」的默认口径），
  同步 `.env.example` 与 `docs/架构/弹性获取栈与环境变量.md`；`AGENTS.md` §9 加一句「额度按内容去重」。
  用例照 `test/quota_integration_test.go:131` 的模板加：同内容窗口内三次只扣一条、换 `itemId` 必须再扣、
  窗口过期再扣、非 200/带内失败不占冷却、匿名与 admin 不受影响；写完做变异验证（§10）。
- **对下游可见吗**：请求仍 200 放行、仍写监控明细，只是不再重复扣额度——是维护者直接要求的口径修正。
- **发现处**：2026-10-03 维护者报（附时间、用户、源、接口），只读复核见上。
- **已处理（`013df54`）·落地口径**：选了上面候选方案 **A（进程内冷却 map）**，
  `gate/dedupe.go` 按 `uid+源+接口+内容标识` 记账，检查与登记**同锁内做**（并发重试不能各自看到「没扣过」）；
  开关 `BILLING_DEDUPE_SEC` **默认 300 秒**（0=退回按请求扣）。
  偏离候选的一处：内容标识除 `bookId`/`itemId` 外还带上**搜索词**，这样「同接口同内容」对 search 也成立。
  自省读数接进 `GET /admin/stats` 的 `billing_dedupe`（挡掉次数/在册键数/窗口）——
  没有这一格，「冷却到底挡没挡」又得靠人肉比流水（P19 的同一课）。
  三条用例 + 变异验证（去掉 billing 那行判断，「三次只扣一条」与「窗口过期再扣」立刻红）。

## P26 控制面不认 API Key：三种鉴权形态只在数据面齐备【已处理】（提交号：`2435f14`）

- **现象/证据**（维护者要求「所有需要鉴权的接口都应该是 token / cookie / apiKey 三形态可用」）：
  清点结果与直觉相反——**网关层三形态齐全（cookie 早就通），控制面反而不认 apiKey**。
  - `middleware/apiauth` → `utils.VerifyAuth`（`utils/auth.go:39-64`）：先 JWT 后 API Key；JWT 取凭证走
    `Authorization: Bearer` → `?token=` → **Cookie `loomproxy_token`**（`utils/jwt.go:17`，登录时由
    `utils.SetTokenCookie` 写，`HttpOnly`/`SameSite=Lax`/`Path=/`）。
  - 控制面 `AuthRequired()`/`AdminRequired()`（`handlers/auth/auth.go:830/846`）→ `parseTokenFromContext`
    （`handlers/auth/auth.go:876`）**只解析 JWT**，完全没有 apiKey 分支。
  - 于是这些端点用 `lp_` 密钥打不进去：`/quota/dashboard`、`/quota/usage-logs`、`/user/source-configs`、
    `/user/import-config`、`/user/redeem`、`/rank/boards`、`/admin/*`。脚本读自己的额度、拉自己的用量，现在做不到。
  - 顺带一条不一致：带过期 Bearer 又没带密钥时，网关文案是「缺少鉴权凭证」而控制面是「登录已过期」（`utils/auth.go:63` vs `handlers/auth/auth.go:876` 路径）。
- **建议修法**：抽一个共用凭证解析（返回 `method / userID / username / sessionID`），网关与控制面都调它，
  会话吊销（`jti` → `auth_sessions`）在函数内单点判。**两条不能松的边界**：
  ① **静态 env 键 = 匿名**（AGENTS §7）→ 不得被注入身份，任何需要归属的端点仍要拒；
  ② **引导类端点保持会话专用**（`/apikey*`、`/auth/password`、`/auth/sessions*`、`/auth/logout`）——
  一把长期密钥若能铸造/撤销别的密钥或改密码，就是提权且无法止血；`/admin/*` 同样只认会话，
  理由是管理面必须随会话吊销立即失效。这两条是对维护者原话的**有意偏离**，理由与影响都记在这里。
- **CSRF 与传输**：cookie 已在参与鉴权，现状靠 `SameSite=Lax` + 状态变更只用 POST/PUT/PATCH/DELETE +
  CORS 不带 credentials（`middleware/transport/cors.go:27-29` 是 `Allow-Origin: *`，浏览器不会为跨源带 cookie）三重压制。
  合并解析路径时**不得放宽 Lax**；cookie 未设 `Secure`（HTTP 部署下明文）是既存的独立风险，另计。
- **配套用例**：受保护端点 × 五形态（Bearer / `?token=` / Cookie / `X-API-Key` / `?api_key=`）参数化跑一遍；
  **反向断言**（会红的那条）：密钥打引导类与 `/admin/*` 必须 401/403；静态 env 键打控制面必须失败；
  cookie 属性（`HttpOnly`/`SameSite=Lax`）被改松即失败。现有 `test/apikey_test.go` 只在数据面验过 `X-API-Key`。
- **发现处**：2026-10-03 维护者提的三条之一；清点由 `middleware/apiauth`、`utils/auth.go`、`handlers/auth/auth.go` 实读得出。
- **已处理（`2435f14`）·偏离原话之处（两条，理由在上面）**：不是「所有端点三形态都开」，而是
  **用户面端点全开（`/quota/*`、`/user/*`、`/rank/boards`），凭证引导类与 `/admin/*` 只认会话**。
  实现走的是建议的共用解析（`utils.Credential` + `resolveJWT`/`resolveAPIKeyWithCredential`，
  对外 `VerifyAuth` 与 `AuthenticateAny`），新增守卫 `auth.AuthOrKeyRequired()`；
  顺手统一了两层不一致的缺失凭证文案（现在会提到 Cookie）。
  用例 `test/three_forms_auth_test.go` 做了三次变异验证：三组守卫退回 `AuthRequired()` → 密钥形态 401；
  去掉 env 键的归属检查 → 匿名静态键 200 进得去 `/quota/dashboard`；cookie 放宽成 `SameSite=None`+非 HttpOnly
  → 属性断言红。**每条反向断言都配了「同端点用会话必须可用」**，否则「被拒」可能只是守卫整个坏了。

## P27 数据库连不上时服务不拒绝启动，而是跑到缓存预热里 panic（崩溃循环会被 `Restart=always` 读成「运行中」）【已处理】

- **现象/证据**（2026-10-03 本地搭临时实例时撞到，非猜测）：`.env` 里把 SQLite 的路径写错（`DB_NAME` 填成了绝对路径，
  而 `db/db.go:49` 的口径是 `filepath.Join(DATA_DIR, DB_NAME+".db")`），启动日志第一行是
  `WARNING: Database init failed: failed to connect database: unable to open database file`，
  随后照常打印中间件链、`LoomProxy starting on [::]:18081`，**紧接着 panic**：
  `gorm.io/gorm.(*DB).getInstance` 空指针 → `handlers/catalog.(*DatasourceHandler).Handle`（`handlers/catalog/datasource.go:108`）
  ← `app.prefillDatasourcesAnon`（`app/app.go:586`）← `app.prewarmCache`（`app/app.go:565`）← 独立协程。
  进程退出，`main.go:27` 那句 `log.Fatalf("Server error")` 根本轮不到。
- **真因**：`db.Init()` 的失败被**降级成一条 WARNING** 就继续装配。装配层其实**有** nil 检查
  （`prewarmCache` 开头就写着 `if db.DB == nil`），但它挡不住这种形态：
  `db.DB = gorm.Open(...)` 失败时那个指针**非 nil、内部却没装配完**，于是检查通过、一路走到
  `DB.Where` 里才炸（panic 栈上 `getInstance` 的接收者是个有效地址，正是这个意思）。
  **`== nil` 判不出「半初始化」**——这条比「少一个检查」更值得记住。
- **影响**：换装现场看到的是一串栈，而不是一句「数据库连不上」；再叠上 `Restart=always`，
  `systemctl is-active` 会显示 active，把崩溃循环伪装成运行中（`docs/运维/构建与部署.md` 的换装三查第三条
  就是为了这个，但**更好是让服务自己拒绝起来**）。生产若出现 DB 抖动，网关与静态路由还会「看起来活着」，
  实际每个请求都 500。
- **已处理**（修法即下面第一条：`log.Fatalf` 拒绝启动）：验证方式是**直接跑坏配置**——
  把 `DB_NAME` 写成绝对路径起一次，现在第一行就是
  `数据库初始化失败，服务拒绝启动: failed to connect database: unable to open database file: no such file or directory`，
  进程不再走到 panic。行为侧的代价（DB 故障时静态路由也不再可用）见下面「建议修法」原文，未改。
- **原建议修法**：**没有数据库就不要启动**——`db.Init()` 失败改成 `log.Fatalf("数据库初始化失败: %v", err)`，
  并把这条写进 `docs/运维/构建与部署.md` 的启动契约（起不来时第一行应该是什么）。
  代价：`/announcement`、`/data` 这类不依赖库的路由在 DB 故障时也不再可用——但它们本来也不是故障时的价值所在。
  如果确实要保留「DB 挂了仍能提供静态通道」的形态，那就把预热与所有 `db.DB` 入口显式 nil-guard 到底，
  并让 `/healthz` 报 degraded；**别选第三条**：现在的「一半检查一半不检查」。
  顺带把 `DATA_DIR`/`DB_NAME` 的拼接口径在 `.env.example` 写成人话（sqlite 时 `DB_NAME` 是不带扩展名的文件名）。
- **发现处**：本轮为验证 P24 的空态形状而搭本地实例时踩到；那台实例后来用正确的 `DATA_DIR` 起成功了。
