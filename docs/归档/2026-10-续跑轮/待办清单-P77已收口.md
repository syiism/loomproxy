## P77 号池的两条后台路径直接调源写的钩子却不 recover——一个源解析畸形响应 = 整进程重启【已处理】

- **状态**：已处理 `cc2aa72`（第十九遍巡检撞出；门禁 `MAKE_EXIT=0`，`-race` 套件全绿）。
- **现象/证据**：`base/pool/state.go` 里 `Start()`（启动装填 + 转正首个活跃号 + 补齐冷备）与
  ticker 协程里的 `Maintain()`，都在直接调 `Provider.Create` / `Refresh` / `Claim`——那是**数据源包写的代码**。
  这两条路径都不在任何 Recovery 中间件覆盖范围内（gin 的只兜请求链），panic 于是终止整个进程。
  **修前证据**：注入一次 `Refresh` panic，用例直接把测试二进制打停（`panic: 模拟源实现 panic（刷新）`，
  栈顶是 `base/pool.(*Pool).refresh` ← `Maintain`）。
  同一原则在本仓已落地两次：`base.RunSourceBoots`（源启动钩子逐个 recover，注释明写
  「单个钩子 panic 不拖垮启动」）与 `app.callSourceHandler`（聚合搜索逐目标 recover，
  注释明写「不让六个源里有一个坏了显示成网关坏了」）。号池是第三处，也是唯一一处**长期跑**的。
- **修法**：`base/pool` 加两处，判定与状态机一字未动：
  - `guardPanic(what string)`：`defer` 用法，recover 后记一条 `ERROR: 号池 <名> 的<路径>panic 已拦下…` 带堆栈，
    **只跳过本轮**——临期号下一 tick 还会再试，与既有的「刷新失败下轮再试」是同一条规矩。
  - `locked(fn func())`：内部 `Lock` + `defer Unlock`。这一半是 recover 那半的前提：
    原来的三段显式 `Lock`/`Unlock` 会被 panic **穿着跑出去**，锁永久 held——
    加了 recover 也只是从「崩」变成「这个池不再维护、而进程活着、面板数字还在」，更难发现。
    `Maintain` 的燃烧型主体因此收成 `maintainBurnLocked`（只为给 defer 一个落点）。
- **对外可见的语义变化（写明）**：从「源 panic → 进程退出（`Restart=always` 秒级重启，连带中断全部在途请求）」
  变成「源 panic → 一条 ERROR 日志 + 该池本轮跳过」。选这个方向的理由与另两处先例一致；
  如果维护者更想要 fail-fast（宁可崩也不要带着半坏状态继续跑），说一声，这是可以单独撤销的一处 defer。
- **用例**：`test/pool_panic_guard_test.go` 两条（`TestPoolMaintainSurvivesProviderPanic`、
  `TestPoolStartSurvivesProviderPanic`）——各验三件事：panic 只留一条 ERROR、**锁已放开**
  （用带超时的 `HotCount` 问，拿不到即红）、拦下之后下一轮照常工作。
  假 Provider 加了故障注入位 `panicRefresh` / `panicClaim`（`test/pool_test.go`）。
- **发现处**：第十九遍巡检（判据「这段代码跑在哪条通路上，谁兜它的 panic」）。
- **被它阻塞的条目**：无。
- **答复后回写位置**：机制本身已收口，但**那两处 `defer guardPanic` 是一次替你做的运行时语义选择**，已按 §3b 登记成报告 §8 的一条（选项 A 保留 / B 改回 fail-fast / C 连续 3 轮 panic 才 fatal / D 不拍即 A）。拍成 B 或 C 时回写本页与 `docs/规范/踩坑判据.md` 那条新条目的「固化」段——**判据要跟着口径改，不能留两处矛盾**。
