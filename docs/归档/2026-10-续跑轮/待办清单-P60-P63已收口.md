## P60 设置项的 `type` 只在校验 `json` 时才管值；bool 判据有两套，同一个 `True` 在两个开关上结果相反【已处理 `3bc078d`】

- **现象/证据**：`type` 这一列在设计里是**行为声明**（AGENTS §10），但写入端只有 `json` 真的按它校验值
  （`UpdateSetting` 里只有 `if setting.Type == "json"` 一支），`bool` 与 `number` 是"存什么就是什么"。
  同时读取端对 bool **有两套判据**：`getSettingBool`（`register_enabled`）去空白又转小写，
  而 `deviceWatchEnabled` / `auto_block_enabled` / 「设备与密钥」那三处是精确 `== "true"`
  （`handlers/auth/device_watch.go:65`、`middleware/ipblock/autoblock.go:36`、`handlers/admin/devices.go:199`）。
  合起来的后果：库里存进 `True`（面板手敲、或运维 SQL）时，`register_enabled` 读成"允许注册"，
  `device_watch_enabled` 读成"没开"——**同一个值两个开关相反**，而面板只显示那个值，不显示它被读成了什么。
- **现网校过再动手**（生产只读）：五个 `bool` 键的存值全是 `true`/`false`，`number` 键全是整数
  （含 `jwt_expire_hours=-1`），所以「按 type 校验值」在今天**不会拒掉任何一行存量**——
  这条与 P53 的接线一样，是先量过再改，不是拿现网试错。
- **改了什么**：
  - 新增 `normalizeSettingValue(type, raw)`：`json` 委托给原有 `normalizeJSONValue`（判据不变），
    `bool` 只接受 `true`/`false`（去空白、忽略大小写）**并归一存储**，`number` 必须是整数；创建与更新走同一条。
  - **只管形态不管语义**：`0` 与负数都是合法整数——把 0 当非法就正是 P48 那一族自己犯过的错
    （`jwt_expire_hours=-1` 还是在用的"永不过期"）。
  - 读取侧 bool 判据收成一处 `db.SettingBool(key, def)`，四处调用点全部改走它；
    归一存储 + 统一判据双保险：即便库里躺着历史遗留的 `True`，所有读取方也给同一个答案。
- **验收**：`test/setting_value_validation_test.go` 四段——合形态的 `TRUE` 收下且**存储值归一成 `true`** →
  `1`/`yes`/`on`/`开启` 一律 400 且**没把库改坏**（拒了之后存储值仍是 true）→
  `-1` 与 `0` 合法、`五个` 被拒 → 绕过 API 直接写库写一个 `True`，
  `db.SettingBool` 与「设备与密钥」读数（过去是精确比较）给出同一个答案。
  变异五次各拦一处：不校验 bool 值 / 收下但不归一 / 把 0 当非法 / 读数侧退回精确比较 / `SettingBool` 不做大小写。
- **发现处**：本轮 §4b 第七遍（P48 修完之后继续问"同一族的别处还有吗"：设置项的声明与读取）。

## P61 整数设置的读取有三份实现，三份的静默面不一样；其中一份把超长数字串溢出成负数当真使用【已处理 `3bc078d`】

- **现象/证据**：P48 给 `handlers/auth` 那份 `settingInt` 加了出声，P60 把 bool 判据收成一处，
  于是回头按**行为**数"整数设置被谁解析"（第七遍），发现另外两份一直没人管：
  `handlers/verify/verify.go:57` 是手写的逐字符十进制解析——任何非数字字符（含粘贴进来的首尾空白）
  与 0 都**静默**回默认，而 `n = n*10 + digit` 在超长数字串上 wrap：
  变异验证时实测 `"99999999999999999999999"` 得到 `-8814407034` 并被当成"验证码有效秒数"用（负数！）；
  `middleware/ipblock/autoblock.go` 那份是 `strconv.Atoi` 配 `, _` 再 `<= 0` 兜默认，
  空值、`0`、`"3O"` 三种全静默。合起来：**同一个填错的值在三个开关上是三种不同的"悄悄不按你填的走"**。
- **现网校过再动手**（生产只读）：`verify_send_interval_sec=60`、`verify_daily_send_limit=10`、
  `verify_code_ttl_sec=600`、`verify_code_max_attempts=5`、`auto_block_threshold=20`、
  `auto_block_window_sec=60`、`device_watch_window_days=7`、`max_active_sessions=5`、
  `suspect_distinct_ips=10`——九个键全是正整数，收成一处读取口在今天**一行都不会改变生效值**。
- **改了什么**：
  - 新增 `db.SettingInt(key, def)`：空/非整数/非正数三态各自出声（复用 P48 的 `NoticeReplacedSetting`，
    同一种替换只喊一次），并 `TrimSpace`；`handlers/auth`、`handlers/verify`、`middleware/ipblock`
    三份本地实现全删，共 9 个调用点改走它（auth 3、verify 4、ipblock 2）。
  - **语义一点没动**：`0` 与负数仍按默认走——"0 该是什么意思"是 P48② 那件还没拍的事，
    拍的时候只改这一处（这正是收口的全部意义）。
  - `make vet` 的 `settings-readers-check` 加第二条：源码里出现 `Atoi(db.GetSetting(`
    或本地 `func settingInt(` 即构建红。模式刻意只覆盖已知的两种写法，不做宽判据。
  - 这条是**同一个形状被修到第三次**，所以按 AGENTS §10 的阶梯直接从判据升到机器拦截。
- **验收**：`test/setting_int_family_test.go` 断言走在**另外两条通路**上（auth 那一族由
  `setting_fallback_notice_test.go` 钉）：`GET /verify/config` 的 `ttl` 回显 + `ipblock.RecordFailure`
  的"第几次拉黑"。五段——带空白的合法值 `" 900 "` 生效且不吭声 → 填 `0` 仍按 600 但出声一次 →
  超长数字串按 600 且出声（改前是那个负数）→ 阈值 `" 5 "` 时第 5 次 403 就拉黑（改前悄悄按 30）→
  阈值「两个」时 6 次不拉黑 + 出声 + 重复读不再喊。用例自己把动过的键还原成 seed 值。
  变异五次各拦一处：去掉 `TrimSpace` / 「不是整数」不出声 / 「非正数」不出声 /
  退回手写逐字符解析 / 去掉出声去重。
- **还留着的一处（不在骨架里）**：按同一条判据横着扫本仓的**携带形态**，撞见**第四份**实现——
  分支的 `sources/uxx/adcooltune.go` 也有一份本地 `settingInt`，而它的语义与骨架这份**不同且刻意不同**
  （0 在那里是"还没有边界证据"的哨兵，冷却本身也可以被设成 0）。
  后果是可证的：**下一次 `main` 合进 `sources/private` 之后，分支的 `make build` 会红在新加的那条扫描上**。
  这一处**本轮没在骨架里替他改**（改法要动分支代码，且需要一次真实的合并作载体），
  登记为待办清单 P63 + 分支侧 S50，出路见 P63。
- **发现处**：本轮 §4b 第七遍（P60 之后继续问"这个判据在代码里还有几份实现"）。

## P63 允许 0 的整数读取口：0 在有的键上是哨兵，不是笔误（P61 扫出来的第四份实现，长在分支里）【已处理 `ffa1798`】

- **现象/证据**：P61 收口之后按同一条判据横着扫携带形态，第四份实现在 `sources/uxx/adcooltune.go`。
  它**不是复制粘贴**：`settingInt(settingAdCoolLo, 0)` / `(settingAdCoolHi, 0)` 用 0 表示
  "还没有边界证据"（判据里写着 `if hi == 0 || w < hi`），`settingInt(settingAdCooldown, 10800)`
  允许管理员把冷却设成 0 = "不设冷却"。而 `db.SettingInt` 把**非正数一律当"没配"**——
  直接换过去会让"设成 0"变成"每次等三小时"，那是借收口之名改行为。
- **不改的后果是可证的**：新加的扫描按名字拦 `func settingInt(`，所以**下一次 `main` 合进
  `sources/private` 之后，分支的 `make build` 会红在这一行**。合并、打 tag、上线都要授权，
  所以这条必须先把骨架侧的出口准备好，否则那一次合并注定带着一颗红的构建。
- **改了什么**：新增 `db.SettingIntNonNeg(key, def)`——与 `SettingInt` **只差合法下界**（0 vs 1），
  两条共用一个实现 `settingIntFloor`（这一整轮的病因就是"同一个判据抄三遍"，不能再犯第四次）。
  空/非整数/负数仍按默认并出声，**0 按 0 走且不出声**。负数两边都不收：它不属于任何已定义口径。
  合法域的上界仍归调用方。**没有替 P48② 拍板**——反而给那一问补上了缺的实例：
  同一个字面值 0，在"会话上限"上更像笔误，在"标定边界/冷却时长"上是哨兵，
  所以判据应当写在**读的那条函数名**上，而不是写在一个全局的"0 算什么"。
- **分支侧的落地（尚未做，需要一次真实合并作载体）**：等这条合进 `sources/private` 之后，
  把 `adcooltune.go` 那三处读取改成 `db.SettingIntNonNeg` 并删掉本地 `settingInt`，
  再跑一次 `make build` 与该源的标定用例。细节与选项记在分支侧 **S50**。
- **验收**：`test/setting_int_nonneg_test.go` 五段——`"0"` 生效为 0 且**不出声**（写进库后**读回存值**
  确认样本真的落到了 0，判据同「0 有业务含义的列必须 Create 后读回来」）→ `"42"` 静默生效 →
  `"-1"` 按默认并出声 → 非整数与空值都出声 → **对照**：同一个 0 在 `db.SettingInt` 那边仍按默认并出声
  （这一条专门防止有人把两条"顺手统一"）。变异六次各拦一处：下界改成 1 / 共用实现里把 0 当越界 /
  `SettingInt` 也允许 0 / 越界不出声 / 非整数不出声 / 空值不出声。
- **发现处**：P61 收口后继续横着扫（第四份实现在携带形态里），分支侧 S50 是它的另一半。
