## P82 `CACHE_TTL` 一名两用：既是缓存存活期，又被拿去当 Redis 的 socket 读超时【已处理】

- **状态**：已处理 `c99e257`（第二十一遍巡检撞出；与 P81 同一次改动）。
- **现象/机制**：`utils/cache.go` 构造 Redis 客户端时写的是
  `ReadTimeout: time.Duration(conf.Config.CacheTTL) * time.Second`。
  于是 `CACHE_TTL` 同时决定两件事：**键活多久**（运营口径）与 **Redis 卡住时一个请求最多挂多久**（网络参数）。
  现网实测 `.env` 里 `CACHE_TTL=300` ⇒ 那个读超时是 **300 秒**，而 go-redis 的库内默认是 **3 秒**。
  没有任何报错，只是"调一个参数，动了一个没打算动的东西"。
  同族的另一面是待办清单 P70（`period` 写进去、存下来、面板当单位显示，而没有任何判定读它）——
  那条是"有写无读"，这条是"一读两用"。
- **现网有没有活症状**：**没有**。14 天 journal 里 Redis 相关只有 72 条"命名缓存已接入 Redis"的 info 行，
  0 条超时/连接错误 ⇒ Redis 一直是快的，这条是机制登记。
- **修法**：`ReadTimeout` 给它自己的值 10 秒（与已硬编码的 `WriteTimeout: 3s` / `DialTimeout: 3s` 同量级），
  `CACHE_TTL` 从此只管存活时间；`.env.example` 在参数旁边写明这件事。
  **没有新增配置项**：socket 超时是部署事实而不是运营口径，与它的两个兄弟保持一致。
- **用例**：`TestCacheTTLNotUsedAsNetworkTimeout` 扫 `utils/*.go`：任何 `Timeout` 行引用 `CacheTTL` 即红。
  为什么扫源码而不是构造客户端——用例环境没有可连的 Redis，而这条改动本来就是
  "初始化那一次赋值取了谁"，判据落在那个表达式上最直接。
  变异：把那行改回 `time.Duration(conf.Config.CacheTTL) * time.Second` → 用例点名到 `utils/cache.go:95`。
- **发现处**：第二十一遍（判法「这条调用带的是谁的 context、超时从哪来」，从号池那条线路上顺手看到的）。
- **被它阻塞的条目**：无。
- **答复后回写位置**：不需要答复（已收口）；若要把读超时做成配置项，那要同时给 Write/Dial 一起做，
  别只开一个口子（三个兄弟一名一义才有意义）。
