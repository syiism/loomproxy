## P65 `PageHeader` 的 actions 插槽能把整页顶出视口：Ranking 在 390 宽实测 414px【已处理 `995cf06`】

- **现象/证据**（第八遍浏览器探针）：22 条路由 × 两档视口逐个走一遍，`/panel/ranking` 在 390 宽下
  页面级 `scrollWidth=414`（横向溢出 24px），越界元素是 `PageHeader.vue:7` 的 actions 容器（398px）
  与它内部那个不换行的 `flex items-center gap-2`——里面并排三个 `w-auto` 的下拉。
- **真因**：flex 子项默认 `min-width:auto`，**不肯缩到内容宽度以下**。插槽内容一旦超过可用宽度，
  父容器上的 `flex-wrap` 救不了它——单个子项本身就是超宽的，没有可断点。
  共享件把这一条兜住之前，每个用 `#actions` 的页面都要各自踩一次（本仓有六处用它）。
- **改了什么**：`PageHeader.vue` 的 actions 容器补 `min-w-0 max-w-full`（兜一层，让"要么换行、
  要么在我的宽度里排"成为插槽内容必须满足的约束）；`Ranking.vue` 那个下拉组补
  `flex-wrap` + `min-w-0 max-w-full`（内容侧才是真正能断行的地方，两处都得改，只改一处仍会溢出）。
- **验收**：改后同一条探针——`/panel/ranking` 390 宽 `scrollWidth=390`、越界元素 **0 个**；
  22 条路由 × 两档重跑，**页面级溢出 0 项**。
  判据补进踩坑判据「窄屏排版」那一族：**共享件的插槽要给宽度约束，插槽内容要给自己可断行**。
- **发现处**：本轮 §4b 第八遍（第一次把「拿浏览器把面板真看一遍」当成巡检手段——
  它捞到了 P64 与 P65 两条，这两条都不会自己报错，也不在任何用例的通路里）。

## P66 账号观察的两个时刻后端一直在发，面板从不显示（第六遍留下的那条交接）【已处理 `0b37985`】

- **现象/证据**：`handlers/auth/account_watch.go` 的快照带 `first_seen`/`last_seen`，
  `/admin/security/attempts` 也原样下发（本轮用只读 GET 复看过两条账号记录，字段都在），
  而 `web/src/pages/admin/BlockedIPs.vue` 那一节只有 登录标识 / 尝试 / 失败 / 不同 IP 数 / 来源样本 五列。
  这是 P58 那一族的又一处：**后端给了、前端没人接**，三层各自都"对"，合起来功能是缺的。
- **为什么值得接上（不是为了好看）**：账号侧要不要独立闸门（P40①）还没拍，
  而那道闸门要分的正是**时间跨度**——同一个标识"今天 8 次"摊在三天里与挤在一分钟里是两件事；
  只有三个计数时这两种长得一模一样，而"慢速试"恰好是现在这条按 IP 限频的盲区（AGENTS §7 明写着不按账号锁）。
- **改了什么**：两列 `hidden md:table-cell`（与同页「来源样本」同一条窄屏纪律），
  用现成的 `fmtDate`，页脚那句话补上"这两列给的是跨度"。**零后端改动、零 DDL、不做任何处置**——
  这一节仍然只报材料，踢不踢人等 P40①。
- **验收**（`/tmp` scratch 实例 + headless Chromium 两档）：造 3 次错密码 + 2 次成功登录之后，
  宽屏 1280 那节七个表头全是 `table-cell`、首行两列读到 `2026-10-05 03:02`；
  窄屏 390 下这两列与「来源样本」一起 `display:none`，**页面级溢出仍为 0、0 个页面异常**；
  顺带确认 `fmtDate` 吃得下后端那种带 9 位小数的 RFC3339（渲染成分钟精度，不是裸时间串）。
- **发现处**：第六遍巡检留下的交接条目；本轮第九遍把面板点开后顺手闭环。

## P67 发码失败两头都不说：给用户的那句是对的，但服务端也不知道为什么发不出去【已处理 `98ecc7b`】

- **现象/证据**（读代码找「不会自己报错的错」）：`handlers/verify/verify.go` 里
  `Issue()` 遇到 `getSender().Send()` 失败时**把 err 整个丢掉**，只回一句固定文案
  「验证码发送失败，请稍后再试」；`handlers/verify/router.go` 的 default 分支那句注释
  还写着「msg 已面向用户脱敏」——**这一半是对的**（`/verify/send` 是公开端点，
  不该看见 `sender.go` 拼出来的「发码平台返回 500: <响应体前 200 字节>」）。
  问题是另一半：这条错误**也没有任何服务端日志**，而 `verification_codes` 里又不留行，
  于是"发不出去"在系统里等于零痕迹——连不上、被平台拒、200 但没含成功关键字三种成因
  在库里长得一模一样。
- **为什么不适用「带内错误」那套判据**：P22/P23 管的是"200 却写着失败"（响应骗人）；
  这里是响应诚实、**服务端失明**。同一条纪律的另一面：AGENTS §10 已写着
  「审计类写入不许吞错」——只为留档而写的表插入失败必须打日志；这条是它的镜像：
  **给用户的安全文案与给运维的归因是两份信息，只做其一就是吞错**。
- **同一条判据横着扫出来的另外两处**（判据与做法见下面 P49 的第十一遍）：
  - `Issue()` 里 `db.DB.Create(&row)` 失败——通道**已经把码发出去了**，库里却没这一行，
    那张码从此不可校验；原来同样只回一句「验证码写入失败，请稍后再试」，无日志。
  - `utils/apikey.go`：`First(&ak)` 的任何错误（含 `no such table`、连接断、方言报错）一律回
    「API Key 不存在」，且 `First(&user)` 的读失败与 `user.Status == 0` 共用一个 `||` 回
    「归属用户不可用」。**这就是 P47 注释里警告过的那个形状**：库出问题时每条密钥都像坏了，
    而服务端一片安静，现场只能怀疑用户。
- **改了什么**（三处同一个形状：**出声的位置是日志，对外一字不改**）：
  发送失败 → `log.Printf("ERROR: 验证码发送失败（通道=%s 场景=%s）：%v", sender.Name(), scene, err)`；
  落库失败 → `log.Printf("ERROR: 验证码落库失败（通道已发出，这张码将不可校验）：%v", err)`；
  密钥查询 → 先 `errors.Is(err, gorm.ErrRecordNotFound)` 分清"查不到"与"查不动"，
  后者出一条带原始错误的 ERROR，两条对外文案（「API Key 不存在」/「归属用户不可用」）**逐字未动**。
  刻意**不记 target**（用户邮箱/手机号），那属 §11 的边界：运维事件不需要它进 journal。
- **验收**：`test/verify_send_failure_test.go`——本地 `httptest` 起一个只会 500 并回吐
  `UPSTREAM-INTERNAL-DETAIL: token=…` 的假"发码平台"，`verify_provider=http` 指过去，
  然后打公开的 `/verify/send`。四段断言：
  ① status 400 且 msg **逐字**等于那句固定文案，且不含上游内容（四个子串逐个查：状态码、
  响应体标记、`Internal`、`token=`）；② 服务端日志里要能读到「通道=http」与上游状态码；
  ③ 那行日志里**不得**出现收件地址；④ 失败不留验证码行（先发送成功才落库的顺序没被改动）。
  末段还自己数了一遍"确实有失败经过这条通路"，防止整条用例空转。
  **A** `sqlite` 的 `BEFORE INSERT` 触发器把 `verification_codes` 的写入钉死 →
  响应仍是那句固定文案且不含任何库细节（六个字样逐个查），而日志里必须有「验证码落库失败（通道已发出」；
  **B** 用 `ALTER TABLE api_keys RENAME` 把表临时藏起来（本地测试库，`t.Cleanup` 改回）→
  调用者拿到的仍是「API Key 不存在」，但日志里必须有「校验查询失败」且带着 `no such table` 原文；
  藏表之前先跑一次**真的不存在**的密钥，断言那一声**不出**——这条才是"分得开"的正面证据，
  否则整段只是在测"有没有日志"。变异共九次各拦一处：不出声 / 归因带上 target / 把上游细节回给用户 /
  让 httpSender 不看状态码（假成功，通路就断）/ 落库失败不出声 / 落库失败的库细节泄给用户 /
  密钥查询不分成因一律出声 / 密钥查询完全不出声 / 把对外的两句文案改掉。
- **发现处**：本轮第十一遍巡检（挑「失败路径没有归因」这一族横切扫，第一个样本就是它）。

## P68 接口缓存的 Redis 段坏了不吭声：`Set`/`Del` 连返回的错误都没接，`Get` 把「连不上」与「没命中」回成同一个值【已处理 `1868819`】

- **现象/证据**（读代码找「不会自己报错的错」，判法见下面 P49 第十二遍）：
  `utils/cache.go` 里 `Set` 是 `c.redis.Set(ctx, key, data, ttl)` ——**返回值直接丢掉**；
  `Get` 是 `val, err := c.redis.Get(...).Result()`，然后 `if err == nil {…}` 否则 `return nil, false`。
  于是 Redis 挂掉（或超时、被拒）之后：写侧从此不再持久化却没有任何痕迹，读侧的
  「连不上」与「这个键没有」长成同一个 `(nil,false)`——这正是 P56 那条
  「辅助函数只返回计数或布尔：失败与本来就没要做的事长成同一个值」在缓存里的复发。
  同一趟扫描（第十二遍）又在同一个文件里找到第三处：`Del` 也是整个丢掉返回值
  （`c.redis.Del(ctx, key)`）——**这一处比 Set 失败更要紧**，因为 `Del` 是失效通路，
  悄悄失败等于「撤销返回成功、缓存照样命中」，正是 `utils/apikey.go` 注释里警告过的形状。
  咬人的时机也是现成的：接口缓存静默失效 → 上游被打穿一层而读数看不出来；
  命名缓存那一侧还会在重启日志里说一次「纯内存」（P16 那格），这一侧连那一句都没有。
  `Close()` 那一处**刻意不接**：那是收尾，报给谁都没意义（记下判据免得下一轮又来"补"它）。
- **改了什么**（**只加观测，不改任何行为**）：
  - `Cache` 里加两个 `redisState{fails atomic.Int64; bad atomic.Bool}`，写侧/读侧各一份；
  - 出错时计数，**只在好→坏翻转时出一条 ERROR**（累计次数写进那句里），
    恢复时出一条不带 `ERROR:` 前缀的「已恢复（此前累计失败 N 次）」——
    判据取自 P36/P48：热路径上每次都喊，会把真正该看的读数泡坏；
  - `Cache` 里因此有三份独立状态：`rSet`/`rGet`/`rDel`（写、读、失效），**不并成一份**——
    并起来之后"Redis 只是写不进去"与"读也全废"在日志里就分不开了；
  - `Get` 侧先把 `redis.Nil`（**正常未命中**）从"故障"里摘出去：`errors.Is(err, redis.Nil)` 不出声也不计数。
    这一条是整件事的核心：没有它，"出声"会变成"每未命中一次喊一次"。
- **验收**：`test/cache_redis_notice_test.go` 走**真实生命周期**——自己起一份 Redis
  （随机空闲端口、`--save ""`、`--dir t.TempDir()`，**绝不碰机器上 6379 那个**），
  打通缓存→①**先**在活着的时候查一个必然没有的键，断言不出声（这条必须排在弄挂之前，
  否则测的是"连不上也出声"，与混判无关——第一版我就是这么排错的，被自己的用例抓回来了）；
  ②杀掉 Redis；③连做三轮读写，断言「写入失败」「读取失败」各**只出一声**且带成因（`connect` 字样），
  并断言那声是 ERROR；④原地重启 Redis 重试到成功，断言出现「写入已恢复」且带上此前累计次数。
  ③ 里每轮都各做一次 `Set`/`Get`/`Del`，断言三种失败**各只出一声**（三句分开断言，
  不是"日志里有失败"这种糊的写法）；④ 恢复阶段除 Set/Get 外还单独走一次 `Del`，
  否则会漏验失效侧那一声——**第一版就是这么漏的**（跑到④报「Del 侧恢复没出声」，
  那是用例排错而不是产品漏，已按断言补齐）。
  全局 `conf.Config` 的 Redis 三项**记下并在 `t.Cleanup` 里还原**（P57 的教训）；
  没有 `redis-server` 的机器直接 `t.Skip`，**不拿断言伪装通过**。变异五次各拦一处：
  写侧不出声 / 读侧把 `redis.Nil` 也当故障 / 去掉翻转去重（每次都喊）/ 恢复不出声 / 读侧完全不接错误。
  （`Del` 那一份与写侧同形，被①③④的三条断言一起盖住；单独变异它同样红。）
- **一处环境坑顺手记下**：本机 Go 是 `go1.27.1-X:nodwarf5`，它的 `os/exec` **没有 `Cmd.Kill` 这个方法**
  （`Cmd.Process.Kill()` 与 `Cmd.Cancel` 都在）。已在测试里写明别"顺手改回"，否则换人接手就是构建红。
