## P55 保留期归档与明细删除不在同一个事务：一次删除失败就让「历史累计」永久性虚高【已处理】

- **现象/证据**（承接 P54 那条交接：「`api_call_stats` 与明细是不是两处写同一份数」）：
  先说结论的前半——**不是双写同一份值**，`api_call_stats` 是「已清理明细的累计归档」，
  `lifetimeCounts` = 归档 + 现存明细 + 未落库内存，两种模式下都不重不漏（这条设计是对的，`app/monitor.go:71` 的注释也没说谎）。
  但顺着这条线读 `PurgeExpiredCallLogs` 撞出了真的那个：**逐行 `Save` 归档 → 然后单独一条 `DELETE`**，
  两步各写各的。只要那次删除报错（锁等待、连接抖、语句被挡）或进程正好在两步之间崩，
  就会出现"归档里已经有这批数、明细里它们也还在"——
  ① `lifetimeCounts` 当场开始**永久性虚高**（同一批行被算两遍），
  ② 下一轮清理又把同一批行**再累加一次**（谓词 `created_at < cutoff` 对它们仍然成立），
  而归档表没有任何幂等键能看出重了；日志里只有一条 `purge old api call logs failed`。
- **为什么现在没爆**：`MONITOR_RETENTION_DAYS` 默认 0 = 整段 no-op，**这条路径今天根本没在跑**。
  它咬人的时机恰好是**P54 拍了"给几张表设保留期"之后**——所以这轮把它修掉，不是清理一个历史遗留，
  是给下一个可能的决策拆雷。
- **修法**：整段收进 `db.DB.Transaction`：聚合 → 逐行累加归档 → `DELETE`（同一个 `created_at < cutoff` 谓词）
  一次提交；任何一步失败整体回滚，下一轮重跑等价于从头再来。报错日志改成说清"已回滚、未产生重复归档"。
  刻意**没有**改成"先 `Pluck id` 再按 id 删"：那要把几万个 id 塞进一条语句（现网明细三万行），
  而谓词在同一事务里是稳定的（新写入的行时间只会更新），谓词删除更短也不跨语句漂移。
- **验收**：`test/monitor_retention_test.go` 新增一段——用 sqlite 的 `BEFORE DELETE` 触发器
  （`SELECT RAISE(ABORT, …)`）把删除钉死，断言①归档**一行都没涨**、②明细仍是全的；
  撤掉触发器重跑，归档 = `2/1/1` 而不是 `4/2/2`；再多跑一轮数字不动（幂等）。
  变异三次各拦一处：让删除失败不再回滚（**就是修前的形状**）/ 归档查不到行时不再中止事务 / 整个清理短路成 no-op。
- **发现处**：本轮 §4b 第四遍巡检留给下一轮的那条交接（查 `api_call_stats` 与 `quota_usage_logs` 是否两处写同一份数）。

## P57 一条毫不相干的用例报 `race detected`：跨进程存活的 janitor 每 tick 读一个测试里会换的全局【已处理，提交 `bac3fc5`】

- **现象/证据**：门禁 `MAKE_EXIT=2`，红的是 `TestUserFilterStatusDeleted`——**它自己没有任何断言失败**，
  报的是 `testing.go:1865: race detected during execution of test`。race 报告的两端：
  写 = `test/setupTestConf`（`testserver_test.go:51` 那次 `conf.Config = &conf.ConfMgr{…}`），
  读 = `gate/dedupe.go:52` 的 `deductWindow()`，而它是在 `startDedupeJanitor` 那个 **5 分钟 ticker** 的协程里被调的。
- **真因**：janitor 是 `sync.Once` 懒启动、**此后跨整个测试进程存活**，每 tick 去读那个全局指针；
  生产里 `conf.Config` 由 `conf.Load()` 写一次就不再动，**测试里每条用例都换它**。
  这是 P25 引入冷却 janitor 时就种下的，一直潜伏。
- **为什么今天才炸**（这一半比缺陷本身更值得记）：只有套件的墙钟跨过 5 分钟，那个 tick 才会落到某条用例的执行窗口里。
  本轮往 `test/` 里加了几条新用例（改密要两次登录、找回密码、撤销路径），把总时长推过了临界点。
  **所以"我加了用例之后，别的用例才开始红"这条线索，先怀疑共同前提被时间跨过（ticker 周期、超时阈值、
  定时任务），而不是怀疑新用例写坏了。**
- **修法**：回收阈值在协程启动时取一次快照，循环里不再碰 `conf.Config`。
  三段判断（`window<=0` 或 `2*window>deductIdleTTL` 时取 TTL）**一字未动**，行为等价；
  注释写清"为什么是快照而不是每 tick 读"，否则下一个人会当成疏漏改回去。
- **为什么不出"专用用例"**：这个缺陷的检测器就是 `-race` 套件本身。要单测"读的是快照"，
  得把 janitor 内部状态导出来喂断言——那是为了造绿光而加的表面，不是防错。判据与注释留档即可。
- **同族扫了一遍（这次扫干净了）**：其余读 `conf.Config` 的函数都在请求路径上
  （`base/circuit_breaker.go` 的阈值/冷却、`base/upstream_cache.go` 的容量、`gate/billing.go` 的开关与错误码、
  `base/pool/state.go` 的 `DefaultConfig()` 只在构造期读）——它们被用例自己的 server 生命周期框住，不构成同类竞争。
  **后台协程 + 每 tick 读 conf 的位置：除这一处之外为 0。**
- **发现处**：P56 那一批的门禁运行（`MAKE_EXIT=2`）。同批判据页补一条。

## P59 号池 `attrs` 解不开时静默当成"没有凭证"：库里有一条坏行而系统与日志都不说【已处理，提交 `d783533`】

- **现象/证据**：`base/pool/store.go` 的 `decodeAttrs` 写的是 `_ = json.Unmarshal(...)` ——
  **错误被整个丢掉**，坏 JSON 与"这个号本来就没附加凭证"返回同一个空 map。
  后果是 `deviceOf` 交出去一个** attrs 为空**的 `Device`：Provider 拿到的是"没有 sn / 没有 cookie"的号，
  表现成"取不到号"或"拿到的号不能用"，而**没有任何一处说这一列出过问题**。
  `models/pool_device.go` 的注释早就写着这个坑（「症状会是号在库里但凭证为空」），
  但它说的是**源自己塞嵌套**那种形态——那种在 Go 里编译不过（`Attrs` 的类型就是 `map[string]string`）；
  真正会发生的是**库外面动过这一列**：手填的 SQL、被截断的文本、别的版本写出来的形态（与 S49 那两张日期后缀表同源）。
- **为什么文档记过还不够**：这条正是判据页那条判据的样本——「文档写过 ≠ 防住了」。
  注释里写着症状，可症状出现时系统一声不吭，读注释的人永远是事后才知道的那一个。
- **改了什么（只加读数，零行为变更）**：拆出 `decodeAttrsErr`（**空串合法**，非空解不开才算异常），
  `deviceOf` 在异常时经 `noticeBadAttrs` 出一条 ERROR：**说清是哪个池、哪个号（`maskIdent` 脱敏）、为什么**；
  同一行只喊一次（这一列被反复读：刷新、领取、巡检都会读它——判据同 P48 的 `NoticeReplacedSetting`）。
  `encodeAttrs` 那条 `return ""` **刻意没动**：`map[string]string` 的 Marshal 不会失败，
  为到不了的路径写处理换来的是一条永远不红的断言（P56 刚为此自纠过一次，同一个道理）。
- **验收**：`test/pool_attrs_notice_test.go` 三段——首次读到坏行必须出声、同一行再读两次不再喊、
  空 attrs 走同一条通路不喊；另外单独验**这条日志里没有原始标识**（凭证不进日志，§11）。
  **它自己先写错过一次**：第一版用 `Start`/`Acquire` 触发出声，变异「去掉去重」居然**不红**——
  因为那两条路径读不读到这行**取决于转正了哪条冷备**，我的"重复读不再喊"根本没样本（判据页「断言空转」的又一形态）。
  改成走 `Reauthorize`（它必然 `refresh → deviceOf` 读这一列）之后四次变异各拦一处：
  吞掉错误（=修前形状）/ 去掉去重 / 日志打原始标识 / 把空串也当异常。
- **发现处**：本轮 §4b 第六遍——拿着「**文档说它做了什么，代码真做了吗**」这句横切扫 AGENTS 的一句话结论，
  前两条就各撞出一个（P56 改密不吊销、P58 提示没人渲染），第三条是这条。
