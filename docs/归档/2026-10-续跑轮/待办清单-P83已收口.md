## P83 错误文案与上游响应摘要按字节截断，中文正文被切成半个字符（日志与面板出现 U+FFFD）【已处理】

- **状态**：已处理 `7676ede`（第二十三遍巡检撞出；门禁 `MAKE_EXIT=0`，`-race` 套件全绿）。
- **现象/机制**：两处截断都按**字节**走，而它们截的都是"上游给的中文文案"：
  - `base/base.go` 的 `errBodySnippet`：`io.LimitReader(body, 256)` 取前 256 字节进 `UpstreamError.Message`
    （注释写着"前 256 字节"——预算是字节没错，但没人在转成文案前问一句尾巴完不完整）；
  - `handlers/verify/sender.go` 的 `truncateStr(string(respBody), 200)`：`s[:n]`。
  汉字 3 字节，256 与 200 都不是 3 的倍数 ⇒ 只要正文够长，截点必落在 rune 中间，
  文案尾部留下一个孤立续字节；经 JSON 出到日志/面板就是一个 U+FFFD。
  **同仓已有做对的一份**：`base/subject.go` 的 `truncateRunes` 注释明写"按 rune 截断（中文安全）"——
  这不是不知道，是同一个动作写了两份、只有一份对。
- **修法**：
  - `errBodySnippet`：`for len(b) > 0 && !utf8.Valid(b) { b = b[:len(b)-1] }`（最多退 3 次，
    保留"256 字节"的预算语义，不改诊断信息的量级）；
  - `truncateStr`：改 `[]rune` 截断，`n <= 0` 与未超长都原样返回；注释写明骨架里两份同语义实现
    不合并的原因是分层约束（`base` 不得导入 `utils`），改语义时两处都要改。
- **用例**：`test/utf8_truncation_test.go` 两条——
  ① 100 个「测」（300 字节）作为上游 403 响应体，走真实请求让摘要进服务端日志，断言那一行 `utf8.ValidString`；
  ② 300 个「渠」作为发码平台 500 响应体，断言「验证码发送失败（通道=」那一行合法。
  **两条都先数样本**（要求日志里出现"响应:"/该中文，否则前提不成立就 `t.Fatalf`）——
  这条纪律当场救了一次：第一版把发码 target 写成手机号，请求在参数校验那关就 400，通道没走到，
  若是裸 `ValidString` 断言就会**空转成绿**。
  变异两处各拦一处：删掉尾部修正 → 用例①红；`truncateStr` 退回 `s[:n]` → 用例②红。
- **分支侧同族**：`sources/uxx/account/client.go:248`、`sources/qimao/protocol/request.go:201`、
  `sources/fq/protocol/request.go:294` 三处同样按字节截中文，登记为分支 S53（骨架侧规则已定，随合并一起做）。
- **发现处**：第二十三遍（判法「这个下标与这段切片的前提，是谁保证的」）。
- **被它阻塞的条目**：无。
