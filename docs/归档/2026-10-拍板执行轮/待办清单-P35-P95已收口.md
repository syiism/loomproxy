## P35 `MaxDevices` 与 `MaxDead` 互不知情：死号既清不掉又占满建号名额【①已处理；②已拍 A：维持手工清，框架不代劳物理清理（全条收口）】

- **现象/证据**：`base/pool/state.go` 里 `MaxDevices`（总号数闸门，计数含 `dead`）与 `MaxDead`
  （死号超量才物理清理）是两个各算各的旋钮。**当 `MaxDevices < MaxDead` 时，清理条件永远不成立、
  而死号永远占名额**——生产 uxx 正是这个形状（`UXX_MAX_ACCOUNTS` 未配 → 默认 5，`POOL_MAX_DEAD=10`），
  于是 2026-10-03 出现过「池内 5 行 = hot1+cold2+dead2、0 个建号位」，框架自己一点不动，
  只在日志里留一条 `create cold device failed: 号池已达总号数上限`。
  当时是靠人工**软删**那两行才腾出名额（分支 S27）。
- **影响**：静默失能。池看起来在跑（`hot=1 cold=2` 是能用的），实际一旦再有号判死就补不回来，
  而且没有任何一个读数说「是因为死号占位」——管理员只能靠背 SQL 查。
- **建议修法**（分支 S27 登记的原文）：`MaxDevices>0` 时有效 `MaxDead = min(MaxDead, MaxDevices - 目标可用号数)`，
  或干脆让 dead 不计入 `MaxDevices`。
- **①已处理（`1d882a4`，文档同步在 `3108146`）**：取**第一条**方案（保留上限给可用性让路），并把「不计入」那条否掉——
  `MaxDevices` 的本职是「上游不可逆增长」的闸门，死号在上游确实还存在，不计入等于放开闸门刷号。
  落地形态：
  - 新增 `usableTarget()`（燃烧型 = 1 活跃 + `ColdSpares`；摊薄型 = `TargetDevices`）与 `deadRetention()`
    （`MaxDevices=0` 时原样返回 `MaxDead`，不改老语义）；`purgeDead` 用生效上限；
  - **建号入口在判住之前先清一次腾名额、再重数**——不等到下一轮巡检，因为间隔里源侧一直在拿不到号的错里空转；
  - 快照加 `dead_retention`、面板在两者不等时显示「死号只留 N（配置 M，被总号上限压到）」：
    谁压的、为什么压，得系统自己说（P19 同一条判据）；
  - `ErrCapacityReached` 的文案带上「死号占位几条 / 保留上限多少」，排查方向一眼分得开。
  偏离原建议之处：原建议只改清理阈值，落地时多加了「建号前先腾位」这一步——
  只改阈值的话，`MaxDevices=1、ColdSpares=1` 这类小池要等一轮巡检才回血。
- **顺带掀出一条藏得更久的错**：写「保留 2 条」的用例时断言实得 0 条，真因是
  `purgeDead` 原来用 `.Limit(n).Delete()`——**SQLite 忽略 DELETE 上的 LIMIT**（不报错），
  也就是说这条「限量清理」在开发/测试库上一直是「全删」。改成先 `Pluck id` 再按 id 删。
  判据与为什么过去没被发现（用例只断言「变少了」）写在 `踩坑判据` 对应那条。
- **②仍在册**：`purgeDead` 与名额计数都走 GORM 默认作用域，**软删的行两边都不看**——
  它们既不占名额（这是 S27 用软删能腾位的原因），也永远不会被清理，表会长一堆隐形垃圾。
  要不要给框架加一条「软删行超期物理清理」（像监控明细那样的保留窗口），是个独立决策；
  现状是运维手工清一次少一次，不 urgent。
- **② 的这一轮（提交 `f50205b`）：先量、再把"看不见"变成看得见，清理本身仍不动**：
  - **现网读数（只读复算，2026-10-04 23:41）**：`pool_devices` 里 `deleted_at IS NOT NULL` 的行 = **0**，
    活行 = 29。所以今天**没有堆积证据**——这不是"正在漏"，是"漏了也没人知道"（S27 那次软删之后，
    我们正是靠 SQL 才数出那两行，面板上从头到尾看不见它们）。
  - **代码侧把"谁会产生软删行"查清了**：框架自己不产生——回收那一路走 `Unscoped()` 硬删
    （`base/pool/state.go` 的 `purgeDead`），管理面也没有任何端点会软删 `pool_devices`。
    也就是说这一格数**只可能因手工 SQL 而 >0**，它同时是一条"有人在库外面动过号池"的探针。
  - **补的读数**：`Status` 新增 `soft_deleted`（按池隔离），面板「号池」页在 `>0` 时给一句
    「手工软删留下 N 行（不计入任何状态，也不会被自动清理）」，`0` 时不挂话（P24 的空态判据）。
    **查不到时报 -1 并按「读数不可用」显示，而不是报 0**：这条读数的用途是"确认没有堆积"，
    把一次查询失败说成 0 就是撒一个让人放心的谎（同 §10 的"审计类写入不许吞错"）。
  - **仍然没做的那一步（等拍）**：要不要框架代劳物理清理。现在这一格有了数，
    拍它的依据从"感觉没有"变成"看得见有没有"；如果长期是 0，就维持手工清这条现状。
- **验收（② 这一轮）**：`test/pool_soft_deleted_test.go` 四段——软删前报 0 /
  软删一行后报 1 **且按状态的合计仍然只数活行**（这两格是一对：只报新数说明不了问题，
  "它哪都不出现、只在新格里露一次头"才是要防的形状）/ 硬删之后归零（钉住 `deleted_at IS NOT NULL`
  那半句：只写 `Unscoped()` 会把活行算成堆积）/ 别的池的软删行不进本池读数。
  变异四次各拦一处：忘写 `deleted_at IS NOT NULL` / 恒报 0 / 去掉按池过滤 /
  **把状态计数也改成 `Unscoped()`**（隐形那一格失效）。
- **②已拍（2026-10-06，A = 不自动清）**：`pool_devices` 的行是**上游凭证的载体**，
  S27 那次正是靠软删才腾出名额——自动物理清理会拿走运维的手工 undo。
  现网那一格读数是 0，且框架自己不产生软删行，所以这条按"看得见 + 手工清"定案。
  **本条到此收口**，整条搬归档时 ①② 一起走（`AGENTS.md` §6 那句「要不要自动清还没拍（P35②）」要同步改掉）。

## P51 静态字典缺位不报错：`/data/<源>/<文件>.json` 缺文件也回 200，正文是自造的 `error` 键【①启动核对已处理；②已拍板并落地：一律 404】

- **现象/证据**（现场在分支侧 S39，机制在骨架）：v66 重启后启动日志有
  `ERROR: 读取七猫字典 data/qm/qm_ranks.json 失败: no such file or directory`，而
  `GET /data/qm/qm_ranks.json` 返回 **200**。两处读的是同一个磁盘 `DATA_DIR`（没有第二份内嵌副本可读——
  上一轮我把根因读成「两个读者各读一份」是错的，全仓 `go:embed` 只有 `modes.json` 与 `web/dist`）。
  200 的真相是**缺文件也回 200**：`handlers/catalog/datafiles.go:165` 走 `ErrorResponse{Error: …, Available: […]}`，
  **信封是成功、正文是错误**，而 `code` 为 0 意味着下游与监控都把它记成一次成功调用。
- **影响**：两层。① 部署缺产物时**没有任何启动期信号说「某个源声明的字典不在位」**——
  七猫那两份从 v62 起就是空的，三轮换装每轮都按启动契约点了名却没看见，因为 grep 的关键词是
  `no such table`/`panic`/`fatal`，而日志里那句是源自己 `log.Printf` 的、且 `sync.Once` 之后不再重说。
  ② 缺文件时下游拿到 200 + 错误正文，榜、覆盖率、调用明细全都记成成功。
- **建议修法（三条，①③ 不改变对外行为，②改变，所以分开拍）**：
  ① **启动期按各源 `DataFiles` 声明位核对在位性**，缺就 error 级点名一次（判据用 `json.Valid`，
     半截文件与没有是同一类故障——`BookSourceReady` 早就是这么判的）。已在 `handlers/catalog` 落地，
     挂在 `app.Run` 的 `base.RunSourceBoots()` 之后：源若在 OnBoot 里自己导文件，那一刻已经算完成。
  ② `/data/<分类>/<文件>.json` 缺文件应该回 **404**（或至少让信封 `code` 非 0）。
     **这是下游可见的行为变更**：Legado 的 bookSource 里 `bookSourceUrl` 指向这些路径，
     阅读器遇到 404 会怎样（重试？报错?静默跳过？）没有实测过，**所以这条不拍不动**。
     要拍就带着「谁在读这些路径」一起拍：面板导入按钮、书源里的字典链接、以及人肉 curl。
  ③ 换装三查里把「**新增数据源 = 同时下发 `data/<源>/`**」写成产物步骤，并把复算判据从
     「HTTP 200」改成「正文是预期的那份」（S39 的教训正好落在这半句上）。
- **发现处**：分支侧 S39（v66 重启后的启动日志核对），按 §3b 登记成「要回 `main` 的阻塞项」；
  本轮由骨架侧做掉 ① 与 ③，②留在册等维护者拍。

## P62 管理端把设置值原样吐出，而生产那一行里躺着发码通道的真实令牌【已处理·按建议选 1，只 `verify_http_headers` 一键；**令牌已轮换、面板不回显已实测（2026-10-06）——全条收口**】

## P64 默认配置下面板「数据源」页整块加载失败：`/endpoints` 把"网关关了"当成"没登录"【已处理·按 C 落地（网关关了也解析凭证），并经维护者追认（2026-10-05）；原建议的 A 留作备用路径；**C 的两半都有断言**（开着仍被网关拦 / 关着不认已吊销会话，两次变异各拦一处）】

- **现象/证据**（`/tmp` scratch 实例 + headless Chromium，两档视口同一套探针）：
  `AUTH_ENABLED` 的**代码默认值是 `false`**（`conf/conf.go:243`），`.env.example` 也写着 `false`；
  在这种配置下带合法登录 JWT 请求 `GET /endpoints` 得 **401**，
  而同一个 JWT 打 `GET /auth/me` 得 200。窄屏/宽屏打开 `/panel/datasources` 都能看到整块「加载失败」。
- **真因（两处都"对"，合起来坏）**：路由挂的是 `middleware.Build("apiauth", Spec{})`（`app/app.go:484`），
  而 `utils.VerifyAuth` 的第一句是 `if !conf.Config.AuthEnabled { return nil }`——**网关关闭时它整个直通，
  于是不会有人往 context 里写 `user_id`**；紧接着处理函数自己 `c.Get("user_id")` 拿不到就回 401。
  中间件说"这次不用鉴权"，处理函数说"我必须有归属"，两条各自合理，接线处没人负责。
- **另一种更糟的读法要先排除**：两种 401 的**文案不同**——中间件回「缺少鉴权凭证（Authorization Bearer /
  Cookie / X-API-Key / api_key）」，处理函数回裸的 `"unauthorized"`。
  生产上实测拿到的是前者（一次匿名只读 `GET /endpoints`，见报告 §5g），
  说明**生产 `AUTH_ENABLED=true`、这条缺陷在现网是休眠的**；亮着的是照 `.env.example` 填的新部署与开发环境。
  顺带：那块错误文案是英文裸词，中文界面里读不出"要登录还是网关没开"（P23① 那条脱敏/可读性的同族）。
- **选项（各含代价）**：
  A 这条路由改用 `utils.AuthenticateAny`（控制面口径：JWT 或**账号级** API Key 必须有归属）——
    代价：静态 env 密钥的调用者从 401 变成 403 + 一句明确文案，是**对外可见的错误码变化**；
    `AUTH_ENABLED=false` 的部署里这条端点从"必然失败"变成"必须带凭证"，更一致但仍拒匿名。
  B 拿不到 `user_id` 时退回"公开清单"（列出全部启用源的端点）——
    代价：把按套餐过滤的信息变成公开面，同一端点两套口径（治理信息不该随配置变形）。
  C 让 apiauth 在网关关闭时也解析并注入身份（"不强制，但带了就认"）——
    代价：**改的是全局中间件语义**，所有挂在 apiauth 后的处理函数都可能从"拿不到归属→401"
    变成"拿到归属→按某个账号走"，风险面远大于这一条端点。
  D 不做，只在 `.env.example` 与文档里写明"关掉网关时 `/endpoints` 不可用"——
    代价：明知有一个默认配置就会坏的整块 UI，用一句注释放行。
- **我的建议**：**A**，并把处理函数那句裸 `unauthorized` 换成与中间件同一族的中文文案
  （"这个端点需要登录会话或账号 API Key：网关鉴权关闭时也要带凭证，因为它按调用者的套餐过滤端点"）。
  **不选 C**——为了一个端点去动全局凭证语义，正是本仓反复讲的"改一处漂三处"。
- **影响范围**：`app/app.go` 一条路由 + `handlers/*` 里那两处 401 文案；**零 DDL、不改数据面**。
  面板「数据源」页在默认配置下恢复可用。
- **被它阻塞的条目**：无。它阻塞的是"新部署者第一次打开数据源页会不会以为产品坏了"。
- **答复后回写位置**：本条状态行；`docs/架构/鉴权模型与会话.md` 补一句"网关开关与逐端点归属要求的分工"；

## P72 趋势图按天分桶由**库侧**判日界：sqlite 把 +08 的串按 UTC 归一，生产 MySQL 按本地【已处理·`426874c`（A：分桶搬回 Go 侧，缓冲那一路也走同一个 `bkey`）；与 P71② 不同，上线不改变生产读数】

## P91 `singleflight` 的兜底超时写在循环里：每轮重新计时，注释说的「上限」于是不是上限【已处理·`426874c`（A：per-call，循环外一只计时器）；**这条刻意没有用例**，理由见正文】

- **现象**：`base/singleflight.go:49` 的 `Do` 是 `for { select { case <-c.done: … continue; case <-time.After(f.timeout): … } }`。
  `NewFlight` 的注释说 `timeout` 是「follower 等待 leader 的**兜底上限**」（`defaultFlight = NewFlight(15 * time.Second)`，
  理由写在旁边：上游客户端超时 10s，留 5s 余量）。但计时器是在**每一轮**里现造的：
  走到 `continue`（leader 返回失败或空结果、不算共享）之后再进下一轮，就重新拿到一整个 `f.timeout`。
  所以总等待可以是 **N × timeout**，而不是注释承诺的那一个上限。
- **另一半（先说清楚，免得被当成泄漏修）**：`select` 里 `time.After` 造的计时器，在另一支先赢时**不会被停掉**，
  它一直挂到 15 秒后自己响。Go 1.23 之前这会真的在 runtime 里堆着；**1.23 起未引用的计时器可被 GC 回收**，
  本仓是 Go 1.26，所以这一半**不是泄漏**，只是每请求多一次分配。别按"修泄漏"的理由去改它。
- **为什么本轮没改**：把 `deadline := time.NewTimer(f.timeout)` 提到循环外，四行就能让注释重新变成真话，
  但**改的是 follower 放弃共享、自己发起上游请求的时刻**（原本可能等 30s，改后 15s 就自己打上游）。
  这不是对外契约变化（响应形状与状态码都不动），却是**上游负载的时序变化**——
  而本仓的规矩是"时序/负载类改动要有能挡住它的断言"。
  **我试着构造那样的断言，结论是构造不出来**： follower 在 `continue` 之后通常会**自己变成 leader**
  （`exec` 已把 map 里的槽删掉），于是新旧两种写法都在一次 `fn()` 后返回，
  要让它真的多轮等待必须让第三方每轮抢先占槽——那是时序竞争，用例只会变成偶发红。
  **既然写不出有牙齿的断言，就不写用例、也不动代码**（判据：没有能挡住错误的断言等于没有断言）。
- **要改的话怎么改**（写给拍板的人，不用再推一遍）：循环外建一次 `time.NewTimer(f.timeout)` + `defer Stop()`，
  `case <-deadline.C` 用同一只；语义变成「从进入 `Do` 起算最多等 timeout」，与注释一致。
  顺带值得同步的是那句 15s 与 10s 客户端超时的余量关系（现网 `TIMEOUT_POOL` 若改，这里也要重看）。
- **已拍（2026-10-06，A：per-call）**：注释承诺的是"兜底上限"，那代码就该给一个上限；
  选 B（维持代码、把注释改成"每轮一个上限"）会把旁边那句 10s+5s 余量的理由作废——余量是按一次等待算的。
  **这是一次"读代码即可定正确性"的改动，风险在上游负载时序、不在正确性**：
  follower 放弃共享自己去打上游的时刻会提前（原来可能等到第二三轮），
  在"leader 持续失败 + 高并发同 key"时上游会多接到一些请求。
  **执行纪律（这条的特殊之处，别当漏写用例）**：**不写断言**——构造不出能区分两种写法的断言
  （`continue` 之后 follower 通常自己变成 leader，要它真多等必须第三方每轮抢先占槽，那是时序竞争、只会偶发红）。
  「没有能挡住错误的断言等于没有断言」在这里的落法是**不写空转的用例，而不是不改代码**。
  改时同步两处：`base/singleflight.go` 的 `defaultFlight` 那句余量注释、
  `docs/架构/弹性获取栈与环境变量.md` 第 6 行那句 singleflight 描述（那里至今没写 follower 等待上限的口径）。
- **影响范围**：只在"leader 失败或返回空结果、且有并发同 key 请求"时显现；
  正常成功路径下 follower 走的是 `<-c.done` 那一支，两种写法完全同值。
- **被它阻塞的条目**：无。卡「singleflight 的兜底语义到底是 per-round 还是 per-call」。
- **答复后回写位置**：本条状态行；改语义时同步 `docs/架构/弹性获取栈与环境变量.md` 第 6 行那句

## P93 `RecordCall` 把锁解在函数尾部：一次 panic 就把监控锁一起带走，症状是整条数据面卡死【已处理·①那处 + ②全仓形状：门禁 `lock-defer-check` 上线（无豁免），首跑 33 处一次改完，顺带修掉 `Status()` 一处无同步读】

- **症状（怎么撞上的）**：给维护模式写用例时，"开着维护 + 普通用户"那一档本该拿到 503，
  实际拿到的正文是**两份 JSON 拼在一起**：
  `{"code":-1,"msg":"系统维护中，请稍后再试"}{"code":-1,"msg":"内部服务异常"}`。
  状态码是对的（503），只有读 body 的人知道出事——而书源那类下游会直接解析失败。
- **第一层真因（新写的字段读在 nil 保护之外）**：`base/metrics.go` 的 `RecordCall` 里
  这次改动加了 `InBandReason: subject.InBandReason`，写在**结构体字面量里**，
  而下一行的 `if subject != nil { … }` 才是原来保护所有 subject 字段读的地方。
  `subject` 为 nil 是**常态而不是异常**：被 access/billing/维护门拦下的请求从没进过 handler，
  monitor 递给 `RecordCall` 的就是 nil（函数注释自己写着「可为 nil——那时各维度留空」）。
  所以这不是"维护门坏了"，是**每一个被拦下的数据面请求都会 panic 一次**。
- **第二层真因（这条才是卡死的原因）**：`RecordCall` 是 `metricsState.Lock()` 开头、
  `metricsState.Unlock()` 写在**函数尾部**——panic 把尾部那句一起跳过了。
  gin 的 recovery 在最外层把 panic 兜住（所以没有崩溃日志、进程照旧 `is-active`），
  于是**监控锁被永久持有**：下一个进数据面的请求在 `RecordCall` 里睡死。
  实测：把第一层那个错还原成变异去跑用例，`--- FAIL` 都没有，直接
  `panic: test timed out after 45s`，dump 里 `goroutine 9 [sync.Mutex.Lock]`。
  **一个"只是少一行读数"的 bug，因为解锁姿势不对，变成了服务挂起。**
- **本轮已处理（①）**：
  - 字段读收进保护：`rc.InBandReason` 移到 `if subject != nil` 那一块里（与其它九个维度同一姿势）。
  - **解锁改成 defer**：把临界区整段拆成 `recordCallLocked(...)`（`Lock()` + `defer Unlock()`），
    `RecordCall` 只做"调用 + 在解锁之后派出落库协程"。拆函数而不是原地加 defer，

## P94 `verify_http_headers` 的形状错了会被**静默丢掉请求头**：写入端只校验"是不是合法 JSON"，发送端要的是"必须是对象"【已处理·`426874c`：两半一起做（写入端 `json_object` 档 + 发送端解不开即中止发码并出 ERROR）；前置 P62 的轮换已完成】

- **症状（还没发生，但轮换那天很可能撞上）**：换令牌是在面板里往 `verify_http_headers` 里贴一段 JSON。
  只要贴的形状不是"字符串到字符串的对象"，**这一次发码会带着空请求头打出去**，
  平台大概率回 401，运维看到的错误是「发码平台返回 401: …」——**它说的是"令牌不对"，不是"你那段 JSON 我们没用上"**。
  更坏的一支：平台某个接口不校验鉴权时会**静默成功**，于是一次配置形状错误变成"看起来没问题"。
- **真因（两处校验的判据不同，中间没人负责）**：
  - 写入端 `handlers/admin/settings.go` 的 `normalizeJSONValue` 只做 `json.Compact`——**任何合法 JSON 都过**；
  - 发送端 `handlers/verify/sender.go` 要的是 `map[string]string`，
    而它写成 `if json.Unmarshal([]byte(headers), &kv) == nil { …逐个 Set… }`——
    **`else` 那一支不存在**：解不开就当没有这个设置，请求照发。
- **实测（一段小程序，跑完即删）**：
  | 贴进去的值 | 写入校验 | 发送侧解析成对象 |
  |---|---|---|
  | `{"Authorization":"Bearer x"}` | 通过 | 通过 |
  | `[{"Authorization":"Bearer x"}]` | **通过** | 失败（cannot unmarshal array） |
  | `"Bearer x"` | **通过** | 失败（cannot unmarshal string） |
  | `{"Authorization":123}` | **通过** | 失败（cannot unmarshal number） |
  三种"通过写入"的形状在发送侧全都是**静默丢头**。
- **影响**：属 P53/P60 那一族（填了没生效），但比它们隐蔽一层——**值本身存进去了，面板上看着也对**，
  只有真正发一次码才暴露，而暴露出来的还是平台的错误码，不是我们的形状错误。
- **建议修法（两半，等拍）**：
  1. **写入端把判据收到与发送端一致**：`type=json` 之外再加一档 `type=json_object`（或给这一键单判），
     要求"对象且所有值都是字符串"，否则保存就 400 带一句人话。代价：设置项的 `type` 是行为声明，
     加一档要同步 seed 与面板的校验分支；**不要**为此写"每个键一个特判"。
  2. **发送端至少出声**：解不开时 `log.Printf("ERROR: verify_http_headers 不是字符串到字符串的对象，本次未带任何请求头")`
     并**直接判这次发码失败**（宁可少发一条，不要把匿名请求打给上游）。
     行为变更点写在第二半里：从不报错变成报错，所以要配用例与变异验证（造三种坏形状，断"这次不发 + 有这句 ERROR"）。
- **为什么先登记不顺手改**：第 2 半是**对外可见的失败面变化**（发码从"照发"变"拒发"），
  按 §3b 与 P22② 那条同规矩等拍；第 1 半（写入口加校验）不改运行时行为，谁先做都行，
  但它单做会留下"库里已有的旧形状值仍然静默"的存量面——**两半一起做才收干净**。
- **已拍（2026-10-06）：两半一起做**，落法照正文那条建议的两步，不拆开发车：
  ① 写入端**加一档 `type=json_object`**（对象且所有值都是字符串，否则保存 400 带一句人话），
  同步 seed 与面板的校验分支——**不为本键写"每个键一个特判"**（那会长出第二份类型判据，违背「设置项的 `type` 是行为声明」那条）；

  断"这次不发 + 有这句 ERROR"，变异退回"照发"必须红）。
- **执行前先读一眼生产那一行的形状**（轮换后的值是刚贴进去的，只读核对；`{"k":"v"}` 之外的一律先当"静默丢头"处理）——
