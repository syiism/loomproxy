## P52 `content_withheld` 有少量行没被标上：核对到时间轴一级【已定案·非缺陷；A 的代码与用例已落 `426874c`；**`content_consent_set_at` 已随 v83~v89 发布序列的 AutoMigrate 落到生产库**（2026-10-06 `information_schema` 核实在位）——残留就此清零】

- **现象/证据**（2026-10-04 生产只读核对，为查分支 S47 那条「五维全空」撞上）：
  关掉留存的 22 个用户里，样本用户 id 1027 有 70 行，其中 **6 行没被标 `content_withheld`**（全在 `recommend`），
  另有 4 行在别的用户身上同样未标——第一眼像「闸口漏了几行」。
- **定案（时间轴逐条对齐，不是推测）**：该用户 `content_consent` 最后更新于 **12:01:47**，
  而那 6 行未标的时刻是 **12:00:36 / 12:00:42 / 12:00:51 / 12:01:04 / 12:01:17 / 12:01:19**，
  全部**早于**这次更新；已标的那 64 行则从 **12:02:35** 起。
  → 未标的 6 行是他**还没关**的时候发生的请求，标记为 0 是**正确**的；已标的最早一行距开关 48 秒，
  说明开关一落地闸口就开始工作。**「access 之前返回所以没置标记」那个假设被这份读数否掉了**（至少在这个用户身上）。
  同一条查询换个角度也自洽：`created_at >= users.updated_at` 之后仍带任何一个内容维度的行 = **0**；
  `content_withheld=1` 却仍带维度的行 = **0**。
- **所以 P52 不是缺陷**，但核对过程中撞出一个真的结构缺口：**同意位没有「变更时刻」**。
  `users.content_consent` 只有当前值，`updated_at` 会被任何一次改昵称/邮箱顶掉——
  这次能定案纯粹是因为那个用户当天只动过这一次、时间轴刚好干净。
  换一个「先关、隔天改昵称、再关回来」的用户，同样的问题就答不了。
  要答得了就加一列 `content_consent_set_at`（只在同意位**真变**时写），
  顺带让「关掉之后还有没有新行被捕获」变成一条随时可查的读数，而不是靠时间轴巧合。
  **加列是生产库写操作（AutoMigrate），单独等授权**；本轮不动。
- **建议下一步**（要拍才做；拍板所需的两个数已数出来，见下一条）：一列 + 写入口在 `POST /auth/privacy` 的**值真变**时盖时刻，
  用例断言「改成同样的值不刷新时刻」「反过来会刷新」——后者正是这次定案所依赖的那条信息。

- **背景/证据（本轮重数过的，第一版这里是错的）**：`gate.GrantPlanSource`/`UngrantPlanSource`
  **不是**只有测试在走——生产有三个调用方，就在同包的 `handlers/admin/admin.go`
