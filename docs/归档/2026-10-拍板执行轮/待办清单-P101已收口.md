## P101 对哨兵错误用 `==` 比较：`switch err { case gorm.ErrRecordNotFound: }` 包一层就永不命中，而 `default` 接住它的那支行为正好相反【已处理】

- **状态**：已处理 `1673115`（第三十八遍巡检撞出；`make vet` 全绿、`make build` `MAKE_EXIT=0`（`./test` 438.5s），那一支的用例覆盖经变异验证）。
- **发现处本身就是这条最值得记的地方**：扫出来的**唯一一处**是本轮 `a5386d0` 我自己刚提交的代码
  （`handlers/verify/verify.go` 的冷却查询分派）。巡检的第一批猎物是执行巡检的人自己上一天的产出，
  这不是巧合——**新写的代码是新写的人的盲区**，而判据页那行「同一个判据在三个包各写一份」管的是旧账，管不到昨天。
- **形状**：
  ```go
  switch err := db.DB.Where(...).Order("id DESC").First(&latest).Error; err {
  case nil:                       // 有行，按冷却判
  case gorm.ErrRecordNotFound:    // 没发过码，直走
  default:                        // 读失败 → 拒绝发码（P99 加的失败关闭）
  }
  ```
  Go 的 `switch`/`case` 是 `==` 语义，`errors.Is/As` 才是为包装链设计的。今天 GORM 返回原句，
  所以这条 case 命中；一旦中间多包一层（驱动、插件、一次"顺手把 err 带上上下文"的重构），
  "查不到"就落进 `default`——而 `default` 干的是**拒绝发码**，与 `case` 的**放行**正好相反。
- **影响**：症状不是崩溃也不是 500，是**"偶尔发不出验证码"**：同一个目标第一次发之后才触发，
  而触发过一次就再也复现不了（那条目标已有行了）。这类"跟着数据走的分支错"是排查成本最高的一种，
  因为它的复现步骤里带着状态。
- **修法**：换成 `switch { case err == nil: … case errors.Is(err, gorm.ErrRecordNotFound): … default: … }`。
  配套的判据（比较"是不是这个错误"一律 `errors.Is/As`、`switch err` 的 case 也算）写进了
  `docs/规范/踩坑判据.md` 的新行《对哨兵错误用 `==`（含 `switch err` 的 case）》。
  `err != nil` 不在这条范围内：它不比较身份，不会被包装骗。
- **验证**：把 case 判死成 `false && errors.Is(err, gorm.ErrRecordNotFound)`，
  `test/p99_verify_gate_test.go` 的基线断言（表里有 schema、目标从没发过码 → 必须真的发出码）当场红
  ——证明"没发过码"这一支**一直有用例覆盖**，这次不是裸改。`MUTATION_EXIT=1`，还原后逐文件核对哈希。

  健康一侧 `errors.Is(` 45 处（非用例 35 处 / 22 个文件）。
