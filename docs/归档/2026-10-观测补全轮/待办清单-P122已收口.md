## P122 带内失败的**业务码**从来没落库：`in_band_reason` 只有形状没有值，于是"站方到底回了哪一档"这个问题无法回答【已收口（2026-10-11）：三半全齐且上线——骨架 `a7af72f`、源侧 S107（deploy `36a8d8d`）、**列随 S108 换装落生产（01:17，`SHOW COLUMNS` 核实）**；S104 攒样本是它自己的条目】

- **现象（现测）**：`api_call_logs` 里 `in_band_error` 那列是布尔——
  `SELECT DISTINCT LEFT(in_band_error,70) … WHERE source='zj_novel' AND in_band_error<>''` 全表只回一个值 `1`；
  `in_band_reason` 只有分类枚举（本轮读数里就一种：`upstream_status` 722 条）。
  **站方信封里那个 `code`（`0/4001/401/403/429`）没有任何一格存着**。
- **影响**：装配仓 S104 的取证跑到第二步就撞墙了——延迟分档已经能排除"求解扫不满"
  （725 条里 304 条 ≤10ms、325 条 11–200ms，而本仓实测扫满上界要 22.2s），
  但**"会话被拒"与"配额/风控 429"这两种形状分不开**，而它们的处置完全不同。
  现在只能靠"手工重放一发 `/zj_novel/content`"去拿码——**那会往 `api_call_logs` 落行**：
  既是间接写库，又会改掉我正在读的基线。**所以这条不办的话，S104 就只能停在"分不出"。**
- **建议修法（骨架侧加采集位，源侧填值；不在源里自己造列）**：现成那支路就是形状——
  `base/legado/observe.go:123-131` 在 `ContentType=="error"` 那一支里已经在抄 `reason`
  （`subj.InBandReason = base.ParamString(data, "reason")`），链路是
  `base/subject.go:40` → `base/metrics.go:31,141` → `app/monitor.go:52` → `models/api_call_log.go:22`。
  同形状补一格 `in_band_code`（`size:32`，空=源没给，**与 `reason` 一样空是合法状态、读数不猜**），
  源侧 `sources/zj_novel/content.go`（`reasonUpstream` 那处）把信封码填进去。
  **P37 那条要一并判**：同意位关闭时抹的是**内容维度**七列，业务码不是内容维度——**不抹**，理由写进注释。
  面板那侧先只加在明细列与筛选，不动榜（榜单维度白名单只有搜索词与书名，§9 那条口径不因此放宽）。
- **影响范围**：`models` + `base` + `app/monitor.go` + 管理端一处展示 + 装配仓一个源；
  新列由 `AutoMigrate` 加（与 `cleared_at` 同一批发布动作）。**被它阻塞的条目**：S104（停在"分不出 ①与②"）。
  **一句防漂（外部分析 §七.2 提的，本仓已有同一个坑做回链）**：`AutoMigrate` **加列也算生产 DDL**——
  `cleared_at` 那一格当时就是按"要单独点头的写动作"走的（P119 ④），别因为它是"自动迁移"就跳过授权意识；
  而且**列上线 ≠ 取证完成**：S104 要的是积累够样本之后的第二轮，这一条是"前置发布"，不是它的结尾。
- **发现处**：2026-10-10 做 S104 取证第二步时，准备查"是哪一档业务码"才发现库里根本没有那一格。
- **落地记录（2026-10-10，骨架侧）**：链路五处各一格——`models/api_call_log.go` 新列
  `in_band_code`（`size:32`，与 `reason` 同形状：空=源没给、是合法状态、读数不猜）；
  `base/subject.go` 的 `CallSubject` 带值；`base/legado/observe.go` 在 `ContentType=="error"`
  那一支里 `base.ParamString(data, "code")` 照抄（JSON 数字型的 `401` 经 `scalarToString` 转成 `"401"`）；
  `base/metrics.go` 的 `RecentCall` 过环；`app/monitor.go` 落库。**P37 那格按登记时的判落死**：
  `WithholdContent` 不清 `InBandCode`（`InBandReason` 同理），理由写在注释里——业务码说的是
  「站方回了哪一档」，不是内容维度，抹了它 S104 那种「会话被拒 vs 配额 429」就永远分不开，
  而留着它不带出用户读了什么。面板：明细表状态列在「·带内失败」后缀 `reason·code`（谁有值显谁），
  历史筛选加 `in_band_code` **等值**（码是档位枚举不是文本；查询参数为空=不筛）；
  榜与覆盖率一概不读它（§9 维度白名单不放宽）。
  **用例四条**：抽取三种形状（数字型/字符串型/没给）+ 正常正文不带码；`WithholdContent` 保留（单元）；
  全链路落库（`test/groupb/inband_code_test.go`）；同意位关闭端到端不清码；历史筛选等值命中。
  **四次变异各红对应那一半**：摘掉信封抽取 → 抽取与端到端红；删掉落库映射行 → 落库读回红；
  删掉筛选 → 筛选用例红；`WithholdContent` 连码一起抹 → 单元与端到端两处红。

  RecentCall 层就是这个原因。为了不让「映射行被删」静默存活（P124 那族「声明了、没人装配」的
  用例版），`app.PersistCallLogs` 按 `PurgeExpiredCallLogs` 的先例导出，用例把 Drain 出来的
  同一批喂进真映射、断言对象换成库里的行。**偏离原建议的两处**：① 面板把 `in_band_reason`
  也一并显出来（原建议只点名 `in_band_code`）——它早就在 API 载荷里、只是从来没渲染过，
  只显码不显分类那一格读不懂；② 历史筛选行加了 `flex-wrap`（多一个输入框后窄桌面会挤出去，
  P65 那条判据的形状）。**剩下的两格在骨架之外**：装配仓 `sources/zj_novel`（`reasonUpstream`
  一族）把信封码填进 `code` 键——源不填，这一列就一直是合法的空；列落到生产库由下一次发布的
  AutoMigrate 带（与 `cleared_at` 同一批发布动作，**加列也是生产 DDL**，照旧要单独点头）。
  列上线 ≠ S104 取证完成：它要的是积累够样本之后的第二轮。
