- **需求原文（维护者）**：新增"额度转移"能力，用于把**其他数据源的额度转移到指定数据源**；
  **可以复用额度覆盖**（`user_quota_overrides`）；**不限额度的数据源既不参与转移、也不接受转移**。
- **落在现有哪一层**（先把归属钉住，免得长出一个平行系统）：
  限额的优先级是 **用户数据源级覆盖（追加语义）> 套餐限额 > 不限**（AGENTS §9），
  所以"转移"的**唯一合法落点就是 `user_quota_overrides`**——它本来就是"这个人在这个源上多给/少给多少"的那一行，
  转移只是把两行的数字重排，**不新造第三份限额事实**。
  另一条现成纪律一起生效：**限额/计费/授权的键一律是数据源码**，分组只是视图（§9），
  所以转移的入参必须是 `(用户, 源A, 源B, 数量)`，不接受 `group_id`。
- **两条硬边界（来自需求，也是判据）**：
  1. **`-1`（不限额）的两端都拒**：转出方是 `-1` 没有"可转的量"，转入方是 `-1` 接受转移毫无意义
     （它本来就用不完）。**判定口在写入之前，不在 UI 上遮一下就算**——两端任一为 `-1` 直接 400，
     文案是给人看的那句「不限额的源不参与转移」，不带 SQL 与内部形状（§10）。
  2. **转入的目标源必须已经授权**：`quota_limits(scope=source, target=源B)` 不存在 = 该套餐根本不能用源B（P34），
     把额度转给一个用不了的源等于造一行永远花不掉的数据。**授权与额度是同一行的两件事**这一条不能在这里破。
- **一条必须先说清的语义（写这段时我一开始把它说错了，改在这里）**：
  `gate.EffectiveSourceLimit` 的口径是 **有效额度 = 套餐限额 + 用户覆盖**（覆盖行是**增量**：正值追加、负值扣减，结果下限 0），
  而 `gate.userOverrideLimit` 里 **`Limit == 0` 不是"覆盖成 0"，是"没有覆盖、回退套餐"**——它是个哨兵。
  于是"转移 N"的正确算术是 `A.覆盖 -= N`、`B.覆盖 += N`，而且**两端都不许把行留在 0 上**：
  转出方一旦正好落到 0，它不是"额度为零"，而是**一夜回到套餐全额**，等于这次转移凭空造出了额度。
  这是 P48（`settingInt` 把 0 当"没配"）与 P85（`pool.Config` 三种 0 并存）那一族「0 是没写还是要 0」的**第三个实例**，
  判据同一条：**先问手里那个 0 是不是一个值**，再决定能不能用它做减法的终点。

- **③ 的自纠（维护者 2026-10-06 问「用户侧的额度转移入口呢」时才暴露）**：我原来写的理由是
  「自助等于让账号之间互相挪额度」——**这句话不成立**：`user_quota_overrides` 的键是 `(user_id, 源)`，
  本人自助只能在**同一个人的两个源之间**重排，跨账户根本没有通道。把一条不存在的风险当作设计依据，
  等于把用户侧入口凭空关掉，而且还让"只管理员"看起来有理由。
  自助真正的风险是另外两件事，都能在判据里堵住：
  1. **守恒**：一次转移 = `A.覆盖 -= N` 且 `B.覆盖 += N`，**同一事务内成对写**——只要增量之和为 0，
     转出去再转回来不产生任何新额度（这条由用例钉：转移前后 `sum(覆盖)` 不变）。
  2. **0 哨兵**（本条上面那条语义）：两端结果**都不许恰好等于 0**——转出方若正好归零，它不是"额度为零"，
     而是**回退到套餐全额**，等于凭空造出额度。要清零就得写 `-套餐限额`（有效额度 0），不是写 0。
     判据是同一条：**先问手里那个 0 是不是一个值**（P48/P85 的第三实例）。
  自助**先不设限频**：反复转移不产生额度、只挪读数，限频换来的复杂度对不上收益——
  但要留一条观察：若现网出现一人一天几十次转移，那是**别的用法**在发生，回头看这里就不该省。
- **共用一个判定口**：两个入口调同一个 `gate.TransferQuota(...)`，**不许在两处各写一遍算术**
  （§9「判定只有一个入口」那条；两端 `-1` 拒、目标须已授权、0 哨兵拒、审计行同事务，四条都在函数内）。
