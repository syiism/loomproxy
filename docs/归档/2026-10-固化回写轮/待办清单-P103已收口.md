## P103 长跑协程的 panic 兜底只覆盖了号池那两条路径：另外四条裸协程一次 panic 就把整个进程带下去【**已收口（2026-10-07）**：①② 落地（`base.Guard`/`base.Supervised` 一处实现 + 四条裸跑路径各包一轮 + proxy_api 全链带 ctx）；③ **维护者拍严格版 A 并落地**——`make vet` 新增 `goroutine-guard-check`（`tools/goroutineguard`），每个长跑循环必须带帧或写一行可见的 `guard-exempt`，三道变异各红一处；本条同时登记了两处机器够不着的地方（defer 层级那半句要调用图；跨包/接口值起的协程解析不到函数体）】

- **现象/证据**（判法是「这条协程死了会怎样」，第四十四遍逐个读循环体，不是抽样）：
  P77/P78 那轮给号池的两条后台路径各上了 `guardPanic`（`base/pool/state.go:220`），
  而**同一形状在别处还有四条，一条都没有兜底**——`grep -rn "recover()" --include='*.go'` 在非测试代码里只有四个落点
  （`base/pool/state.go`、`base/registry.go`、`base/legado/observe.go`、`app/aggregate_search.go`），下面四条都不在其中：
  1. `app/subject_store.go:85` → `run(ctx)`：命名缓存的后台批量落盘（pipeline 写 Redis）。
  2. `app/monitor.go:166`：名称回填定时循环（`RunSubjectBackfillTick`，默认 900 秒一轮）。
  3. `app/app.go:777` → `prewarmCache(...)`：启动预热。
  4. `base/proxy_api.go:53` → `maintainProxyPool(ctx, gap)`：动态代理池的水位维护。
- **影响**：**Go 里任何协程的未恢复 panic 终止的是整个进程**，不是那一条循环。
  所以这不是"少一行读数"，是**整机下线**；而 `Restart=always` 会把崩溃循环伪装成"运行中"
  （AGENTS.md §3 的换装三查第 3 条就是为这个写的——只看 `is-active` 不够）。
  号池那两条被承认过要兜底，恰恰说明这族的后果已被判过一次；**判过一次却没有铺开，就是留了四条同形状的**。
  四条里最难看见的是第 1 条：它挂了之后，写侧 `case s.writes <- …: default:` 会走"队列满即丢"那条路
  （`app/subject_store.go:146`，每千条告一次 WARNING），**症状以"面板上 `name_cache.persist` 的读数一直不掉"出现**，
  而真正该问的是"那个消费队列的协程还在不在"。
- **同一次巡检顺手读到的第二半（同一文件、不同轴）**：`base/proxy_api.go` 的 `StartProxyAPIRefresher(ctx)`
  收了 ctx，`maintainProxyPool` 也在 `select` 里听 `ctx.Done()`，**但真正干活的两处 HTTP 出口没用它**：
  `fetchProxyAPI`（`:145`）与 `checkProxyAlive`（`:216`）写的都是 `http.NewRequest`（无 ctx 形式），
  靠 `http.Client{Timeout: 15 * time.Second}` 与 `proxyCheckTimeout` 各自兜住时长。
  后果是**关停时这一轮不可取消**：一轮补充 = 1 次取列表 + N 次逐个校验，N 大时这一步在上限之内能跑到分钟级，
  而调用方以为传了 ctx 就可控。**"接了 ctx 却不往下传"比"不接 ctx"更坏**——前者让上层误以为有截止。
  两处都设了 client 级 Timeout，所以这不是无界阻塞，是**取消性缺失**：严重度低一档，判据同一族（P81 的 `hookCtx` 管的正是"传下去的 ctx 要带截止"）。
- **建议**（三条，一次做完）：① 给这四条循环各包一层"只在状态变化时出声"的 panic 兜底——
  **兜底不等于吞**：`log.Printf("ERROR: …协程已退出/已恢复…")` 之后要决定是重启这条循环还是退出进程，
  而"重启循环"必须是有限次（否则就是崩溃循环换了个名字）；② `proxy_api` 那两处换 `http.NewRequestWithContext(ctx, …)`，
  并把 ctx 一路传进 `replenishProxies`/`validateProxies`；③ 上一条 `make vet` 扫描：**顶层 `go` 起的循环体里没有 `recover()` 即红**——
  形状确定（P77/P78 已把这条判据实例化过一次），误报面比"裸 goroutine"的字面量小得多，
  因为一次性协程（`app.go:814` 那种 serve 一次的）本来就不该要求兜底，要按"是否有 ticker/for 循环"筛。
- **拍板（2026-10-06，授权代拍）：③ 不做**，维持在册——理由就是本条自己写的那句：
  要先能区分一次性协程与长跑循环，而这个筛法本身得先在存量上跑一遍看命中形状；
  ①② 已把产品侧的洞补住，扫描器是第三层的收益，不值得为它在这一场动门禁（§5b 门禁闸也在看着）。
- **为什么不上门禁就完事**：第 ③ 条要能判"一次性 vs 长跑"，那是读循环体的形状；先按 ① 补兜底，
  扫描器等补完之后再做，做的时候按页上那条规矩**先注入一次违例证明它会红**。
- **发现处**：第四十四遍巡检（判法「这条协程死了会怎样」；来源是同一天第 43 遍之后余下的扫描面）。
- **影响范围**：`app/subject_store.go`、`app/monitor.go`、`app/app.go`、`base/proxy_api.go`；零 DDL、不改数据面语义。
- **被它阻塞的条目**：无。它**被 §5b 的发布闸挡着**：这是产品代码，登记不落地，与 P99②/P100/P102 同一处境。
- **落地记录（①②，2026-10-06）**：兜底收成**一处实现** `base.Guard` / `base.Supervised`（`base/supervise.go`），
  号池的两处改成**直接** `defer base.Guard(...)`（第一次写成"`defer p.guardPanic`、里面再调 `base.Guard`"，
  而 `recover()` 只认被 panic 的函数**直接 defer** 的那一个调用，多包一层就返回 nil——`TestPoolMaintainSurvivesProviderPanic` 当场红）
  动态代理池的一轮补充。`subject_store` 那一处顺带把 `batch = batch[:0]` 挪进 defer：**panic 之后也要清空**，
  否则下一轮拿同一批再炸一次。② 是 `base/proxy_api.go` 全链带 ctx（`replenishProxies`/`fetchProxyAPI`/
  `validateProxies`/`checkProxyAlive` 四个签名 + 两处 `http.NewRequest` → `http.NewRequestWithContext`），
  重试等待也改成 `select` 听 `ctx.Done()`。
  **变异三条各红一处**（同一条违例反着做）：① 把 `Guard` 的 `recover()` 摘掉 → 包内测试红（panic 带走测试进程）；
  ②③ 分别把两处 `NewRequestWithContext` 改回 `NewRequest` → 各自那条用例红。
  取消那两条用例都配了**正例**（先证明请求真的发出去了：`fetch` 读回 2 条、`checkProxyAlive` 等满 300ms 慢响应），
  否则"取消后立刻返回 false"可能是空转——判据页第 ⑩ 种失灵就是这么定义的。
- **② 的断言为什么钉耗时而不是钉存活**：代理为空串时 `clientForProxy` 走的是默认客户端，
  存活与否还取决于客户端配置；而"取消之后不该等满一个响应"只取决于 ctx 有没有传下去。**断言要钉在那条唯一由被测改动决定的量上**。
- **③ 的前置存量清点已跑完（2026-10-07，一次性原型在 /tmp，不进仓库）**：拍板那句留的条件是
  "筛法本身得先在存量上跑一遍看命中形状"，现在形状量出来了（判据：`go/ast` 解析全仓非测试代码的
  **16 处 `go` 语句**，循环体里出现 `for` 或 `NewTicker/NewTimer/Tick/After` 判为长跑，纯 `range` 一次不算）：
  - **长跑 8 处，判错 0 处**——这半条筛法可靠（一次性那 8 处也全对：`aggregate_search` 的扇出、
    `metrics` 的 flush、`apikey` 的异步写、`fakegateway`/`main.go` 的 serve）。
  - **"有没有帧"也可靠**：4 处的循环体里当场找到 `base.Supervised("…的一轮", fn)`（`app/app.go:787`、
    `app/monitor.go:166`、`app/subject_store.go:85`、`base/proxy_api.go:53`），正是 ① 落地的形态。
  - **难的是"有没有调到外部实现"那一步，两条路各撞一头**：按语法把 `x.Y()` 当外部调用，
    今天会把 `deductMu.Lock`、`ticker.Stop`、`t.Stop`、`dnsCacheMu.Unlock` 这类**本地变量上的方法**
    误判成"裸调外部"（4 处假红全在这里：`base/pool/state.go:299`、`gate/dedupe.go:129`、
    `gate/ratelimit.go:132`、`utils/network.go:51`）；反过来只认"包名.函数"就会**漏掉真正危险的那一形**——
    号池的钩子是 `p.provider.Refresh(...)` 这种**接口值上的调用**，包名规则看不见它，
    而那恰恰是 P77/P78 的原始形状。**分不清要靠 `go/types`，纯语法做不到两边都对**。
  - 因此可上的规则只剩两种形状，**代价不同，等一句决定**：
    **A（严格但纯语法可靠）**：每个长跑循环体必须自带帧，不看它调不调外部实现。
    今天 4 处要各补一个 `Supervised`（清理类循环，行为上是把"崩了换重启"改成"这一轮恢复、下一轮照跑"），
    换来**零漏报**——`p.provider.Refresh` 那一形天然被循环级帧盖住。
    **B（按语义判）**：只有调到外部实现的循环要求有帧——那要引入类型信息（`go/types` 或 `x/tools`），
    等于为一条门禁给构建链加依赖。
    我的建议是 **A**：它把"什么算外部实现"这个不可判的问题换成了"循环就要有帧"这个可判的问题，
    而 4 处补帧的成本低于一次"后台循环把进程带下去"的排错。
