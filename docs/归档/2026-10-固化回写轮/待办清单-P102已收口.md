## P102 `scripts/deploy.sh` 的构建段比 `make build` 窄：没有 `-race`、不跑包内单测、不跑 `make vet` 那一串门禁【**已收口（维护者 2026-10-07 判定）**：② 由 `2fca46e` 落地（选 A，`make vet && make test`，两条路径口径实测各验一次）；剩下的那半"要在下一次真实发布里走过"——维护者的话是「deploy.sh 的内容不用管」，**判为不再追，收口方式是判定而不是已验证**】

- **现象**：`deploy.sh` 的构建段实测是
  ```bash
  (cd "$REPO_ROOT/web" && pnpm install --frozen-lockfile && pnpm build)
  go vet ./... && go test ./test/ -count=1        # 仅当 SKIP_TESTS=0
  CGO_ENABLED=1 go build -ldflags="-s -w" -o "$BIN.new" .
  ```
  而 §3/AGENTS 说的**唯一门禁是 `make build`** = web + `make vet`（16 个检查目标、`scripts` 下 14 个 check-*.sh）
  + `make test`（`go test ./... -race -count=1 -timeout 20m`）+ 两个产物。
- **差别不是一点点**：
  1. **没有 `-race`** —— P78/P80 那两条号池竞争全靠 `-race` 才红（报告里写着「单跑那条用例撞不出来」）；
  2. **只跑 `./test/`** —— 包内单测不在部署前跑。这正是分支侧 S30 记的盲区，
     而 `make test` 跑 `./...` 就是为它改的（AGENTS §3 写了这条历史），**部署脚本没跟着改**；
     对分支尤其要紧：`sources/*` 的用例只在包内（S59 的 wd 用例也按这条放包内）。
  3. **16 道门禁一道都不跑** —— sql 保留字、css 类名、导航完整性、设置读取口、`tz-check`、
     `ledger-write-check`、`lock-defer-check`、`todo-status-check`……全都不在部署路径上。
- **影响**：**部署脚本绿不等于门禁绿**。现网每次发布如果只敲 `deploy.sh`，
  那从上一次 `make build` 之后引入的所有回退都不会被发现——而 `deploy.sh` 的自动回滚只在**冒烟失败**时触发，
  冒烟只测 `GET /` 是否 200（15 秒窗口），**代码能跑起来不等于检查都过了**。
- **建议（拍一个才动，属工具链不是产品行为，但仍是要一句决定的事）**：
  | 选项 | 做法 | 代价 |
  |---|---|---|
  | **A（我的建议）** | 把 `deploy.sh` 的那一段换成 `make vet` + `make test`（或干脆 `make build` 后取现成产物） | 部署慢一些（`make test` 是 `-race ./...`，本仓实测 `./test` 一包就 ~440 秒）；换来"部署路径上的门禁与开发路径同一份" |
  | B | 保持脚本不变，在发布预案里硬性要求"先 `make build` 绿再 `deploy.sh`" | 零代码改动，但**靠人记**——正是 P79 那次把「换装三查」从纪律搬进脚本时所否定的形态 |
  | C | 给 `deploy.sh` 加 `--full-gate` 开关，默认仍窄 | 又是"两条路径"，默认那条还是漏的 |
  **B 是我现在给 S60 写的做法**（预案里硬性要求先 `make build`），A 才是把纪律变成机器的那一步。
