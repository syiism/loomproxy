## P40 登录防爆破的状态只能靠「重启进程」来查看和清除：现在可读、可定向解锁；账号侧形状已可观察【轻方案已处理；①已拍 A：只观察、不做账号闸门；②**已拍（2026-10-07，维护者选 A）：不吃**——两条机制继续互不知情；两个子项都已拍完，**本条因此收口**——它记的是一条明知存在的边界，不是待办；① 那句"配一周读数回看"另立一条最小登记项（**P108**）承接，别让它沉在只读归档里】

- **现象/证据**：限频器 `ipAttemptLimiter`（`handlers/auth/auth.go`）把窗口计数、失败连击、锁定到期全放在
  进程内存的 map 里，**库里没有任何表承载它，管理面也没有端点读它**。
  所以在它之前，「这个 IP 被锁了吗、锁到几点」只有一个答案办法——重启进程，而重启会连带清掉所有人的锁、
  中断所有在途请求。附带一条同源缺陷：条目只按 IP 建、**没有任何回收路径**，见过的每个 IP 都留一行，
  被爆破时内存直接跟着对方的 IP 池长。
- **影响**：误锁一个 NAT 出口（同一出口 IP 下多个正常用户同时重登录）时管理员没有定向手段；
  「防爆破有没有在工作」在面板上不可见，出事只能靠 journal 里的 401/429 行反推。
- **本轮做的（轻方案：只加「可读」与「可清」，不加留存）**：
  - `handlers/auth/auth.go`：加 `pruneLocked`（越过 `attemptPurgeThreshold=4096` 时顺手扫一次，平时热路径零额外成本；
    快照也扫，所以「面板开着」不再等于内存增长）、`SecurityAttemptSnapshot()`、`ResetAttemptLock(ip)`
    （锁与失败连击一起归零，返回清掉的条数——0 不是错误，那个 IP 本来就没记录）。
  - 两条管理端点：`GET /admin/security/attempts`、`POST /admin/security/attempts/reset`（同一个 `AdminRequired()` 组，只认会话）。
    reset 用 POST 是有副作用的写；**刻意不与 `DELETE /admin/blocked-ips/:id` 同形**——那是删库里的一行，这是清进程内状态。
  - 面板「IP 拉黑」页加一节「登录限频锁定」：锁定项排前面，列通道 / IP / 窗口内尝试与上限 / 失败连击 / 锁到几点 + 解锁按钮；
    空态一句话写明「读数只反映当前进程，不代表最近没人试过」。
- **没做的那一半，以及为什么**：另一条路是新建 `login_attempts` 表把每次尝试落库（可事后统计、可告警）。
  本轮刻意不做——那会把「谁在何时用什么用户名试登录」变成一份新的长期敏感留存（IP + 用户名），
  按 §11 要定保留期、只能经 `/admin/*` 出明细；而**当下的痛点只是「读不到、解不了」**。
  真需要审计链时按那份口径单独立项，不要顺带塞进一个运维按钮。
- **仍在册的两条**（同一片代码，别以为 P40 把它们一起解决了）：
  ① 锁定**只按 IP、不按账号**，所以分布式爆破或「挑一个账号慢速试」都摸不到阈值，账号侧没有独立闸门；
  ② 自动拉黑（`middleware/ipblock/autoblock.go`）只数**数据面路由**的 403/429（`monitor` 的 `Applies` 是 `s.Source != ""`），
  **登录失败根本不喂给它**，两条机制互不知情；`verify_code_scenes` 现网是 `register,forgot_password`（登录没有验证码这道闸）。
- **① 的准备已做完，停在执行门前（同日续跑批次，提交 `212b229`）**：先量了现网的形状（只读 journal，14 天，
  只取方法与计数，IP 与账号一律不进仓库）——
  `/auth/login` 共 **1179 次**：200 × 610、401 × 536、429 × 19、400 × 14；
  那 **536 次失败来自 222 个不同 IP**，直方图是 106 个 IP 各失败 1 次、49 个 2 次、29 个 3 次……
  **单 IP 14 天内最多 14 次**。读法有两层：
  ① 这个分布**完全落在按 IP 那道闸的视野之外**（阈值是 10 次/分钟、连错 10 次锁），
  所以"没有一条锁定"既可能是没人爆破，也可能正有人在慢慢试——**今天的系统答不出这两种的区别**；
  ② 失败率 47%（536/1146）本身就值得有人看一眼，而看一眼需要的正是"按账号聚合"这一维。
- **为这个决策新加的读数（只观察、零处置）**：`handlers/auth/account_watch.go` 按登录标识记
  尝试数 / 失败数 / **不同 IP 数** / 至多 8 个来源样本，保留一小时、越 4096 条扫一次、键长夹到 64 字符，
  **全程不入库、不参与 `locked()` 判定**；经 `GET /admin/security/attempts` 的 `accounts` 出，
  面板「IP 拉黑」页多一节「账号侧登录尝试（只读观察）」，标黄阈值走响应的 `accounts_meta.multi_ip_yellow`
  （复用 `suspect_distinct_ips` 那一条定义，**面板不许自己抄数字**——P46 的判据，新写的列也不能犯）。
  文案刻意不出现"攻击/爆破"：一个用户连错三次与一个脚本各错一次在这一列里长得一样，判定是人做的。
  验证码侧那条路（`forgot`）暂未接入观察，接的话就是同一个 store 再挂一个调用点。
- **本轮自纠的一处用例纪律**：这条读数最初还写了「空标识不进表」的守卫与断言，
  变异验证（删掉守卫）之后**它照样绿**——因为 `Login` 在查库前就 trim + 小写，纯空白用户名走的是"没填"那条 400，
  永远到不了这个 store。守卫与断言都已删除并在此写明：**为一个到不了的路径写检查，换来的是一条永远不红的断言**
  （判据页「断言空转」那条的第三种形态：不是样本为 0，而是那条路径根本不存在）。
- **验收（轻方案那一批的）**：`test/groupb/login_lockout_test.go` 两条新用例（读快照 + 解锁后同一 IP 立刻能登录；会话独占与 IP 合法性）。
  变异验证两次都红：`ResetAttemptLock` 改空实现 → 「reset 说清掉 0 条」；快照 `Locked` 写死 false → 「快照说它没在锁里」。
  其中一条断言是**用例先错后对**：第一版把「reset 后记录消失」的复检放在成功登录之后，而那次登录自己重建了一条记录，
  测出来的是假红——挪到登录之前，测的才是 reset 的语义。
- **验收（① 的准备这一批）**：`test/login_account_watch_test.go` 两条——
  ① 一个账号被 12 个不同 IP 各试错一次：记账 `fails=12`、`distinct_ips=12`、样本 IP ≤8，
  而**没有任何 IP 处于锁定**、随后正确密码仍然 200（这两条是反向断言：观察不许变成闸门），
  再核端点带回 `accounts` 且 `accounts_meta.multi_ip_yellow` 等于 `suspect_distinct_ips`（面板不许自己抄数）；
  ② 键的形状：三种写法（大小写/首尾空白）合成一条、超长标识被夹成 64+省略号且**只聚成一条**、失败多的排在前。
  变异验证五次各拦一处：不记账 / 不归一化 / IP 样本上界抬到 100 / 不截断键长 / **让观察参与判定**（fails≥5 就去锁 IP）。
- **①已拍（2026-10-06，A = 只观察、不做账号闸门，配一周读数回看）**：B（按标识做失败连击闸门）的误伤面
  比它防的东西更糟——**用户名可被任意填**，攻击者能点名把某个账号锁在门外，而锁的是"这个标识登不进来"而不是"对方被打退"。
  C（按 账号×IP 组合）阈值更难定且对真分布式仍无效。所以这一列**永远只是给人看的**，
  那条"观察不许变成闸门"的反向用例（`test/login_account_watch_test.go` 第①条的后半）从此是**定案的守卫**，不是临时保险。
  **② 已拍（2026-10-07，维护者选 A）**：自动拉黑**不吃**登录失败，两条机制继续互不知情。理由沿用 ① 那条定案的同句判据——
  登录失败的来源 IP 大多是 NAT/共享出口，把这种计数喂给 `auto_block`（阈值是给数据面 403/429 定的）等于让攻击者的连击
  把一整栋楼拦在门外；这与 ① 拒绝"按账号锁人"用的是同一个顾虑：**观察到的形状不该直接变成闸门**。
  **本条因此保持登记**（它记的是一条明知存在的边界，不是待办）；真要补这个洞，形状是先给那条计数做自己的阈值与
  自己的窗口、并把"被拉黑的理由"单独出一格，而不是把它接进现有那条——这是当时给出的 B 方案，未选。
