## 四、未来发展方向（归类提炼）

### 1. 性能与可观测性 —— 唯一真正的技术硬骨头
- **P118⑤ 是现网告警的大头**：`/rank/boards` 尾部已被 P118① 救回，但 `Coverage`、趋势图仍 560~787ms，根因是 `api_call_logs` **窗口≈全表（89%）**——P118② 已用生产 DDL 实测证明复合索引无效。**唯一解法**是有界保留期（`MONITOR_RETENTION_DAYS` 从 0 改）或日粒度预聚合表。
- **保留期本身是决策点**：入库量日增（10-08 尖峰 23,846 行/日未归因），需先答"行为明细为谁留"，再动结构——这是维护者级决策，不是纯技术活。

### 2. 跨仓数据治理与取证 —— 新兴主线
- **P122 带内业务码落库**：骨架加采集位、源侧填值（如 `zj_novel` 把信封码填入）。它**阻塞装配仓 S104 的取证**（分不清 429 风控 vs 会话被拒，而两者处置完全不同）。
- **zj_novel 86 条带内失败**：P121 第 0 步已确认 S103 已在线上，说明问题不在发版——需**另起一轮**按业务码查封套（P122 正是为此铺路）。这是骨架仓与装配仓**协同排查**的典型场景。

### 3. 产品取舍 —— 收口尾声的对外可见变更
- **P119 残项（①③ B 档）**：① 收回"额度清零时间"对外能力需答存量用户回落问题；③ 去掉固定间隔判定等于**放宽限流**，是对外可见行为变更。两者都该"先读数据再拍"，不宜顺手改。

### 4. 工程化收尾 —— 让新架构真正闭环
- **P116 CI 真正跑起来**：deploy 仓 `.github/workflows/build.yml` 已接线（钉 `skeleton-v110`），但**首次实跑待 runner 到位**；观察期过后改写 AGENTS 口径。

### 5. 安全与合规 / 账号策略
- **P108 账号自动闸门回看（10-13 到期）**：到期即回看，严格按"现网真出现低速跨 IP 连击才立项"的纪律，不因为"有观察数据"就加自动处置。
- 既有约束稳如磐石：凭证不入库、SSRF 按来源区别对待、AGPL 义务、内容维度同意位（P113 已收口，存量旧名称不追溯删）。

## 七、三项悬置决策的具体推进建议

> 对应 §三 表中 P118⑤ / P122 / P116 三项，以及用户追问"你有什么建议吗"的答复。本节把那三项从"待处置"落成**可执行的推进路径**，每条都标注真实卡点与推荐动作。

### 7.1 P118⑤ 保留期决策 —— 策略待拍板，但 A 是必做项

**性质**：维护者级决策，不是纯技术活。现网 71/82 条 SLOW SQL 来自 `Coverage`(:508, 560–606ms) 与趋势(:209, 552–787ms)，`WHERE` 无等值列、走 `idx_created_at` 扫全窗口（窗口≈全表 89%），复合索引已在生产 DDL 实测否决（② 撤下）。

**三选项评估**（修复报告原文）：

| 选项 | 含义 | 我的判断 |
|---|---|---|
| **C** 永久保留 + 接受告警 | 不止血 | **排除**：把噪声与只增不减的表当正常，与"慢查询要出声"口径自相矛盾 |
| **A** `MONITOR_RETENTION_DAYS` 改有界 | 改一个 config，无 DDL、无新代码 | **必做（止血）**：立刻止住表无限增长、稳住"全部数据源"全表扫（0.08s 且持续变慢）；但治不了 7 天窗口内 coverage/trend 的 `GROUP BY` 临时表 |
| **B** 日粒度预聚合表 | 新表 + 迁移 + 历史回填 | **结构解（治愈）**，但动手前先问更便宜的问题 |

**推荐路径**：
1. **先做 A**：把保留期设为有界（建议 30 天，覆盖 7 天窗口并留余量）。这是单条 config 变更，风险最低，应先于一切结构改动落地。
2. **A 落地后先验证 B 的廉价版**：文档已说行为明细**正在被 `api_call_stats` 日粒度累计归档**——先查 `api_call_stats` 这张现成日聚合**能否直接喂 coverage/trend 查询**。能，则 B 退化成"端点从扫原始行改为读现成日聚合"，比新建表便宜一个数量级；只有确认 `api_call_stats` 缺维度，才值得新建预聚合表 + 回填任务。
3. **给维护者的一句话问题**（决定 A 取多少天 / 是否上 B）：**"那张每天几千行的行为明细到底为谁留着？"** 答"只给近期排障"→ 仅 A（30 天足够）；答"面板要长期历史趋势"→ 走 B 且优先复用 `api_call_stats`。

### 7.2 P122 跨仓取证 —— 设计已完，建议优先落地

**性质**：已设计好、只差落地的小改动，且是**解锁项**。现状：`in_band_error` 是布尔、`in_band_reason` 只枚举无值，站方信封 `code`(0/4001/401/403/429) 从没存过 → 装配仓 S104 取证第二步撞墙（"会话被拒"与"429 风控"分不清，处置却完全不同）；现只能手工重放，又会往 `api_call_logs` 落行污染基线。

**推荐动作（落地步骤）**：
1. 骨架侧加 `in_band_code`（`size:32`，**空 = 源没给，合法状态、读数不猜**），在 `base/legado/observe.go` 既有支路上补一格，`sources/zj_novel/content.go` 填信封码。
2. P37 同意位关闭时**不抹**业务码（它不是内容维度，理由写进注释）。
3. 面板只加明细列 + 筛选，不进榜（维度白名单不因此放宽）。
4. 排进**下一个骨架 tag** 发布（与 `cleared_at` 同批 AutoMigrate 动作）。

**两个落地提醒**：
- **AutoMigrate 加列也算生产 DDL**：文档把 `cleared_at` 标为"生产 DDL＝要授权"，`in_band_code` 同批，别因"自动迁移"跳过授权意识。
- **取证要等数据积累**：列上线后需先跑一段时间攒够样本，S104 才能区分两种形状——所以 P122 是"前置发布"，真正的 S104 分析是跟在后面的第二轮（修复报告已点明"zj_novel 那条要另起一轮去查封套业务码，不是靠发版"）。

### 7.3 P116 CI/观察期 —— 卡在 runner，不在决策

**性质**：卡在外部条件的验证缺口，不是技术争议。deploy 仓 `.github/workflows/build.yml` 已接线、`SKELETON_TAG` 钉 v110，但**首次实跑待 runner 到位**；线上已接管（10-09 12:52 换装、12:56 验收 0 拒连），剩"观察期：跑过一两个版本、面板无异动再收"。

**先澄清一个易误判的耦合**：**P125（私有侧 `origin_` 缺骨架 tag v110/v111）不是 P116 CI 的硬阻塞**。文档明确"CI 的 clone 源是公开 gitee，版本正本是 `build.yml` 的 `env.SKELETON_TAG`"——私有侧无任何链路读那个 tag。P125 是**检查卫生项**，建议取 B（摘掉私有目标，别让"没人读的复算检查"制造假依赖），可顺手收，但不挡 CI 跑。

**推荐动作**：
1. **真正 blocker 是 runner，不是代码**：整套新架构唯一"建而未跑"的缺口就是它，先把 runner Provision 起来。
2. **别用 markdown 改动去验证 CI**：报告自己写"本轮装配仓只改了 markdown，跑一次全量构建不构成 CI 那条链的验证"。要让 CI 真被锻炼，得推一个**真正改构建/携带清单**的改动走完 build→tag→换装全路径。
3. **观察期不要提前收**，顺序固定为：`runner 到位` → `一次真改动跑通 CI` → `生产跑 1–2 版 + 面板监控` → `无异动才收`。
4. **提前定义"无异动"的判据**：建议明确为 `/datasources` 与新老二进制逐 id 对拍一致、`OnBoot` 号池链路无变化、401/拒连无尖峰——这几点本地对拍已过关，观察期只需确认生产随时间仍成立。

## 八、工作模式改进意见

> 本项目的工作模式（先入册再动手、门禁台账、基于判据、归档、修复报告加减账、变异测试、巡检、自纠、字面量互证）成熟度极高，10-10 轮能靠巡检自己抓出 P120/P123/P124 并当天固成门禁即为佐证。以下不是在挑刺，而是针对本轮暴露的几处"模式级盲点"提的加固意见——均来自文档中已发生的真实事件。

### 8.1 把"断言空转"从被动发现变主动门禁

**本轮最深的重复失败模式**是"明明有检查、检查全绿、但什么都没验到"：
- **P120**：面板探针语法自 10-07 起坏掉，**无人报**（门禁没覆盖探针自身语法）。
- **P123**：`deploy.sh` 装上一颗"零数据源"二进制，`md5`/`active`/契约行全部"成功"——门禁对"携带数为 0"失明。
- **P124**：`RankCacheSec` 声明了、有人读、**装配块没接**→ P118③ 缓存装了等于没装（0 语义恰是"每次真算"），四条榜用例全绿。

三者本质同一类：**验证器对"它声称要验的东西"失明**。项目已为其立了判据页《断言空转》第⑬种，并补了 `config-wired-check` 门禁——但这是**事后**由巡检抓出来的。

**建议**：把"负对照"设为新检查/新门禁/新配置字段的**一等公民**——每新增一个"声明了就得接上"的东西，必须同时附带一个"故意不接/故意损坏就必红"的用例，像变异测试（`五次变异各红`）那样前置，而不是等巡检来抓。尤其对"声明式配置字段"（如 `RANK_CACHE_SEC`）应默认要求 `config-wired-check` 类的装配断言。

### 8.2 跨仓依赖从"文本提及"升级为权威索引

10-10 轮已跨三个仓库作战：公开骨架仓、`loomproxy-deploy` 装配仓、以及 S 系列取证单（S104 等）。但"谁阻塞谁"目前只是待办清单里的**一句文本**：P122 写"被它阻塞的条目：S104"、P116 写"待 runner"。当一项悬置决策横跨多仓，这种文本耦合会让关键路径**藏在某一个仓的待办里看不见**。

**建议**：在 `规范/` 下维护一张轻量**跨仓依赖/阻塞索引表**（甚至就是一页），每轮刷新，作为"跨仓谁阻塞谁"的权威来源。它能在任何一仓准备收口时，先回答"是否有未解的跨仓 blocker 因此轮不可见"——避免一个仓顺利收口、另一个仓的取证却因前置列没上线而卡死（正是 P122→S104 的形状）。

### 8.3 "待复采 / 观察期 / 回看"类条目做触发式收口

本轮大量条目处于"等外部事件"状态而非"等代码"：P118③ 现网读数"待下一次 tag + deploy 换装后复采"、P116 观察期"跑过一两个版本再收"、P108"一周读数回看（10-13 到期）"。这些是**合法的等待**，但若只挂在待办里不带触发条件，容易在多个发版轮次后悄悄蒸发。

**建议**：给每个"等待类"条目打上**触发事件标签**（如 `trigger: 下一骨架 tag + deploy 换装`、`trigger: 10-13 到期`），并在每轮修复报告的"加减账"里强制扫一遍"本轮回火的触发事件是否覆盖了这些条目"。把"等一个事件"显式化成发版检查单的一项，而非散落在各处的人肉记忆。

### 8.4 门禁名额 2/2 硬上限要配"候补清单"，防沉默丢弃

本轮 `script-syntax-check` + `config-wired-check` 把门禁闸名额用满（2/2），报告明确"本场不再加第三条"。这对聚焦是好事，但代价是**该查的被推迟**——下一轮若又抓出 P120 一族的新盲点，没有名额就进不了门禁。

**建议**：保留"每轮新增门禁类型 ≤2"的聚焦纪律，但同步维护一张**门禁候补清单**（本轮发现、因名额暂未固化、但值得固化的检查），让它随下一轮一并评审。这样名额上限变成"节流阀"而非"遗忘黑洞"——候选项始终可见，不会因一轮名额用尽而消失。

### 8.5 "按判定收口"强制留痕，否则等于静默丢弃

10-10 轮把收口逻辑从"做完才收口"升级为"按判定收口"——P112① 凭现网读数据判"暂不办"、P118② 凭生产 DDL 实测否决撤索引、P118④ 凭口径判"不动 200ms 档"。这是工程成熟度提升。但风险也在此：**"判定收口"若不留证据，就退化成"静默丢弃"**。

**建议**：把"判定收口须带一条证据指针"立为硬规则，权重等同一次代码改动——可以是那三条只读 SQL 的回显、可以是 `SHOW INDEX` 的复验、可以是口径页的对应条目。文档目前大多已这么做（值得肯定），但应**显式成规**而非靠个人习惯，确保任何一轮的"按判定收口"都能被下一轮的读者一键复核，不靠翻聊天记录。

> **小结**：本项目的模式强在"先入册、基于判据、变异自证、巡检抓漏"；上述五条不是推翻，而是把已存在的优点**前置化、索引化、触发化**——让"断言空转"在写检查时就被挡下、让跨仓 blocker 一眼可见、让等待类条目随事件自动收口、让门禁候补与判定证据都不因一轮结束而蒸发。

## 九、骨架开发 ↔ 数据源开发的协同工作建议

> 协作形态已由《骨架当库-数据源当应用》定案：骨架是 Go module **库**（`main.go` 仅信号处理 + `app.Run`，`sources/all.go` 是空边界标记），`loomproxy-deploy` 是**应用**（唯一携带清单 `sources/deploy_all.go`，靠 `replace` 指骨架、靠 `SKELETON_TAG` 钉版本），**唯一真实产物是 deploy 编出的 `loomproxy-go`**，骨架自身二进制只用于自测。所有协同摩擦都集中在"库↔应用"这条仓库边界上。本节建议均锚定已发生的真实事件（P116/P119/P122/P123/P125）。

### 9.1 CI 拼接流水线应是第一公民，而非"接线待跑"

**现状**：P116 的 deploy 仓 CI 已接线（`build.yml` 钉 `skeleton-v110`）但**首次实跑待 runner**；而骨架自己已有 `vet`/`test` 门禁。deploy 仓 CI 的**唯一不可替代价值**是"跨仓拼接"——checkout 骨架@tag + 构前端 `web/dist` + `replace` 指绝对路径 + CGO 编二进制 + `sources/deploy_all.go` 空白导入拼装。这条拼接链正是真正的风险面（`web/dist` 不进 git 的 embed 耦合、replace 路径、CGO、parity），而它恰恰从未被实跑验证过。

**建议**：把"让跨仓拼接流水线先绿"排在所有其他门禁之前。deploy 仓的 `vet`/`gofmt` 与骨架自测**重复**，可放轻；拼接链（含第 9.3 条的 parity）才是必须第一个跑通的。P125（私有侧 `origin_` 缺 tag）已澄清不是阻塞——CI clone 源是公开 gitee、版本权威是 `build.yml` 的 `env.SKELETON_TAG`——所以真正待办只有一件事：**把 runner Provision 起来，推一个真正改构建/携带清单的改动走完整条链**。

### 9.2 验证产物边界纪律化：依赖携带源的一律用部署仓产物

**现状（P119 落地的关键学习）**：报告原文已记——"自 P116 之后，某一屏有没有某个控件这类黑盒验证**必须拿装配仓的产物跑**，骨架产物里那些屏天然是空页——空页上'没有这个控件'永远成立，是断言空转的新入口"。这不该只当一次性教训，它是普遍规则的一个实例。

**建议**：在 `开发约定.md` 立一条硬规则，把 P119 的经验**泛化**：
- **骨架自测（`./...` + `make vet`）只证骨架内部逻辑**——它不携带任何源，`sources/` 是空包，源包测试（在 deploy 仓 `tests/`）它跑不到。
- **任何依赖携带源的行为，验证必须用 deploy 编出的产物**（或空白导入 `deploy_all.go` 的测试 harness）：榜单读取、`quota` 按源计费、`in_band` 信封处理、以及**任何会列出源的 UI 屏**。
- 一句话判据：**"这个行为在骨架二进制上跑得通吗？"如果骨架二进制根本没带源，那它在这上面的'通过'一律不作数。** 这条规则同时堵住 P119 的"空页假绿"和 P120 那类"探针对形状失明"的变体。

### 9.3 携带清单自校验 + 持续 parity 门禁，堵死"零源二进制"

**现状（P123 的教训）**：`deploy.sh` 曾装上"零数据源"二进制，而 `md5`/`active`/契约行**全部"成功"**——门禁对"携带数为 0"失明。文档风险清单第 5 条也点明"空白导入缺位 → 构建不报错，最阴的一条"，但那是手动 smoke（`curl /datasources`），不是门禁。P116 零停机换装时做过一次**一次性** `/datasources` 逐 id 对拍，但那是事件级、非 recurring。

**建议**：
1. **manifest 自测**：deploy 仓加一个测试，断言已注册源数 `> 0`（或 == 期望数），让"清单漏登记"在 `go test` 阶段就红，不必等运行时 curl。
2. **部署时硬拒**：P123 已加"携带数 == 0 即拒装 + `--allow-no-sources`"，把它从脚本 flag 升级为**门禁级**——无 `--allow-no-sources` 时携带数为 0 直接 fail，且这条检查必须进 CI。
3. **parity 常态化**：`/datasources` 与新老二进制逐 id 对拍、OnBoot 号池链路一致，做成**每次发版的 recurring gate**（而非 P116 那次一次性对拍），因为"拼接是否仍等价"只在发版时才有意义。

### 9.4 跨仓"观测契约"显式化——P122 的根因就在这里

**现状（P122 的根因）**：骨架负责观察（`api_call_logs`、`in_band_reason`/`in_band_error`），数据源负责产出信封（reason/code）。但"骨架观察什么"与"源必须填什么"**从没写成合同**——源 emit `reason`，骨架 collect `reason`，而信封里的 `code`(0/4001/401/403/429) **从未进合同**，于是落库时只剩形状没有值，S104 取证在第二步撞墙。这是"有形状没值"类缺陷的源头，P122 只是第一例。

**建议**：维护一份显式的**观测契约**（可以是 `docs/架构/` 一页，也可以是 envelope struct 的 godoc）：列清骨架期望源在信封里填充的字段（reason、code、media 等），并写明**"空 = 源没给，合法状态、读数不猜"**的惯例（项目已有此口径，应固化进契约）。**强约束**：envelope struct 增删字段，必须同 PR 更新契约页——这样下一个"形状有了值没存"的坑在写代码时就被拦下，而不是等取证时才发现。

### 9.5 两阶段跨仓票据 + 回退路径定期演练

**现状（P122→S104 的形状）**：骨架加采集位（`in_band_code`）必须**先发且上线**，deploy 仓再累积若干天数据，S104 才能按业务码分两种形状——这是天然的"Phase 1 骨架 / Phase 2 部署"两阶段，却只以"被它阻塞的条目: S104"一句文本记录在 P122 里（见 §8.2 的跨仓索引建议）。同时《落地清单》的"回退方法"写得很完整（源可整目录搬回骨架、零损失），但 `sources/private` 已冻结、回退路径**从未实际演练过**。

**建议**：
1. **两阶段票据建模**：凡是"骨架加采集/观察位、部署仓后续消费"的跨仓项，拆成显式两阶段——Phase 1 的 done 标准是"已发 + 已上线"，Phase 2 才能启动且必须注明"需先累积 N 天数据"；依赖进 §8.2 的跨仓索引，避免卡在某仓待办里看不见。
2. **回退演练常态化**：回退是安全网，但"写在文档里的回退"不等于"能回退"。建议每个大版本（或每次骨架 bump）在 staging **真跑一次回退**（搬一个源回骨架、编出、对拍 parity），确认《落地清单》"第 3/4 步文件从未在生产改过形态"这个前置仍成立。否则回退只是希望，不是保证。

> **协同工作的核心矛盾**：库与应用各自门禁都很强，但**边界处的拼接、验证、契约、回退**四件事没有持续化——它们只在 P116/P119/P122/P123 出事时才被一次性补上。上述五条就是把"边界处的临时补丁"变成"边界处的常设纪律"。
