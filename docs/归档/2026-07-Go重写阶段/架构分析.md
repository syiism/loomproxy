# LoomProxy-Go 架构分析

> 本文基于 2026-09-14 的代码现状（dev 分支，Go 代码约 2.2 万行）撰写，从架构视角分析 loomproxy-go 的分层结构、核心机制、关键设计决策与已知权衡。权威的现状性事实以仓库根目录 `AGENTS.md` 为准，本文侧重"为什么这样设计"与"各部分如何协作"。

## 1. 项目定位

loomproxy-go 是一个**网络小说书源 API 代理/聚合网关**（Python 版 `api-proxy` 的 Go 重写）。它解决的核心问题：

- **对上**：代理十余个小说/有声书平台的私有接口，处理各平台迥异的协议细节（签名、UA 伪装、HTML 抓取、字段漂移）。
- **对下**：输出统一格式的 **Legado（阅读 App）书源**风格数据，客户端用一套标准动作（搜索/详情/目录/正文/推荐/榜单）消费全部书源。
- **商业化**：在聚合能力之上叠加完整的用户体系（注册/JWT/角色/套餐/卡密兑换）与多租户资源管控（数据源访问控制、额度计费、速率限制）。

因此它同时具备两种属性：**协议适配网关**（类似 API 聚合层）与**多租户 SaaS 后端**（用户/计费/管控/运营面板）。架构设计围绕这两条主线展开。

## 2. 技术栈与依赖

| 关注点 | 选型 | 架构影响 |
|---|---|---|
| Web 框架 | Gin | 路由+中间件模型决定了全项目的"责任链"扩展方式 |
| ORM | GORM + SQLite（默认）/MySQL/PostgreSQL 三方言 | 多方言带来 SQL 方言分流成本（如 user_roles 去重、趋势图日期函数）；SQLite 默认使单二进制即可运行 |
| 缓存 | go-redis v9（失败回退纯内存 LRU+TTL） | 缓存接口双模实现，上层无感；Redis 不可用时自动降级 |
| 认证 | JWT HS256 + bcrypt + 静态 API Key | 无外部身份依赖，会话吊销靠自建的 `auth_sessions` 表 |
| HTML 抓取 | goquery | 仅 uxx（海阔视界）一个源需要 |
| 并发原语 | golang.org/x/sync（singleflight/errgroup）、自研泛型注册表、sync.Pool | 无消息队列、无外部调度器，全部进程内解决 |
| 前端 | Vue 3 + Vite 5 + Tailwind 3（pnpm），`go:embed` 打进二进制 | 前后端同进程交付，部署单元 = 二进制 + .env + data/ |
| 部署 | Makefile / systemd 脚本 / Docker（多阶段） | 三条交付通道，同源 glibc 规避 CGO（sqlite3）运行时错配 |

刻意保持的**零外部中间件**（除可选 Redis/MySQL）：无 MQ、无定时任务框架、无配置中心——所有后台协程（号池维护、代理池水位、限流器回收、监控落库）都是进程内 goroutine + ticker。这降低了部署门槛，代价是多实例水平扩展时状态各自为政（见 §12 权衡）。

## 4. 进程生命周期

`main.go` 极薄（信号监听 + cancel），全部装配在 `app` 包：

```
main()
  └─ SIGINT/SIGTERM → ctx cancel
  └─ app.Run(ctx)
       ├─ conf.Load()            环境变量 > CWD/.env > 可执行文件目录/.env（不覆盖已有环境变量）
       ├─ CreateApp()
       │    ├─ db.Init()         GORM 三方言连接 + AutoMigrate + 数据修复（user_roles 去重、
       │    │                    组码展开为源码、卡密明文迁移哈希、seed 角色/设置/套餐/管理员）
       │    │                    失败仅告警不阻断启动（预热等协程判空跳过）
       │    ├─ SetTrustedProxies / 全局中间件 / 各业务域 RegisterRoutes
       │    ├─ registerHandlers() 遍历 base.All() 动态挂载 54 个处理器
       │    └─ validateRoutes()  对照 expectedRoutes 校验路由齐全（仅警告）
       ├─ initMonitorPersistence()  监控明细淘汰批落库回调注入
       ├─ go prewarmCache()      预填 /datasources 与 /data 的 Redis 缓存（30s 超时）
       ├─ go xmly.GetDevicePool() 号池启动即初始化（XMLY_POOL_ENABLED 控制）
       ├─ base.StartProxyAPIRefresher()  动态代理池水位维护（配置 UPSTREAM_PROXY_API 时）
       ├─ base.SetProxySourcesGetter()   注入按数据源启用代理的配置读取
       └─ http.Server{ReadTimeout:10s, ReadHeaderTimeout:5s, MaxHeaderBytes:1MB}
            关闭：15s 优雅停机 → lifecycle.RunCleanups()（监控明细兜底落库等）
                  → utils.CloseAll()（Redis 等）→ shutdownDone
```

要点：

- **优雅停机是显式编排的**：`ListenAndServe` 返回后等待 `shutdownDone` 才退出，修复过 `log.Fatal` 抢在清理前 `os.Exit` 的竞态。
- **启动即完成重资源初始化**（号池、缓存预热、代理池），首个用户请求不承担懒加载成本。
- **`lifecycle` 包提供注册式清理钩子**，关停动作可由各包自行登记，避免 app 包反向了解所有子系统细节。

## 5. 核心机制一：处理器自注册（插件式数据源）

这是全项目最重要的扩展点，新增数据源不改任何既有代码：

```go
// handlers/fq_tutu/search.go init()
base.Register("fq_tutu_search", newSearchHandler, 0, metadata)
```

机制分解：

1. **泛型注册表** `base/registry.go`：`Registry[T]` 内部 `sync.Map`，包级函数（Register/Get/All/...）委托默认实例。注册携带 name、factory、priority、metadata（含 source/action）。
2. **接口契约** `base.Handler`：`Handle(ctx, params)` + 路由自描述（GetPath/GetMethods/GetQueryParams/AuthRequired 等）。路由信息由处理器自己声明，app 包无需硬编码路由表。
3. **模板方法继承**：数据源处理器内嵌 `base/legado/` 的基础处理器（如 `legado.SearchBaseHandler`），基础处理器实现完整的"取参 → 拼上游 URL → FetchJSON → 归一化 → Legado DTO"流程，子类只需覆盖 `APIConfig`（上游前缀）与字段归一化逻辑。五个基础处理器对应 Legado 的五个标准动作。
4. **动态挂载**：`app.registerHandlers()` 遍历 `base.All()` 生成 gin 路由，路径统一为根级 `/{source}/{action}`；`expectedRoutes` 启动时对照校验（缺失仅警告，不阻断）。

**架构评价**：这是"注册表 + 模板方法"的组合，相当于一个进程内插件系统。54 个处理器、10 个数据源共用 5 套骨架代码，归一化差异（如各平台 isVip 判定口径不同）被约束在子类的少量覆盖方法里。代价是处理器间以 `map[string]interface{}` 传参（已知的性能取舍，见 `docs/方案补充.md`），以及注册依赖包级 `init()` + 空白导入的隐式装配。

## 6. 核心机制二：请求处理管线

### 6.1 全局中间件链（所有请求）

```
requestID(X-Request-ID) → recovery → logging → CORS(*) → cacheControl(no-cache) → ipBlock
```

- `ipBlock`（IP 黑名单）置于 CORS 之后——不影响预检，但先于一切业务逻辑拦截被拉黑 IP（含登录/注册）。
- 真实 IP 还原依赖 `SetTrustedProxies(127.0.0.1, ::1)`：只信本机 nginx，XFF 从右起跳过可信段取首个不可信 IP。生产为 Cloudflare 橙云链路时，真实 IP 由**服务器 nginx 的 real_ip 模块**（CF 官方 IP 段 + `CF-Connecting-IP`）还原，gin 拿到的 `$remote_addr` 已是真实访客 IP。该 nginx 配置在仓库之外，是部署层面的隐性依赖（迁移服务器必须随迁）。

### 6.2 数据源路由的独立中间件链（业务闸门）

以 `GET /tutu/search?key=...` 为例，一次请求穿过六道闸门：

```
┌─ authMiddleware        仅当处理器 AuthRequired()（网关层：JWT 或 API Key，白名单跳过）
├─ monitorMiddleware     调用监控（不计额度），置于最前以覆盖后续所有 403/429/5xx
├─ baseURLCheckMiddleware 解析 baseUrl 三级来源并做 SSRF 分级校验
│    请求参数(严格) → 用户个人配置(严格) → 平台默认配置(管理员可信，允许内网)
├─ DataSourceAccessMiddleware  数据源启用? 用户套餐包含该源?（匿名按免费套餐）
├─ BillingMiddleware     status=0 禁用→403；请求前查当日额度(不足 429)；
│                        上游 200 后按 quota_costs 扣减 + 写 quota_usage_logs
├─ RateLimitMiddleware   套餐级>全局；窗口计数>固定间隔；IP 与用户双维度都放行才放行
└─ handlerFunc           buildParams(对象池复用 map) → handler.Handle → 统一响应封装
```

顺序设计有据可依：监控在计费**之前**（失败调用也要可观测）；访问控制在计费之前（无权者不计费）；计费在限流之前（额度判定优先于速率判定）；计费以**响应成功**为扣费条件（`captureWriter` 包装 ResponseWriter 捕获状态码，上游 200 才扣减）。

### 6.3 统一错误映射

处理器返回的 error 由 `app.handleError` 集中翻译：超时→504、上游非 2xx 透传状态码（`UpstreamError`，Message 附响应体前 256 字节摘要以区分同为 403 的风控/下架）、上游读取/解析失败（StatusCode=0）→502、SSRF 拒绝→400、DNS/连接拒绝→502、客户端取消静默不记日志。下游永远看到统一信封 `{"code","msg","data"}`，错误细节（如 xmly 签名 URL）经脱敏不透传。

## 7. 核心机制三：弹性获取栈（base.Fetch 链路）

所有打上游的请求汇聚到 `base.BaseHandler.Fetch/FetchJSON/FetchText`，形成五层防护：

```
请求 → ① 上游短TTL缓存（UPSTREAM_CACHE_TTL，默认10s）
         命中直接返回；search/detail/chapter/explore 开启，content 不缓存
      → ② singleflight 请求合并（键=URL+请求头，并发相同请求只打一次上游；
         15s 超时兜底、失败结果不共享、leader panic 防护）
      → ③ 按上游 host 熔断（连续失败 CIRCUIT_BREAKER_FAILURES=5 次开启，
         冷却 30s 内快速失败 503；4xx 与客户端取消不计入）
      → ④ 代理池故障转移（按数据源接口门控启用；网络错误自动换代理/回退直连
         重试一次；上游 403 计入代理失败促轮换；免费 socks5 代理寿命分钟级，
         池按水位模型自维护：低于 5 个自动复验+拉新）
      → ⑤ 失败时降级返回过期缓存（过期项只在写入时清扫，专为降级保留）
```

配套机制：UA 轮换池（12 个指纹，`UPSTREAM_UA_ROTATE`）、响应体 `sync.Pool` buffer 池、共享 `http.Client` 连接池（代理按代理懒建独立 Client）、xmly 的签名 URL 天然绕过合并/缓存（nonce/timestamp 唯一）而无签名端点享受缓存。

**实测价值**（见 AGENTS.md）：开启 10s 上游缓存后番茄系 100 并发成功率 ~2%→~78%，混合负载 QPS 43→95。这一层是整个网关在上游风控高压下存活的关键。

## 8. 认证、会话与权限模型

三层正交概念，易混淆需区分：

| 层 | 机制 | 作用域 |
|---|---|---|
| 网关层 | `authMiddleware`→`utils.VerifyAuth`：JWT（Bearer/query/Cookie）或静态 API Key；`AUTH_ENABLED=false` 时整体关闭（计费随之关闭，但接口禁用仍生效） | 数据源路由按 `AuthRequired()` 逐个声明 |
| 用户层 | `AuthRequired()` / `AdminRequired()`（查库校验 admin 角色） | `/auth/me`、`/user/*`、`/quota/*`、`/admin/*` |
| 会话层 | JWT `jti` ↔ `auth_sessions` 行（设备名/IP/最后活跃，5 分钟节流写）；无 jti 的旧 token 一律 401 | 两层鉴权都校验；logout/禁用/软删除/改名均同步吊销会话 |

设计要点：

- **吊销即时生效**：无状态 JWT + 有状态会话表的组合，换取"管理员禁用用户立即踢下线"。
- **token 有效期四级解析**：用户个人设置 > 系统设置 > 环境变量 > 默认 168h；任一级为 -1 即永不过期（JWT 不写 exp，Cookie 写 10 年）。
- **角色单选模型**：用户至多一个角色，`db.ReplaceUserRole` 直接操作关联表（绕开 GORM many2many Append 的重复插入坑）；套餐可绑定角色，套餐变更/卡密兑换自动同步角色（永不自动授予 admin，防自助兑换提权）。
- **找回密码的防枚举**：用户名不存在与邮箱不匹配返回统一模糊错误；IP 限频 + 连续失败锁定；可叠加场景化验证码。

## 9. 商业化三轴：访问控制 × 额度 × 限流

对每一次数据源调用，系统沿三个正交轴做管控：

1. **能不能用（Access）**：`DataSourceAccessMiddleware` 按 `data_sources.status` 与 `quota_plan_data_sources` 关联判定，匿名用户按免费套餐视图。
2. **用多少（Billing）**：套餐限额链解析——用户数据源级覆盖（追加语义：套餐限额 + 覆盖值，下限 0）> 套餐限额 > 不限；北京时间零点重置；上游成功后扣减并写流水；**并发下允许少量超扣**（先成功后扣，已知取舍）。
3. **用多快（RateLimit）**：双模型并存——`limit_count+window_sec` 滑动窗口计数（允许突发）与 `interval` 固定间隔（不可突发），优先级 套餐级 > 全局、窗口 > 间隔；IP 与用户双维度各自计数都放行才放行，用户维度 key 含 planId 隔离套餐；管理员豁免；限流器闲置 10 分钟回收，配置直查库保存即生效。

套餐体系本身是数据库驱动的：`quota_plans`（含 level 等级与绑定角色）→ 卡密兑换（哈希存码、事务+审计、时长叠加/等级判定）→ 兑换成功同步角色。管理端提供全套 CRUD，系统行为（注册开关、默认角色、代理门控、自动拉黑阈值、公告、发码平台配置等）全部由 `system_settings` 表驱动，多数带 10s 缓存 + 写时失效。

## 10. 可观测性与自愈

**运行时 profiling（2026-09-15）**：`/debug/pprof/*` 整组由 `AdminRequired` 保护挂载（heap/goroutine/profile/trace 等标准端点），性能分析从猜测变为可测量——此前全仓库无 pprof 入口。

**监控双轨制**（`base/metrics.go` + `app/monitor.go`）：

- 内存聚合计数（重启清零）+ 最近 200 条明细环形缓冲；
- 缓冲满 250 淘汰最旧 50 条**异步批量落库** `api_call_logs`（保留 7 天）；关停时 Drain 兜底，且先等飞行中的异步批完成（`flushWG`）再取环——堵过"淘汰批已离环而落库未跟踪"的丢失竞态；
- 清理明细前按 数据源/接口 聚合累加进 `api_call_stats` **永久归档**；lifetime 口径 = 归档 + 未清理明细 + 会话内存 − 已落库淘汰部分（修过双计虚高 50 倍数的 Bug）；
- 趋势接口合并落库明细与内存未落库明细，避免低流量时段图表空白。

**IP 自动拉黑**（`app/autoblock.go`）：监控 RecordCall 后钩子按滑动窗口统计 403/429，达阈值写 `blocked_ips`（Source=auto），回环地址永不自动拉黑（防同机部署的数据源项目自锁）。配置走系统设置即时生效。

**xmly 号池**是项目中最复杂的自治子系统（状态机 hot/cold/spent/dead）：平时只烧 1 个热号（免广告时长按墙钟倒计时，多热号并行燃烧是浪费）+ 2 个冷备；临期原地续领或退役转正（优先已领取未过期的冷备）；spent 次日 0 点复活（逐个刷新迭代，修过只试最小主键导致其余永不复活的饿死缺陷）；501 自愈（singleflight 按设备合并补领，最多重试 2 次）；错误率驱动热号扩容（窗口内非 501 错误率 >30% 且样本 ≥20 判疑似限流，热号 +1 上限 3）；全局风控冷却闸门 + 全局并发信号量（单 IP ~130 次触发 `album risk invalid`，冷却 65s；有健康代理时改为 1s 退避换代理）。

## 11. 数据模型与前端

**模型分组**（`models/`，GORM AutoMigrate）：

- 用户域：`User`（软删除、PlanID、TokenExpireHours、UsernameChangedAt）、`Role`、`UserRole`、`AuthSession`、`VerificationCode`（场景化验证码，只存 SHA-256 哈希）
- 商业域：`QuotaPlan`（level、RoleID）、`QuotaLimit`、`UserQuota`、`UserQuotaOverride`、`QuotaCost` / `QuotaCostPlan`（速率双模型；`group_code` 列实际存数据源码——组概念已移除，存量启动时自动展开为每源一行）、`QuotaUsageLog`、卡密（明文仅生成时返回一次）
- 数据源域：`DataSource`、`QuotaPlanDataSource`、`UserSourceConfig`、`PlatformSourceConfig`（baseUrl 三级解析的持久化）
- 安全/运维域：`SystemSetting`、`BlockedIP`、`ApiCallLog`/`ApiCallStats`、`XmlyDevice`

**前端**（`web/src`，约 40 个文件）：分层为 `api/client.js`（fetch 封装：token 注入、401 跳登录、`code!==0` 抛 ApiError）→ `api/index.js`（按域端点）→ 页面（不拼路径）；`store.js` reactive 会话态 + 路由守卫；共享组件（UiTag/UiModal/UiPagination/UiTrendChart 纯 SVG 无图表库/VerifyCodeField 自按场景开关渲染）+ styles.css 基样类。产物经 `go:embed` 进二进制，`/panel` 由 SPA 回退文件系统承载（静态优先，未匹配回退 index.html）。

## 12. 架构权衡与已知缺口

明确记录在案的取舍（多为性能/简单性换正确性边界）：

1. **进程内状态多**：限流器、熔断器、内存缓存、号池、监控环均为单进程态——多实例部署时各实例独立计数（限流/额度口径会放宽 N 倍）。当前定位单实例够用。
2. **并发超扣**：计费先成功后扣减，允许少量超扣换取无锁热路径。
3. **`map[string]interface{}` 传参**：处理器间参数传递放弃类型安全换灵活性，是迁移方案中的已知取舍。
4. **SSRF DNS 结果永久缓存**：无过期，上游换 IP 需重启生效。
5. **CORS `*`**：面向阅读 App 的开放 API 场景，收紧需评估客户端影响。
6. **全局单例**（`conf.Config`、`db.DB`、`utils.DefaultCache`、限流器 map）使集成测试禁止 `t.Parallel()`，用例间靠清缓存/独立接口隔离。
7. **测试金字塔偏薄**：黑盒集成测试（testserver 脚手架：临时 SQLite + 完整 gin 引擎）覆盖认证/找回密码/计费/限流/监控/号池主路径，但数据源归一化逻辑依赖手动 curl 验证，无 CI（仓库无远端）。集成测试曾两次抓住真实生产 Bug（限流器双重加锁死锁、会话相关回归），投入产出比高。
8. **SQLite 默认**：零依赖交付友好，写入并发是天然上限；切换 MySQL/PG 只需环境变量。2026-09-15 起 DSN 启用 WAL + busy_timeout + synchronous=NORMAL 并 `SetMaxOpenConns(1)`，消除并发写 `database is locked` 隐患（读事务升级写的 SQLITE_BUSY_SNAPSHOT 不被 busy_timeout 重试，单连接彻底规避）。同期两项加固：管理端数据源/套餐写操作经 `Cache.DelPrefix` 主动失效 `/datasources` 缓存（此前仅按 300s TTL 自然过期）；登录接口接入与找回密码同口径的按 IP 限频+连续失败锁定（此前登录无任何防爆破）。
9. **嵌入前端无 CDN 分流**：二进制 ~35MB（strip 后），面板静态资源全部由 Go 进程服务。

## 13. 扩展指南（架构视角）

- **新增数据源**：新建 `handlers/<source>/` 包，嵌入 legado 基础处理器，init 注册，数据库补 `data_sources` 行与套餐关联——零改动既有代码，符合开闭原则。注意 baseURLCheck/访问控制/计费/限流四个闸门自动生效。
- **新增业务接口**：在对应域包加 handler 并在其 `RegisterRoutes` 挂载；管理接口自动受 `AdminRequired()` 保护。
- **新增系统行为开关**：优先走 `system_settings`（10s 缓存 + 写时失效），避免新增环境变量导致的重启成本。
- **触碰易复发区域前**（embed 前端缓存、上游字段名兼容、GORM 方言差异、号池/限流状态机、可信代理与真实 IP）先查项目知识库 `/home/muyang/Documents/obsidian/loomproxy/` 的 Bug 条目。

## 14. 小结

loomproxy-go 的架构可概括为：**一个以"处理器自注册 + 责任链中间件 + 五层弹性获取栈"为骨架的单体网关**。它没有引入重量级中间件，而是把并发控制（singleflight/熔断/对象池）、资源池化（代理池/设备号池）、商业化管控（三轴闸门）全部收敛在进程内，用约 2.2 万行 Go 实现了协议适配、多租户管控与运营后台的闭环。设计上最突出的三个决策：

1. **数据源即插件**——注册表 + 模板方法让 10 个源 54 个接口共享 5 套骨架；
2. **弹性链路前置**——缓存/合并/熔断/降级全部压在 base.Fetch 一处，各数据源无感获得抗压能力；
3. **管控与业务正交**——访问控制、计费、限流以中间件闸门形式横向切入，数据源处理器完全不感知商业化逻辑。

主要架构风险集中在单进程态的水平扩展上限与测试/CI 缺口，对当前部署形态（单实例 VPS + systemd/Docker）是可接受的；若未来需要多实例，限流器/熔断/号池状态的外置（Redis 化）是首要改造点。
