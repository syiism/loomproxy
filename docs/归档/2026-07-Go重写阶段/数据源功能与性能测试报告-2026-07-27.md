### 发现的功能缺陷（3 个系统性 Bug + 1 个稳定性问题）

1. **fq_mufan / chapter：`itemId` 字段全部为空**（系统性）
   返回 `{"chapterList":[{"title":"第1章 …","itemId":"","chapterInfo":""},…]}`，标题解析正常但章节 ID 丢失，导致 content 无法获取。疑似章节接口上游字段名变更、归一化时未取到。

2. **fq_jingluo / chapter：`chapterList` 恒为空数组**（系统性）
   用搜索返回的多本书（`7542602438201576472`、`7529358240547621950`、`7455224372689636414`）验证均为 `{"chapterList":[]}`。search/detail 正常，仅 chapter 失效。

3. **qm_luomu / chapter：所有字段均为空**（系统性）
   返回 `{"chapterList":[{"title":"","itemId":"","chapterInfo":""},…]}`，数组长度正常但字段全部解析失败，疑似上游响应结构变更导致字段映射失效。

4. **sq_luomu / content：偶发慢请求/失败**（稳定性）
   压测中出现一次 10.03s 且校验失败；随后手动复测 3/3 通过（200~800ms）。注意其 `itemId` 为**带时效签名的上游 URL**（`ut=…&sign=…`），章节列表缓存过久或上游偶发慢时可能失败，建议关注。

## 五、治理项实施：上游缓存 + 签名重试（2026-07-27 04:36 已上线）

针对首轮报告暴露的"限流对策躺平""sq 签名时效定性含糊"两条批评，已实施两项治理并回归验证：

### 5.1 上游响应短 TTL 缓存

- **实现**：`base.BaseHandler` 新增 `UpstreamCacheTTL` 字段，`FetchJSON`/`FetchText` 按 URL 缓存上游响应；search/detail/chapter/explore 四个 legado 基础处理器默认开启，content 不缓存（章节 URL 唯一，缓存无意义且挤占容量）。配置项 `UPSTREAM_CACHE_TTL`（默认 10s，≤0 禁用）、`UPSTREAM_CACHE_MAXSIZE`（默认 512）。缓存实现在 `base/upstream_cache.go`（自包含，规避 base→utils→legado→base 循环依赖）。
- **效果**（04:36 回归 vs 04:24 无缓存回归）：

| 指标 | 无缓存 | 有缓存 | 变化 |
|---|---|---|---|
| detail 串行基线 avg | 234ms | **60ms** | -74%（命中时 ~14ms） |
| chapter 串行基线 avg | 394ms | **86ms** | -78% |
| C1 100 并发成功率 | 2.2%（22/1000） | **77.5%**（775/1000） | 上游限流大幅缓解 |
| C1 50 并发成功率 | 12.5%（125/500） | **82.8%**（414/500） | 同上 |
| C2 全源混合 p50 | 656ms | **473ms** | -28%，成功率 100% 保持 |
| C3 持续负载 QPS | 43.2 | **95.1** | +120%，p50 303ms→21ms |

### 5.2 sq_luomu 签名失效自动重试

- **实现**：content 请求失败时，解码过期 itemId 提取 `chapterId`，重拉目录匹配同一章节的新签名 URL 并重试一次（`handlers/sq_luomu/content.go`）。
- **验证**：04:36 回归中 sq_luomu 全链路通过（582ms）。已知的残余风险：若中间 API 的目录缓存未刷新，重拉得到的签名与旧签名相同则跳过重试（避免无意义重复请求）；若中间 API 整体挂起（实测曾出现 40s 无响应），重试同样无效——这两种均属上游故障范畴，代理层已无进一步动作可做。

## 六、治理项实施（二）：请求合并 + 熔断降级（2026-07-27 04:55 已上线）

### 6.1 请求合并（Singleflight）

- **实现**：`base/singleflight.go`（自包含，无新依赖）。`FetchJSON`/`FetchText` 的调用链变为 **缓存 → singleflight（键 = URL+请求头）→ 熔断 → 过期缓存降级**。并发相同请求由先行者打一次上游，跟随者等待并共享结果；singleflight 内部对缓存做 double-check。
- **单元测试**（`test/resilience_test.go`）：20 并发相同请求上游只被调用 1 次（`TestSingleflightCoalescesConcurrentRequests`）。

### 6.2 熔断降级

- **实现**：`base/circuit_breaker.go`，按上游 host 维度：连续失败达 `CIRCUIT_BREAKER_FAILURES`（默认 5）开启，`CIRCUIT_BREAKER_COOLDOWN`（默认 30s）内快速失败 **503**，冷却结束放行探测，成功关闭/失败重开。计入失败：网络错误、超时、5xx、响应体解析失败；不计入：客户端取消、上游 4xx。上游故障且存在缓存时**降级返回过期缓存**（过期项改为只在写入路径清扫）。
- **单元测试**：阈值开启（`...OpensAfterThreshold`，熔断后上游零触达）、冷却恢复（`...HalfOpenRecovery`）、过期降级（`TestStaleCacheFallbackOnUpstreamFailure`）。全部 `go test -race` 通过（11/11，含既有 7 个）。

### 6.3 上线后回归（04:55 轮次）

| C1 100 并发成功率 | 77.5%（775/1000） | **100%（1000/1000）** |

## 七、治理项实施（三）：IP 代理池 + 请求头轮换（2026-07-27 05:06 已上线）

- **实现**（`base/proxy.go`）：
  - **IP 代理池**：双来源——`UPSTREAM_PROXIES`（逗号分隔）与 `UPSTREAM_PROXY_FILE`（每行一个，# 注释，5s 热加载）；随机选取健康代理，按代理懒建独立 `http.Client`；**连续失败 3 次封禁 60s**（日志可观测）；代理网络错误时自动换代理/回退直连重试一次（上游 4xx/5xx 不换代理，避免无意义重试）。
  - **请求头轮换**：`UPSTREAM_UA_ROTATE=true` 时按请求从 12 个移动端/桌面端指纹池随机注入 User-Agent；Handler 显式设置的 UA 优先（兼容 xmly 微信 UA 等特殊场景）。
- **单元测试**（`test/proxy_test.go`）：请求经代理发出（目标服务器零触达）、不可达代理自动回退直连、UA 注入与显式 UA 优先。`go test -race` 14/14 全过。
- **实机验证**：代理文件写入不可达代理，连续请求全部 200（每次经故障转移完成），第 3 次失败后日志输出 `代理连续失败 3 次，封禁 1m0s`，随后请求跳过坏代理。
- **上线回归**（UA 轮换开启，05:06 轮次）：功能 **9/9**；C2 108/108；C3 **1125/1125（100%），QPS 124.3**（再创新高高），p50=29ms。
- **使用方式**：在 `.env` 配置 `UPSTREAM_PROXIES=http://user:pass@host:port,socks5://...` 或 `UPSTREAM_PROXY_FILE=data/proxies.txt`（当前未配置真实代理，机制已就绪；UA 轮换已开启）。

## 八、统计口径说明

为避免误读，统一本报告的成功/失败判定口径：

- **功能测试（阶段 1）**：单线程串行请求，"通过" = search/detail/chapter/content 四个动作均返回 HTTP 200 且响应体业务校验有效（bookId/itemId 非空、正文非 error）。该阶段未触发上游限流，9 个源均无 400，故修复后 9/9 成立。
- **性能测试（C1/C2/C3）**：以**单请求**为统计单位，HTTP 200 计成功，其余状态码（含上游限流被映射的 400、uxx 上游的 520）与网络错误一律计失败。功能阶段的 9/9 与 C2 的 106/108 不矛盾——前者是链路可用性判定，后者是请求级成功率，两者均将 400 计为失败。
- 性能阶段的 400 失败**全部可归因于上游限流/上游异常**（服务端日志：上游返回空响应体 → `解析 JSON 失败`），非代理自身逻辑错误；代理自身逻辑错误（5xx、超时、panic）在整个测试期间为 0。

## 九、结论与后续计划

1. **功能结论**：首轮发现的 6 个缺陷 + 错误码映射缺陷已全部修复（见第四节），9/9 数据源全链路可用。
2. **性能结论**：代理自身在 30~100 并发下无内部错误、无资源泄漏。短 TTL 缓存上线后（见第五节），上游限流压力大幅缓解——100 并发成功率从 2.2% 提升到 77.5%，混合负载 QPS 从 43 提升到 95，缓存命中时 p50 低至 21ms。缓存未覆盖的 search 多关键词/翻页场景仍受上游限流约束，建议客户端并发控制在 **50 以内**（缓存加持下）。
3. **后续迭代计划**（按优先级）：
   - **长时浸泡测试**：低并发持续跑 2~4 小时验证 Goroutine/定时器泄漏（当前 1 小时尺度不足以暴露慢泄漏）。
   - **请求合并（Request Coalescing）**：缓存未命中的并发相同请求可合并为单次上游调用（singleflight），进一步压低峰值上游 QPS。
   - **熔断降级**：上游持续 5xx/超时时短时熔断并返回降级提示，避免线程堆积在上游挂起期间。
   - **uxx 520 友好提示**：上游 Cloudflare 错误的透传信息可对客户端更友好。
