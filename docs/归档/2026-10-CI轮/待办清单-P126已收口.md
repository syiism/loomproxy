## P126 `make build` 的测试段从 245s/255s 跳到 400s/409s，之后三次复跑同值【已收口（2026-10-23：归因不到即结论、`gate-watch.sh` 已入库、口径钉整段墙钟，commit `e0d2203`）】

- **现象（读数全部来自门禁日志本身）**：四次跑的是同一套 `go test ./... -race -count=1`——

  | 跑次 | 结束时刻 | `loomproxy/test` | `test/groupb` |
  |---|---|---|---|
  | gate10 | 11:07 | 245.439s | 255.563s |
  | gate11 | 13:09 | 399.859s | 408.364s |
  | gate12 | 14:0x（本场收尾） | 400.575s | 408.938s |
  | gate13 | 15:0x（v113 那颗发版前） | 399.686s | 409.566s |

  **其余包全程稳定**（`base` 1.767→1.798、`app` 1.373→1.398、`utils` 1.222→1.243、`gate` 1.021→1.048），
  所以慢的不是这台机器，是那两个集成包里共用的某件事。
- **一条我自己的猜想被读数否掉了**：报告 §22 当时写「跳了近 160 秒，很可能是与装配仓构建并行压的」。
  gate12 与 gate13 各自都是同一台机器上**唯一在跑的任务**（没有别的构建与它们同时），数值一模一样——
  **"并行"这一半解释被连续两次读数推翻**，留着这句是因为它示范了"未复算的归因写成结论"的下场。
- **两个包同时变慢 + 只有一个 Go 侧改动**：11:07 到 13:09 之间进树的提交里，
  动到 Go 的只有 `3a32651`（P124：`conf/conf.go` 补 `RankCacheSec: envInt("RANK_CACHE_SEC", 60)`，
  外加 `test/conf_env_notice_test.go` 与两支脚本），其余是 docs/shell/`feat(web)`。
  **可疑路径**：`handlers/rank/rank.go:231` 那一段，`ttlSec` 从此从 0 变成 60 →
  `/rank/boards` 开始走缓存分支（`utils.DefaultCache()` 的 Get/Set 都要把**榜的整份 payload** 过一遍序列化）。
  两个包里都有榜的用例（`rank_visitors`/`rank_public`/`rank_visibility`/`privacy_consent`）。
  **这条只是"目前唯一有形状的路径"，不是结论**——没测过。
- **已经查过并排除的三条**（写下来是给下一轮省路，不是凑数）：
  ① **探针泄漏浏览器抢 CPU**——本机在跑的 26 个 `chrome` 进程逐条看过，全是维护者自己的 Google Chrome
  （`~/.config/google-chrome` + plasma 扩展 + wayland），**启动于 15.6 小时前**，也就是 gate10 那一刻它们也在跑，
  所以解释不了"11:07→13:09 之间跳一档"；playwright 那两支探针 `browser.close()` 后没留下 headless 进程。
  ② **临时库落盘**——`/tmp` 是 tmpfs、用 2%（7.6G 空闲），内存 8G 可用，集成用例那些临时 SQLite 文件没有掉到磁盘上的迹象。
  ③ **机器整体在忙**——`/proc/loadavg` 2.35/2.91/2.93（16 核），且 `base`/`app`/`utils`/`gate` 这些包三次读数全稳，
  真要是机器被占满，不会只有那两个集成包动。
  **三条都是"排除"，不是"证明过"**：下一条线索要从 ① 那两步取数法里长出来，不是继续猜环境。
- **影响**：门禁从约 8.5 分钟变到约 13.5 分钟（+62%）。它不改变正确性，但**门禁变慢会被人的行为吃掉**：
  一旦超过"随手跑一次"的心理预算，下一轮就开始有人只跑 `make vet`、或者跑之前先 `| tail`（那就是 P109）。
- **两步取数法跑完了，结果是"到边界"**（2026-10-10 下午，同一棵树 `4fade1d`）：
  ① **定位到用例**——`-v` 跑完两包：`./test` 178 条合计 239.8s（均值 1.35s）、`groupb` 129 条合计 245.3s（均值 1.90s），
  **合计与包读数几乎相等**，也就是没有"包级空白时间"；最慢的是 `TestLoginAccountWatchObservesWithoutDisposing` 11.35s、
  `TestCacheRedisDegradationSpeaks` 16.42s 这一族（登录/设备/限速那族），**榜与缓存那族最大只有 2.23s、进不了前 8**。
  ⇒ 所以 ②（A/B `conf.go` 那一行）**没必要跑**：要推翻的那条路径被 ① 直接排除，不做没有对象的实验。
  ② 之后补的是三个真会改变输入的 A/B：单包串行 `240.9s/246.4s`、两包放进同一次调用并发 `259.4s/269.4s`（墙钟 270s，
  **并发只贵 8%**）、完整 `make build` 两次 `256.8s/266.5s` 与 `256.4s/266.5s`——第二次是**故意让前端变一个字节**
  （在 `web/index.html` 加一条 HTML 注释，跑完对比 `web/dist/index.html` 的 md5 **确实变了**，
  因为 `//go:embed dist/*` 会作废下游全部测试二进制）。**四种跑法没有一个回到 400s。**
- **排除清单**（每条都带"凭什么"，不是"我觉得不像"）：代码变更（四种跑法同树全快）；并发形状（只贵 8%）；
  `RANK_CACHE_SEC` 那条路径（① 的分布）；共享 Redis（`testkit.SetupConf` 是**字面量**构造 `conf.Config`、
  里面没有 Redis 字段 → 集成用例默认 `RedisEnabled=false`，只有 `cache_redis_notice_test.go` 自己显式开）；
  内存与 `/tmp`（可用 8.4G、`/tmp` 是 tmpfs 用 2%）；探针泄漏浏览器（`pgrep -f ms-playwright` 只剩自己那条 grep；
  在跑的 26 个 `chrome` 是维护者自己的浏览器，启动时刻早于 gate10）；别的工作树在那两段有活动
  （按文件 mtime 对窗查，慢的三窗**没有**任何其它仓的新改文件，反而快的两窗有我自己的日志）；
  遗留临时实例与临时目录（`/tmp/loom-viewport.*` 一个都不剩）。
- **还剩什么**：**归因不到，而且承认归因不到**。慢的三次窗口（13:01–13:09、13:51–13:58、14:08–14:15）
  里没有任何采样器在跑，事后 `ps`/`ss` 看不到当时——这一条本身就是结论：
  **一个不被当场采样的量，事后只能给出"排除"，给不出"成因"**。
  所以下一次门禁变慢，先并行开 `scripts/gate-watch.sh`（已落进仓库，每 5s 抄 load / 前 5 个吃 CPU 的进程带累计秒数与
  存活时长 / TCP 的 TIME_WAIT 与 ESTAB / 内存可用与回收计数），拿那段日志再判；**不要先改代码，也不要先改口径**。
- **口径先钉住**：`ok loomproxy/test 400.5s` 这类**每包秒数不是可比指标**——它是那个包自己的墙钟，
  受同一次调用里并发了谁、当时机器上有什么影响。要比较的是**整段墙钟**（那三次 `make build` 全程
  7m12s / 7m03s / 7m08s，今天这几次 4m37s / 4m38s——按日志文件的创建与最后写入时间对出来的窗口，不是回忆），
  写进发布单与台账的数也应当是它。这一句同步落在 `docs/运维/构建与部署.md` 的"门禁的耗时怎么读"那一格。
- **发现处**：本场收尾复算 gate11 耗时时留下的那一格（报告 §22），gate12 是它的第二次读数。
