## 0. 为什么这件事必须在阶段 C（源迁入）之前做

`阶段C-数据源迁入方案.md` 的逐源声明里，`fq_hg` 的 `SearchTabs=[2听书,3小说,8漫画,10短剧,13漫剧]`、
`xmly` 是 `Category=xmly` 的音频站——**媒介类型的第一个真实消费方就是迁入驻**。而分支的接缝清单只允许改
`sources/**`、`data/**`、`.env.example`、品牌文案、`middleware/all/all.go`（且后者本次明确不许动）。

如果骨架先不带这些声明位与明细列，源分支只能：改 `base/registry.go` 加字段、改 `models/api_call_log.go`
加列、改 `handlers/admin/monitor.go` 加筛选——**三处都是骨架受保护路径**，审计判据（对 `skeleton-v1` 的
骨架路径 diff 必须为空）当场破。所以顺序是：骨架先把声明位与记录能力做齐 → 源迁入只填声明、不改骨架。

**现状印证（2026-09-30 核对，分支 `sources/private` 正在迁入中、工作区有未提交暂存）**：
`sources/fq_hg/actions.go:193-228` 的正文处理器**已经在按媒介分流**——按上游返回
`legado.ContentResponse{ContentType: "audio" | "video" | "manga" | "novel" | "error"}`，
请求侧也已在读 `tabType`（`getParam(params, "tabType")`）。但它的 `SourceMeta`（`actions.go:292`）
只有 `Code/Display/Category/Description/SortOrder/Status/Actions`，**既没声明 `SearchTabs`
也没有任何媒介字段**——媒介信息现在只活在源实现的响应里，骨架没有任何地方能把它记进明细、
聚合成运维口径。这正是「先补骨架、源只填声明」的实锤场景。

### M2 内容维度本体：`base/subject.go`（骨架改造版）

- 结构：`CallSubject{Keyword, BookName, ChapterTitle, Media, ResultCount int, BookKey, ChapterKey}`

- ctx 键 `CallSubjectKey = "call_subject"`：骨架里跨包契约已有归属（`middleware.CtxResolvedBaseURL`），
  故这个键放 `middleware/middleware.go` 的 const 区，与既有约定一致；`base` 只放类型与抽取逻辑（`base`
  不依赖 gin，别在这里引入）。
- 命名缓存：沿用 `nameCache`（互斥锁 + FIFO + 24h TTL + 上限 2 万条），`namedEntry` **扩一个 `media` 字段**
  （书名与媒介类型同源同生命周期，不必再开第三张表）；`NameCacheStats()` 导出供面板/自检展示缓存条目数。
- 截断：`truncateRunes` 按 rune（中文安全，按 byte 会截出半个字），上限 100/120/200 保持不变；
  `normalize()` 收口在抽取末尾，**内存环形缓冲与落库都界内**。
- 抽取入口 `ObserveResult(params map[string]interface{}, result interface{}, subj *CallSubject)`——
  注意签名里**没有 action**（改造点 1），内部按形状分支。**骨架的实际信封与参考实现不同，已核对**：
  迁入的源返回的是 `base/legado` 的**强类型 DTO 值**（`sources/fq_hg/actions.go:49,90,174,203`），
  所以主路径是类型断言，map 只是兜底（AGENTS.md §12 允许源自己返回 map）：

  | 形状 | 断言/键 | 抽什么 |
  |---|---|---|
  | 搜索结果 | `legado.SearchResponse` / map 的 `bookList` | `ResultCount=len(BookList)`；逐条把 `BookItem.Name` 灌书名缓存，键取 `BookId`（兜底 `bookUrl`/`url`/`u` 首个非空） |
  | 书籍详情 | `legado.BookDetail` / map 顶层 `name`+`bookTypeCode`（也认 Legado 的 `bookInfo` 包装） | 书名 = `Name`；媒介 = `BookTypeCode`/`BookType`；回写缓存 |
  | 章节目录 | `legado.ChapterResponse` / map 的 `chapterList` | `ResultCount=len`；逐条把 `ChapterItem.Title` 灌章节缓存，键取 `ItemId`/`Url`；书名查缓存 |
  | 正文 | `legado.ContentResponse` / map 的 `contentType`+`data` | **媒介 = `ContentType`**（M3 优先级 1）；章节名查缓存，书名由章节标识推书标识再查缓存；`data.content` 非空 → `ResultCount=1` |

  `BookItem` 现在**没有** `bookType/bookTypeCode` 字段（`BookDetail` 有）——这是 D4 要补的加法。
- 搜索词：`key` → `keyword` → `wd` → `url` query 里的 `keyword`；tab 参数 `tabType` → `tab_type` → `searchType`
  （M3 的 tab 判定要用，多字段兼容读取，AGENTS.md §10）。
- 结果既可能是 `map[string]interface{}` 也可能是 legado DTO：**两条都覆盖**——先类型断言，再退到 map；
  **不要**用 `json.Marshal/Unmarshal` 往返（每请求付费）。
- 容错到底：`result` 为 nil/奇怪形状只给空值，绝不 panic、绝不阻断请求路径；对外错误只用于「源自己声明的
  抽取规则不合法」这类启动/登记期问题，请求路径上的失败一律静默 + 服务端 debug 日志。
- 单元测试放 `test/subject_test.go`（骨架纪律）：缓存链路（先 search 灌书名 → 后 content 只带标识也能标出
  书名与章节名）、FIFO 淘汰与 TTL、rune 截断、奇怪输入容错。

### M3 书籍媒介类型（本次新增项）

骨架**不内置任何「哪个源是什么媒介」的知识**（那是 `case "xmly"` 式硬编码，A3 刚拆掉的就是它）。
媒介类型只有三类合法来源：**响应里的 Legado 字段**、**源自己的声明**、**同一本书的历史判定**。

- `base/media.go`：枚举 `novel` / `audio` / `comic` / `video` / `unknown`；
  三个纯函数把上游/DTO 的写法归一到枚举——
  `MediaFromBookTypeCode(int)`（**Legado 规范**：0 小说 / 1 漫画 / 2 听书 / 3 视频 / 4 文件→小说）、
  `MediaFromBookTypeName(string)`（认「小说/漫画/听书/音频/短视频/番剧」等中文名）、
  `MediaFromContentType(string)`（认 `novel/manga/audio/video/text/image`；
  `error` 与空串 → `unknown`，**不**当成小说）。
  这些都是阅读 App 的公开规范与 `base/legado` 的自有字段语义，属平台能力，不是源知识——
  与本仓「Legado 信封键名」同一档。
- 两个新声明位（`base/registry.go`，都是加法、向后兼容）：
  - `SourceMeta.MediaType string`：**源默认媒介**（xmly 声明 `audio`）。缺省空 = 未声明（≠ novel）。
  - `SearchTab.MediaType string`：**tab 级媒介**，覆盖源默认。这是最有说服力的一条：`fq_hg` 一个源同时
    覆盖听书/小说/漫画/短剧/漫剧，`Category` 与 `tabType` 才是判定依据，而 tab 已经声明在 `SearchTabs` 里，
    只是现在没有媒介语义。
  - 登记期校验：`RegisterSource` 里校验取值落在枚举内（含空）。注意**光返回 error 不够**——现有源包的
    `init()` 全都忽略返回值（`sources/fq_hg/actions.go:292` 就是裸调用），非法声明会静默过关；
    媒介枚举这种新增校验走 `log.Fatalf`，与 `middleware.Register`（`31f0c91`）确立的「宁启动失败不带病运行」同风格。
    `/datasources` 下发：源级 `media_type` 与 tab 的 `media_type` 都下发，下游与面板都能看到。
- **判定优先级**（写进 `ObserveResult`，一条短路链）：
  1. **响应自带**——正文的 `ContentResponse.ContentType`（`fq_hg` 已按 audio/video/manga/novel 分流，
     这是最省事的现成信号），详情的 `BookDetail.BookTypeCode`/`BookType`，搜索条目若带也取；
  2. 请求 `tabType` 命中的 `SearchTab.MediaType`——搜索/发现类请求常常不带类型字段，tab 是唯一体现媒介的地方；
  3. 命名缓存（同一 `BookKey` 之前判定过）——`chapter`/`content` 只带标识，靠这里；
  4. `SourceMeta.MediaType` 源默认；
  5. `unknown`。
  **判定结果（除 unknown）回写书名缓存**，让后续只带标识的请求也能标出来。缓存里也带上源码做键隔离，
  避免两个源复用同一 `bookId` 时串味（键 = `source + "|" + bookKey`）。
- 为什么不用 `Category` 推媒介：`Category` 是源的分组码（`fq/qq/qm/sq/xmly/uxx`），与媒介**不正交**——
  `fq_hg` 一源四类；骨架里写 `if category=="xmly" → audio` 就是把数据源知识塞回底座，违反唯一硬判据。
- 参数名容错：`tabType` 读 `tabType` → `tab_type` → `searchType`（`utils.FirstNonEmpty` 口径）。
- 决策点 D2（**已定**）：四类枚举固定，**短剧与漫剧都归 `video`，`comic` 只表示漫画**；
  映射写在源侧 tab 声明里（见 §4b），骨架不加第五/六类枚举。

### 4b. 源侧回填映射（D2 定稿后，迁入分支照抄即可）

**骨架看不见的事实来源**：`fq_hg` 自己早就有 tab → 形态 的映射，它在源私有数据文件
`sources/fq_hg/protocol/data/modes.json` 的 `FQ_TAB_KIND` 里，实测值为
`{1:text, 2:audio, 3:text, 7:text, 8:comic, 10:video, 11:video, 13:video, 19:video}`，
由 `protocol/modes.go:43 TabKind()` 读取、`protocol/client.go:419` 决定正文走哪条分支。
**`SearchTab.MediaType` 就是这个映射在骨架侧的表达**——不是新知识，是把已经存在、但骨架无法用于
记录与聚合的信息声明出来。骨架不读 `modes.json`（那是源私有数据），一致性由源侧负责。

按 D2（`comic` 只表示漫画）落成的五个 tab：

| tab | 上游名称 | `SearchTab.MediaType` | `FQ_TAB_KIND` 的形态 |
|---|---|---|---|
| 3 | 小说 | `novel` | `text` |
| 2 | 听书 | `audio` | `audio` |
| 8 | 漫画 | `comic` | `comic` |
| 10 | 短剧 | `video` | `video` |
| 13 | 漫剧 | `video` | `video`（**不是** `comic`：漫剧走的是视频分支） |

配套的归一表（`base/media.go` 的 `MediaFromContentType`，认正文响应已有的 `ContentType`）：
`audio→audio`、`video→video`、`manga|image→comic`、`novel|text→novel`、`error|空→unknown`。
注意 `actions.go:207` 把 kind `video` 直出 `ContentType:"video"`、kind `comic` 改写成 `ContentType:"manga"`
（Legado 的正文类型词），所以**漫剧的正文会带 `video`、漫画的正文会带 `manga`→归 `comic`**，
与上表的 tab 判定天然一致；tab 判定只在响应没给类型时才生效（M3 优先级 1 > 2）。

其余源与 xmly 的 `SourceMeta.MediaType`：`xmly=audio`，`fq_hg` **不声明源默认**（一源五类，默认值只会造成误判，
让 tab 与响应说话），`qq_luomu/qm_luomu/sq_luomu/uxx=novel`。这些都是**源侧声明**，不写进骨架任何地方。
