# 死号清理执行记录

> 长期不活动的账号要清出去，动机是**回收用户名与邮箱**（软删做不到这件事，见 §2）。
> 本页只记**口径、行数、流程与回滚**；**名单（用户名/邮箱）不进仓库**——它在库里，
> 出处就是 §4 那段只读 SQL 与 §5 那几张隔离表。这个仓库的 `main` 是可推送的公开分支，
> 把「谁在用这个站」写进 git 历史与 §11 的隐私口径直接冲突。

## 1. 判定口径

**不用 `users.last_login_at`**：它只在注册、密码登录、改密三处写（`handlers/auth/auth.go`），
网关调用与 API Key 流量一次都不碰它——按它判会把「只走 Key 的人」误杀成死号。

活动信号取这四个的最大值，任一为空则回落到 `created_at`：

| 信号 | 来源 | 写入时机 |
|---|---|---|
| `users.last_login_at` | 面板/密码登录 | 登录、改密 |
| `api_keys.last_used_at` | 网关调用 | 每次 Key 命中（5 分钟节流，`utils/apikey.go`） |
| `auth_sessions.last_active_at` | JWT 会话 | 每次会话活跃（5 分钟节流） |
| `quota_usage_logs.created_at` | 计费 | 每次扣额度的请求 |

阈值：**四个信号全部 ≥60 天前**。另两条排除条件：`status=1`（`status=0` 是被禁的号，那是处置结果不是死号）、
不持有 `admin` 角色。

## 2. 动手前必须知道的三件代码事实

1. **`DELETE /admin/users/:id` 是软删**（`handlers/admin/admin.go:289`：写 `users.deleted_at` +
   `db.RevokeOtherSessions` 吊销全部会话），可 `POST /users/:id/restore` 放回。库里**没有硬删路径**，
   也**没有批量端点**。
2. **软删永久占名**：软删用户的用户名与邮箱不能重新注册（`test/auth_integration_test.go:134`），
   邮箱唯一索引一直被占（`:182`）。所以「回收名字」这一步必须落到硬删。
3. **全库没有任何外键**（`db/db.go` 一律 `AutoMigrate`）——删用户不会级联清掉任何东西，
   反过来也不会被任何东西挡住。要动哪几张表必须自己列清单（§4 的实测结果）。

另有一条不影响本轮但要知道：软删/硬删都**不清 API Key 缓存**，`apikey:<明文>` 里缓存的是归属身份，
命中路径不复查用户（`utils/apikey.go:44`），所以被删用户的 Key 最长还能用 `CACHE_TTL`（默认 300 秒）。
本轮这批人 **0 个 Key**，该坑没有落地。

## 3. 引用用户的全部位置（逐表清点）

| 表 | 列 | 类型 | 本轮处置 |
|---|---|---|---|
| `users` | — | — | 删（第一刀硬删 / 第二刀软删） |
| `user_roles` | `user_id` | 数字 | 随删 |
| `auth_sessions` | `user_id` | 数字 | 吊销（第一刀随删） |
| `api_keys` | `user_id` | 数字 | 本批 0 行 |
| `user_quotas` / `user_quota_overrides` / `user_source_configs` | `user_id` | 数字 | 本批 0 / 0 / 1 行 |
| `quota_usage_logs` | `user_id` | 数字 | **保留**（审计凭据） |
| `redemption_logs` | `user_id` | 数字 | **保留**（审计凭据） |
| `redemption_codes` | `used_by` | 数字、可空、**无索引** | **保持悬空**，见 §6 |
| `api_call_logs` | `username` | **字符串** | 本批 0 行，无需匿名化 |
| `verification_codes` | `target`（邮箱） | 字符串 | 本批 0 行 |
| `quota_limits` | `target` | 存的是**数据源码**，不是用户 | 无关 |

`api_call_logs.username` 是全库唯一按用户名字符串 join 的表——这也意味着**删用户不会动到任何阅读明细**，
而榜与监控的口径（`COALESCE(NULLIF(username,''), ip)`，见 P18）不随身份消失而改变。

## 4. 只读判定 SQL（可复跑，不写任何行）

```sql
WITH cohort AS (
  SELECT u.id, u.username, u.email
  FROM users u
  LEFT JOIN (SELECT user_id, MAX(last_used_at) k FROM api_keys        GROUP BY user_id) ak ON ak.user_id = u.id
  LEFT JOIN (SELECT user_id, MAX(last_active_at) s FROM auth_sessions GROUP BY user_id) se ON se.user_id = u.id
  LEFT JOIN (SELECT user_id, MAX(created_at) q FROM quota_usage_logs  GROUP BY user_id) qu ON qu.user_id = u.id
  WHERE u.deleted_at IS NULL
     OR GREATEST(COALESCE(u.last_login_at, u.created_at), COALESCE(ak.k, u.created_at),
                 COALESCE(se.s, u.created_at), COALESCE(qu.q, u.created_at))
        < DATE_SUB(NOW(), INTERVAL 60 DAY)
)
SELECT (SELECT COUNT(*) FROM user_roles    WHERE user_id IN (SELECT id FROM cohort)) AS user_roles,
       (SELECT COUNT(*) FROM auth_sessions WHERE user_id IN (SELECT id FROM cohort)) AS auth_sessions,
       (SELECT COUNT(*) FROM api_call_logs WHERE username IN (SELECT username FROM cohort)) AS call_logs;
```

两条写 SQL 的坑（都是本仓库的老坑）：别名/列名**不要**用 `keys`、`rows` 这类 MySQL 8 保留字
（SQLite 不报，只有生产报，见 §10 开发约定与 P1）；`users.email` 是 `utf8mb4_general_ci` 而
`verification_codes.target` 是 `utf8mb4_unicode_ci`，跨这两列比较要显式 `COLLATE`，否则 1267。

## 5. 分三刀执行（本轮做到第二刀）

| 刀 | 对象 | 动作 | 状态 |
|---|---|---|---|
| 一 | 已软删的号（早已不可用，只剩占名） | 硬删：`users` + `user_roles` + `auth_sessions` | **已执行**：2 人 / 2 角色行 / 3 会话行，名字已释放 |
| 二 | ≥60 天四信号全无的死号 | 软删 + 吊销会话，**冷冻 14 天** | **已执行**：67 人 / 新吊销 68 会话 |
| 三 | 冷冻期满仍无人认领的 | 硬删（第一刀同一套流程） | 待 **2026-10-16** 之后 |

- **回滚点一律是同库隔离表**，不往磁盘倒文件——明细与账号表都是个人数据，落成 `/root/*.sql` 就多一处会外流的敏感件：
  `deadgate_users_20261002` / `deadgate_user_roles_20261002` / `deadgate_auth_sessions_20261002`（第一刀），
  `deadgate_b_cohort_20261002`（第二刀名单本体，含四个活动信号与 `deleted_at_before`）。
- 第一刀回滚：按 `users → user_roles → auth_sessions` 顺序 `INSERT INTO <表> SELECT * FROM deadgate_*`。
- 第二刀回滚（冷冻期内有人回来说明判错了）：
  `UPDATE users SET deleted_at = NULL WHERE id IN (SELECT id FROM deadgate_b_cohort_20261002);`
  会话是吊销而非删除，需要人工按需放回（或直接让用户重新登录，代价更小）。
- 走 SQL 而不是循环打管理端接口，是因为本轮没有可用的管理员凭据；**语义必须自己补齐**——
  `DeleteUser` 干的第二件事（`RevokeOtherSessions`：`WHERE user_id IN (...) AND revoked_at IS NULL`）
  在事务里显式做了。**别只写 `deleted_at` 就完事**，那样未过期的 JWT 会话会继续可用。

## 6. 三条判断，记下来免得每次重议

- **`redemption_codes.used_by` 保持悬空、不置 NULL**：置 NULL 会把「这张卡已经被用过」这条状态线索一起抹掉，
  而悬空的数字在 `users` 删除后本来就反查不到人，泄露面上没有区别。
- **有兑换记录或有用量记录的号从名单里摘出来人工判定**（本轮摘 4 个）：花过卡密的人即使长期不活动，
  删名字等于把「这张卡谁用过」的链条断掉；宁可少删几个，回头再补。
- **明细与审计（`quota_usage_logs` / `redemption_logs` / `api_call_logs`）一律不删**：
  清理的动机是回收身份，不是删历史。真要抹身份，动的是 `api_call_logs.username` 这一个明文列
  （改成 `deleted:<id>` 占位），而不是删行——本批是 0 行，所以这一步没执行。

## 7. 遗留：清理不是闸门

本轮清出来的总数是个位数级别的量，而**单日新增注册是它的数十倍**。也就是说 60 天口径的死号清理
只是在给一个持续进水的池子抽水：真正决定「库里有多少废号」的是**注册侧**（验证码与图形/邮件验证的强度、
注册频率限制、注册即弃号的特征识别），不是清理侧。清理作为运维动作保留，但别把它当成治理手段。
另有一条相关的老问题在 P10（明文卡密文件的存放）与 §11 里记着，同一族。
