# LoomProxy Base 设计评审说明

> 本文档面向同行评审，自包含、不要求阅读仓库。版本基线：`skeleton-v107`（2026-10-09）。
> 目的：让评审者在 30 分钟内看清这是什么、关键决策为什么这么做、哪些是有意取舍、哪些是未解决的问题。
> 立场：客观陈述，不替项目辩护；"已知取舍"与"未解决问题"两节是评审重点。

---

## 1. 项目一句话

**LoomProxy Base 是一个上游 HTTP 接口的代理与治理平台骨架**：把异构的第三方接口代理进来、归一响应形状，并对其做鉴权、计费、限流、熔断、缓存、监控与生命周期管理。**骨架本身不携带任何具体上游实现**——接入一个接口 = 写一个 Go 包自注册 + 加一行导入 + 重编。

内置的一种下游输出契约是 **Legado（阅读 App）书源协议**（search/detail/chapter/content/explore 五动作），但这是"一种输出形状"不是项目边界——同一套骨架也可以代理音视频、漫画、元数据或任意 HTTP API。

## 2. 问题域与边界

**解决**：
- 给一批上游接口套一层统一的用户系统（注册/JWT/API Key/角色）、额度计费（按源扣减、套餐授权）、速率限制、调用监控（含内容维度）、管理面板。
- 给上游接口提供弹性获取栈：短 TTL 缓存、singleflight 并发合并、按 host 熔断、过期缓存降级、IP 代理池、UA 轮换、SSRF 防护。
- 提供一个通用"号池"框架（`base/pool`）：管理凭证型上游资源（设备号、账号、临时 token）的冷热分离、临期续领、耗尽换号、错误驱动扩容。

**不解决**：
- 不做 BFF/网关的通用形态（服务发现、多种 RPC、灰度），只针对 HTTP 上游。
- 不做具体书源/视频源的解析与归一——那是数据源包的事。
- 不做多租户 SaaS 隔离（部署实例即一个租户）。

## 3. 技术栈

| 层 | 选型 | 备注 |
|---|---|---|
| 后端 | Go 1.26 + Gin + GORM | CGO 必需（mattn/go-sqlite3） |
| 存储 | SQLite（WAL + 单连接）/ MySQL / PostgreSQL 切换 | Redis 可选，连不上自动回退纯内存 |
| 前端 | Vue 3 + Vite + Tailwind，`go:embed` 进二进制 | 单二进制交付 |
| 鉴权 | JWT + bcrypt + 会话表（`jti` 对应 `auth_sessions`） | API Key 双通道 |
| 许可 | AGPL-3.0 | 有意为之：拿它对外提供服务就得回馈改动 |

代码量：约 4.2 万行 Go（含约 100 个测试文件）+ 7.4 千行 Vue。

## 4. 分层与请求管线

```
┌─────────────────────────────────────────────────────────┐
│ 下游客户端（Legado App / 浏览器 / 服务间调用）              │
└─────────────────────────────────────────────────────────┘
            │  /{source}/{action} （根级路由）
┌─────────────────────────────────────────────────────────┐
│ 中间件链（按 Order 数字装配，自注册）                       │
│  RequestID(10) → Recovery(20) → Logging(30)               │
│  → CORS(40) → CacheControl(50) → IPBlock(60)              │
│  → APIAuth(100) → Monitor(200)                             │
│  → BaseURL(300) → RequiredParams(350)                     │
│  → Access(400) → Billing(500) → RateLimit(600)             │
└─────────────────────────────────────────────────────────┘
            │
┌─────────────────────────────────────────────────────────┐
│ Handler（数据面，源包自注册）                               │
│  └─ base.BaseHandler 弹性获取栈                            │
│     短TTL缓存 → singleflight → 熔断 → 代理池/UA轮换         │
└─────────────────────────────────────────────────────────┘
            │
        上游 HTTP 接口
```

**硬边界**：
- `middleware` 根包是叶子包（不导入子包、不导入 `gate`），防 import 环。
- `base` 不反向导入 `base/legado` 与 `utils`。
- 源包不直接操作 gin context，靠 `map[string]interface{}` 传参与平台声明位（`SourceMeta`）装配。

## 5. 关键设计决策（含代价）

### 5.1 源包自注册，而非配置驱动
源包在 `init()` 里调 `base.RegisterSource(SourceMeta{...})` 声明动作集、固定 baseURL、必填参数、自有设置项；路由对账、seed 播种、面板展示全部以声明为唯一事实来源。

- **选它**：强类型、编译期检查、接入新源不碰 `app.go`/`db/seed.go`。
- **代价**：加源必须重编；不能运行时热加。取舍见 §9。

### 5.2 授权与限额是同一行
`quota_limits(scope=source, target=源)` 存在即该套餐可用该源；`-1` = 不限额；删行 = 回收授权。原来的关联表（`quota_plan_data_sources`）已停用并在生产 DROP。

- **选它**：消除"授权在哪、限额在哪"两份事实来源的漂移。
- **代价**：语义耦合——"授权"和"额度"在 schema 上不可分，查"谁能用某源"和"某源给多少额度"是同一行。

### 5.3 会话行是鉴权执行点，不是 JWT 自验
每个请求都查 `auth_sessions.revoked_at`，改密/禁用用户/找回密码时与状态写入同事务吊销。

- **选它**：JWT 无状态但会话有状态；"一次登出全部失效"要可靠。
- **代价**：每请求一次库查询（有短缓存兜底密钥归属，但会话行本身每请求查）。

### 5.4 错误文案双层脱敏
对外响应过 `sanitizeUpstreamMsg`（含 URL 整句换掉）；服务端日志过 `scrubQueryForLog`（URL 查询串隐去、留协议+域名+路径）。判据分读者（管理员可信 vs 下游不可信）与来源（预定义句 vs 驱动/上游原文）两轴。

- **选它**：上游错误常带完整请求 URL（含签名参数、用户搜索词），不能原样吐给下游也不能原样进 journald。
- **代价**：调试时对外看到的是固定句，要进服务端日志才能看真因。

### 5.5 号池框架是状态机不是连接池
`hot/cold/cooldown/spent/dead` 五态，三钩子 `Create/Refresh/Claim`（Claim 必须叠加无损）。水位参数（冷备数、热号上限、死号上限）与总号名额是两个独立声明位。

- **选它**：凭证型上游的失败模式是"墙钟烧完"或"用量摊薄"两种，框架用 `Config.Kind` 分叉而不是硬编码一种。
- **代价**：Provider 实现方必须理解状态机语义，接入成本高于简单连接池。

### 5.6 内存缓存 + Redis 双层，不强制 Redis
`REDIS_ENABLED=false` 或连不上时退纯内存，请求不失败；缓存层按"好→坏/坏→好"翻转出日志。

- **选它**：部署简单（单二进制 + SQLite 就能跑），同时给高部署留横向能力。
- **代价**：内存态的东西（登录防爆破计数、API Key 归属缓存、限流锁）重启即失，不能依赖它们做精确计数。

## 6. 安全模型

- **SSRF 分来源校验**：用户填的 baseUrl 严格校验（DNS 解析后拒回环/私有/保留 IP，含 IPv6）；平台默认 baseUrl 视为管理员可信；`FixedBaseURL` 源整体跳过。
- **CORS `*`**：面向阅读 App 开放 API 场景，**未做环境变量收紧**（见 §9 未解决项）。
- **可信代理**：只信 `127.0.0.1`/`::1` 的 X-Forwarded-For，防伪造 IP 绕黑名单。
- **登录防爆破**：按客户端 IP（10 次/分、连击 10 次锁 1 小时），进程内存、不落库。**不按账号**（用户名可被任意填，按账号锁等于让攻击者点名锁人——这是有意选择，不是遗漏）。
- **管理面只认会话**：长期 API Key 进不了 `/admin/*`、也改不了密码/留存同意位（防密钥泄露被提权）。
- **路径穿越双守卫**：静态托管 `/data/<分类>/<文件>.json` 在入口（段内不许 `.`/`..`）与落盘点（解析后必须在根目录内）两处都验。
- **JWT 默认值保护**：`AUTH_ENABLED=true` 且 `JWT_SECRET` 是默认值时直接拒绝启动。

## 7. 数据与留存（合规面）

- 监控明细 `api_call_logs` 记录调用的内容维度（搜索词/书名/章节名/媒介/标识）。
- 用户可关 `content_consent`：关闭后写库前抹掉七个内容字段（含标识，否则名称回填会补回来）。
- **但**：留存面有"五面"——响应、库、进程日志、指标、缓存。`content_consent` 最初只盖了库与响应两面；日志那面（journald 里的请求 URL 查询串）已由 `scrubQueryForLog` 洗；缓存那面（命名缓存 Redis、FetchShared 的 POST 响应缓存）2026-10-08 刚补——**命名缓存写入口现在接同意位**（本次基线），但 FetchShared 的 POST 响应缓存（Redis 里的加密信封）仍不受同意位控制，这是拍板接受的代价。
- `MONITOR_RETENTION_DAYS` 默认 0 = 永久保留，对外部署前必须自设保留期。
- 公开榜单只出聚合（top20、名称+次数），窗口钉死 1/7/30 天。

## 8. 工程纪律（这是项目相对突出的地方）

- **Makefile 内置 10+ 条自定义门禁**：手写 SQL 保留字扫描、前端未定义 Tailwind 类扫描、goroutine-guard（每个顶层 `go` 长跑循环必须带 recover 帧）、台账写库不许吞错（8 张判定/审计表的写入必须检查 `.Error`）、设置键必须有后端读取方、文档引用路径核对、判据页数字必须等于当场数的。
- **测试**：黑盒集成测试集中在 `test/`（两组并行跑），用 `-race`；新写的断言要求做"变异验证"（把改动反转跑一次确认测试会红）。
- **文档体系**：AGENTS.md 是索引页（13 节、每节一句话）；细节在 `docs/架构/`（8 页）、`docs/规范/`（待办清单 P 系列、踩坑判据、已知取舍、安全合规）。每个已收口的问题编号归档。
- **无 CI**：构建纪律靠本地 Makefile + 基线 tag 三点 diff。这是已知取舍（见 §9）。

## 9. 并发与状态管理（评审重点）

**基础模型**：Gin 默认每请求一 goroutine，无 worker pool。以下是共享状态的逐处同步方案与热点：

| 共享状态 | 同步方案 | 每请求代价 | 评审追问点 |
|---|---|---|---|
| **限流计数器** | 纯内存 `map[key]*rateLimiter`，每个 limiter 一把 `sync.Mutex`；窗口用定长环形缓冲；闲置 10 分钟回收 | 锁竞争按 key（用户/IP）分片，不是全局锁 | 不用 Redis——多实例部署时限流不共享，这是有意取舍 |
| **额度扣减** | `db.DB.Create(&QuotaUsageLog{})` **同步写库**，失败只打 ERROR 不挡请求 | 每次成功请求一次 INSERT | **SQLite 单连接下这是串行点**（见下） |
| **调用监控（含内容维度）** | 内存环形缓冲，**异步批量落库**；关停时兜底 flush | 写缓冲通道，不阻塞请求 | 通道满时淘汰旧行，丢失的只是监控不是计费 |
| **会话校验** | 每请求一次 `SELECT` 查 `auth_sessions.revoked_at/expires_at`；`last_active_at` 更新节流到 5 分钟一次（`lastActiveMinInterval`） | 每请求一次 SELECT，写被节流 99% | SELECT 与业务写共用 SQLite 单连接 |
| **API Key 归属缓存** | 进程内短缓存；命中不复查用户状态（禁用用户必须显式 `InvalidateUserApiKeys`） | 一次缓存查 | 已在 §6 安全模型说明 |
| **Redis 健康翻转** | `atomic.CompareAndSwap` 状态机——只有 bad→true（首次坏）与 true→bad（恢复）各打一条，后续同一种只计数不出声 | 翻转瞬间不会日志风暴 | 已做去重 |
| **上游缓存/singleflight/熔断** | 按 host 的熔断器 + singleflight 合并键 | 见 §5 获取栈 | — |

**SQLite 单连接这个取舍必须摆上台面**：

- 配置：`sqlDB.SetMaxOpenConns(1)`，理由是多连接下读事务升级写会触发 `SQLITE_BUSY_SNAPSHOT`（busy_timeout 不重试），GORM 官方建议。
- 代码注释的判断是"进程内 SQLite 查询为微秒级，单连接不构成吞吐瓶颈"——**这个判断没有压测背书**。

**请求路径上的真实 DB 访问清单**（按中间件链顺序，全部走这一条连接）：

| # | 访问 | 来源 | 有缓存？ |
|---|---|---|---|
| 1 | `auth_sessions` SELECT（校验 revoked/expired） | `ValidateSession`（每请求） | 无（仅 `last_active_at` 写节流到 5min） |
| 2 | `data_sources` SELECT（源配置） | `gate/access.go`（每请求） | **无** |
| 3 | `users` + roles + plan Preload | `gate/access.go` / `billing.go`（每请求） | **无** |
| 4 | `quota_cost` SELECT（计费单价） | `gate/billing.go` | **有**（`getCachedCost`） |
| 5 | `quota_cost_plan` SELECT（套餐级限流配置） | `gate/ratelimit.go`（每请求） | **无** |
| 6 | `quota_usage_logs` INSERT（用量流水） | `gate/billing.go`（成功时） | — 同步写 |

即每请求约 **4 个无缓存 SELECT + 1 个有缓存 SELECT + 1 个同步 INSERT**，全部串行在一条 SQLite 连接上。监控异步批量写（`api_call_logs`）虽然不抢请求路径，但最终也落到同一条连接，批量写时同样占用。

- **真正要压测的不是"单连接能不能扛"，而是这 6 类访问叠加后的 P99**：并发 500/1000 时，会话 SELECT、源配置 SELECT、用户 Preload、套餐限流 SELECT、计费 INSERT、monitor 批量写，六者叠加的队列深度峰值与 P99 延迟。
- **MySQL/PostgreSQL 部署不受此限**（连接池正常）；SQLite 部署的实际并发上限是多少，**没有数字**——这是已知最大风险点，不是"未压测"，而是"未量化，且已知是第一风险"。

**失败模式组合**（网关最该验证的场景）：

- **Redis 挂**：内存缓存继续服务，命名缓存退纯内存，请求不失败；日志只出一条 ERROR（翻转去重），恢复时一条 INFO。
- **上游全超时**：按 host 熔断开启，冷却期快速失败 503；同时若有过期缓存，端出"过期未超过 TTL×3"的旧值（本次基线新增的闸）。
- **号池耗尽**：热号到顶 + 冷备转正仍失败 → 该源请求 503；错误驱动扩容在后台跑，不阻塞请求。
- **DB 挂**：启动期拒绝启动（`log.Fatalf`）；运行期写失败请求仍 200（计费流水丢一行，ERROR 日志）——读路径失败按失败关闭（授权读不到就一个源都不给）。

## 10. 已知取舍与未解决问题（**本次评审最该咬的部分**）

> **导读**：本节是评审重点，优先看 §10.2 第一条（SQLite 并发上限未量化，已知最大风险）与第二条（脱敏靠约定无机制兜底）。前两个是性能风险，第三个是安全风险。

### 10.1 有意的取舍（已拍板，不是 bug）

| 取舍 | 理由 |
|---|---|
| 处理器间传参用 `map[string]interface{}` | 换取统一 Legado 形状与低接入成本，牺牲类型安全与 GC 压力（高并发下 map 分配/装箱未优化） |
| **SQLite 单连接 + 同步计费写** | 消除 `SQLITE_BUSY_SNAPSHOT`；代码判断"微秒级不构成瓶颈"但**未压测**，MySQL 部署不受限 |
| 限流用纯内存不用 Redis | 单实例部署模型；多实例时限流不共享（有意） |
| SSRF 的 DNS 结果永久缓存 | 简化，接受 DNS rebinding 窗口期 |
| 配额按请求计数（含缓存命中） | 计费模型简单；按上游真实调用计费是另一个特性 |
| 登录防爆破不按账号 | 防"攻击者点名锁人"，接受慢速分布式尝试 |
| 错误脱敏靠 `sanitizeUpstreamMsg`/`scrubQueryForLog` 两个中间件 | 源包自己 `log.Printf` 打原始 URL 会绕过脱敏——**无 lint 强制，靠约定** |
| 号池 `Claim 无损` 是文档约定 | Provider 实现违反时框架不检测，靠测试与 code review |
| 无 CI | 单人维护项目，本地门禁已覆盖 |
| 不引入 Go plugin / sidecar | Go 运行时插件生态不成熟，编译期拼装是语言现实 |

### 10.2 未解决问题（还在 backlog）

| 编号 | 问题 | 影响 |
|---|---|---|
| **—（最大风险）** | **SQLite 单连接下 6 类访问叠加的并发上限未量化** | 每请求 = 4 个无缓存 SELECT（会话/源配置/用户 Preload/套餐限流）+ 1 个有缓存 SELECT + 1 个同步 INSERT，全部串行在一条连接。代码注释"微秒级不构成瓶颈"无数据背书。**建议动作**：压测 500/1000 并发下的 P99 与连接队列深度；给 `data_sources`/`user+plan`/`quota_cost_plan` 加进程内缓存（这三个变更比压测本身更能降风险） |
| — | `map[string]interface{}` 传参的 GC 量级未量化 | 每个请求经 12 个中间件 + handler，map 分配次数随中间件数线性增长。**建议动作**：`go test -bench` + `pprof` 拿单请求分配数与 GC 频率，把"代价可接受"从定性变定量 |
| — | 源包日志脱敏靠约定，无机制兜底 | 源包自己 `log.Printf` 打原始 URL 会绕过 `scrubQueryForLog`。**建议动作**：提供 `logx` 包装（内部自动 scrub），规定源包禁止直接用 `log` 包；或在 Makefile 加一条自定义检查（源包目录下禁 `log.Printf`/`fmt.Printf`） |
| P112① | GET 通路（`FetchJSON`/`FetchText`）缓存不判 body 内容，HTTP 200 但业务失败的坏信封会被缓存并在 TTL 内反复命中 | 用户看到"同章 15 次 2ms 失败"。已做的：降级时限。未做的：ResponseFilter 回灌到 GET 通路 |
| P113② 残留 | FetchShared 的 POST 响应缓存（Redis 加密信封）不受 `content_consent` 同意位控制 | 关掉留存的用户，其"某本某章被请求过"的键仍在 Redis 活到 TTL——拍板接受的代价 |
| — | CORS 硬编码 `*`，无环境变量收紧 | 对外部署要改代码才能配白名单 |
| — | `conf.go` 硬编码 `DB_USER=root`/`DB_PASSWORD=123456`/`DB_TYPE=mysql` | 漏配 .env 时会拿弱默认值去连库 |

### 10.3 技术债观察

- 间接依赖链带进了 quic-go、mongo-driver、bytedance/sonic 全家桶——项目本身不用 MongoDB/QUIC，是 JSON 库的传递依赖，供应链面偏大。
- 信封错误码不统一：错误响应用 `conf.Config.ErrorCode`（-1），但 `NoRoute` 硬编码 `code:404`、部分 401 硬编码 `code:401`。
- 授权=限额同行（§5.2）：套餐批量调整靠 `POST /admin/source-groups/:id/apply-limits` 落库为每源一行，**没有"改额度顺带改授权"的误操作防护**——这是个写入入口，不是数据库约束，误操作靠管理员谨慎。

## 11. 建议评审关注点

如果评审时间有限，建议按以下顺序看：

1. **§9 并发与状态管理**：SQLite 单连接 + 每请求会话 SELECT + 同步计费写，三者叠加的并发上限你是否接受，要不要补压测。
2. **§5 关键决策**：每个"选它/代价"的判断你是否同意，特别是 5.2（授权=限额同行）与 5.5（号池状态机）。
3. **§7 数据留存**：`content_consent` 盖了哪几面、没盖哪几面，这个合规模型你是否接受。
4. **§10.2 未解决项**：SQLite 压测、P112①（坏值缓存）、CORS/DB 默认值，哪个应该升到 P0。
5. **§8 工程纪律**：这套 Makefile 门禁 + 待办清单编号体系，对单人维护项目是否过重。
6. **架构硬边界**（§4）：`middleware` 叶子包、`base` 不反向依赖 legado，这两条边界在包膨胀后能否守住。
