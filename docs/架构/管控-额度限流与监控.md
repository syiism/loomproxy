# 管控：额度、限流、访问控制、监控

> 本页由 `AGENTS.md` §9 拆出（2026-10-01 文档瘦身）。AGENTS 只留条目与一句话总结，细节以本页为准；
> 代码永远是最终事实来源，与本页冲突时以代码为准并回来更新本页。

- **计费**（`gate.BillingMiddleware`）：`quota_costs.status=0` 的接口对全员 403；未配置或 cost=0 不计费；匿名不计费；admin 不限不记；上游 200 后按 `quota_costs` 扣减并写 `quota_usage_logs`（当日口径见下面的「起算点」，并发下允许少量超扣）。
  **当日用量的起算点只有一个定义处：`gate.UsageSince`** = 「北京时间零点」与「该用户的管理员刷新时刻」里较晚的那个（`users.quota_reset_at`，NULL=从未刷新，待办清单 P41）。
  判定（429）与读数（`/quota/dashboard`、`/admin/users/:id/quota` 的 `used`）**都走它**——起算点要是长在两处，刷新后一处归零、另一处还挂着旧值，面板就成了「说不清哪边是真的地方」。
  管理员刷新走 `POST /admin/users/:id/refresh-quota`（只认会话）：它**不删也不冲正流水**（那是只追加的账本，删行等于毁掉「今天到底用了多少」的证据），
  也**不改限额**——放开的是「再一天的量」，所以紧接着的下一次消耗照样撞 429（用例把这条钉着）。过了零点水印自然失效，不需要定时任务去抹。
  可以反复点，每次都在服务端留一行 `ADMIN: 刷新单日额度 …` 日志（谁刷的、刷掉了多少已用量）。
  **`quota_limits.period` 今天不参与任何判定**：`gate/plan.go` 只按 `plan_id + scope` 取行，窗口一律是上面那个「当日」——
  但面板把这一列当单位显示（`100 / month`）也让人改它，`/admin/quotas/limits` 缺省还落 `month`。
  现在三个写口（新建、更新、按分组套用限额）在周期是个"装饰值"时各出一条归因 ERROR 说明生效窗口是哪一个；
  **这一列要不要真的开窗口、还是从面板摘掉，是待办清单 P70 等人的那一拍**。
  同理，`POST /admin/quotas/plans/:id/data-sources` 的响应**报的是读回来的那一行**（`limit` 取套餐默认档，
  free=100 / vip=1000 / admin 与自定义=-1），不是过去那句字面量 `limit:-1`。
  **日界只有一个算法**：`utils.DayStart(days)`（按 `TZ_OFFSET_HOURS`），`/monitor/trend` 的日标序列与
  榜单窗口、额度日界用的是同一个时刻；**每天那根柱子的高度也在 Go 侧按同一个日界归日**——
  过去它由库侧 `date(created_at)` 分桶，sqlite 会把带 +08 的串先归一到 UTC（实测北京 10-05 04:40 存成
  `2026-10-05T04:40:00+08:00`、`date()` 给 `2026-10-04`），而生产 MySQL（`loc=Local` + Asia/Shanghai）恰好一致，
  于是这条差异只在开发/测试库露头。P72（2026-10-06 拍板选 A）把它收进 `handlers/admin/monitor.go` 的一处 `bkey`，
  库侧不再判日界；`test/p72_trend_day_bucket_test.go` 钉住「明细归到平台日、且那天在 `days` 序列里」，
  变异=把归日改回 UTC 就红。内存环形缓冲那一路也走同一个 `bkey`（它原先自己按进程时区格式化，是第三套口径）。
  播种的默认单价只有 `content` 是 1，其余动作全 0**（`db/seed.go:seedQuotaCosts`）：正文是「一次请求换一整章上游内容」，而 search/detail/chapter/explore 是导航与元数据，按请求计费会让「翻一次目录」吃掉几十点额度，而网关侧那些动作多数还有上游缓存——成本与读数对不上。已有行不会被播种改写（只补缺失的 `(源, 接口)` 行），改现网口径**走面板「接口消耗」就是立即生效**
  （`PUT /admin/quota-costs/:id` 保存后调 `gate.InvalidateCostCache`，待办清单 P39——改之前全仓没有任何一处删除这份缓存，
  所以「改完单价」与「禁用接口」都要等一个 `CACHE_TTL`（默认 300 秒）才见效，症状不是算错钱而是「改了没反应」）；
  **直接改库则没有这个联动**：键格式只有一处定义（`gate.CostCacheKey`），手工 SQL 绕过了写侧，
  仍要等 TTL 过期或自己按同一个键删——成本缓存在 Redis 里，重启不清它。
  **扣减带一个内容冷却**（`BILLING_DEDUPE_SEC`，默认 300 秒，0=关）：同一用户对「同源 + 同接口 + 同内容」在窗口内只扣一次——真实形态是第一条正文 10 秒才回来、客户端放弃后重试同一篇，两次都 200 就扣两次（待办清单 P25）。内容标识取 `CallSubject` 的 `bookId`/`itemId`/搜索词，**取不到标识就不去重**（宁可多扣一次，也不能把两篇不同内容并成一条扣费）；请求照常放行、明细照常记，状态只在进程内（单二进制部署，重启最多让人多扣一次，不会漏扣）。`GET /admin/stats` 的 `billing_dedupe` 报「累计挡掉次数 / 在册键数 / 当前窗口」，不用人肉比流水。`AUTH_ENABLED=false` 时计费关闭（接口禁用仍生效）。

- **额度流水只有一个写入口，而它写失败是"漏扣"而不是"报错"**：`gate.recordUsage`（计费中间件与
  聚合扇出共用一处）。上面那句「不会漏扣」只覆盖去重状态那一层——**流水本身写不进去才是真漏**：
  `quota_usage_logs` 是 `UsedToday` 的读对象，少一行就少一格用量，而请求已放行、明细记成功、
  面板偏小，所以这里必须出声（日志原文「额度流水写入失败（用户/源/接口/点数）」）。待办清单 P88。
- **三个配置写入口失败即 500**：`PUT /user/source-configs`（用户自配地址）、`PUT /admin/source-configs`
  （平台默认地址——它决定所有没自配地址的人打到哪个域）、`PUT /admin/users/:id/quota`（额度覆盖）。
  过去这三处不看写库结果就回「已更新」，与同族的 `/apikey`、`blocked_ips`、`display-alias`（都回 500）不一致；
  本轮补齐，固定句「保存失败」不带 SQL 细节。行为变化本身登成待拍（报告 §8）。
  请求期真正读这两张配置表的是 `middleware/source.ResolveBaseURL`（用户覆盖 > 平台默认）。
- **验证码失败次数写不进库时只出声、不改判定**：`verification_codes.attempts` 是防爆破计数器，
  本次请求按内存值 `row.Attempts+1` 判定，库里不前进意味着**下一次读到旧值**。
  改成 fail-closed 是语义选择，已登成待拍；现网这条路开着但极冷
  （`verify_code_scenes = register,forgot_password`，全表 4 行、`MAX(attempts) = 0`）。
- **访问控制**（`gate.DataSourceAccessMiddleware`）：先查数据源 `status`，再问「这个套餐有没有 `fake_x` 这一行限额」——
  授权与限额是**同一行**（`quota_limits(scope=source, target=数据源码)`，`gate/grant.go`，待办清单 P34），没有这行就 403。
  曾经的第二张表 `quota_plan_data_sources` 已停写、已从 `AutoMigrate` 摘掉、生产已 `DROP`（待办清单 P34②）；
  模型与 `db/seed.go` 的 `alignPlanGrants` 只为「比 P34 更旧的存量库」保留一次性搬迁，并按「表在不在」自我开关。
- **维护模式是数据面闸门，不是全站停机**（`app/app.go` 的 `maintenanceBlocked`，待办清单 P53②）：
  设置项 `maintenance_mode` 开着时，**数据面路由**（`/{source}/{action}`，即 `source != ""` 那批）
  在进 handler 之前一律 `503` + `{code, msg="系统维护中，请稍后再试"}`；
  **管理员放行**（角色码 `admin`，与 `AdminRequired()` 同一条判据，不另立一份），
  **控制面 `/admin/*`、登录注册 `/auth/*`、`/data` 下发通道都不受影响**——维护期内要能登进面板看读数。
  两个刻意选择的口径写在代码注释里：**查不到角色按拦处理**（失败关闭，"维护中放没放人"不能取决于一次库查询的成败）、
  **读取走 `db.SettingBool`**（10 秒缓存，关着时热路径零成本，所以拨下去之后最长 10 秒还在拦）。
  匿名调用在 `apiauth`（Order 100）就先拿 401，到不了这道门——那是分层事实，
  只有 `AUTH_ENABLED=false` 的部署里维护门才真的拦得到匿名。
  **被这一挡拦下的请求不进 handler，所以 `CallSubject` 从来没被挂上**：`monitor` 拿到的是 nil、
  各内容维度为空，但**这次调用仍然要完整走完观测并落进环形缓冲**（P93 那条断言钉的就是这件事）。
- **限额解析优先级**：用户数据源级覆盖（`user_quota_overrides`，**追加语义**：生效额度 = 套餐限额 + 覆盖值）> 套餐限额（`quota_limits`）> 不限。
  「有这行才有权」改变的是**读权限的那一半**，限额数值算法没动：`limit=-1` 仍是能用且不限。
- **单日额度的起算点有两种模式（待办清单 P106）**：`day`=平台时区自然日 0 点（默认），
  `subscription`=本人注册时刻的那个钟点，每 24h 一轮。**面板上那个切换入口 2026-10-10 按 P119 ① 摘掉了，
  端点与字段原样保留**（A 档：已经切过的人继续按其钟点清零，只是再不能自己改；要恢复入口就从 git 里取回那一节）。
  写入口仍是 `POST /auth/quota-cycle`（只认会话，
  30 天冷却；重复提交同一个值不算切换、不占名额），判定读的还是**同一处** `gate.UsageSince`——
  它只是多了一个候选，管理员那一次「刷新额度」在两种模式下都仍压过起算点。
  **窗口长度没有第二种**：限额仍然是「/ 日」，切模式不改限额、不改流水，只改"这一轮从几点算"。
- **额度转移**（待办清单 P97）：把自己两个源之间的**日限额增量**重排——转出方 `user_quota_overrides` 减 n、
  转入方加 n，**总数不变**；已用量与 `quota_usage_logs` 流水一概不回改。判定只有一个口 `gate.TransferQuota`，
  本人端（只认会话）与管理端都走它，四条边界：两端都不能是**不限额**、目标源必须**已授权**（P34 那行同时管两件事）、
  可转量不超过转出方的当日限额、**增量算出来是 0 就删行**（0 的语义是"没有覆盖"，留一行 0 会进「被手工刷过额度」的筛选）。
  每次成功转移与两行覆盖**同一事务**写一条 `quota_transfer_logs`（含 `via` 与 `operator_id`——
  不记是谁动的，本人自助与管理员代操作在审计里就分不开）。
- **本人可以清除自己那一列记录，但清除是软删（待办清单 P119 ④ 的 C 档）**：
  `DELETE /quota/transfers` 只把 `quota_transfer_logs.cleared_at` 标成当前时刻，**行不删**。
  三条口径各自有理由：**只认会话**（与 `POST /quota/transfer` 同一条边界——长期密钥读得到这个人挪过什么，
  不该能销毁痕迹；所以这条端点挂在 `/quota` 那组**外面**，不在组里叠第二层守卫）；
  **只动自己的行**（归属条件是唯一的 `user_id`，越权的形状是 0 行而不是报错）；
  **不碰判定**（判定读的是 `quota_limits` 与覆盖行，转过去的增量在清除之后照旧生效——
  用例专门钉了这一条，因为"顺手把额度也回滚了"才是这种功能真正危险的形状）。
  读侧：`GET /quota/transfers` 过滤 `cleared_at IS NULL`（`total` 跟着变，分页不许把已清除的算进去）；
  **管理端 `GET /admin/users/:id/quota-transfers` 一概不过滤**，但每行带 `cleared` / `cleared_at` 两格——
  管理员看到一份被本人清过却看起来像原始记录的列表，比看不到更糟。
  面板上这一列默认折叠（`UiCollapse`），清除按钮两步确认、文案直说"记录仍在管理端可查"。
  **上线影响**：新列由发布序列的 AutoMigrate 落库（与 P52 那一族同一条路），本轮**没有对生产库做任何 DDL**。
- **用户侧首页那四张汇总卡的口径**：`今日总额度` / `今日剩余` **只统计有限额的源**——
  混合时不写「数字 + 不限」那样的模糊值（一个可核对的数与一个档位并存时，读的人两头都拿不到），
  **全部源都不限额时才显示「不限」**。「不限」这件事并没有被藏起来：每张源卡自己那一格照写，
  `平台数` 卡也在。因此「今日剩余」不是全部可见源的合计，这一条是被有意选择的展示口径。
- **速率限制**（`gate.RateLimitMiddleware`）两种口径并存，优先级：套餐级 > 全局，同级内 窗口计数（`limit_count` + `window_sec`，允许突发）> 固定间隔（`interval`，令牌桶容量 1，不可突发）；套餐级配了任一种即不回退全局。同时作用于 IP 维度与用户维度（key 含 planId），两者都放行才放行；管理员豁免全部；配置直查库，保存即生效。
- **监控**（`base/metrics.go` + `app/monitor.go`）：内存聚合 + 最近调用环形缓冲，缓冲满 250 条批量落 `api_call_logs`；明细保留期由 `MONITOR_RETENTION_DAYS` 决定（**默认 0=永久，`PurgeExpiredCallLogs` 整段 no-op，归档表恒空、明细表即全量**），设了天数才在删除前按 数据源/接口 聚合累加进 `api_call_stats` 永久归档（**聚合与删除同一个事务**：删除失败就整体回滚，否则"归档已加、明细还在"会让 `lifetimeCounts` 从那一刻起永久性虚高，重跑一次更糟——待办清单 P55）——`lifetimeCounts` 的「归档 + 明细 + 未落库内存」三口径在两种模式下都不重不漏；`GET /admin/monitor`、`/monitor/trend`（7 天是**展示窗口**、与保留期无关，按天×源聚合，合并内存中未落库明细）、`/monitor/history`、`POST /monitor/reset`。
- **调用明细的内容维度**（`base/subject.go` + `base/legado/observe.go`）：`api_call_logs` 除路由与状态码外，还记录 `keyword`（搜索词）/`book_name`/`chapter_title`/`media`（媒介）/`result_count`。取值来自**规范化响应**而非请求参数——app 在进 handler 前把 `*base.CallSubject` 挂到 `middleware.CtxCallSubject`，handler 返回后 `ObserveCall` 回填，`source/monitor` 在 `c.Next()` 之后读走（所以被管控拦掉的请求各维度为空）。名称靠「标识→名称」命名缓存跨请求反查（search 灌入、content 反查），上限 2 万条 / 24h。**键的段数由"标识在哪个范围内唯一"决定**：书名是 `source|书标识`，章节名是 `source|书标识|章节标识`——章号在多数上游只书内唯一，少一段就会把一本书的章名发给另一本书（现网实测 123 组跨书撞键，待办清单 P84）。没有书标识时**整条不登记也不反查**：名称留空是合法状态，猜一个才是错。
  **同意位关闭时这里全部不清**（待办清单 P37）：`source/monitor` 在 `RecordCall` 之前调
  `CallSubject.WithholdContent()` 把七个字段抹掉并打上 `content_withheld`——
  那一格的存在是为了让「用户选择不留」与「采集在漏」在覆盖率表上分得开（P19 的反方向：读数要自己说得清）。
  命名缓存的写入不受同意位影响：它存的是「某个书目标识叫什么」这类书自身的元数据，不与任何用户关联。
  该缓存可挂 Redis（`REDIS_ENABLED` 且可达时由 `app.initSubjectStore` 注入 `base.SubjectStore`）从而**跨重启存活**；
  未启用或连不上就是纯内存（现状行为），`/admin/monitor` 的 `name_store_persistent` 字段说明当前是哪种。
  明细同时记 `book_ident`/`chapter_ident`：名称当时反查不到（缓存未命中）也先留标识，等映射建立后由
- **命名缓存的写侧体检**（`app/subject_store.go`）：接 Redis 后落库是异步队列——队列 32768 深、
  一批 512 条 pipeline、单批 3s 超时；两类丢失分别计数（队列满丢的 `dropped`、投进去了但 Redis
  没写进去的 `failed`），连同当前排队深度经 `GET /admin/monitor/subjects` 的
  `name_cache.persist` 出到面板。纯内存（没接 Redis）时这个键**缺席**——「没接」不等于「接了但一条没丢」。
  丢弃过去只活在关停日志的一行里，运行期间没人看得见（待办清单 P2）。
  `POST /admin/monitor/backfill-subjects` 是同一个回填的手动入口（`admin.RunSubjectBackfill`），
  **默认路径是定时循环**（`app.startSubjectNameBackfill`，间隔 `MONITOR_BACKFILL_SEC` 默认 900 秒，0=关掉只留手动）：
  单批上限 5000 行、一轮里连续捞到「捞空」或「补不动」为止（反查不到映射的标识会一直留在结果里，
  不认这个条件就每轮重复捞同一批行，所以「本轮一处没补」就是停止条件），回填幂等所以随便重跑。
  这件事必须周期性做而不是等人点：缺名的成因是结构性的——重启后命名缓存还没 warm，那第一批只带
  `bookId`/`itemId` 的正文调用就只记下标识；等这些书再被搜索命中，映射回来了、那些行本补得动，只是没人记得去点（P20）。
  **扫描按 id 倒序**（取最近的上限行）：榜、覆盖率、明细页读的都是近窗口，补不到的必须是没人再看的旧行——
  旧的升序配上新循环等于让一批永远反查不到的陈旧行长期霸占整个扫描窗口，新行一条也进不来。
  查询端：`/admin/monitor/history` 支持 `keyword`/`book_name`/`chapter_title` contains 筛选（LIKE 通配符已转义）与 `media_type` 等值；`GET /admin/monitor/subjects?dim=keyword|book|chapter|media&days=&source=&media=` 出维度榜（含 0 结果次数、涉及数据源数、命名缓存条目数）。书名维度额外带一个 **`book_id`**（该书名最近一次调用所带的书目标识）：面板不展示它，给的是**拿榜单去检索的人**——书名会重名，详情与正文只认标识。取「最近一条非空标识」而不是「最近一条明细的标识」，因为旧行可能只记到名称。**这两栏（`last_called_at` 与 `book_id`）现在与主聚合在同一趟里取 `MAX(id)`**（书名维度另取 `MAX(CASE WHEN book_ident <> '' THEN id ELSE 0 END)`），值整页一次主键点查取回——原来每个条目两条单查，一次公开榜就是 40~60 条（待办清单 P118 ①）。公开榜 `/rank/boards` 的阅读榜**也给**同一个 `book_id`（那里依旧只给名称、次数与这一个标识——不给 `last_called_at`、不给涉及数据源、不给成功率与耗时，那几样才能把明细反推到「谁在读哪本书的哪一章」。给标识不构成新的泄露面：同一批 `bookId` 本来就随数据面的搜索与详情响应下发给登录用户，见 `base/legado/search_base.go`）。
  `dim=book`/`dim=chapter` **只统计 `action='content'`** 的明细（动作白名单写在 `subjectrank.Dims` 里，SQL 与内存两条读取路径都过滤）：一次打开书目会产生 detail 与分多页的 chapter，全计入会把同一本书凭空乘几倍——榜单回答「读了什么正文」而非「点开了什么」。`keyword` 与 `media` 不受动作限制。
- **公开榜有缓存，管理端榜没有**（待办清单 P118 ③）：`/rank/boards` 在**出口层**缓存「要发出去的那两张榜的行」，
  TTL 是 `RANK_CACHE_SEC`（默认 60 秒，**<=0 就是每次真算**）。缓存键的原料必须有
  `dim` 集合 / `days` / **窗口起点** / `source` / `media` / `limit` / **allowSources 的散列** / **管理员还是公开榜** 这几段——
  少最后一段就是 P84 那一族（管理员那次「不限源」的合并结果被发给只看得到两个源的人；少窗口那一段，
  跨日界还会把昨天的总体发到今天）。**陈旧只发生在榜的计数上**：`sources` 与 `medias` 两个下拉每次现取，
  改名或下架一个源，下拉框立刻跟着现实走；但**榜上的行在 TTL 内仍可能带着刚下架那个源的计数**（最长
  `RANK_CACHE_SEC` 秒）——这是缓存的固有代价，本轮没为它加失效口：改白名单会让键自己换一格，
  而下架一个源在几十秒内少几条热度不改变任何判定。响应带 `cache_ttl_sec` 把陈旧窗口说出来，面板不自己抄那个数。
  管理端 `/admin/monitor/subjects` 不缓存，因为它带 `last_called_at`——那一栏陈旧的语义是"排障时看到一个假时刻"，
  要说这件事得先决定怎么在响应里标出来，不在这一轮顺手做。
  **另有一条给后来数 SQL 的人**：GORM 的 `Scan` 收尾不跑 query 回调链，本仓那个数查询条数的回调
  对榜单主聚合**失明**（报 0 条不等于没查库）——判据正本在踩坑判据「用回调数 SQL」那一条。
- **两张榜的排名数字不同义**（待办清单 P18）：一条 content 明细就是**一章正文**，所以书名榜按
  「同数据源内的访问人数」排名——身份是 `COALESCE(NULLIF(username,''), ip)`（注册用户用用户名，
  匿名退到 IP），按 `(书名, 数据源)` 去重后**跨源相加不再去重**（跨源去重会把「同一个人在两个源读过」
  变成可推断的关联，且匿名 IP 跨源合并只会低估）。章节榜与搜索榜仍按次数：章节被打开的次数才是它们要的答案。
  声明位在 `Dim.PerSourceVisitors`，不是全局开关。
  两个口径同时下发（`Item.Visitors` / `Item.Requests`），公开榜另带 `unit`+`metric` 把单位写在数据里，
  免得「20」被统一读成热度。**成功率与平均耗时分母一律是请求数**——拿人数当分母会把
  「一个人读五章里失败一次」的失败率稀释成五分之一。
  内存环形缓冲里还没落库的明细**参与去重**：按 `(名称, 源, 身份)` 三元组回查已落库的身份集合
  （只查内存里出现过的名称，规模受环上界 200 条约束），否则同一个人既有旧章节落库、
  又有新章节在环里，会被数成两个人。
- **带内失败单独标记**（待办清单 P22①）：源的 `content` handler 在参数缺失/上游失败时返回
  `ContentType=="error"` 的正文、HTTP 仍是 200（Legado 书源的传统写法）。`base/legado.ObserveCall`
  认出它在明细标 `in_band_error`（`api_call_logs` 新列，NOT NULL 默认 false；SQL 判据用
  `IS TRUE`/`IS NOT TRUE`，三方方言通用且对 NULL 安全——旧行自动回落纯 HTTP 口径），
  **成功率类读数一律计入失败**：会话聚合（`base.RecordCall`）、维度榜、趋势图、保留期归档；
  覆盖率表的 `failed` 同口径并单列 `in_band_failed`。对下游的响应、计费与 IP 封禁**不受影响**
  （P22② 已判定：**维持带内、不改 5xx**，见 `待办清单修复报告_20261004.md`）。
- **带内失败的成因是一列，不是一个日志**（P22②-b 的 ②-b1）：`api_call_logs.in_band_reason`（`size:32`）
  由 `ObserveCall` 从错误正文的 `reason` 键照抄，**骨架只搬运不解释**。
  它的来路是分支 S20 那条判据：`in_band_error` 只是布尔，"哪一类错误"过去**只能去读日志**，
  而②-b 那次定案就是在读日志上做的。**今天现网读到的必然全是空串**——还没有源报这个键，
  空是"源没给"而不是"没坏"（所以别把空值当采集缺口，也别拿它做告警）；
  这一列的价值是**下一次要分类时不再靠定性**。
- **带内失败的业务码是另一列**（待办清单 P122）：`api_call_logs.in_band_code`（`size:32`）由
  `ObserveCall` 从错误正文的 `code` 键照抄，与 `reason` 同形状——空=源没给，是合法状态、读数不猜。
  `reason` 是源的成因分类（"是上游回的错误"），业务码才是「站方到底回了哪一档」：
  S104 取证那种「会话被拒（401/403）」与「配额/风控 429」靠它才分得开。
  **同意位关闭时不清这一格**（P37 在 P122 上的判：`WithholdContent` 抹的是内容维度七列，业务码不是内容维度）；
  管理端明细有 `in_band_code` 等值筛选、状态列带 `reason·code` 标注，**榜不读它**（维度白名单不放宽）。
  骨架只提供采集位与搬运；源侧填值在装配仓（`sources/zj_novel` 的 `reasonUpstream` 一族把信封码填进 `code` 键）。
- **聚合搜索的治理口径**（`app/aggregate_search.go`，待办清单 P38）：`GET /{source}/search?sources=a,b`
  在 handler 内部调其他源，那条路**不经过中间件链**，所以 access/billing 的判定要在扇出侧逐源重走一遍——
  用的是从中间件里抽出来的同一组函数（`gate.SourceAccessVerdict` / `gate.AggregateTargetVerdict`），
  不是复制的逻辑：两处各写一遍「谁能用哪个源」迟早漂移，而这里的漂移方向是安全漂移。
  每个真正打出去的目标各扣一次额度（不扣就是「免费档 200 次/日换 N 个源」的空头支票），
  而**入口源不重判也不重扣**（链上已经为它做过，重复一次就是双计）。
  **扇出的并发按源闸住、跨请求共享**（待办清单 P110）：`aggregateAcquire(ctx, source)` 取一枚该源的在飞许可，
  上限来自 `AGGREGATE_PER_SOURCE_MAX`（默认 4，0/负数按默认）。这一句在 2026-10-08 之前是不成立的——
  那时那道闸是**每个请求新建**的一个容量 4 的信号量，挡得住"一个请求同时打 8 个源"，
  挡不住"N 个用户各发一个聚合请求打同一个源"（3 个用户 × 8 目标 = 同时在飞 24 发），
  而旁边的注释写的威胁恰恰是跨请求的那种。排队而不是拒绝（聚合的语义就是能回多少回多少），
  但尊重 ctx：客户端在排队阶段就走了，那一源记新成因 `canceled` 而**不是** `upstream_failed`——它根本没碰上游。
  逐源结果只以成因枚举 `sources_status` 下发，不含上游文案；被跳过的源（未授权 / 额度满 / 缺参 / 停用）
  连上游都不打。**限流与自动封禁不在这一刀里**（仍按入口源判定，在册偏差，见待办清单 P38 第 3 条）。全部目标都失败时照实报错——返回「200 + 空列表」等于把「上游都坏了」说成「这次没搜到」，
  成功率、覆盖率、榜三处一起说谎。

- **覆盖率的分母不含退出行**（待办清单 P37）：`rows_` 与 `failed` 都只数
  `content_withheld IS NOT TRUE` 的行，另出 `withheld` 一列、面板覆盖率表加「未捕获」列。
  覆盖率回答「采集在不在漏」，用户选择不留不是漏——混在一个分母里就会长出一个假的缺陷。

- **内容维度覆盖率**（`subjectrank.Coverage`，随 `GET /admin/monitor/subjects` 的 `coverage` 下发）：按
  `源 × 接口` 数窗口内每一格维度**有值**的行数，回答「哪个源的采集在漏」——在这之前，口径出问题
  （`book_id` 常年为空、书名一直没记上）全靠人肉写 SQL 撞见。三条判据是这块的全部要点：
  ① **只数「有」，缺失由 `rows - 有` 推出**，条件一律 `COALESCE(col,'') <> ''`——`book_ident`/`chapter_ident`
  是后加的列，旧行是 NULL，而 `col <> ''` 在 NULL 上是 unknown，两套判据并存必然漏算（实测生产 6691 行里
  NULL 2914 / 空串 952）；② **`expect_book` 随数据下发**（`detail`/`chapter`/`content` 为真）：search/explore
  返回的是一批书，没有「这一本」可言，它们的 0% 是正常状态，面板据此决定要不要标红，而不是对着一片合法的空报警；
  ③ **少于 5 行的组合不返回**，零星请求的百分比（无论 0% 还是 100%）都不说明问题。
  口径是**已落库明细**，不含环形缓冲里那 ≤200 条（这是健康度趋势，不是实时榜）；统计失败不拖垮整页，
  另出 `coverage_error` 让面板单独说明。列名用 `rows_` 而非 `rows`（`ROWS` 是 MySQL 8 保留字，见开发约定）。
- **管理端读数要分得开「没有」与「读不动」**（待办清单 P99）：`Find`/`Count`/`First` 不取 `.Error` 是 Go 里的默认写法，
  后果是"查询失败"与"这张表里没有这条"落成同一个零值。现在读侧一律取结果，失败经 `db.LogReadFail` 出一条 ERROR
  （按 (落点, 表) 去重，同一种只喊一次——读配置在热路径上，每请求一条会把读数泡坏）。
  面板那半给了**第三态**：`GET /admin/stats` 的四个 `Count` 读失败填 `-1`（形状照 P54 的 `table_growth`），
  `Admin.vue` 按负值渲染「读数不可用」；而 `normal_count` 在任一上游读数失败时**不再做减法**——
  拿哨兵做算术会算出一个看起来正常的假数。**列表页的分页 total 仍是旧形状**（读失败显示 0），那一格仍登在 P99。
- **自动拉黑**（`middleware/ipblock/autoblock.go`）：滑动窗口统计数据源路由的 403/429，达阈值写黑名单（`source=auto`）；回环地址永不自动拉黑；开关与阈值走系统设置（`auto_block_enabled`·`auto_block_threshold`·`auto_block_window_sec`）。
- 历史字段名注意：`quota_costs` / `quota_cost_plans` / `user_quota_overrides` 的 `group_code` 列**实际存的是数据源码**（组概念已移除，启动时按各源 `LegacyGroups` 声明把存量组码行展开为每源一行并删除组行；无声明则组行留在库中不生效）。同理，本部署下线的历史源由环境变量 `RETIRED_SOURCES` 声明，seed 据此清理其在各配置表的存量行（`db.cleanupRemovedSources`，历史用量流水保留）。
