# 通用号池（base/pool）

> 本页由 `AGENTS.md` §6 拆出（2026-10-01 文档瘦身）。AGENTS 只留条目与一句话总结，细节以本页为准；
> 代码永远是最终事实来源，与本页冲突时以代码为准并回来更新本页。

凭证/额度型上游资源（设备号、账号、临时 token）的复用框架，与具体上游协议无关：

- **Provider 接口**（源包实现）：`Name()` / `Create(ctx) (*Device, error)`（只建号不领取）/ `Refresh(ctx, dev) (Quota, error)`（拉真实额度，不产生领取）/ `Claim(ctx, dev) error`（领取一次，**必须叠加无损**——多次领取延长有效期而非重置）。可选实现 `ResourceExpiredClassifier`，把「资源到期」类错误从限流信号里剔除。**三个钩子的契约随形态不同**，见下条。
- **形态声明位 `Config.Kind`——框架按它分叉调度**（待办清单 P5）：
  - 空 / `pool.KindBurnWallClock` **墙钟燃烧型**：资源按墙钟自燃，多号并行等于同步燃烧，所以
    「只保持 1 个活跃号 + N 个冷备，临期续领、用尽换号、限流扩容」，三个钩子全用得上。
  - `pool.KindSpread` **用量摊薄型**：号不因墙钟过期，燃烧速度取决于请求量，被风控时只是
    **临时**不可用。这一形态下框架**只调 `Create`**——不 `Claim`、不 `Refresh`、启动不逐行探活
    （打上游探活本身就是风控成本）；`hot` 就是「全部可用号」，`Acquire` 在它们上面轮询；
    失效由业务侧经 `Pool.Cooldown(ident, until, reason)` 上报，到期自动回轮询。
    对这种池套用「只保持 1 个活跃号」等于把所有请求打到同一台设备上，比不接池更糟。
    一台可用号都没有时 `Acquire` 报错，并把原因分三方言明：没建过号 / N 台全部在冷却 /
    想补号却被 `MaxDevices` 拦住（后两者常同时发生，就两条都报，且 `errors.Is(ErrCapacityReached)` 仍成立）。
    **不设上限时全冷却会自行补一台**——池不停摆优先于「等冷却」，这是设计选择，用例钉住了。
  - 摊薄型专属配置：`TargetDevices`（目标可用号数，0 → 取 `MaxDevices`，再 0 → 1）、
    `CooldownDefault`（`Reauthorize` 的兜底冷却时长，默认 10 分钟）。源侧有精确冷却口径时应直接
    调 `Cooldown`，`Reauthorize` 只是兜底路径——它把号**冷却**而不是转 `spent`。
  - **总号数上限 `Config.MaxDevices`**（0=不限，刻意不参与零值回填）：判在 `createColdLocked` 入口，
    覆盖 `Acquire`/`Reauthorize`/补冷备/摊薄型补号四条建号路径（`TargetDevices` 越不过它）。
    计数含 `spent`/`dead`（与源侧原先自己实现的口径一致，`purgeDead` 腾出的名额重新可用；
    **软删的行不占名额**——GORM 默认作用域过滤 `deleted_at`，这也是手工清死号用软删就能腾位的原理）。
    到顶时报 `pool.ErrCapacityReached`，`Acquire` 用双 `%w` 把它与「无可用号」一起带出，
    调用方可 `errors.Is` 判定。**为什么在框架里**：建号对上游是不可逆增长，这道闸门是每个会建号的
    源都要的共性，不该各自数一遍 `pool_devices`（待办清单 P4）。
  - **水位被名额压，但名额不被水位压**：`MaxDevices > 0` 时 `withDefaults` 把可用目标夹进名额之内——
    燃烧型 `ColdSpares ≤ MaxDevices - 1`（那一个名额该给活跃号），摊薄型 `TargetDevices ≤ MaxDevices`。
    **只夹水位、不动 `MaxDevices`**：闸门按水位收紧会把错误驱动扩容的余量一起削掉（P35 特意留给它的那部分）。
    **夹的下限是 1**：建号只走「补齐冷备」这一条路，夹到 0 等于告诉池「不要号」，它一个都建不出来。
    夹完仍然补不齐的是**单设备池**（`MaxDevices=1`：活跃号占满名额，冷备永远无处安放）——
    生产七猫游客池就是这个形状。这种「被上限判住」是闸门在做事、不是故障，所以
    `topUpColdLocked` 对 `ErrCapacityReached` **只在状态变化时出声**（首次一条，之后沉默；
    换实例即重启后再判住会再出一条），其余建号失败照旧每轮都喊。
    不收口的代价不是功能坏（活跃号照常服务），是**读数被泡坏**：生产上这条每 60 秒一条 error，
    看日志的人只会得出「这个池一直在出问题」（待办清单 P36；分支 S34 发布时实测）。
  - **死号保留上限是算出来的，不是配出来的**：`MaxDead` 是留档愿望，`MaxDevices` 是不可逆增长闸门，
    两者过去互不知情——**`MaxDevices < MaxDead` 时死号既清不掉又占满名额**（生产 uxx 就是 5 < 10），
    池只会留一条 "create cold device failed" 的日志静默失能。现在生效上限
    `deadRetention() = MaxDevices - usableTarget()`（与 `MaxDead` 取小，`MaxDevices=0` 时就是 `MaxDead`），
    规则是**先留得下可用号、再谈留档**：燃烧型可用目标 = 1 活跃 + `ColdSpares`，摊薄型 = `TargetDevices`
    （所以满配的摊薄池保留上限是 0——那类池每台死号都是纯名额损失）。
    建号入口在被判住前会**先清一次腾名额再重数**（不等下一轮巡检，间隔里源侧一直在空转），
    快照带 `dead_retention`、面板在两者不等时显示「死号只留 N（配置 M，被总号上限压到）」（待办清单 P35）。
    快照另带一格 `soft_deleted`（按池数 `deleted_at IS NOT NULL` 的行）：**框架自己不产生软删行**
    （清理那一路是 `Unscoped()` 硬删、管理面也没有软删入口），所以这一格只可能因手工 SQL 而 >0，
    它同时是"有人在库外面动过号池"的探针；这些行在所有按状态的计数里全都隐形（不占名额、也不会被自动清），
    面板在 `>0` 时才挂一句说明，**查不到时报 -1 显示「读数不可用」而不是 0**（待办清单 P35②）。
- **状态机**（`models.PoolDevice`，表 `pool_devices`，按 `pool + ident` 唯一）：
  `hot`（活跃，已领取且在有效期内；摊薄型语义即「可用」）/ `cold`（冷备，未领取不过期）/
  `cooldown`（临时不可用直到 `expire_at`，`note` 记原因；只摊薄型会填）/
  `spent`（周期次数用尽，周期重置后复活）/ `dead`（上游持续失败，超过生效保留上限后物理清理——
  上限见上条 `deadRetention`，最旧的先删）。
  - 冷却与判死是两件事：会话被冻一小时与账号被永久封禁混成 `dead`，就会被 `MaxDead` 清理掉，
    号池从此不可恢复。
- **凭证的两处落点**：`Attrs` 是**扁平 `map[string]string`** 的 JSON；想塞嵌套在 Go 里就编译不过
  （这一列的类型就是 `map[string]string`），所以旧文档说的"嵌套被静默丢弃"并不是真实风险，
  真实的形态是**这一列被库外面改坏**（手填 SQL、截断的文本）：`decodeAttrs` 过去连 `json.Unmarshal` 的错都不报，
  症状同样是「号在库里但凭证为空」，而系统一声不吭。现在 `deviceOf` 会出一条 ERROR
  （说清池与号、标识走 `maskIdent` 脱敏、**同一行只喊一次**，待办清单 P59）；
  **空串仍然合法**——那个号就是没附加凭证，喊它就是给正常形态造噪声。
  设备会话 cookie 这类嵌套凭证走 `Device.Payload` /
  `pool_devices.payload`（`text`，框架不解析内容，源侧自编解码，回写走 `Pool.UpdatePayload`）。
  没有把 `Attrs` 放宽成 `map[string]any`：那要 xmly/uxx 两个现成 Provider 全体改一遍，收益只是省一个新字段。
- **策略（燃烧型）**：`Acquire` 轮询活跃号（一个活跃号可服务无限并发）；`Maintain`（默认每分钟）
  负责临期原地续领、耗尽退役并转正替补、冷备补齐（优先逐个复活 spent，再新建）、dead 清理、
  错误驱动扩容（窗口错误率 >30% 且样本 ≥20 时活跃号 +1，上限 `MaxHot`，恢复后靠到期自然缩容）；
  `Reauthorize` 用 `base.Flight` 按号合并并发自愈（可补领则补领，否则换号）；`Report(err)` 供业务侧上报调用结果。
  **摊薄型的 `Maintain` 只做三件事**：放行到期冷却、把可用号补到 `TargetDevices`、清死号——
  续领与错误驱动扩容都是燃烧型概念（摊薄型的所有可用号本来就在轮询）。
- **维护循环的出声规矩**（待办清单 P76）：`Maintain` 里三处失败出口——台账刷新失败、续领（`Claim`）失败、
  转正替补失败——都走 `noteBad` / `noteGood`：**同一种失败只说第一句，恢复时补一条并带上此前累计次数**；
  错误文案变了就算状态变化，会再说一次（键 = 身份 + 路径：`refresh <ident>` / `renew-claim <ident>` / `promote`）。
  动因与下面 `ErrCapacityReached` 那条同源：维护是**每 tick 一次的重试路径**，而「续领失败」里包含
  业务上的正常状态（某源金币当天到顶是一天里的常态，不是要人看板的故障）。
  **`topUpColdLocked` 的建号失败仍每轮喊**——那是 P36 明确保留的决定（建号不是对同一目标的无损重试），不是漏网。
- **转正候选排序** `PrioritizeClaimed`：已领取且仍在有效期的冷备优先（时间在白烧），越早到期越优先，
  其余保持原序在后。只服务燃烧型；摊薄型转正不探活、不领取，直接取冷号列表首个。
- **源要在启动时登记池？用 `base.SourceMeta.OnBoot`，不要放在包 `init()` 里**：`conf.Load()` 读
  `.env` 发生在 `app.Run`，而包 `init()` 早于 `main`——在 init 里 `os.Getenv` 读不到 `.env` 的值，
  症状是「配置文件里改了却不生效」。`OnBoot` 由 `app.Run` 在 `conf.Load` + `db.Init` 之后、
  `pool.StartAll()` 之前调用，正好满足两件事：读得到源自有开关，且**登记的池会被同一次 StartAll 启动**、
  导入的号会被 `initLedger` 装载。钩子返回 error 或 panic 都只记日志不阻断启动（一个源的准备失败
  不该让别人起不来），且要写成幂等。用例 `test/source_boot_test.go` 钉这三条。
- **接线**：源包 `pool.Register(pool.New(provider, cfg))` → `app.Run` 里 `go pool.StartAll()`
  （`POOL_ENABLED=false` 整体跳过）→ 启动按形态装载存量号（燃烧型逐行探活分类，摊薄型纯本地分类）→
  维护协程按 `Interval` 巡检 → 关停经 `lifecycle` 自动 `StopAll` → 管理面板读 `GET /admin/pools`
  （`pool.StatusAll()`）。
- **可观测性**：标识与凭证值一律脱敏——标识留前 8 后 4，`attrs` 与 `payload` 都只出**键名**
  （`creds` / `payload_keys`），`note` 出冷却原因。面板「号池」页按形态给两套摘要（燃烧型：冷备/活跃上限/
  临期续领；摊薄型：轮询目标台数/兜底冷却），计数区含「冷却中」一列。
- 底座项目不携带任何 Provider：号池列表为空是正常状态，框架由 `test/pool_test.go` 的假 Provider 覆盖
  （两种形态都有用例，摊薄型那组专门钉住「不 Claim、不探活、冷却不进判死、载荷值不出接口」）。
