> 线上实态：机 `hk`、路径 `/www/go_project/loomproxy`、二进制名 `loomproxy`（模板已随收口对齐，别再按 `/opt/loomproxy` 抄）。
> 动机：旧的升级方式 = `systemctl restart loomproxy`，restart 瞬间端口关闭，
> 在途请求被拒绝、新连接收到 connection refused / RST。

## 1. 原理

端口由 **systemd 持有**（`.socket` 单元），不是进程持有：

1. `loomproxy.socket` 让 systemd 在 8081 上 `listen()`；
2. 有连接到达（或 `systemctl start`）时 systemd 拉起 `loomproxy.service`，把已 listen 的 fd 经
   `LISTEN_FDS`/`LISTEN_PID` 环境变量 + fd 3 传给子进程；
3. 进程侧 `app.Run` 先试 `activation.Listeners()`（`github.com/coreos/go-systemd/v22/activation`，
   纯 Go、不碰 CGO，与 sqlite3 无冲突）：
   - 拿到 fd → 直接 `srv.Serve(activated[0])`，**不自己 bind**；
   - 拿不到（本地开发、非 systemd 部署）→ 回退 `net.Listen("tcp", addr)`，行为与改造前完全一致。
4. 升级时 `systemctl restart loomproxy.service` **只重启 service、不动 socket**：
   老进程收到 SIGTERM 后优雅停机（在途请求处理完才退，`TimeoutStopSec=30` 兜底），
   期间新连接排在由 systemd 维持的 listen backlog 里，新进程起来后从同一个 fd 继续 accept——
   客户端看不到 connection refused。

两个关键落点（代码为准）：

- 监听选择在 `app/app.go` 的 `Run`（`net.Listen` 本来就在那里，不在 `main.go`——main 仍只有信号处理 + `app.Run`，
  维持《骨架当库-数据源当应用》§3.1 的"main 薄"契约）。
- `activation.Listeners()` 自己核对 `LISTEN_PID`：不是 systemd 直接拉起的那个子进程时返回空切片，
  不会把别人残留的环境变量当激活信号。

## 2. 单元文件（模板正本在 `deploy/`，本页是副本）

### `deploy/loomproxy.socket`

```ini
[Unit]
Description=LoomProxy HTTP socket（零停机升级的端口持有者，待办清单 P115）

[Socket]
ListenStream=8081
NoDelay=true
Backlog=1024
RemoveOnStop=true

[Install]
WantedBy=sockets.target
```

### `deploy/loomproxy.service`（收口时已对齐线上实态）

```ini
[Unit]
After=network.target mysql.service redis-server.service loomproxy.socket
Requires=loomproxy.socket
[Service]
WorkingDirectory=/www/go_project/loomproxy
ExecStart=/www/go_project/loomproxy/loomproxy
Restart=always
User=loomproxy
Group=loomproxy
NoNewPrivileges=true
TimeoutStopSec=30
```

正本以 `deploy/loomproxy.service` 为准（与生产机 `/etc/systemd/system/loomproxy.service` 一致）；
线上原有形态（mysql/redis 依赖、`Restart=always`、运行用户）在合并时**全部保留**，
新增的只有 `Requires=`/After 绑定与 `TimeoutStopSec=30`。切换前的原 unit 备份在生产机 `/root/loomproxy.service.bak-2026-10-09-1254`。

- **`ListenStream=8081` 必须与 `.env` 的 `SERVER_PORT` 一致**——socket 模式下进程不再 bind，
  `.env` 里的端口只在回退路径生效；不一致的症状是"服务起来了但端口不对"。
- `RemoveOnStop=true`：显式 `systemctl stop loomproxy.socket` 时连同 socket 收掉；
  日常升级走 restart service，不触发它。

## 3. 升级步骤（首次切换，线上操作需维护者执行，本轮不碰线上）

```bash
# 0. 前置：老进程在跑，loomproxy.service 是旧模板（无 socket 绑定）
sudo cp deploy/loomproxy.socket /etc/systemd/system/
sudo cp deploy/loomproxy.service /etc/systemd/system/   # 新版含 Requires=loomproxy.socket
sudo systemctl daemon-reload

# 1. 先停旧服务，再启用 socket（顺序反了会撞 address already in use：
#    旧服务自己 bind 着 8081，socket 单元 bind 不上）
sudo systemctl stop loomproxy.service
sudo systemctl enable --now loomproxy.socket

# 2. 拉起服务（此时进程从 systemd 手里接 fd）
sudo systemctl start loomproxy.service

# 3. 验收：启动日志必须出现 socket activation 关键行（按启动契约核对，不看 is-active——AGENTS §3）
journalctl -u loomproxy -n 5 | grep 'socket activation'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/panel/
```

之后的日常升级照旧走 `scripts/deploy.sh`（其 `systemctl restart loomproxy` 只重启 service，
socket 由 systemd 保持监听——这正是零停机的含义）。验证方式：restart 期间持续
`curl http://127.0.0.1:8081/panel/ -o /dev/null -w '%{http_code}\n'`，不出现 `000`（connection refused）。

## 4. 回退方法（回到进程自己 bind 的老形态）

```bash
sudo systemctl disable --now loomproxy.socket
# 还原 service：删掉 Requires=loomproxy.socket 与 After 里的 loomproxy.socket，TimeoutStopSec 可留 30
sudo systemctl daemon-reload
sudo systemctl restart loomproxy.service
# 代码不用回退：activation.Listeners() 拿不到 fd 自动走 net.Listen
```

回退是安全的：Go 侧改动只加了一条"拿不到 fd 就自己 bind"的分支，删掉单元文件依赖即回到原行为。

## 5. 本地验证记录（2026-10-09，开发机，systemd 262）

- 回退路径：`SERVER_PORT=18081 go run .` → 日志 `LoomProxy starting on [::]:18081`，`/panel/` 200。
